# digest 작성 스킬 — 수렴을 판정하고 거부할 수 있는 증류

## 1. 문제

digest는 수렴한 논의의 결론을 사람이 빠르게 읽기 위한 다리다(ADR-0035).
discussion 작성 스킬은 설계됐다(`261006_2122`) — 인터뷰로 지형을 만들고 판정 줄로 닫는다.
그 반대편, discussion에서 digest를 뽑는 스킬은 아직 모양이 없다.

discussion 스킬과 무엇이 달라야 하나가 출발점이었다.
인터뷰 중 둘이 바로잡혔다.
digest 작성은 사용자가 지시하지만, agent가 **아직 논의가 더 필요하다고 판단하면 작성을 거부하고 그 부분을 알려야** 한다 — 그래서 수동 호출이 아니라 agent가 판정하는 호출이어야 한다.
그리고 digest 작성에 추가 탐색은 필요 없다 — 필요한 탐색은 discussion에서 이미 끝났다.

## 2. 실측

- 첫 digest(`261006_1640`)는 이 흐름 없이 손으로 썼다. 결론 표·문제와 계기·버린 대안·기댄 사실·외부 조사·미결의 골격은 거기서 정해졌고, 자족성(discussion이 제거돼도 결론 표와 문제·계기로 맥락이 선다)도 그때 결정됐다.
- ADR-0035가 정한 것: 규범력 없음 · 단위는 틀 · 결론이 바뀌면 고쳐 쓰고 틀이 바뀌면 교체 · `current` → `superseded` · 메타데이터 하한(`ref-adrs` · `sources` · `superseded_by`).
- 새 discussion 구조에서는 축마다 "선택:" 또는 "판정(사람, 날짜):" 줄이 있다 — 결론 표의 행은 거의 기계적으로 뽑힌다. 사람의 판단이 드는 곳은 체인 병합·"어디에 사는가"·문제와 계기의 자족적 재서술이다.
- digest의 값이 가장 큰 시점은 ADR·티켓이 생기기 **전**이다(ADR-0035). 그때 "어디에 사는가"의 답은 discussion의 임계선 절이 이미 말한 **예정 행선지**다 — ADR 예정 · 방금 저작된 ADR id · 티켓 예정 · 코드(저장소 이름).
- ops-workflow 논의의 행선지는 ADR · 코드 저장소(`workspace/ref/<repo>`) · 티켓이다. 하네스 파일이 행선지인 것은 정책 토픽뿐이다 — steward의 시점을 design-partner의 스킬에 섞지 않는다.
- `related:`가 체인을 이미 잇고 있다 — sources 후보는 거기서 나온다.

## 3. 인터뷰에서 닫힌 축

### 3-1. discussion 스킬과의 차이

**선택: 사람과 만나는 때가 반대다.** discussion 스킬은 쓰기 전에 인터뷰한다 — 답이 사용자의 머릿속에 있어서다. digest 스킬은 쓴 뒤에 검수받는다 — 의도는 이미 discussion에 있고, 첫 독자가 사람이라 "읽고 바로 이해되는가"는 사람이 읽어야 판정된다. (인터뷰, 2026-10-07)

| | discussion 스킬 | digest 스킬 |
|---|---|---|
| 방향 | 발산. 지형을 만든다 | 수렴. 지형에서 결론을 뽑는다 |
| 입력 | 사용자의 머릿속, 코드, 조사 | 쓰인 discussion들 |
| 사람과 만나는 때 | 쓰기 전 인터뷰 | 쓰기 전 수렴 판정, 쓴 뒤 검수 |
| 고유한 일 | 축을 닫힌/열린으로 가름 | 수렴 여부를 판정하고 거부할 수 있다 |
| 기본 모드 | 생성 | 생성, 그 뒤 수정. 교체는 승인 |
| 병합 | 한 호출 한 문서 | 한 틀, discussion 여럿 |
| 금지 | 질문 절, 답 덧붙임 | 경위, 옵션 비교, discussion 참조 |

<details><summary>버린 안</summary>

- digest 스킬이 discussion과 행선지(ADR·하네스·티켓)를 **대조**해 "아직 없음"을 찾는다 — 사용자가 바로잡았다. digest의 값이 큰 시점엔 행선지가 아직 없고, 필요한 탐색은 discussion이 이미 했다. 대조는 digest의 일이 아니다.

</details>

### 3-2. 호출 — 사용자가 지시하되 agent가 판정한다

**선택: 사용자가 digest 작성을 지시하고, 스킬은 model-invocable로 둔다.** agent는 호출 전에 수렴 여부를 판정하고, 부족하면 호출을 거부하며 무엇이 더 논의돼야 하는지 알린다. (인터뷰, 2026-10-07 — `261006_1549`의 "사람이 수동 호출·`disable-model-invocation`"을 뒤집는다.)

<details><summary>버린 안</summary>

- 사람이 수동 호출(`disable-model-invocation`) — 호출 자체는 사람의 결정이지만, 그러면 agent가 "아직 아니다"를 말할 자리가 호출 뒤로 밀린다. 거부는 호출 전에 있어야 한다.
- agent가 discussion이 `done`될 때 스스로 — 지시 없는 생성이다.

</details>

### 3-3. 거부 기준

**선택: 셋 중 하나면 거부한다.** ① 판정 없는 열린 축이 있다. ② 틀을 막는 미결이 있다 — 다른 축의 결론을 바꿀 수 있는 미결. 단순 후속 작업 미결은 해당 없음. ③ 체인 안에서 같은 축에 다른 판정이 있는데 나중 것이 앞 것을 명시적으로 뒤집지 않았다. (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- 사실에 기대는 축이 즉석 답으로 닫힌 것 — discussion 스킬의 3-18이 그 자리에서 막을 일이다. digest가 다시 검사하지 않는다.
- "어디에 사는가"가 비어 있음 — 거부 사유가 아니다. 그것이 digest가 가장 값진 시점이다.

</details>

### 3-4. 거부의 출력과 그 뒤

**선택: 부족한 점 목록만 돌려주고 멈춘다.** 어느 축이 왜 안 닫혔나를 채팅에 나열한다. discussion 스킬 재호출은 필요 없다 — digest를 거부한 시점은 discussion이 아직 끝나지 않았다는 뜻이고, 사용자가 목록을 보고 다음 지시를 내린다. (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- 거부와 동시에 그 축의 인터뷰를 시작한다 — 사용자가 다음을 정한다. agent가 이어가지 않는다.
- "그래도 써라"로 밀면 빈 행을 미결로 두고 쓴다 — 열린 축이 비어 있는 digest는 결론 문서가 아니다.

</details>

### 3-5. sources — 어느 discussion을 덮나

**선택: 사용자가 지시한 discussion에서 `related` 체인을 agent가 따라 모으고, "이 N건을 덮습니다"로 사용자 확인을 받는다.** (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- 지시한 discussion만 — 체인을 덮으려면 사용자가 여럿을 지시해야 한다.
- related 체인을 확인 없이 전부 — 다른 틀의 문서까지 끌려 들어온다.

</details>

### 3-6. 체인 병합

**선택: sources를 시간순으로 읽고 축을 병합한다.** 같은 축의 판정이 여럿이고 나중 것이 앞 것을 명시적으로 뒤집었으면 나중 것이 결론이고 앞 것은 버린 대안이다. 명시적 뒤집음이 없으면 충돌이고, 거부 사유 ③이다. (인터뷰, 2026-10-07)

### 3-7. "어디에 사는가" — 탐색하지 않는다

**선택: discussion의 임계선·다음 단계 절에서 예정 행선지를 가져온다.** ADR 예정 또는 저작된 id · 티켓 예정 또는 발행된 번호 · 코드(저장소 이름) · 아직 없음. 코퍼스·하네스·코드를 추가로 탐색하지 않는다. (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- ADR 코퍼스 + 하네스 파일 + GitHub 티켓을 grep·검색 — steward의 시점이었고, 탐색은 discussion에서 이미 끝났다.
- 전부 사용자에게 묻는다 — discussion이 이미 답한 것을 다시 묻는다.

</details>

### 3-8. 검수 루프

**선택: 파일을 쓰고, 사용자가 읽고, 채팅으로 고친다.** 결론 표를 먼저 보이거나 미확인을 먼저 묻지 않는다 — 첫 독자가 사람이므로 사람이 읽는 것이 검수다. (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- 결론 표를 채팅에 먼저 보이고 확인 뒤 파일 — 틀이 틀리면 일찍 잡지만 왕복이 하나 는다. 틀은 거부 기준이 이미 거른다.
- "어디에 사는가" 미확인만 먼저 묻고 파일 — 3-7로 물을 것이 없어졌다.

</details>

### 3-9. 수정 — 결론이 바뀌거나 내려앉았을 때

**선택: 사용자가 바뀐 것을 말하고, agent는 가리킨 ADR·티켓의 상태만 확인해 그 행을 고친다.** "ADR-0035 accept됐다", "#120 발행했다", "축 X는 B로 바뀐다" 같은 지시. 결론이 바뀌면 옛 결론은 버린 대안으로 내려간다. 틀은 그대로다. (인터뷰, 2026-10-07)

<details><summary>버린 안</summary>

- 새 discussion을 지시하면 agent가 그 판정을 반영 — 후속 discussion도 결국 사용자가 "이것이 바뀌었다"로 말한다. 입력의 형태를 둘로 둘 이유가 없다.

</details>

### 3-10. 교체 — 틀이 바뀔 때

**선택: 새 digest를 쓰고 옛 것에 `superseded_by`를 단다. 사용자 승인이 필요하다.** 기준은 방향 폐기, 또는 축의 추가·제거로 결론 표의 모양이 달라지는 것 — discussion 스킬의 3-17과 같은 선. (인터뷰, 2026-10-06 — `261006_1549`에서 결정, 여기서 재확인)

### 3-11. 골격과 자족성

**선택: `261006_1640`의 골격을 그대로 템플릿으로 쓴다.** 결론 표(축 · 결론 · 어디에 사는가, 화면 하나 상한) · 문제와 계기(필수) · 버린 대안과 이유 · 기댄 사실 · 외부 조사 · 미결. 표 밖은 길이 자유, 시간순 누적 금지. 본문은 discussion을 가리키지 않는다 — 경로는 `sources`에만. 판정 질문: "`sources`가 전부 지워져도 결론 표와 문제·계기가 읽히는가." (인터뷰, 2026-10-06 — 첫 digest에서 결정, 여기서 재확인)

## 4. 열린 축 — 논의

없음.

## 5. 반대편 — 이 설계가 틀리는 조건

- **거부 기준이 느슨하면 빈 digest가, 엄격하면 digest가 안 나온다.** ①②③은 전부 discussion 문서에서 읽히는 것이라 agent의 재량이 작다. 재량이 드는 곳은 ②의 "틀을 막는가"뿐이고, 거부 목록에 이유를 적으므로 사용자가 바로 뒤집을 수 있다.
- **행선지를 탐색하지 않으므로 "아직 없음"이 오래 남는다.** 그것은 digest가 아니라 ADR·티켓 저작이 밀린 신호다(ADR-0035 무효화 조건). digest는 그 신호를 보여줄 뿐 고치지 않는다.
- **체인 병합에서 "명시적으로 뒤집었다"의 판정이 흔들린다.** 새 discussion 구조에서는 선택 줄에 "처음 A였다가 바꿨다"가 적히므로 명시적이다. 옛 구조의 discussion(45건)은 그렇지 않다 — 기존 문서의 소급 증류에서 충돌 거부가 잦을 것이고, 그때는 사용자가 어느 쪽인지 말한다.
- **수정 입력이 사용자의 말뿐이라 digest가 현실과 어긋난 채 남는다.** ADR-0035가 받아들인 대가다 — 낡은 digest는 틀린 길이지 틀린 결정이 아니다.

## 6. 버린 것

- **digest 스킬에 대조(discussion ↔ 행선지) 기능을 두는 것.** 3-1·3-7에서 버렸다.
- **수동 호출.** `261006_1549`의 결정을 뒤집었다 — 거부가 호출 전에 있어야 해서다.
- **거부 시 "그래도 써라" 우회.** 열린 축이 빈 digest는 결론 문서가 아니다.

## 7. 임계선 — ADR감인가

아니다.
호출의 성격·거부 기준·검수 루프·sources 결정·수정 입력은 전부 하네스가 어떻게 하나의 문제다.
ADR-0035는 그대로다 — 이 논의는 그 결정을 집행하는 스킬의 모양만 정한다.
`261006_1549`의 "사람이 수동 호출" 결론은 바뀌었다 — 그 discussion은 로그이므로 고치지 않고, digest `261006_1640`의 저작 행을 고쳐 쓴다(3-9의 첫 적용).

## 8. 하네스 델타 — 이 논의가 낳는 것

- `.claude/skills/digest/SKILL.md` — model-invocable(`disable-model-invocation` 없음). 트리거: 사용자의 digest 작성·수정·교체 지시. 절차: 지시받은 discussion + `related` 체인 제안·확인 → 수렴 판정(거부 기준 ①②③ — 걸리면 부족한 점 목록만 돌려주고 멈춤) → 시간순 병합 → 결론 표 작성("어디에 사는가"는 discussion의 임계선·다음 단계에서) → 문제와 계기를 자족적으로 재서술 → 파일 작성 → 사용자 검수·채팅 수정. 수정 모드: 사용자가 말한 변경 + ADR·티켓 상태 확인 → 해당 행 고침. 교체 모드: 틀 변경 판정 → 사용자 승인 → 새 파일 + 옛 파일 `superseded_by`. 금지: 경위·옵션 비교·discussion 참조·질문 절.
- digest 템플릿 — `261006_1640`의 골격.
- `261006_1640` 저작 행 수정 — "사람이 수동 호출·`disable-model-invocation`" → "사용자 지시, agent가 수렴 판정 후 호출, 부족하면 거부".
- `context-scout/SKILL.md` — digest를 ADR 다음 2순위로(`261006_1549`에서 결정).
- `design-partner.md` — 수렴 절에 "discussion이 done이면 사용자가 digest를 지시할 수 있다" 한 줄. 티켓 발행과는 별개.
