# ticket-engineer 워크스페이스 엣지 케이스 — 낡은 클론·남의 브랜치·중단된 작업

티켓 집행 agent(ticket-engineer)의 워크스페이스(`workspace/<repo>`)는 **티켓 간 공유되는 클론**이다.
그래서 티켓의 시작·재개 시점에 워크스페이스가 "깨끗한 최신 main"이 아닌 경우가 구조적으로 생긴다.
이 문서는 그 케이스들을 분해하고, 처리 옵션과 트레이드오프를 펼친다. **정하지 않는다** — 논점을 드러내고,
수렴되면 하네스(스킬·스크립트) 델타로 내려보낸다.

> 현행 구조 (조사 원천: ticket-engineer `CLAUDE.md` · `ticket-start`/`ticket-report` skill · `prep-repo.py`):
> - `prep-repo.py` — 있으면 `fetch --prune`; **main이면** `pull --ff-only`(실패 = exit 1, 사람과 정리);
>   **작업 브랜치면 fetch만** 하고 알린다(*"병합 판단은 사람·세션의 것"*).
> - `ticket-start` ⑤ — `git switch -c ticket/<N>-<slug>`. **기점 미지정 — 현재 HEAD에서 분기한다.**
> - 규약: reset·force 우회 금지 · 머지·close는 사람 · 티켓당 브랜치.

---

## 1. 케이스 A — 새 티켓 시작, 클론은 이미 있다

### A1. HEAD가 다른 티켓의 브랜치다

**지금 무슨 일이 벌어지나:** `prep-repo.py`는 fetch만 하고 통과한다. 이어서 ⑤가 **그 브랜치 위에서**
새 티켓 브랜치를 딴다 → 새 PR에 **남의 티켓 커밋이 섞인다.** 오염이 규율이 아니라 **절차의 구멍**으로 열려 있다.
(세분: 그 브랜치의 PR이 아직 열려 있는 경우 — 검수 대기 중인 작업 — 와 이미 머지·폐기된 경우가 있다.
어느 쪽이든 새 티켓의 기점이 되어선 안 된다는 점은 같다.)

**옵션:**

- **① 분기 기점을 `origin/main`으로 명시 고정한다** — `fetch` 후 `switch -c ticket/<N>-<slug> origin/main`.

  HEAD가 어디에 있든 기점 오염이 **구조적으로 사라진다.** A2(낡은 main)도 함께 해결된다 —
  로컬 main을 경유하지 않으니 ff-pull 성공 여부와 무관하게 기점이 항상 공표된 최신이다.
  단, **워킹 트리가 더럽면**(uncommitted) switch가 변경을 끌고 가거나 충돌로 실패한다 → ②가 전제로 필요하다.

- **② 시작 전 clean-tree 게이트** — `git status --porcelain`이 비어 있지 않으면 **거부(exit 1)**, 멈추고 사람에게.

  남의 uncommitted 변경을 새 티켓이 흡수하는 사고를 막는다. reset·stash로 자동 "정리"하지 않는다 —
  그 변경이 무엇인지는 agent가 판정할 수 없다(검수 대기 중인 작업일 수 있다).

- **③ 티켓당 fresh clone / git worktree** — 공유 클론 자체를 없앤다.

  가장 확실하지만: fresh clone은 느리고 디스크를 먹으며 멱등 준비(`prep-repo`)의 의미가 사라진다.
  worktree는 병렬 티켓에 강하지만 하네스 복잡도가 뛰고, **지금 운영 모델은 "사람이 티켓을 하나씩 지정"**이라
  동시 집행이 실재하지 않는다. 문제(순차 재사용의 잔재)보다 큰 해법일 수 있다.

### A2. HEAD는 main인데 낡았다

현행 `prep-repo.py`의 ff-pull이 이미 처리한다(실패 = 로컬 분기 존재 = 사람과 정리). 남는 구멍은
*"prep-repo를 건너뛰고 브랜치를 따는"* 경로뿐인데, ①을 채택하면 기점이 `origin/main`이라
로컬 main의 신선도 자체가 무관해진다 — **A2는 A1의 해법에 흡수된다.**

## 2. 케이스 B — 이전 티켓을 이어서 진행한다 (`ticket/<N>-<slug>` 브랜치와 커밋이 이미 있다)

**공통 전제:** "이어서"는 사람이 티켓 번호를 다시 지정하며 시작된다. 착수 절차가 같은 번호의
기존 브랜치를 발견하는 순간이 분기점이다 — 지금 절차에는 이 발견에 대한 지시가 **없다**
(`switch -c`는 기존 브랜치가 있으면 실패한다 — 우연히 멈추긴 하나, 안내 없는 실패다).

### B1. 커밋만 있고, uncommitted 변경은 없다

이어서 일하는 것 자체는 안전하다(자기 티켓 브랜치의 공표된 상태). 논점은 **밑이 낡았을 때**다:

- **① 그대로 이어서** — main 반영 없이 계속. 단순하고 안전. PR 시점에 충돌하면 그때 해결.
- **② `origin/main`을 rebase로 반영** — 깨끗한 히스토리. 그러나 이미 push된 브랜치면 **force-push가 필요**해진다
  — 현행 규약(우회·force 금지)과 정면 충돌. force-with-lease를 티켓 브랜치 한정으로 허용하는 것은 별도 결정이다.
- **③ `origin/main`을 merge로 반영** — force 불요. 히스토리는 지저분하나 PR squash 머지면 무해.

현행 `prep-repo.py`의 자세(*"병합 판단은 사람·세션의 것"*)를 유지한다면: 기본은 ①,
낡음이 실제로 작업을 방해할 때만(컴파일 불가 등) 사람과 ②/③을 정하는 절충이 있다.

### B2. uncommitted 변경도 있다

이전 세션이 중단된 잔재다. **그 변경이 유효한 진행분인지, 버려진 실험인지 agent는 판정할 수 없다.**

- **① 멈추고 사람에게** — `git status`·diff 요약을 보이고 처리(이어쓰기/커밋/폐기)를 묻는다.
  기존 원칙(reset·force 금지, 모르면 묻는다)과 정합. 대가: 재개마다 사람이 한 번 개입.
- **② 자동 WIP 커밋** — 유실은 막지만, 검증 안 된 스냅샷이 티켓 브랜치 히스토리에 박힌다.
  PR 전 정리(squash) 규약이 없으면 소음이 공표된다.
- **③ 자동 stash** — 워킹 트리는 깨끗해지나 변경이 **눈 밖으로 사라진다.** stash는 브랜치와 달리
  발견 가능성이 낮다 — "숨겨두고 잊는" 실패 모드가 열린다.

②·③은 판정을 미룰 뿐 없애지 못한다. **자기 티켓 브랜치 위의 변경이라는 점에서 B2는 A1의
남의-변경보다 온건하지만**, "지난 세션의 나"도 이번 세션에겐 타인이다 — 맥락이 소실됐다.

## 3. 관통 논점 — 사용자와 정할 것

- **Q1. 분기 기점을 `origin/main`으로 구조 고정하나?** (A1①) 가장 싼 수로 A1·A2를 동시에 닫는다.
  스크립트(`prep-repo.py` 확장 또는 신설 `start-branch`)가 거부·강제하는 형태가 §8 관통원칙(구조로 강제)에 맞는다.
- **Q2. clean-tree 게이트를 거부(exit 1)로 세우나?** (A1②) 세우면 B2도 같은 문에서 걸린다 —
  케이스 셋(A1·B2·미지의 잔재)이 게이트 하나로 수렴한다.
- **Q3. 재개 시 main 반영 정책** — 기본 ①(그대로 이어서)로 두고 rebase/merge는 사람 판단으로 남기나?
  force-with-lease를 티켓 브랜치 한정 허용하는 결정까지 갈 것인가?
- **Q4. 기존 브랜치 발견 시의 절차** — "이어서인가 새로인가"를 사람에게 묻는 명시적 단계를 ticket-start에 넣나?
- **Q5. worktree/티켓당 클론은?** 지금의 순차 운영 모델에선 과한 해법으로 보이나, 병렬 집행이 실재해지면
  재론한다 — 그 시점의 신호(동시 티켓 지시가 반복됨)를 무효화 조건처럼 기록해 두면 된다.
- **Q6. 이것은 ADR감인가?** 전부 절차·스크립트 수준이라 되돌리기 쉽다 — 임계선(one-way door) 아래로 보인다.
  **하네스 잔류(ADR 없음)가 잠정 판정.** 단 Q3에서 force 정책을 바꾸면 그것은 규약 변경이라 무게가 다르다.

## 4. 잠정 제안 (수렴 전)

**Q1+Q2를 한 스크립트로**: ticket-start에 브랜치 준비 스크립트를 신설 —
ⓐ 워킹 트리 더럽면 거부(멈추고 사람에게) → ⓑ `ticket/<N>-*` 기존 브랜치 있으면 "이어서/새로"를 묻는 안내와 함께 멈춤 →
ⓒ 새 브랜치는 항상 `origin/main` 기점으로 분기. B1은 현행 자세 유지(기본: 그대로 이어서),
B2는 게이트 ⓐ가 잡아 사람에게 넘긴다. worktree(Q5)는 미룬다.

수렴되면: ticket-engineer 하네스 델타(스킬 ⑤ 개정 + 스크립트 신설)로 내려보내고, 이 문서를 `done`으로 닫는다.
ADR은 내지 않는다(Q6 잠정 판정 유지 시).

## 5. 수렴 결과 — 원격-우선 + 티켓별 worktree (사용자와 확정)

§4의 잠정 제안보다 두 걸음 더 나간 설계로 수렴했다. 두 반전이 있었고, 각각 근거가 있다.

**원칙 1 — 원격이 진실의 원천이다.** "이어서인가 새로인가"의 판별 기준은 *이 티켓 번호로 남긴
집행 흔적이 있는가*이고, 흔적은 규약 덕에 전부 기계가 조회한다(브랜치 명명 `ticket/<N>-*` ·
PR 본문의 티켓 참조 · 티켓 코멘트). 그중 **원격 티켓 브랜치를 유일한 판별·기점 원천**으로 삼는다:
새 브랜치는 로컬이 아니라 **원격에, 원격 기본 브랜치 HEAD 기준으로 생성**한다. 그러면 로컬 HEAD가
남의 브랜치든(A1) 낡은 main이든(A2) 판별·기점에 영향을 못 준다 — §3 Q1의 "기점 고정"보다 강한 해소다.
Status 필드는 판별 원천으로 쓰지 않는다(비강제 보드 — 신뢰 불가).

**원칙 2 — 로컬은 티켓별 worktree다 (Q5 반전).** §3 Q5는 "순차 운영이라 worktree는 과함"이었고
*병렬 집행이 실재해지면 재론*을 조건으로 걸었다 — 사용자가 동시 다중 티켓 진행을 요구하며 **그 조건이
발화했다.** bare 저장소(`workspace/.bare/<repo>.git`) + 티켓별 worktree(`workspace/<repo>/ticket-<N>/`)로:
공유 HEAD가 사라져 A1이 소멸하고, B2 잔재는 그 티켓 안에 격리되며, 같은 브랜치 이중 체크아웃은
git이 거부해 티켓↔디렉터리 1:1이 구조로 선다. base를 bare로 두는 이유: 일반 클론이면 "main
작업트리는 안 쓴다"가 규율이 되지만, bare면 더럽힐 트리 자체가 없다.

**재개 시 정렬은 3축 사전 판별이다** — pull을 시도하고 실패를 처리하는 오류 경로가 아니라 일급 분기:
ⓐ behind(원격에만 있는 커밋) · ⓒ ahead(push 안 된 커밋) · ⓑ dirty(미커밋 변경).

| ⓐ | ⓒ | ⓑ | 동작 | exit |
|---|---|---|---|---|
| 0 | 무관 | 무관 | 그대로 진행 (dirty·미push는 보고에 포함) | 0 |
| >0 | 0 | 없음 | ff-pull (ⓒ=0이면 ff는 항상 성공) | 0 |
| >0 | 0 | 있음 | pull 안 함 — agent가 파악해 **처리 방안 제안 → 사람 승인 → 진행** | 2 |
| >0 | >0 | 무관 | 양방향 분기 — agent는 **보고만**, 처리는 사람과 (force 불변) | 3 |

exit 코드가 곧 agent의 다음 행동이다(0 진행 / 1 전제 거부 / 2 제안 후 승인 / 3 보고만) —
개입 강도가 코드에 단조로 실리며, 프롬프트 해석에 기대지 않는다.

**B2 ①의 정련(부분 반전):** "멈추고 사람에게"는 케이스별로 갈린다 — 잔재 단독(ⓐ=0)은 agent가
파악하고 진행(worktree 격리로 잔재가 항상 *자기 티켓의 것* — 남의 변경 흡수 위험 소멸),
원격 커밋과 얽히면 제안·승인(exit 2), 양방향 분기는 보고만(exit 3). 파괴적 정리(reset --hard·
stash drop·강제 checkout)는 어느 경우에도 agent가 하지 않는다 — 유실이 걸린 판단은 사람에게.

**함께 확정된 것:**
- **단일 진입점** — 진행 스크립트가 착수를 품는다(원격 브랜치 부재가 곧 착수 신호). 별도 시작 스크립트 없음.
- **Status 착수 전이** — Backlog·Todo → In Progress는 도구가 대행한다(착수 자체가 사람의 티켓
  지정이므로 "사람이 지시한 전이의 대행"). 그 외 상태면 중단·사람에게. **CLAUDE.md §5 문구를 이에 맞춰 개정.**
- **코퍼스 클론**(workspace/ops-workflow)은 worktree화하지 않는다 — 읽기 전용 단일 뷰 + SessionStart
  hook가 세션 시작 시 최신화(ff-only, 실패는 경고만 — 세션을 막지 않는다).
- **뒷정리**는 사람이 close를 확인하고 지시했을 때만 도구가 돕는다(worktree·브랜치 삭제 — 자동 실행 없음.
  티켓 열림·미커밋 변경·열린 PR이면 도구가 거부).
- **마이그레이션 없음** — 확정 시점의 workspace에는 코퍼스 클론뿐이었다.
- **Q3·Q4·Q6은 §3 권장대로**: main 반영은 기본 "그대로 이어서"(반영은 사람과, force 불변) ·
  재개 판별은 위 원칙 1 · **ADR은 내지 않는다**(절차 수준 — 임계선 아래. §5 Status 문구만 규약 개정).

**파생(하네스 델타):** ticket-engineer — `ticket-run.py`(단일 진입점)·`ticket-clean.py`(뒷정리)·
`refresh-corpus.py`(SessionStart hook)·guard-write에 `.bare` 쓰기 거부 추가·`ticket-start`/`ticket-report`
skill 개정·CLAUDE.md §1 레이아웃 개정, `prep-repo.py` 제거(역할이 hook와 ticket-run으로 흡수).
ops-workflow — CLAUDE.md §5 Status 문구 개정. 파생이 끝나 이 문서를 `done`으로 닫는다.
