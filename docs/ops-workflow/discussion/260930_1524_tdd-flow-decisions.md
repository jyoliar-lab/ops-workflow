# TDD 집행 흐름 — 결론

`260930_1356` 의 논의를 **결론만** 추린 문서다. 옵션 · 반대편 · 정정의 경위는 그 문서에 있다.
사람 판정은 전부 2026-09-30.

## 1. 무엇을 정했나 — 한 줄씩

| 축 | 결론 |
|---|---|
| **적용 범위** | 저장소 목록 없음. agent 가 **티켓마다 판정**하고 착수 요약에 적는다. 사람이 읽고 승인 또는 방향 제시 |
| **흐름** | scenarios → **승인** → red → **승인** → green → refactor → verifier → **사람 확인 · 승인** |
| **컨텍스트** | scenarios · red = 주 대화(스킬 `tdd-loop`). green + refactor = subagent 하나(opus). verifier = subagent(Fable) |
| **강제** | 없음. 단계 제약은 **규약**. 지켰는지는 커밋 diff 와 코멘트를 **읽어서** 안다 |
| **임계선** | 집행 흐름 = 티켓. **테스트 정책**(티어 · 범위 · 의존성 처리) = ADR 감이나 **지금은 쓰지 않는다** — 시도로 답을 모은다 |
| **첫 집행** | 사람이 정한다 |

## 2. 적용 판정 — 규약 문장

착수 요약(`ticket-start` ⑥)에 고정 자리 하나: **`TDD: 대상 / 비대상 — 근거 한 줄`**. 적지 않으면 착수 요약이 아니다.

판정 기준 — *변경 전에 · 저장소 안에서 · 이번 변경의 약속을 · 실패하는 테스트로 쓸 수 있는가.* 하나라도 아니면 비대상:

| 아닌 경우 | 왜 |
|---|---|
| 렌더 · 플랜 · 배포 뒤에야 검증된다 — Terraform · Ansible · k8s manifest | 약속이 변경 전 테스트에 담기지 않는다 |
| 테스트 골격(러너 · 설정 · CI 잡)이 없다 | red 가 성립하지 않는다. 골격을 세우는 것은 이 흐름 밖 |
| 이번 변경에 약속이 없다 — 설정값 1줄 · 의존성 갱신 · 삭제 · 문서 | 시나리오 표가 빈다 |

**Bug 는 생략 사유가 아니다.** 코드 저장소에서 버그는 곧 시나리오다 — 재현 테스트가 red, 수정이 green.

"테스트 파일이 있다" 는 기준이 아니다 — 인프라 저장소의 smoke 테스트(`jyoliar-k8s/smoke_test.py`)는 배포 뒤 실측이지 변경 전 약속이 아니다.

## 3. 다섯 단계 — 규약

| 단계 | 컨텍스트 | 하는 것 | 남기는 것 | 멈추나 |
|---|---|---|---|---|
| **scenarios** | 주 대화 | AC 에서 시나리오를 도출하고, AC 밖 경계 · 예외도 더한다 | **시나리오 표** — 티켓 코멘트 | **멈춤 — 사람 승인** |
| **red** | 주 대화 | 시나리오를 테스트로 쓴다. 소스는 stub 만. 저장소 테스트 명령으로 **신규 전부 fail · 기존 pass** 확인 | **red 커밋** 1개 + 실행 결과 답글 | **멈춤 — 사람 승인** |
| **green** | subagent 하나 · opus | 테스트를 통과시킨다. **테스트 불변.** 구현 불가면 보고 | green 커밋 + 실행 결과 답글 | 흐름 |
| **refactor** | (같은 subagent) | 소스 정리. **테스트 불변 · 전부 pass 유지** | refactor 커밋 + 실행 결과 답글 | 흐름 |
| **verifier** | subagent · Fable | §4. **직접 게시**하고 주 대화엔 코멘트 링크만 돌려준다 | 대조표 + 발견 — 티켓 코멘트 | **멈춤 — 사람이 다음 절차 승인** |

- 스킬은 하나 — **`tdd-loop`**. `ticket-start` 는 판정 자리만 갖고, 대상이면 `tdd-loop` 로 넘어간다. 비대상은 건너뛴다.
- 승인의 흔적은 남기지 않는다 — 다음 산출물이 흔적이다. **새 세션에서 재개** 시 agent 는 진행의 흔적(코멘트 · 커밋 · PR)으로 현황을 파악하고 **사람에게 확인을 요청**한 뒤 진행한다.
- 표 승인 뒤 시나리오가 틀렸음을 발견하면 표를 새 코멘트로 다시 내고 **재승인**. 조용히 고치지 않는다.
- target 이 여럿이면 TDD 판정은 **target 마다**.
- PR 체크리스트 갱신은 주 대화가 한다(subagent 복귀 뒤). 실행 결과 "답글" 은 티켓의 새 코멘트다.
- subagent 는 hook · 권한을 그대로 상속한다 — worktree 만 쓴다.

시나리오 표의 열 — `시나리오 | 시그니처 | 종류(정상 · 경계 · 예외) | 출처(AC-n · 추가) | 테스트 이름 | 티어(단위 · 통합 · e2e) | 의존성 처리(실제 · 녹화 replay · fake · mock/stub)`.
마지막 두 열은 이 티켓의 검수용이 아니라 §5 의 ADR 을 위한 **증거**다.

stub 의 하한 — 시그니처 + `raise NotImplementedError` / `panic("TODO")` / `throw new Error("TODO")`. 컴파일이 살고, 신규 테스트만 실패하며, 나머지는 통과한다. 그 아래는 언어 · 저장소의 것.

커밋 경계(red / green / refactor)는 강제가 아니라 **읽기 단위**다 — verifier 와 사람이 diff 로 stub 범위 · 테스트 불변 · 하드코딩을 읽는다.

**PR 은 red 커밋 직후 Draft 로 연다**(`ticket-pr.py --draft`). 이후 커밋은 같은 PR 에 쌓인다 — 커밋 타임라인이 단계 타임라인이다. red 커밋의 CI 빨강은 의도된 것이며 "신규 테스트가 실제로 실패했다" 의 증거다.
본문은 링크로 쓴다 — 열 때: 시나리오 코멘트 링크 + 단계 체크리스트(red · green · refactor · verify). 단계마다 체크리스트를 갱신한다(`gh pr edit`). verifier 뒤: verifier 코멘트 링크. 사람 승인 뒤 `gh pr ready`.
red 승인은 PR diff 에서 한다(테스트 본문) — 시나리오 승인은 티켓 코멘트에서.

"구현 불가" 는 시나리오나 AC 가 틀렸다는 뜻이다 — 보고하고 멈춘다. 테스트를 고쳐 통과시키지 않는다. red 로 되돌리는 것은 사람의 승인 뒤다.

## 4. verifier — 하는 일

| 입력 | 검사 | 출력 칸 |
|---|---|---|
| 티켓 AC ↔ 시나리오 표 | 약속 누락 | 발견 |
| 시나리오 표 ↔ 테스트 코드 | 이름 일치 · 단언이 성질인가(약화) | 대조표 근거 · 발견 |
| red 커밋 소스 diff | stub 범위 | 발견 |
| green · refactor 커밋 | 테스트 경로 diff = 0 · 하드코딩 의심 | 발견 |
| **직접 실행** | 전부 pass · 답글과 일치 | 대조표 |
| **반증 테스트**(하드코딩 의심 시) | 입력을 바꿔도 통과하나 — worktree 안에 쓰고, 커밋하지 않고, 보고 뒤 지운다 | 발견 — 실패하면 red 되돌림 제안, 사람 승인 |
| **커버리지**(저장소에 도구가 있을 때) | 변경 소스의 안 도는 분기 | 발견 — 시나리오 후보 |

저장소 전체는 읽지 않는다 — 읽는 양은 약속의 수에 비례한다.
대조표의 근거 칸은 **테스트 이름**이다(코드 위치가 아니라).
커버리지는 게이트가 아니라 탐지 신호다 — 100% 가 목표가 아니다. 도구가 없으면 생략하고 설치하지 않는다.

## 5. 임계선 — 대상이 둘

| 대상 | 판정 |
|---|---|
| **집행 흐름** (§2–§4) | 되돌리기 한 시간대 — **티켓**. ADR 을 기다리지 않는다 |
| **테스트 정책** — 어느 테스트를(단위 · 통합 · e2e) 언제 · 어느 범위로, 의존성(프론트→백엔드 API · 백엔드→DB · obs-toolkit→모니터링 백엔드)은 실제 · 녹화 · fake · mock 중 무엇으로 | **ADR 감** — 정책 위에 저장소마다 스위트가 쌓이고 뒤집으면 저장소 수만큼 다시 쓴다. 그러나 **지금은 쓰지 않는다** — 방향이 없고, 시도로 답을 모은다 |

그 ADR 이 답해야 할 것(지금 보이는 만큼):
- 티어의 축 — "실패하면 사람이 무엇을 하나"(obs-toolkit 의 contracts · format · infra)인가, 범위 · 의존성(단위 · 통합 · e2e)인가, 둘 다인가
- 의존성 경계마다의 기본값 — 실제 / 녹화 replay / fake / mock. 저장소 부류마다 다른가
- 언제 e2e 인가 — careerhub-web #9 가 선례
- 사람이 읽는 것은 어느 티어인가
- 저장소에 남는 것만 약속 인공물로 인정하나

증거는 시나리오 표의 **티어 · 의존성 처리** 열이 티켓마다 남긴다. ADR 을 쓸 때 읽을 것은 그 코멘트들이다.
