# 티켓(컨트롤 플레인) 결정을 ADR로 승격하기 — 후보 분해와 논점

이 문서는 **티켓 관련 결정을 ADR로 쓰기 전의 조사·발산·수렴**이다. 정책을 *정하지* 않는다 —
(a) 티켓 정책이 지금 어디에 어떻게 서 있는지, (b) 무엇이 이미 경험적으로 굳었는지,
(c) 무엇을 ADR로 승격할지 후보를 분해하고, (d) 사용자와 정해야 할 논점을 드러낼 뿐이다.
결정과 그 입도는 실제로 ADR 초안을 써 보며 갈린다.

> 조사 원천 세 곳: **CLAUDE.md §5**(산문 규약) · **`ticket` 스킬 + `scripts/`**(구조적 강제) ·
> **`260712_1731_skill-friction-log.md` §8**(dogfood에서 굳은 경험지).

---

## 1. 왜 지금인가 — 두 플레인의 근거가 비대칭이다

| 플레인 | 근거 ADR | 상태 |
|---|---|---|
| **지식 플레인** (문서·ADR 체계) | ADR-0002 ~ 0008 (7건) | 전부 `proposed` |
| **컨트롤 플레인** (티켓 §5) | **없음 (0건)** | CLAUDE.md §5 산문 + `ticket` 스킬로만 |

ADR-0001(두 플레인 분리)이 **양쪽의** founding이다. 그 아래 지식 플레인은 0002~0008로 축이 갈라져
나왔는데, **컨트롤 플레인 쪽 하위 축은 아직 하나도 ADR이 아니다.** 티켓 정책의 실질은 전부
CLAUDE.md §5의 산문과 `ticket` 스킬(스스로 *"잠정판(관측 장비)"* 이라 부른다)에만 있다.

그런데 그 정책은 **이미 진짜를 통과했다.** 마찰 로그 §8(dogfood 본편)에서 agent가 첫 ADR을
근거로 epic을 발행하며, 티켓 결정 다수가 픽스처가 아니라 실제 이슈·Project를 통과하며 굳었다.
**영수증을 끊을 때가 됐다.**

> ⚠ 승격은 §5를 **복제**하는 것이 아니다. §5 중 **임계선(§4②)을 넘는 결정**만 골라 "왜"의
> 영수증으로 남기고, 되돌리기 쉬운 값·규칙은 §5(또는 코드)에 잔류시킨다. ADR은 설계 문서가
> 아니라 결정의 영수증이므로(§4), 잘 되면 §5는 **얇아진다.**

## 2. 현재 티켓 정책의 지도 — 산문인가, 구조가 강제하는가

같은 원칙(§8 관통원칙: *규율이 아니라 구조*)이라도, 어떤 것은 이미 스크립트가 exit 1로
거부하고 어떤 것은 아직 산문일 뿐이다. **이 구분이 "무엇을 ADR로 올릴 가치가 있나"의 1차 필터다** —
이미 코드가 강제하는 결정일수록 그 "왜"가 영수증으로 남을 값이 크다.

| # | 결정 | CLAUDE.md | 구조적 강제 (스크립트) | dogfood 근거 |
|---|---|---|---|---|
| T1 | Issue Types **4종**(Epic·Feature·Task·Bug), 라벨 아닌 Issue Type, 단일 선택, story·spike 없음 | §5 | ✅ `create.py` argparse `choices` — 4종 밖 값 자체를 못 받음 | §4·§8 (읽기 경로 실증) |
| T2 | **컨테이너 티켓(Epic·Feature)은 accepted ADR을 전제** — 결정이 계층을 낳는다 | §5 | ✅ `adr-gate.py` — 근거 없음/미accept/**미공표** 거부 | §8① §8④ (게이트가 `origin/main`을 읽도록 교정) |
| T3 | **Feature는 규모가 아니라 독립 하위 축 결정(sub-ADR)이 있을 때만** | §5 | △ 경고만 (`adr-gate.py`: Feature 근거 ADR에 `parent` 없으면 경고) | §4 (거부로 올릴지 미결) |
| T4 | 티켓 계층은 **3층에서 멈춘다** (GitHub 제약, ADR 깊이와 분리) | §5 | ✅ `link-sub.py` — 리프는 부모 불가, Feature 밑 Feature 불가 | §5 산문 (연결 경로 미실증) |
| T5 | **브리지는 이슈→문서 단방향**, 역방향은 **Project `ADR` 필드** + GitHub 검색 | §1 §5 | ✅ `create.py` — 본문 링크 2개(HEAD+permalink) + Project `ADR` 필드 | §8① §8② §8⑤ (`ticket:` 필드 삭제) |
| T6 | **강제의 사정거리** — Status는 강제 불가, 도구는 초기값(`Backlog`)만; 모든 티켓 Project 등록 | §5 | ◐ 초기값만 넣음, 이후 전이 미개입 (설계상 비강제) | §8③ (플랫폼이 연 문에선 구조 강제 불성립) |
| T7 | **진단 agent 쓰기 경계** — 컨트롤 플레인 write, 지식 플레인 write 불허 (자기오염 차단) | §6 | ✅ agent 도구 권한(지식 플레인 write 미부여) | §8⑦ (agent 정의가 행동을 규정) |

아래는 **임계선 밑**이라 마찰 로그가 이미 "ADR 아님"으로 판정한 것들이다(§6③) — 승격 후보에서 뺀다:

| # | 결정 | 왜 ADR이 아닌가 |
|---|---|---|
| X1 | **자동 close 미사용**(`Closes #N` 금지), close는 사람 | 되돌리는 데 한 시간 — §4② 임계선 아래. §5·스킬에 잔류 |
| X2 | 초기 Status = `Backlog`, `accepted_at` 비권위 등 **값** | 값은 코드·설정에 산다(§4①). 되돌리기 쉬움 |

## 3. 후보 결정 — 임계선(§4②) 판정과 예상 parent

각 후보를 *`되돌리기 어려움 × 영향 범위`* 로 재고, 예상 계층 위치를 붙인다. **판정은 잠정이다.**

- **T2 — 컨테이너 티켓은 accepted ADR을 전제한다.**
  임계선 **위**. 지식 플레인과 컨트롤 플레인을 **결합**하는 결정이라 되돌리면 두 플레인의 관계
  전체가 바뀌고, 영향 범위가 전 시스템(모든 컨테이너 티켓)이다. 이것이 *"결정이 계층을 낳는다"* 의
  실체다. → **컨트롤 플레인의 founding 결정.** parent = **ADR-0001**.

- **T1 — Issue Types 4종.**
  임계선 **위**(경계일 수 있음). "라벨이 아니라 Issue Type"은 플랫폼 계약 채택(§4② 트리거:
  인터페이스·계약)이고, 타입을 갈면 모든 티켓의 분류가 바뀐다. 다만 *어떤 4종인가*는 값에 가깝다 —
  **"단일 선택 강제 · 컨테이너/리프 이분"** 이라는 성질이 결정이고, 이름 4개는 그 예화다.
  → parent = **ADR-0001** 또는 T2의 형제. T2와의 관계는 §4에서 상호무효로 가른다.

- **T3 — Feature는 독립 하위 축 결정일 때만.**
  T2의 **특수화**다("컨테이너는 결정을 전제한다"를 Feature에 적용). T2가 뒤집히면 T3은 무효.
  역은 아니다(Feature를 규모로 허용해도 T2는 산다). → **한 방향 의존 = 하위 축.** parent = **T2**.

- **T4 — 3층 상한.**
  임계선 **경계**. 순수 GitHub 제약의 수용이라 "왜"가 얇다 — *우리가* 정한 게 아니라 플랫폼이
  정했다. 하지만 *"ADR 깊이와 티켓 깊이를 분리한다"* 는 **비자명한 결정**이고(§5의 ★),
  깊은 ADR 계층을 티켓에 옮기려는 유혹을 구조로 막는다. → T2의 하위 축일 여지. **논점(Q4).**

- **T5 — 브리지 방향(이슈→문서 단방향).**
  임계선 **위**. 여기 함정이 있다 — 마찰 로그 §9는 이 결정을 **ADR-0001에서 덜어냈다**.
  근거가 *"문서가 얼기 때문"* 이라 **동결(ADR-0006)과 공동무효**이지 두 플레인 분리와
  공동무효가 아니기 때문이다. `ticket:` 필드가 원리적으로 채워질 수 없던 것도 같은 뿌리다(§8①).
  → parent 후보가 **ADR-0006(지식 플레인 subtree)**? 아니면 ADR-0001? **논점(Q2).**

- **T6 — 강제의 사정거리.**
  임계선 **위**(원칙 결정). *"규율이 아니라 구조로 강제한다"* 는 관통원칙이 **우리가 매개하는 문
  (스크립트·스키마)에서만 성립하고, 플랫폼이 연 문(보드 UI)에서는 성립하지 않는다"* — 이 경계의
  인정은 되돌리기 어려운 **메타 결정**이다(§8③). 다만 이것은 티켓만의 것이 아니라 **하네스 전체의
  자기이해**라, 티켓 배치에 넣기엔 큰 축일 수 있다. **논점(Q3).**

- **T7 — 진단 agent 쓰기 경계 (자기오염 차단).**
  임계선 **위**. §6 전체(무인 write 금지)의 핵심이고, 되돌리면 지식 코퍼스의 신뢰가 무너진다
  (agent가 자기 추정을 인용). **티켓보다 넓은 거버넌스 축** — 컨트롤/지식 양쪽에 걸친다.
  이번 티켓 배치와 별개 세션이 나을 수 있다. **논점(Q3).**

## 4. 공동무효 분해 — 상호무효로 읽는다

마찰 로그 §6①의 교훈을 그대로 적용한다: 입도 테스트는 **한 방향이 아니라 상호무효**로 읽는다 —
*X가 Y를 죽이고 **Y도 X를 죽일 때만*** 한 ADR이고, 한쪽만 죽이면 그것은 **하위 축**이다.
그리고 §6⑨의 경고: 묶는 인력의 정체는 *"공동무효"* 가 아니라 ***"주제가 비슷하다"*** 이니,
"전부 티켓 얘기니까 한 ADR"의 유혹을 경계한다. **부분 폐기가 불허라(§3), 뭉치면 되돌릴 수 없다 —
입도는 작성 시점의 의무다.**

예상 경계(잠정):

```
ADR-0001 (두 플레인 분리) ★founding★
├── [지식 플레인 subtree] ADR-0002 … 0008
└── [컨트롤 플레인 subtree]  ← 지금 비어 있다. 아래를 채운다
     ├── T2  컨테이너 티켓은 accepted ADR을 전제한다   parent: ADR-0001   ★컨트롤 founding★
     │    └── T3  Feature = 독립 하위 축 결정일 때만    parent: T2
     │    └── T4  티켓 깊이 3층 ≠ ADR 깊이 (?)           parent: T2  또는 ADR-0001
     ├── T1  Issue Types 4종 (단일선택·컨/리프 이분)     parent: ADR-0001  references: T2
     └── T5  브리지 이슈→문서 단방향                     parent: ADR-0006(?)  references: ADR-0001
```

상호무효 점검 몇 개:

- **T1 ↔ T2**: 타입 체계(T1)가 뒤집혀도 "컨테이너는 결정을 전제"(T2)는 산다. 게이트(T2)가
  뒤집혀도 4종 타입(T1)은 산다. → **상호무효 아님 = 별개 ADR.** T2는 "컨테이너"라는 개념에
  기대므로 **references: T1** 정도.
- **T2 ↔ T3**: 위에서 봤듯 **한 방향** → T3은 T2의 하위 축.
- **T5 ↔ ADR-0006(동결)**: 마찰 §9의 판단으로는 **공동무효** — 동결이 없으면 "문서를 되쓸 수
  없으니 단방향"의 근거가 사라진다. 그렇다면 T5는 별개 ADR이 아니라 **ADR-0006에 흡수**되거나
  그 하위 축이어야 한다. 그런데 브리지는 컨트롤 플레인의 것이기도 하다 — 이 긴장이 **Q2**.

이 그림은 **제안**이다. 마찰 로그 §6·§9가 두 번 보여줬듯, 실제 경계는 초안을 얼리기 직전에야
갈린다("관련 있는 것을 모으는 쪽"으로 끌리는 오류를 매번 되돌렸다).

## 5. 사용자와 정해야 할 논점

- **Q1 — 승격 범위.** §5를 얼마나 ADR로 올릴까?
  *권장: 임계선 위(T2·T1·T5, 그리고 T3)만.* §5는 파생 규약으로 잔류. X1·X2는 승격 안 함.
- **Q2 — T5(브리지 방향)의 집.** 동결(ADR-0006)과 공동무효라면 parent가 지식 플레인 subtree로
  들어간다. 브리지는 컨트롤 플레인의 것이기도 한데 괜찮은가? 아니면 T5를 독립 ADR로 두고
  ADR-0006을 references로? (마찰 §9는 "동결과 공동무효"라 단언했다 — 그 판단을 유지할지.)
- **Q3 — 배치 경계.** T6(강제 사정거리)·T7(자기오염 차단)은 티켓보다 넓은 **거버넌스 축**이다.
  이번 티켓 배치에 넣을까, 별도로 뺄까? *권장: 이번엔 뺀다 — 티켓 결정에 집중.*
- **Q4 — T4를 ADR로?** "티켓 3층 ≠ ADR 깊이"의 "왜"가 ADR 값을 하는가, §5 산문으로 충분한가.
- **Q5 — `founding/sub` 게이트를 경고→거부로?** `adr-gate.py`는 지금 Feature parent 부재를
  **경고만** 한다(§4). 이건 정책이자 도구 결정 — 티켓 ADR을 쓰며 함께 정하면 자연스럽다.
- **Q6 — 몇 건, 어떤 순서로?** 마찰 §6 교훈: 한 세션에 여러 건 쓰면 dogfood가 아니라 문서 공장.

## 6. 다음 걸음 제안

**첫 ADR로 T2 하나**를 권한다 — *"컨테이너 티켓은 accepted ADR을 전제한다 (결정이 계층을 낳는다)"*,
parent: ADR-0001, 컨트롤 플레인의 founding 결정. 근거:

1. **이미 구조가 강제한다** — `adr-gate.py`가 미accept·미공표를 거부한다.
2. **진짜 dogfood를 통과했다** — §8①·§8④에서 게이트가 `origin/main`을 읽도록 교정되며 굳었다.
3. **임계선이 명백하다** — 두 플레인의 결합이라 되돌리기 어렵고 영향 범위가 전 시스템.
4. **founding이라 다른 후보의 parent 자리**가 되어, 이후 T3·T1·T4를 얹기 좋다.

그다음 사용자와 Q1~Q6를 정하고, T1·T3·(T5)를 한 건씩 얼려 나간다. 상호무효로 경계를 긋고,
얼리기 직전 "독립적으로 뒤집힐 결정이 섞였나"를 매번 다시 검사한다(§6⑨).

## 7. 진행 로그 — 무엇이 ADR이 됐고 무엇을 미뤘나

사용자가 **문서↔티켓 상관관계(언제·어떻게 연관)를 뒤로 미루기로** 했다. 가장 안 굳은 축이고
(마찰 §8① `ticket:` 필드가 원리적으로 못 채워졌던 지점, Q2 브리지의 집이 유일한 미해결 논점),
그 결합을 빼면 지금 얼릴 수 있는 것은 **컨트롤 플레인의 내부 구조**뿐이다.

**"업무를 티켓으로 관리한다"는 그대로는 ADR이 못 된다** — ADR-0001의 컨트롤 플레인 절반과 공동무효다.
대신 그 결정의 문서-독립 알맹이를 입도(§4③, 상호무효 읽기)로 갈라 아래를 저작했다:

| ADR | 결정 | parent | 상태 |
|---|---|---|---|
| **ADR-0009** | 작업 이슈는 정확히 하나의 타입을 갖는다 (라벨 아닌 Issue Type). 지금 타입 Task·Bug | ADR-0001 | proposed |
| **ADR-0010** | 이슈 타입은 컨테이너(묶는다)/리프(수행한다)로 갈린다. 리프는 하위 없음. 컨테이너=Epic | ADR-0009 | proposed |

평면으로 가도 단일 타입은 살고, 다중 라벨로 가도 서브이슈 계층은 산다. **뭉치면 계층만 바꿀 때
단일 타입까지 supersede해야 하므로 갈랐다**(부분 폐기 불허, §3 / 마찰 §6⑨의 "묶는 인력").
