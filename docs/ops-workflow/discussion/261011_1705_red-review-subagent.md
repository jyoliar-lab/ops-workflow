# red 승인을 subagent에게 — 테스트 검토·보강 subagent와 ac-verifier의 역할 분리

## 1. 문제

tdd-loop는 시나리오 표 뒤와 red 뒤에 사람 승인을 둔다.
2026-09-30 결론은 둘을 "시나리오 승인은 티켓에서 *무엇을*, red 승인은 PR에서 *어떻게*"로 갈랐다.
red 승인은 사람이 PR diff에서 테스트 본문을 읽는 일이다.

실제 운용에서 red의 테스트 코드는 자주 약했다.
Then의 성질 하나를 빠뜨리거나, 느슨한 포함 단언으로 시나리오를 가르지 못하거나, 동률·경계 입력이 없어 정렬 규칙을 검사하지 못했다.
그 약함은 사람의 red 승인에서가 아니라 verify 단계의 ac-verifier가 "테스트가 약하다" 묶음으로 잡았고, 그때마다 red 보강 커밋 → 사람 승인 → green 재호출의 되감기가 생겼다.
사람이 red에서 멈춰 읽는 비용은 들면서 약함은 잡히지 않았다.

정하려는 것은 둘이다.
red 뒤의 사람 승인을 없애고 그 자리를 무엇으로 채우나.
테스트의 약함을 검토·보강하는 일을 어느 컨텍스트가 어느 시점에 하나.

열려 있던 것: 사람 멈춤이 어디에 남나, 검토자가 무엇까지 고칠 수 있나, 흔적을 어떻게 남기나, 모델, ac-verifier에서 무엇을 빼나, red 재진입에도 같은가, 검토자가 무엇을 받나, 보고의 형태.
그리고 검토자가 **무엇을 기준으로** 약함을 판정하나 — 척도 · 판정의 형태 · 과단언의 처리 · 기준의 자리.

## 2. 실측

- 집행 흐름은 정책 ADR이 아니다.
  2026-09-30 결론 §5가 "집행 흐름 — 되돌리기 한 시간대 — 티켓. ADR을 기다리지 않는다"로, §6이 "개정은 steward가 한다 — 티켓으로 흐르지 않는다"로 판정했다.
- ac-verifier의 현재 검사 중 red 산출물을 보는 것은 셋이다.
  표 ↔ 테스트(이름 전부 있나 · given/when/then 일치 · 단언이 성질인가 · 층 중복), red 커밋 diff(stub 범위 · 가드 아닌데 통과 = 동어반복), 그리고 발견 묶음 "테스트가 약하다 → red 추가 커밋".
  verify.md는 그 묶음에 "표 재승인 없이 테스트만 고친다 — 새 red 커밋으로 올리고 사람 승인 뒤 green을 다시 부른다"를 둔다.
- red.md §2(c)는 이미 주 세션이 red에서 스스로 보는 실패의 종류 표를 갖는다.
  "가드가 아닌데 통과했다 → 단언을 구체화해 다시 돌린다. 그래도 통과하면 시나리오가 틀린 것 — 사람에게."
  "collect 실패는 red가 아니다 → stub 보강."
- 보강의 실제 모양 — obs-toolkit PR #14, 커밋 `cb4cc00`("red 보강 — 검수가 약하다 한 다섯 테스트").
  `any("없음" in line for line in lines)` → slow 묶음 줄을 골라 그 줄에 "없음" 단언.
  `"3" in line and "0" in line` → idle 3·7 parametrize, `"%d개"`·`"0건"` 토큰 단언.
  정렬 테스트에 배율·건수 동률 쌍을 더해 (caller, callee, endpoint) 사전순을 가름.
  표본 테스트에 `trace_id` 목록 단언 추가(누락 필드).
  다섯 전부 구현은 이미 만족해 통과했다 — 약함은 구현이 아니라 테스트의 것이었다.
- 다섯의 공통 성질은 하나다.
  **Then이 약속한 성질을 하나 깬 결과를 상상하면 원래 단언이 그것을 통과시킨다.**

  | Then의 약속 | 성질 하나를 깬 결과 | 원래 단언 | 통과하나 |
  |---|---|---|---|
  | slow 묶음 줄에 "없음" | "없음"이 normal 줄에 찍히고 slow 줄은 비어 있다 | `any("없음" in line for line in lines)` | 통과 |
  | 알려진 호출 3개가 0건 | 한 줄에 `p95 30ms · 0 errors` | `"3" in line and "0" in line` | 통과 |
  | 동률은 (caller, callee, endpoint) 사전순 | 동률 둘의 순서가 뒤집혔다 | Given에 동률이 없다 | 깬 결과를 만들 수조차 없다 |
  | 표본은 앞 limit개 트레이스 | 개수는 맞는데 뒤의 트레이스가 들어갔다 | `sample == 3` | 통과 |
  | callee 없으면 "미확인" · server 없으면 "서버 —" | 둘 다 없고 빈칸 | `not any("30" in line)` | 통과 |

  하드코딩은 이 표에 들어오지 않는다 — 이 입력에서는 Then의 성질을 하나도 깨지 않는다.
  하드코딩이 깨지는 것은 다른 입력에서이고, 그것은 verifier의 반증 테스트가 잡는다(입력을 바꿔 돌린다).
  두 검사는 겹치지 않는다 — red 검토자는 "이 입력에서 성질이 깨진 결과를 단언이 거르나", verifier는 "입력을 바꿔도 구현이 성질을 지키나".
- red.md §2(a)에 단언 · Given 규칙이 이미 산문으로 있다 — 성질마다 한 줄 · `and` 금지 · 값 복사 아님 · Given은 표대로 · 대역은 최소 입력 · 모킹 격리.
  검토자의 기준이 다른 파일에 생기면 원천이 둘이 된다.
- 재개 규약은 "승인의 흔적은 남지 않으니 사람에게 묻는다"다.
  red 뒤 승인이 없어지면 red의 끝을 말하는 흔적이 따로 필요하다.
- tdd-green은 티켓 본문도 표도 받지 않는다(테스트가 명세의 전부).
  ac-verifier는 맥락을 전부 받는다(대조가 일).
  새 검토자는 그 사이다 — 표는 받되 AC는 받지 않는다(§3-7).

## 3. 인터뷰에서 닫힌 축

### 3-1. red 뒤 사람 멈춤의 자리

**선택: 조건부 멈춤.** 검토 subagent가 보강으로 닫을 수 있는 것은 닫고 흐름으로 green에 간다. 표 자체가 틀렸다고 판단한 것만 멈춰 사람에게 — 기존 "시나리오가 틀렸음을 알게 되면 표를 새 코멘트로 다시 내고 재승인" 규약 그대로. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 항상 흐름 — 표 수준 문제도 verify에서 verifier가 잡게 둔다. 틀린 표 위에서 green 한 번을 버린다.
- 보고 뒤 흐름 — 멈추지 않되 발견을 코멘트로 남긴다. 사람이 읽을 시점이 없는 코멘트는 흔적이 아니라 소음이다.

</details>

### 3-2. 검토 subagent의 보강 권한

**선택: 테스트 본문 + stub.** 단언 보강 · Given 정정 · GWT 구분 · 누락 필드 — 테스트 본문은 고친다. red가 red로 서도록 stub 누락분(시그니처 + raise/panic/throw)도 채운다. 표의 행 · 테스트 이름 · 소스 본문은 건드리지 않는다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 테스트 본문만 — stub가 모자라 collect가 안 되면 보고만 하고 돌아온다. 되감기 한 번이 더 생긴다.
- 테스트 + 표의 행 추가 — 표가 재승인 없이 바뀐다. "표 승인 = 무엇을 검사할 것인가의 소유 시점"과 충돌.

</details>

### 3-3. 보강의 커밋 단위

**선택: 별도 red 커밋.** 주 세션의 red 커밋 뒤에 `test(#N): red 보강 — …` 커밋 하나. 초안과 보강이 diff로 갈려 검토자가 무엇을 잡았는지 읽힌다. verifier는 이미 green 전 커밋 전부를 red로 읽는다. 고칠 것이 없으면 커밋하지 않는다 — 빈 커밋 없음. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 커밋 전 검토 → 커밋 하나 — 깨끗하지만 보강의 흔적이 사라진다. 검토자가 값을 내는지 측정할 자리가 없다.
- subagent가 amend — 흔적 없음. Draft PR 전이어야만 가능.

</details>

### 3-4. 모델

**선택: opus.** tdd-green과 같은 모델. 다른 눈의 효과는 컨텍스트 격리에서 온다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- Fable — verifier의 근거(쓴 모델과 다른 모델이 읽어야 맹점을 공유하지 않는다)를 적용. 주 세션이 Fable이면 그 근거가 약해지고 비용은 높다.
- 주 세션과 같은 모델 — 격리만. 명시하지 않으면 주 세션의 모델에 따라 흔들린다.

</details>

### 3-5. ac-verifier에서 빼는 것

**선택: 표 ↔ 테스트 대조 전부.** 이름 일치 · given/when/then 일치 · 단언이 성질인가 · 층 중복 · red diff의 stub 범위 · 동어반복 — 전부 검토 subagent로 옮긴다. "테스트가 약하다 → red 추가 커밋" 묶음은 사라진다. verifier에 남는 것: AC ↔ 표의 약속 누락, green·refactor diff(테스트 경로 0 · 하드코딩 의심 · refactor 범위), 직접 실행, 반증 테스트, 커버리지. 대조표의 근거 칸(AC마다 대표 테스트 이름)은 표의 테스트 이름 열과 직접 실행 결과에서 쓴다 — 테스트 본문을 읽지 않고도 채워진다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 테스트 품질 검사만 빼고 이름 일치는 남김 — 이름 대조도 표 ↔ 테스트의 일이라 반쪽만 옮기면 두 agent가 같은 표를 읽는다.
- 약화 검사만 빼기 — GWT · 층 중복 · stub 범위를 두 번 본다. 이중 검사는 누가 잡아야 하는지를 흐린다.

</details>

### 3-6. red 재진입

**선택: 모든 red 진입 동일.** 처음이든 verify 뒤 표 재승인 · 반증으로 되돌아왔든 red 초안 → 검토 subagent → (조건부 멈춤) → green. red에서 사람 승인은 어디에도 없다. 사람은 표와 verify 코멘트에서만 개입한다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 재진입은 사람 승인 유지 — 한 번 틀린 맥락이니 사람이 읽는다. 승인 자리가 둘이 되어 재개 규약이 분기한다.

</details>

### 3-7. 검토 subagent의 입력

**선택: 시나리오 코멘트 URL + red 커밋 sha + worktree + 테스트 명령.** 표가 명세다. 티켓 AC는 받지 않는다 — AC ↔ 표는 verifier의 것. 주 세션의 의도 설명 · "이 테스트는 X를 검사한다"류는 넣지 않는다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 표 + AC — 표의 AC 누락을 verify 전에 잡지만 verifier와 겹친다. 3-5에서 verifier에 남긴 것을 다시 둘로 만든다.
- 표 + 주 세션의 의도 메모 — 표에 없는 의도가 있다는 것 자체가 표의 구멍이다. 메모는 구멍을 덮어 표를 고칠 기회를 없앤다.

</details>

### 3-8. 보고의 형태

**선택: 고정 결과 블록 → 주 세션의 red 완료 코멘트 하나.** 검토 subagent는 tdd-green처럼 고정 블록(결과 · 보강 커밋 sha · 실행 결과 · 멈춤 사유)만 돌려준다. 티켓 코멘트는 주 세션이 red 완료 보고 하나로 쓴다 — 검토 뒤의 최종 수(신규 fail · 가드 pass · 기존 pass). 보강 여부는 코멘트에 따로 말하지 않는다. 보강의 흔적은 커밋이다(3-3). (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- subagent가 코멘트 직접 게시 — "티켓 코멘트는 주 세션이 쓴다"의 예외가 둘로 는다.
- 코멘트 없음 — red 완료 코멘트가 재개 규약의 흔적이라(3-13) 없앨 수 없다.

</details>

### 3-9. 척도 — "테스트가 충분하다"는 무엇으로 재나

**선택: Then의 성질을 깬 결과 사고실험.** 테스트마다 검토자는 Then이 약속한 성질 하나를 깬 결과를 머리로 하나 떠올린다. 단언이 그 결과를 여전히 통과시키면 약하다. 깬 결과를 Given으로 만들 수조차 없으면(동률 · 경계가 Given에 없다) Given이 약하다. 깬 결과가 떠오르지 않으면 Then이 성질을 말하지 않은 것 — 표의 문제라 멈춤 조건(3-13)으로. 실행은 없다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 표의 Then 대조만 — 성질마다 단언이 있고 Given이 표대로인지만 본다. 예시의 `any(...)` 단언은 이 기준으로는 통과한다 — 약함의 다섯 중 셋을 놓친다.
- 깬 결과를 실제로 만들어 돌린다 — 결과를 내려면 구현이 있어야 하고, 그것은 green의 일이다. 비용이 테스트 수에 비례한다.
- 사고실험 + 확신 못 할 때만 stub 상수 반증 — stub의 raise 자리에 깬 결과를 상수로 넣고 그 테스트만 돌려 실패를 본다(미커밋 · 보고 뒤 삭제). 구현은 아니지만 red에서 소스에 값을 쓰는 예외가 생기고, 부수효과가 Then이면 상수로 못 만든다. 사람 판정으로 버림.
- "통과시키는 틀린 구현이 있나" — 첫 판의 표현. 어떤 테스트든 기대값을 돌려주는 하드코딩은 통과하므로 언제나 참이라 기준이 못 된다(사람 지적, 2026-10-11). 결과에 대한 사고실험으로 고쳐 썼다.

</details>

### 3-10. 판정의 형태

**선택: 원리 하나 + 알려진 패턴 목록.** 판정은 원리(3-9)로 한다. 패턴 목록은 원리의 예시다 — 새 모양도 원리로 잡고, 목록은 발견될 때마다 자란다. 지금 목록: 결과를 특정하지 않는 포함 단언(`any(tok in line …)`) · 우연히 맞는 짧은 토큰(`"3" in line`) · 부정 단언만("없다"만 있고 맞는 것이 있다는 단언이 없다) · Then의 성질 누락(둘을 약속하는데 단언은 하나) · Given이 성질을 가르지 못함(규칙을 약속하는데 그 경우가 없다) · 대역이 일을 대신함(fake가 창을 잘라 준다) · 동어반복(항상 참 · stub이 우연히 만족 · 아무것도 안 부름). (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 고정 체크리스트만 — 목록 밖 약함이 통과한다. 예시의 다섯도 처음엔 목록에 없었다.
- 원리만 — 같은 약함을 두 검토가 다르게 읽는다. 목록이 재량을 좁힌다.

</details>

### 3-11. 과단언 — Then이 말하지 않은 것을 단언하는 줄

**선택: 더하기만, 버리지 않는다.** 검토자는 모자란 단언만 채운다. Then 밖의 단언 · 값 복사(픽스처의 우연 "65줄")는 그대로 둔다 — 그것은 약함이 아니라 깨지기 쉬움이고, 사고실험을 통과한다. 깨지는 것은 refactor · 다음 티켓의 일이다. red.md의 "단언은 성질이지 값의 복사가 아니다"는 쓰는 자의 규칙으로 남고 검토자의 교정 대상은 아니다. (인터뷰, 2026-10-11)

<details><summary>버린 안</summary>

- 양방향 보강 — Then에 없는 성질을 단언하는 줄은 버린다. 검토자가 테스트를 줄이는 권한을 갖게 되고, 버린 줄이 실은 표에 빠진 성질이었을 때 되돌릴 흔적이 약하다.
- 과단언은 보고만 — 주 세션이 표 재승인 없이 고칠 수 없어 사실상 기록만이다.

</details>

### 3-12. 기준의 자리

**선택: tdd-loop 공유 파일 하나 — 읽는 역할은 둘.** `tdd-loop/` 안에 기준 파일 하나에 쓰기 규칙(red.md §2(a)에서 옮김) · 패턴 목록(3-10) · 사고실험 원리(3-9)를 함께 둔다. 주 세션은 red를 쓸 때 읽는다 — 규칙과 패턴은 피할 것으로 적용하고, 원리는 "검토자가 이것으로 판정한다"로 알기만 한다. 테스트마다 사고실험을 하라고 주 세션에 요구하지 않는다. 검토자는 판정할 때 읽는다 — 테스트마다 사고실험을 수행하고 패턴 목록은 원리의 예시로 쓴다. 원천은 하나, 수행은 검토자만. (인터뷰, 2026-10-11 — 처음 "양쪽이 전부 읽고 적용"이었다가 주 세션의 인지 부하 지적으로 가름)

왜 원리를 주 세션에 숨기지 않나 — 검토자가 무엇으로 판정하는지 모르면 돌아온 보강 커밋을 읽을 때 왜 고쳐졌는지 읽지 못한다. 알되 수행하지 않는 것이 부하를 늘리지 않는 선이다.

<details><summary>버린 안</summary>

- 양쪽이 전부 읽고 적용 — 주 세션이 테스트마다 사고실험까지 하면 부하가 실제로 커지고, 형식적으로 "했다"고 넘기면 검토자의 다른 눈이 무뎌진다.
- 검토자 agent 정의에만 — 주 세션의 부하는 가장 작다. 그러나 다섯 약함 전부가 쓸 때 피하기 쉬운 모양이었다(`any()` 대신 줄 고르기 · "3" 대신 "3개" · 동률 입력 하나). 모르고 쓰면 보강이 재작성에 가까워져 초안과 보강의 diff가 커지고, red.md의 쓰기 규칙과 검토자 기준이 같은 것을 두 파일이 말한다.
- 대상 저장소의 rules에 — 저장소 규칙은 모양(이름 · 자리 · 픽스처)을, 하네스는 변별력을 말한다 — 층이 다르다.

</details>

### 3-13. 기본값 — 인터뷰에서 묻지 않고 agent가 둔 것

사람이 확인했다(2026-10-11). 선택마다 한 줄.

**멈춤 조건.** red.md §2(c)·§7이 이미 "사람에게"로 보내는 넷과 같다 — 선언과 행이 어긋난다 · Given을 손으로 만들 수 없다 · 단언을 구체화해도 통과한다(가드 아닌데) · stub를 채워도 red가 서지 않는다. 이 넷은 표의 문제라 검토자가 고칠 수 없다. 그 외는 보강으로 닫는다.

**검토자는 보강 뒤 전체를 한 번 돌린다** — 신규 fail · 가드 pass · 기존 pass. 보강한 단언이 stub에 통과하면 그것이 동어반복이다. 돌리지 않으면 보강을 검증할 수 없다. 주 세션도 복귀 뒤 한 번 더 돌린다 — green 복귀와 같은 규약.

**Draft PR과 red 완료 코멘트는 검토자 복귀 뒤.** red의 끝이 검토자 복귀로 옮겨가므로 push · PR · 코멘트는 거기서 한 번. 검토자는 커밋만 하고 push하지 않는다.

**재개 규약.** red 완료 코멘트의 유무가 "검토까지 끝났다"를 말한다. 코멘트가 있으면 green으로, red 커밋만 있고 코멘트가 없으면 검토 subagent부터. 표 승인과 verify 뒤 지시는 여전히 흔적이 없으니 사람에게 묻는다.

**이름 `tdd-red-reviewer`.** `tdd-green` · `ac-verifier`와 같은 결.

**기준 파일 `tdd-loop/strength.md`.** 제목은 "변별력 — 깬 결과를 거르나". 쓰기 규칙(red.md에서 옮김) · 패턴 목록(3-10) · 사고실험 원리(3-9). 파일 안에서 "쓸 때"와 "판정할 때"를 절로 가른다 — 주 세션은 앞을, 검토자는 둘 다 읽는다. 검토자 정의와 red.md가 둘 다 가리킨다.

## 5. 반대편 — 이 설계가 틀리는 조건

- 주 세션과 검토자가 같은 표를 명세로 본다.
  표에 없는 의도는 아무도 잡지 못한다 — 사람의 표 승인이 "무엇을"의 전부여야 한다.
  표 승인이 형식이 되면 이 설계는 틀린 red를 verify까지 그대로 흘린다.
- 사람이 테스트 본문을 처음 읽는 시점이 verify 뒤로 밀린다.
  틀린 red의 비용은 green 한 번(subagent 호출 하나)이다.
  green이 비싸지는 저장소(e2e · 실 의존성)에서는 이 비용이 red 승인의 비용을 넘을 수 있다.
- 검토자가 opus다.
  주 세션이 opus이면 모델 분리가 없고 컨텍스트 격리만 남는다.
  격리만으로 약함이 잡히지 않으면 모델을 Fable로 올리는 것이 다음 손잡이다 — 3-4의 선택 줄을 고친다.
- 사고실험은 검토자의 재량이다.
  깬 결과를 떠올리지 못하면 약한 테스트가 통과한다.
  패턴 목록이 그 재량을 메우는데, 목록이 자라지 않으면 기준이 낡는다 — verify의 반증 · 사람의 PR 읽기에서 나온 약함은 목록에 더해야 한다.
- 검토자가 보강 커밋을 내지 않는 비율이 높으면 둘 중 하나다.
  주 세션의 red가 충분히 강해졌거나, 검토자가 보지 못한다.
  verify의 반증 · 사람의 PR 읽기에서 약함이 계속 나오면 후자다.

## 6. 버린 것

- **시나리오 뒤 red 전체를 subagent에게.** 초안까지 subagent가 쓰면 주 세션은 표만 쓰는 역할이 된다.
  그러나 시나리오의 의도를 가장 명확히 아는 컨텍스트가 주 세션이다 — 초안은 거기서, 검토는 밖에서.
  검토자에게 의도를 넘기지 않는 것(3-7)과 같은 이유의 반대면이다.
- **ac-verifier에 약화 검사를 남겨 이중 검사.** 두 agent가 같은 것을 보면 누가 잡아야 했는지가 흐려지고, 발견 묶음이 둘로 갈린다.
  검토는 red 쪽에 모은다 — verifier는 red가 끝난 뒤의 고리(구현)와 사슬의 양 끝(AC ↔ 표)만 본다.
