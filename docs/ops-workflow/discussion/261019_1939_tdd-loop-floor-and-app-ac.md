# tdd-loop 의 바닥과 애플리케이션 AC — 테스트가 약속 대신 구현을 고정하는 기제

## 1. 문제

출발 가설은 "ticket-engineer 의 tdd-loop 가 AC 에 맞춰 시나리오를 억지로 만들어 테스트 품질을 떨어뜨린다" 였다.
증거는 obs-toolkit 의 tdd-loop 티켓 6건(#94 · #102 · #109 · #111 · #119 · #120)이다.
실측(§2)은 가설을 좁혔다 — AC 행 규칙 일반은 주범이 아니고, 층 규칙에 바닥이 없는 것과 애플리케이션 티켓에 "상태" AC 가 허용된 것이 테스트를 공개 경계 아래로 내린다.

이 문서는 obs-toolkit 테스트 품질 논의(`../../ai-agent/discussion/261019_1623_obs-toolkit-test-quality.md`, 이하 **A**)에서 2026-10-19 에 분리했다.
A 는 obs-toolkit 의 경계 정의 · 소스 인터페이스 · 리팩토링 티켓을 다루고, 이 문서는 하네스(ticket-engineer 의 tdd-loop · ops-workflow 의 티켓 템플릿) 쪽 축만 다룬다.
아래에서 **A-3-1** 은 A 의 3-1(공개 경계의 정의 — 연산 + 환원 · 파서, 호출 규칙), **A-3-4** 는 A 의 3-4(메타테스트 규칙은 티켓 안에서), **A-4-1** 은 A 의 4-1(mutation 측정), **A-4-7** 은 A 의 4-7(Task 셋의 순서)이다.
축 번호(4-2 ~ 4-6)는 분리 전 문서의 것을 그대로 둔다 — 채팅과 판정이 그 번호로 났다.

앞선 결정은 goal `tdd-execution-flow` 의 논의 셋과 digest `261011_1740` 에 있다.
260930_1828 은 "AC 는 동작 또는 상태다" 를 정했고 §3 에서 애플리케이션은 동작만이라 분석했다.
261011_1705 3-11 은 red 검토자의 권한을 "더하기만" 으로 정하고, 값 복사 · 과단언의 정리를 "다음 티켓의 일" 로 넘겼다.
이 논의는 그 둘을 obs-toolkit 의 증거로 재검토한다.

## 2. 실측

티켓 코멘트(시나리오 표 · red 메모)와 `workspace/ref/obs-toolkit` · `workspace/ref/ticket-engineer` 에서 읽은 것이다.

**AC → 테스트 대응 (tdd-loop 티켓 6건: #94 · #102 · #109 · #111 · #119 · #120)**

- 행 규칙은 "AC 항목마다 **최소** 하나 + AC 밖도 더한다" 다. 행 대부분이 `추가` · Requirements · Technical Notes 에서 왔다 — #102 는 39행 중 17행, #94 는 70행 중 약 24행이 AC 밖이다.
- 약 150개 테스트 중 AC 문구를 옮긴 것 약 10개, red 에서 이미 통과하는 가드 8개. 가설이 말한 "AC 행 → 베낀 테스트" 는 소수다.
- 내부 형태에 결합한 테스트 약 17개가 가장 크고, 이것들이 갈렸다 — #111 의 신규 7개는 11일 뒤 #119(`eb0c2fc`)가 전부 지웠고, #94~#96 의 `Evidence.*` 테스트 11개는 #120(`28c090f`)이 지웠다. `RunResult` 튜플 넷째 자리를 단언한 #120 의 행 셋은 #119 에서 셋째 자리로 고쳐 썼다.
- 내부 결합의 원천은 층 규칙(scenarios.md §1.5 "한 주장은 가장 낮은 층 하나에")이다 — `signals_of` · `window_preamble` · `client.log` · `red_query` 문자열로 단언이 내려간다.
- 베낀 테스트는 AC 자체가 구조일 때 생긴다 — "길이 1 목록이다"(#111) · "필드가 없다"(#120) · "templates 는 1+k 회"(#119). 템플릿 규칙 "AC 는 동작 또는 상태"(2026-09-30)는 "상태" 가 내부 형태를 막지 못한다.
- 기존 테스트 수정 — #120 에서 red 가 기존 테스트를 3튜플 · 4튜플 양쪽에 통과하도록 구부렸고 사람이 "테스트 꼴 정정" 으로 잡았다. 규칙("수정은 더하기만", scenarios.md §2.5)은 있었고 위반이 났다.
- 가장 큰 쪼갬 사건은 #107 의 `and` 분리 138개 · 15테스트 → 약 50 이다. 사람이 지시한 재편이고 tdd-loop 가 아니다.
- tdd-loop 가 잡은 것도 있다 — #94 AC-3 의 "대역이 창을 잘라 줘서 통과" 를 verifier 가 발견해 행 69 를 정적 응답으로 더했다. 다만 red 의 행 · AC 규칙이 아니라 green 뒤 verifier 가 잡았다.

**refactor 단계의 폭** — tdd-loop 를 밟은 PR 넷의 refactor 커밋 다섯은 소스 1~3파일 · 8~60줄이고 테스트 파일을 한 번도 건드리지 않았다. 고친 것은 전부 테스트가 이름 부르지 않은 private 헬퍼다. 커밋 목록과 수치는 A §2. 테스트가 부르는 층이 곧 설계가 굳는 층이라는 것이 이 논의의 전제다.

## 4. 열린 축 — 논의

### 4-2. tdd-loop 의 기존 테스트 정책

실측 — scenarios.md §2.5 는 `수정 — 더하기만` 을 허용하고, #120 에서 red 가 기존 테스트를 양쪽 꼴에 통과하도록 구부린 위반이 났다. 사람이 잡았다.

- **A. 수정 금지 — 대체만** — 기존 테스트는 그대로이거나 처분표의 삭제 · 대체뿐이다. 단언 추가도 새 테스트로 쓴다. 시그니처 변경으로 옛 테스트가 못 살면 대체다. 옛 가드가 사라지는 길이 구조적으로 막힌다 / parametrize id 하나 더하는 것도 새 함수가 돼 테스트 수가 는다.
- B. 수정 금지 + 삭제 · 대체는 별도 승인 — A 에 더해 처분표의 삭제 · 대체 행은 시나리오 승인과 별도로 명시 승인을 받는다. 지금도 처분표는 승인 대상이라 실질은 "따로 물어야 한다" 다 / 승인 지점이 둘이 돼 흐름이 느려진다.
- C. 현행 유지 + 검토자 대조 — `더하기만` 을 두고 red 검토자가 기존 테스트 diff 에서 삭제 · 변경된 단언이 없는지 대조하는 항목을 더한다. 규칙이 아니라 집행의 문제였다는 읽기 / 검토자가 놓치면 같은 일이 난다.
- D. 안 바꾼다 — 위반은 한 번이고 사람이 잡았다 / 기존 테스트가 "현재 약속의 기록" 이라는 지위를 못 갖는다.

**판정(사람, 2026-10-19): C — append-only.** 같은 결과의 새 성질은 기존 테스트에 단언을 더하고, 옛 단언은 빼거나 약하게 하지 못한다. 결과가 바뀌면 대체다. 집행은 red 검토자의 기존 테스트 diff 대조.

### 4-3. 층 규칙과 공개 경계 — ticket-engineer 델타의 모양

실측 — scenarios.md §1.5 는 내리기 규칙이고 바닥이 없다. "한 주장은 가장 낮은 층 하나에" 와 판별 "Then 을 확인하는 데 협력자의 대역이 필요 없으면 조립 시나리오가 아니다 — 한 층 내린다" 가 단언을 공개 경계 아래까지 내린다 — `window_preamble` · `client.log` · 질의 문자열 전문 · `RunResult` 튜플 자리.
원리 자체(아래 층이 주장을 소유하고 위 층은 배선 예 하나)는 A-3-1 의 호출 규칙과 같다. 다른 것은 바닥의 유무다 — A-3-1 은 "자기 주제의 층 하나" 에서 멈추고 §1.5 는 멈출 곳이 없다.
`signals_of` 로 내려간 단언은 A-3-1 의 경계 안이라 문제가 아니다 — 환원 층이 경계를 소유하는 것이 맞다.
둘째 지렛대는 층 표다. 조립 행 "배선 · 순서 · 호출 수" 와 외부 호출 행 "`Client`" 가 관찰점을 `Client.log` 로 이끈다. A-3-1 은 같은 성질을 transport 대역의 호출 기록에서 본다 — 관찰점이 모듈 안이 아니라 I/O 경계 밖이다.
문제를 한 문장으로 — 단언의 주인이 약속을 소유한 함수가 아니라 그 Then 을 대역 없이 만들 수 있는 가장 낮은 함수가 되고, 그 함수가 경계 아래면 테스트가 약속 대신 구현을 고정한다.
내려간 것은 배선이 아니라 결과의 성질이다 — 배선은 §1.5 에서도 조립 층의 것이고 실제로 `red` · `exemplars` 테스트에 남았다.
#120 이 전형이다. AC 는 "summary.txt 머리는 창 · 기준선" 이고 주인은 `*_run` 의 출력인데, 판별이 `window_preamble(w)` 로 대역 없이 확인된다며 한 층 내려 단언 둘이 `window_preamble` 에 붙었다(test_cli.py:397,414). 위 층의 배선 예 하나는 `cli._finish` 를 직접 부르고 Then 을 `[*cli.window_preamble(w), "a 1", "b 2"]` 로 적었다(444-446) — 위 테스트의 기대값이 아래 함수의 출력으로 표현돼 `window_preamble` 을 인라인하면 셋이 함께 깨진다. 약속은 그대로인데.
A-3-1 이 obs-toolkit 의 경계를 정했지만 ticket-engineer 는 저장소마다 다른 경계를 모른다.

- **A. 범용 규칙 파일** — ticket-engineer 의 `.claude/rules/` 에 좋은 테스트의 범용 특징(공개 경계 위에서 · 한 동작 · fake · mock 으로 내부 동작을 검증하지 않는다 · 대역은 정적 응답)을 적고 준수를 지시한다. 저장소마다 규칙 파일이 없어도 하한이 생긴다 / 경계가 어디인지는 여전히 저장소가 말해야 한다.
- B. 층 규칙에 하한 — §1.5 를 "저장소가 정한 공개 경계 위에서 가장 낮은 층" 으로 고치고, 경계는 저장소 규칙 파일(obs-toolkit 이면 `python-tests.md`)이 정한다. 경계가 없는 저장소에서는 지금과 같다 / 저장소 규칙 파일이 경계를 적어야 작동한다.
- C. red 검토자 판정 항목 — "Then 이 내부 형태(튜플 자리 · 질의 전문 · private 속성)를 말한다" 를 약함의 모양 목록에 더한다. 행을 쓸 때가 아니라 검토에서 잡힌다 / 표 승인 뒤라 되감기 비용이 든다.
- D. 안 한다 — 내부 결합 churn 은 제품이 raw · evidence 의 자리를 정하던 10일(#94 → #111 → #119 → #120) 특유의 것일 수 있다 / 같은 규칙이 다음 저장소에서 같은 결과를 낸다.

A 와 B · C 는 양립한다 — A 가 하한이고 B · C 가 집행이다.

**판정(사람, 2026-10-19): A + B.** 범용 규칙(A)이 하한이고 §1.5 의 바닥(B)이 집행이다. C 는 4-2 의 검토자 대조 항목과 같은 자리라 B 의 일부로 함께 간다.
경계의 운반체는 경로가 아니다. obs-toolkit 은 한 파일 안에 층이 섞여 있다 — traces.py 에 private 15 · 조립기 3 · 파서 7 · 환원 5 · 연산 4 가 같이 산다. 경로로 층을 가르려면 모듈 넷을 열두 파일쯤으로 쪼개는 소스 재편이고, 그것은 A-4-7 의 인터페이스 Task 가 필요할 때만 한다. 운반체 후보는 이름 규약(`_` · `*_query` · `*_lines`) · 모듈 `__all__`(지금은 어디에도 없다. 경계를 소스가 선언하고 메타테스트가 "테스트는 `__all__` 밖 이름을 부르지 않는다" 로 기계 검사할 수 있다) · 규칙 파일(`python-tests.md`)의 경계 절이다. 어느 것으로 할지는 A-3-4 대로 리팩토링 티켓 안에서 정한다.
B 가 들어갈 자리는 red.md:30("저장소의 테스트 규약을 따른다 — `.claude/rules/*`")이 아니라 scenarios.md §1.5 다. 층의 소유를 정하는 단계가 시나리오인데 지금 §1.5:43 은 "파일 배치는 저장소 규칙이, 어느 층이 주장을 소유하나는 이 스킬이" 로 나눠 두어 저장소 경계가 시나리오 단계에 들어올 입구가 없다. 저장소 규칙 읽기를 red 가 아니라 시나리오 전으로 당기는 것이 B 의 실체다.

### 4-4. AC 작성 규칙 — "상태" 의 뜻, 그리고 누구의 어휘인가

실측 — 베낀 테스트는 AC 가 내부 구조를 말할 때 생겼고(#111 · #119 AC-5 · #120), 그것들이 1~2주 안에 지워졌다.
템플릿 주석(`harness/design-partner/.claude/skills/ticket/templates/task.md:33`)은 "AC 는 동작 또는 상태다" 라고 조건 없이 적고, 종류(형상 · 수렴 · 지속)는 "인프라면" 에만 단다.
"상태" 의 출처는 260930_1828 이다 — 그 문서 §3 은 "애플리케이션 티켓은 첫째 한 종류(동작)만 있어야 한다" 고 썼는데, 결정 1 과 템플릿 주석은 "동작 또는 상태" 로 합쳐 적었다. 분리는 분석에 있었고 규칙에는 없다.
세 티켓은 전부 그 주석 뒤에 발행됐다 — #111(10-03) · #119 · #120(10-11).
그 "상태" 행들은 인프라 어휘로는 **형상**이다 — "길이 1 목록이다" · "`RunResult` 의 원본 자리 타입이 `list[Response]` 하나다"(#111) · "`Evidence` 에 필드가 없다"(#120) · "원소 수가 GET 수와 같다 — templates(1+k) · around(3)"(#119 AC-5).
인프라에서 형상은 선언(렌더 결과)에 대한 단언이고 선언이 곧 제품이다. 애플리케이션에서 형상은 소스 구조에 대한 단언이고 소스 구조는 구현이다. 같은 말이 한쪽에서는 약속이고 다른쪽에서는 구현 고정이다.
기제는 셋의 곱이다 — 형상 AC × 행 규칙("AC 항목마다 최소 하나", scenarios.md) × TDD 판정("실패하는 테스트로 쓸 수 있는가" — `hasattr` 로 쓸 수 있으니 대상이다). 셋 중 하나만 빠져도 구조 테스트는 나오지 않는다. 원래 가설("AC 행이 억지 시나리오를 만든다")은 이 좁은 꼴로 맞다 — AC 행 일반이 아니라 상태형 AC 행이다.
#120 의 반례도 있다 — 같은 티켓의 "summary.txt 머리에 창이 있고, compare 는 기준선 창도 있다" 는 동작이고, 거기서 나온 테스트는 4-3 의 층 문제만 있었지 베낀 것이 아니다. 구조 변경 티켓에도 동작 AC 는 쓸 수 있다.

- A. 주석을 좁힌다 — "상태는 밖에서 관찰 가능한 상태다. 내부 타입 · 필드 · 반환 꼴은 AC 가 아니라 Technical Notes 다." 를 템플릿 주석에 더한다. 비용이 한 줄이다 / "밖" 이 어디인지 티켓 저자가 저장소마다 판단한다. A-3-1 의 경계 논의가 티켓 저자에게 옮겨 온다.
- B. 구조 변경 티켓은 AC 없이 — "필드 제거" 같은 티켓은 관찰 가능한 동작이 없으므로 TDD 비대상으로 가고 AC 는 "pyright 통과 · grep 0" 류의 검사만 적는다. #120 이 실제로 AC-1 을 "참조 제거 + pyright" 로 처리했다 / 구조 변경에 딸린 동작 변화(#120 의 창 표시)는 여전히 AC 가 필요하다.
- C. 안 바꾼다 — 증거가 세 티켓이고 모두 제품이 자리를 정하던 시기다 / 같은 꼴의 AC 가 오면 같은 테스트가 온다. 주석이 바뀌지 않는 한 다음 저장소에서도 "상태" 는 형상으로 읽힌다.
- **D. 티켓의 부류로 가른다** — 애플리케이션 티켓의 AC 는 **동작만**(Given · When · Then 으로 쓸 수 있는 문장). "상태" 는 인프라(IaC · GitOps) 티켓의 어휘이고 거기서만 형상 · 수렴 · 지속으로 갈린다. 구조 변경이 목표인 애플리케이션 티켓은 그 구조를 Goal · Technical Notes 에 적고, AC 에는 그 구조가 낳는 관찰 가능한 동작만 적는다 — 없으면 B 다(검사만 적고 TDD 비대상). 260930 §3 이 이미 이렇게 분석했고 규칙만 합쳐 적혔으니, 분석대로 규칙을 가르는 것이다 / 운반체가 필요하다 — 템플릿 주석의 두 갈래가 가장 싸고(AC 는 사람이 design-partner 와 쓴다), 템플릿 분리(task-app · task-infra)나 저장소 부류 표(260910_1900 §2 C · E, 미결)는 더 비싸다 / 경계 사례 — GPL 로 쓴 IaC(`smoke_test.py`)와 CLI 도구의 설정 파일 변경은 어느 부류인가를 티켓 저자가 정해야 한다.

A 는 D 에 포함된다(D 가 "밖" 을 부류로 답한다). B 는 D 의 한 가지다. D 가 이기는 조건은 다음 애플리케이션 티켓의 AC 에서 "~이다 · ~가 없다 · ~개다" 꼴이 사라지고 테스트가 그 티켓의 연산 · 환원을 부르는 것이다.

**판정(사람, 2026-10-19): D — 티켓의 부류로 가른다.** 애플리케이션 AC 는 동작만, "상태" 와 세 종류는 인프라 티켓의 어휘다. 구조만 바뀌는 애플리케이션 티켓은 검사만 적고 TDD 비대상(B 흡수). 운반체는 템플릿 주석의 두 갈래(task.md · bug.md). 경계 사례(GPL 로 쓴 IaC · 도구의 설정 파일)는 티켓 저자가 부류를 정하고, 그 판단이 반복되면 그때 부류 표를 논한다.

### 4-5. red 검토자의 과단언 — 3-11 의 재검토

실측 — 261011 3-11 은 "더하기만, 버리지 않는다" 로 정했고, 깨지기 쉬운 단언을 "refactor · 다음 티켓의 일" 로 넘겼다. 그 다음 티켓이 이번이고, 값 복사 약 22곳 · 문구 리터럴 약 24테스트가 그 비용이다.

- **A. 유지** — 검토자의 권한은 더하기만이다. 지우는 것은 사람이 리팩토링 티켓에서 한다. 검토자가 테스트를 줄이는 권한을 갖지 않는다는 3-11 의 이유가 그대로 산다 / 비용이 주기적으로 쌓인다.
- B. 보고만 — 검토자가 값 복사 · 내부 형태 단언을 blocked 가 아니라 "보고" 로 남기고, 주 대화가 표 재승인 없이 그 줄만 성질 단언으로 바꾼다. 3-11 은 이것을 "사실상 기록만" 이라 버렸지만, 이번에 쌓인 비용이 그 기록의 쓸모를 보인다 / 재승인 없는 수정이 생긴다.
- C. 번복 — 검토자가 값 복사를 성질 단언으로 고쳐 쓴다. 비용이 발생 지점에서 사라진다 / 버린 줄이 실은 표에 빠진 성질이었을 때 흔적이 약하다(3-11 의 이유).

**판정(사람, 2026-10-19): A — 유지.** 검토자의 권한은 더하기만이고, 지우는 것은 사람이 리팩토링 티켓에서 한다. 값 복사 · 내부 형태 단언이 다시 쌓이는 것은 4-3 의 바닥(공개 경계 위에서 가장 낮은 층)과 4-4 의 부류 규칙(애플리케이션 AC 는 동작만)이 발생 지점에서 막는다 — 검토자가 아니라 시나리오 단계가 막는다.

### 4-6. 가드 행 — red 에서 통과하는 테스트

실측 — red 에서 통과한 가드 8개를 출처로 가르면 셋이고, "고치는 함수의 다른 동작을 지키는 새 테스트" 는 하나도 없다.

## 5. 반대편 — 이 설계가 틀리는 조건

- 내부 결합 churn 이 제품 초기 10일 특유의 것이었다면, 층 규칙을 고치는 것은 조립 층의 검사를 약하게 할 뿐이다. 지금 `RunResult` · `client.log` 가 안정됐다면 4-3 은 D 가 맞다.
- 구조적 AC 를 금하면 #120 같은 "필드 제거" 티켓은 AC 를 쓸 수 없다. 그런 티켓이 TDD 비대상으로 가는 것이 맞다는 전제 위에서만 4-4 D 가 선다.
- 바닥을 "저장소가 정한 경계" 에 두면 경계를 적지 않은 저장소에서는 지금과 같다. 범용 규칙(4-3 A)이 하한을 주지만, 그 하한도 "공개 경계" 가 어디인지는 말하지 못한다 — 다음 저장소가 경계를 적지 않으면 같은 결과가 난다.
- 애플리케이션 AC 를 동작만으로 묶으면 "필드 제거" 같은 티켓은 TDD 비대상이 되고 검사(pyright · grep)만 남는다. 그 티켓에 딸린 동작 변화를 티켓 저자가 AC 로 못 뽑아내면 테스트 없는 변경이 생긴다.

## 6. 버린 것

- **tdd-loop 를 원인으로 한 하네스 대개편** — 실측이 AC 행 규칙을 주범에서 뺐다. 베낀 테스트 약 10개 · 가드 8개는 약 150개 중 소수다. 고칠 것은 층 규칙의 하한과 AC 의 "상태" 정의이지 흐름이 아니다.
- **AC 행 규칙("항목마다 최소 하나")의 폐지** — 행 규칙은 상태형 AC 와 곱해질 때만 구조 테스트를 낳는다(4-4). 상태형 AC 를 부류로 걷어내면 행 규칙은 그대로 둬도 된다.
- **red 검토자에게 지우는 권한** — 4-5 C. 3-11 의 이유(버린 줄이 표에 빠진 성질이었을 때 흔적이 약하다)가 그대로 선다.
