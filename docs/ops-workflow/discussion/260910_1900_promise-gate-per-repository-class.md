# 약속 게이트의 저장소별 적용 — 테스트가 없는 곳에서 약속은 무엇에 담기나

## 문제

앞 discussion(`260910_1817`)은 사람의 이해 병목을 **"소유하려는 구조적 약속과 그것을 담은 인공물(테스트)이 연결되지 않는다"** 로 재정의하고, 절차 하나로 수렴했다:

```
착수 전  agent: 약속 목록 + 각 약속을 검사할 테스트 이름 → 티켓 코멘트
         사람: 검수 · approve                              ← 소유의 시점
구현     agent: 코드 + 테스트(규약대로) → push → PR
검수     사람: 약속 테스트만 읽는다
```

이 절차는 **"약속을 담는 인공물 = 테스트"** 를 전제한다.
사람의 질문은 그 전제가 서지 않는 곳이다 — *테스트 코드 작성이 어려운 저장소(GitOps 등)는? 저장소에 따라 이 절차를 넣을지 뺄지도 정해야 한다.*

이 문서는 (a) 실제 target 저장소들이 무엇으로 검증하고 있는지 읽고, (b) 절차를 저장소별로 어떻게 켜고 끌지 옵션을 벌린다.
정하지 않는다 — §7 의 답 뒤다.

## 1. 실측 — target 저장소들은 무엇으로 검증하나

`.claude/ref-repos.txt` 의 16개 저장소 + obs-toolkit 을 `workspace/ref/` 에서 읽었다(2026-09-10).

| 부류 | 저장소 | 검증 인공물의 실물 |
|---|---|---|
| **① 테스트 스위트 + CI 게이트** | posting·review·userinfo-service · api-composer · auth-service(`*_test.go` 5~17 · `go-test.yaml`) · obs-toolkit(pytest 59 · pyright strict) · goutils(19 · CI 없음) | 테스트 이름이 곧 약속. 앞 discussion 의 전제가 그대로 선다 |
| **② 코드지만 테스트가 거의 없음** | careerhub-front(0 · CI 는 `create-tag` 뿐) · careerhub-incident-agent(0) · posting-skillscanner(2) · review-crawler(3) | 약속을 담을 자리가 **없다** — 표를 요구하면 "첫 테스트를 세우라" 가 된다 |
| **③ 선언형 인프라** | jyoliar-k8s(kustomize · ArgoCD · `smoke_test.py` 1개) · onpremise-k8s(ansible · `smoke-test.yaml` playbook · `validate: 'visudo -cf %s'`) · jyoliar-platform-terraform(`terraform plan`/`output`) | **렌더·플랜·실측**이 검증이다. 저장소 안에 "테스트" 로 남는 것은 거의 없다 |
| **④ 하네스** | ticket-engineer · ops-workflow `.claude/`(#98 의 target) | hook 의 거부 · 스크립트 exit code |
| **⑤ 브라우저** | careerhub-web(playwright e2e 5 · `g1-check.yml`) | e2e 명세 = 약속. #9 *"e2e 명세를 재작성 전에 쓴다"* 가 이미 이 모양이었다 |

### 1-1. 인프라 티켓의 보고는 이미 "약속 + 근거" 다

③ 에서 닫힌 티켓의 완료 보고를 읽었다. 근거 칸에 든 것:

| 티켓 | 약속(AC) | 근거로 제시된 것 |
|---|---|---|
| #63 aws-ec2 제거 | baremetal overlay 의 kustomize build 가 삭제 전과 동일하게 성공 | `kustomize build --enable-helm` 을 **51개 kustomization 루트 전부** 삭제 전/후 실행 → `OK=51 FAIL=0` · 두 목록 `diff` 무차이 · `grep -rn "aws-ec2"` 0건 |
| #53 Zitadel 배포 | ArgoCD sync 성공 · 콘솔 접속 | `zitadel-helm` app Synced·Healthy · `/ui/console` 200 · discovery 200(`issuer: …`) |
| #83 watcher crashloop | crashloop resolve · 재발 없음 | node-exporter 실측 `node_systemd_service_restart_total{…} 0` · `state="active" 1` — 3대 동일 |

즉 인프라에서 약속은 이미 **명령 + 기대 출력** 으로 표현되고 있다.
문제는 그것이 **보고 코멘트에만 살고 저장소에는 남지 않는다** 는 것이다 — 다음 변경이 #63 의 "51개 전부 build 성공" 을 깨도 아무것도 울지 않는다.

예외가 있다. **알림 규칙**(#26 promcheck · #81 CoreDNS forward 실패 알림)과 **smoke playbook**(`smoke-test.yaml`)은 저장소에 남아 계속 검사된다.
이 클러스터에서 인프라 약속의 지속 검사는 테스트가 아니라 **알림 규칙**이었다.

### 1-2. 재정의

약속은 저장소 부류와 무관하게 있다.
갈리는 것은 **약속을 담는 인공물**이고, 인공물은 두 축으로 다르다:

| 축 | 한쪽 | 다른 쪽 |
|---|---|---|
| **지속성** | 저장소에 남아 다음 변경에도 검사된다 — 테스트 · e2e 명세 · 알림 규칙 · smoke playbook · 렌더 단언(kubeconform·conftest) | 1회 실측 — 보고 코멘트의 명령 + 출력 |
| **가독성** | 사람이 "약속 하나" 로 읽는다 — `test_get_only` · `CoreDNSForwardFailing` | 읽으려면 산술·환경을 알아야 한다 — `OK=51`, `node_systemd_service_restart_total 0` |

앞 discussion 이 테스트에 대해 한 진단(한 테스트=한 주장 · 픽스처 숫자의 유도)은 **오른쪽을 왼쪽으로 옮기는 규약**이었다.
인프라에도 같은 이동이 필요한지, 아니면 오른쪽을 인정할지가 이 문서의 질문이다.

## 2. 옵션 — 저장소마다 어떻게 켜고 끄나

축: **소유가 남는가**(지속성) · **누가 판단하나** · **되돌리기 비용** · **저장소 지식이 어디 사나**.

### A. 안 한다 — 테스트 있는 ①⑤ 에만 게이트

나머지는 현행(AC 대조 + 실측 근거)을 유지한다.
- 소유: ① ⑤ 에서만. 되돌리기 0. 판단: 저장소에 테스트 디렉터리가 있나 — 기계적.
- 반대편: **가장 되돌리기 어려운 곳이 빠진다.** 코드 저장소의 실패는 revert 지만 인프라의 실패는 클러스터 상태다(§4② one-way door 를 코드에 적용하면 ③ 이 가장 위험 티어). 소유 없이 머지되는 것이 정확히 거기서 계속된다.

### B. 인공물을 일반화한다 — 표의 둘째 열이 "테스트 이름" 이 아니라 "검증 인공물"

절차는 하나, 값만 다르다: 테스트 이름 | 렌더 단언 | 알림 규칙 | 실측 명령+기대 출력.
- 소유: 인공물 종류에 따라. 판단: engineer 가 저장소를 보고 고른다. 되돌리기 0.
- 반대편: **1회 실측을 인공물로 인정하면 게이트가 퇴화한다** — "명령 목록 승인" 이 되고, 머지 뒤 저장소엔 아무것도 없다. 앞 discussion 이 풀려던 문제(소유가 남지 않는다)로 되돌아간다. 인정하지 않으면 ③ 에서 매 티켓마다 지속 검사를 새로 세워야 한다 — 그것이 §4 의 두 번째 질문이다.

### C. 저장소가 선언한다 — 각 target 저장소 `CLAUDE.md` 에 "이 저장소의 약속은 X 에 담긴다"

jyoliar-k8s 는 이미 `CLAUDE.md` 에 kustomize 규칙을, onpremise-k8s 는 `smoke-test.yaml` 을 적어 뒀다. 거기에 한 절을 더한다 — *약속 인공물 = kustomize 렌더 단언 + 알림 규칙* / *= playwright e2e* / *= `go test`*. engineer 는 읽고 따른다(이미 `ticket-start` 는 저장소 CLAUDE.md 를 읽는다).
- 소유: 저장소가 정한 만큼. 판단: 저장소 소유자(사람) 1회. 저장소 지식은 **저장소에** 산다 — ADR-0016 이 target 을 하네스가 아니라 티켓에 둔 것과 같은 방향.
- 반대편: 저장소 CLAUDE.md 는 steward 밖이라 **저장소마다 Task 하나씩**이다(리프라 ADR 불요). 선언 없는 저장소의 기본값이 필요하다 — 기본값이 "테스트" 면 ② 는 표 요구 = 첫 테스트 요구가 된다.

### D. 티켓이 정한다 — 발행 시 design-partner 가 표 필요 여부와 인공물 종류를 적는다

- 소유: 티켓마다. 판단: 발행자. 되돌리기 0. **저장소가 아니라 변경의 성질로 끌 수 있다** — #83(장애 복구 Bug) · #63(삭제·정리) · 설정값 1줄 변경에는 표가 과하다. Anthropic best practices 의 *"If you could describe the diff in one sentence, skip the plan"* 이 이 축이다.
- 반대편: 매 발행마다 판단 — **규율**이다. 발행 시점엔 인공물 종류를 아직 모를 수 있다(#83 은 착수해서 읽어야 원인이 나왔다). 그리고 발행자가 "불요" 를 기본값으로 찍기 시작하면 ADR-0017 의 무효화 조건(*"무의존 선언이 반사적 통과 의례가 된다면"*)과 같은 붕괴다.

### E. 하네스에 저장소 부류 표를 둔다

ticket-engineer 하네스에 `{저장소 → 인공물 종류}` 표. steward 관할이라 한 번에 고친다.
- 소유: 표대로. 판단: steward+사람 1회. 되돌리기 낮음.
- 반대편: **저장소 지식이 하네스에 스며든다.** engineer 는 저장소를 티켓의 '저장소' 절로 알지 하네스로 알지 않는다(ADR-0016). 저장소가 추가될 때마다 하네스가 낡고, 그 드리프트를 conformance 가 잡을 근거 ADR 도 없다.

### 옵션이 이기는 조건

| 사람이 원하는 것이… | 이기는 옵션 |
|---|---|
| 코드 저장소부터 빨리, 인프라는 나중에 | **A** → 나중에 C |
| 절차는 하나, 저장소가 자기 방식을 말한다 | **C** + 기본값(§7-4) |
| 저장소보다 변경의 성질(긴급·삭제·1줄)로 끄고 싶다 | **D** 를 C 위에 얹는다 — 저장소는 인공물을, 티켓은 생략을 |
| 하네스 한 곳에서 다 보이게 | **E** — 단 ADR-0016 방향과 어긋남을 감수 |

C 와 D 는 배타가 아니다 — C 는 *무엇에 담나*, D 는 *이번엔 생략하나* 를 답한다.

## 3. 생략 조건은 저장소가 아닐 수 있다

§2 를 벌리다 보니 "저장소별" 이라는 사람의 질문 자체가 두 질문이었다:

1. **이 저장소에서 약속은 무엇에 담기나** — 저장소의 성질. 한 번 정하면 오래 간다.
2. **이번 변경에 표가 필요한가** — 변경의 성질. Bug 긴급 복구 · 삭제 · 1줄.

1 은 저장소 부류(§1 표)가 답하고, 2 는 티켓 타입·규모가 답한다.
둘을 한 스위치로 만들면 ③ 인프라 저장소의 Bug 긴급 복구(#83)와 ③ 의 큰 신규 배포(#53)가 같은 취급을 받는다 — #53 은 표가 있었으면 좋았고 #83 은 표가 있었으면 복구가 늦었다.

## 4. 사람의 반대편에 서서

**"GitOps 는 테스트를 못 쓴다" 는 반쯤 틀리다.**
kustomize build 결과에 대한 단언(kubeconform · conftest/OPA · `yq` assert)은 저장소에 남는 검사이고, jyoliar-k8s 에는 이미 `smoke_test.py` 가 하나 있다.
못 쓰는 것이 아니라 **안 써 왔다** — 비용 대비 얻는 것이 불분명했기 때문이고, 그 계산은 사람의 것이다.

**반대로, 인프라 약속의 대부분은 렌더가 아니라 실행 상태에 있다.**
#53 의 약속은 "매니페스트가 이렇게 생겼다" 가 아니라 "ArgoCD 가 Synced 이고 콘솔이 200 이다" 다.
렌더 단언은 그 약속을 검사하지 못한다.
실행 상태의 지속 검사는 이 클러스터에서 **알림 규칙**이 해 왔다(§1-1).
그렇다면 ③ 의 "약속 테스트" 는 테스트가 아니라 **알림 규칙 이름**일 수 있다 — 사람이 읽을 것은 `CoreDNSForwardFailing` 이지 `kustomize build` 출력이 아니다.
이 관점이 서면 B 의 함정(1회 실측 인정)이 열리지 않고도 ③ 에 절차가 선다.

## 5. 버린 것

- **인프라 전용 별도 절차 신설** — 절차가 둘이면 "어느 쪽인가" 가 매번 판단거리가 된다. 절차 하나에 인공물만 다른 B/C 가 같은 자리를 채운다.
- **② 저장소에 테스트 도입을 이 게이트에 얹기** — 별개 결정이다(저장소별 투자 판단). 게이트가 "테스트 없는 저장소엔 테스트부터" 를 강요하게 두면 게이트 회피가 생긴다.
- **PR 크기·diff 줄 수로 생략 판정** — 픽스처·골격이 줄 수를 오염시킨다(앞 discussion §3-B). 생략은 성질로.

## 6. 임계선 — ADR 감인가

저장소별 적용 자체는 되돌리기 쉽다 — 스킬 문장 · 저장소 CLAUDE.md 한 절.
§4② 로 **티켓감**이다.

ADR 감은 여전히 앞 discussion 의 하나 — *"검수 = 승인된 약속 목록과 그것을 검사하는 인공물을 읽는 것"*.
이 문서가 그 ADR 에 주는 영향은 Decision 에 **"인공물이 무엇인지는 저장소가 정한다"** 한 줄이 들어가느냐뿐이다.
ADR-0016·0017 이 표기를 도구에 위임한 것과 같은 구조 — 결정은 *약속과 인공물의 연결* 까지, 인공물의 종류는 저장소의 값.

## 7. 사람에게 묻는다 — 코드에 없는 것

1. **인프라에서 소유하고 싶은 것은 무엇인가.** 매니페스트의 형상(렌더)인가, 클러스터가 그렇게 돼 있음(실행 상태)인가. 후자면 ③ 의 인공물은 알림 규칙 쪽이다(§4).
2. **1회 실측을 약속 인공물로 인정하나.** `OK=51` 같은 명령+출력을 표에 올리고 approve 하는 것으로 충분한가, 아니면 저장소에 남는 것만 인정하나. 인정하면 B 가 서고, 안 하면 ③ 은 매 티켓 지속 검사를 세운다.
3. **생략의 기준은 저장소인가 변경의 성질인가.** #83 같은 긴급 Bug 에도 표를 요구하나. 아니라면 누가 생략을 판정하나 — 발행자(D)인가 티켓 타입(Bug = 생략)인가.
4. **② 테스트 0 저장소의 기본값.** careerhub-front · incident-agent 에서 표를 요구하면 첫 테스트를 세우라는 뜻이 된다. 그것을 원하나, 아니면 이 저장소들은 당분간 A 인가.

답이 오면 — C 는 저장소별 리프 Task(저장소 CLAUDE.md 한 절), D 는 design-partner 쪼갬 기준 한 줄, 절차 본체는 ticket-engineer 하네스 델타로 흐른다.
