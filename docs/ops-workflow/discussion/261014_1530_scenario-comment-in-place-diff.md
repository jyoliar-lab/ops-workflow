# 시나리오 코멘트의 갱신 — 제자리 수정과 변경의 가시화

## 1. 문제

tdd-loop의 시나리오 표는 티켓 코멘트로 게시되고, 사람이 그것을 승인하는 순간이 "무엇을 검사할 것인가"의 소유 시점이다.
표가 뒤 단계에서 틀렸음이 드러나면 규약은 표를 **새 코멘트로 전문 재게시**하게 한다 — 머리 한 줄에 "v<n> — 무엇이 바뀌었나 · 앞 코멘트를 대체".
#119에서 이 일이 세 번 일어났다.
코멘트 하나가 13~14k자, 약 160줄인데 한 판에서 실제로 바뀐 줄은 열 줄 안팎이다.

아픔은 **v(n) 승인 순간**에 드러난다.
사람은 무엇이 바뀌었는지 찾으려고 160줄을 다시 읽거나, 머리 한 줄의 산문 요약을 믿고 승인한다.
그래서 잃는 것은 둘이다.
요약에 적히지 않은 변경을 모른 채 승인한다 — 표 승인의 의미가 약해진다.
그리고 관문 스크립트가 코멘트 전량을 agent에게 먹이므로, 재게시마다 중복 표가 수십 k자씩 재개·보고 세션의 컨텍스트에 들어간다.

정하려는 것은 하나다.
시나리오 표를 바꿀 때 **변경을 git diff처럼 한눈에** 보이게 하는 길.

열려 있던 것: 표의 정본이 어디 사나, 승인 자리는 티켓인가, 승인된 판은 어느 수준으로 남아야 하나, 비교의 기준, 변경을 보이는 수단과 입도, 승인 흔적을 코멘트에 적나.

## 2. 실측

- #119의 시나리오 코멘트 셋 — 첫 코멘트는 게시 12분 뒤 제자리 PATCH(v1→v2, 승인 전 수정), v3·v4는 새 코멘트다.
  v3→v4의 차이는 13줄(추가 7 · 삭제 6) — 머리 줄, 행 6 수정, 행 21·22 추가, AC 커버리지 표 세 줄.
- 규약의 자리 — `tdd-loop/scenarios.md` §5(승인 전은 PATCH, 뒤 단계는 새 코멘트 · "diff는 두 코멘트가 보인다"), `red.md` §5-2, `verify.md`의 "표가 틀렸다" 행.
  GitHub는 코멘트 둘을 diff해 주지 않는다 — "두 코멘트가 보인다"는 사람이 둘을 나란히 읽는다는 뜻이다.
- 코멘트 ID는 세션 기억에만 있다 — `tmp/github-issues/`에는 초안 파일뿐, ID를 적는 자리가 없다.
  새 세션은 PATCH할 ID를 모르므로 새 코멘트를 낼 수밖에 없다.
- `tdd-red-reviewer`·`ac-verifier`는 표를 **코멘트 URL**로 받아 `gh api`로 읽는다.
  red 커밋 메시지·PR 본문·완료 코멘트도 그 URL을 가리킨다 — 제자리 수정이면 이 URL이 안정된다.
- GitHub GraphQL `userContentEdits`는 편집된 코멘트의 **판마다 본문 전체**를 돌려준다(#119 첫 코멘트: 2판, 14,522자·13,029자 확인, 2026-10-14).
  제자리 수정은 복원 가능하고, 임의 두 판의 diff를 도구가 만들 수 있다.
- GitHub UI의 편집 이력("Viewing edit" 모달)은 원문 markdown 위에 단어 단위 diff(초록 삽입 · 빨강 취소선)를 보여 준다.
  머리 줄 한 문장을 고친 v4 코멘트의 이력은 바뀐 구절만 색이 입어 그대로 읽힌다(화면 확인, 2026-10-14).
  행 일곱을 지운 v1→v2의 이력은 정렬이 어긋나 표 전체가 빨강·초록 벽이 된다(화면 확인, 2026-10-14).
  표의 행 하나만 고친 경우는 재지 않았다 — 그 행 한 줄 안에서 단어 diff가 될 가능성이 높다.
  모달은 판 하나의 전문을 보여 주므로 어느 행이 더해지고 빠졌는지의 요약이 없고, 바뀐 곳으로 데려가지 않는다.
- v3→v4를 세 모양으로 만들어 쟀다.

| 모양 | 크기 | 읽힘 |
|---|---|---|
| 줄 diff(` ```diff ` fence, 행 = 줄) | 20줄 · 3.7k자 · 최장 줄 749자 | GitHub가 색을 입힌다. 바뀐 행은 보이나 행 안의 바뀐 단어는 찾아야 한다 |
| 단어 diff(`[-옛-]{+새+}`) | 15줄 · 3.4k자 | 단어가 보인다. 렌더되지 않는 monospace, 표 기호 사이에 끼어 읽기 거칠다 |
| 행 단위 렌더 표(번호로 대응 · 칸 안은 `~~옛~~ **새**`) | 10줄 · 1.15k자 | 추가·삭제·수정 행이 표로 렌더되고 바뀐 칸이 보인다. 번호 있는 행만 잡는다 — 선언·산문·AC 커버리지 변경은 보조 수단이 필요하다 |

- 코멘트 한도 65k자 — 표 14k + 변경 블록 수 k는 넉넉히 든다.
- 집행 흐름은 정책 ADR이 아니다(2026-09-30 결론 §5·§6) — 개정은 steward가 하네스에서 한다.

## 3. 인터뷰에서 닫힌 축

### 3-1. 정본의 자리와 버전의 모양

**선택: 코멘트 하나를 제자리에서 고친다.** 표는 언제나 한 코멘트에 현행본만 있고, 지난 판은 GitHub 편집 이력이 보존한다. (인터뷰, 2026-10-14)

<details><summary>버린 안</summary>

- 버전마다 코멘트 하나(현상) — 전문이 반복되고 diff는 사람이 두 코멘트를 읽어 만든다
- PR 본문을 정본으로 — 승인 자리는 티켓이 최선이고, 전환 비용이 있다
- PR 브랜치에 파일로 — target 저장소를 더럽히지 않는다
- ops-workflow 지식 플레인에 문서로 — engineer는 ops-workflow 파일을 쓰지 못하고, 작업 수명의 산출물은 그 자리가 아니다

</details>

### 3-2. 승인 자리

**선택: 티켓.** 승인 행위와 표의 링크는 ops-workflow 이슈에 남는다. 다른 자리는 전환 비용이 크지 않을 때만 고려한다. (인터뷰, 2026-10-14)

### 3-3. 승인된 판의 보존 수준

**선택: 복원 가능하면 된다.** 판마다 전문이 한 곳에 펼쳐져 있을 필요는 없다 — GraphQL 편집 이력이 판마다 본문 전체를 돌려주므로 충족된다. (인터뷰, 2026-10-14)

<details><summary>버린 안</summary>

- 승인 시점의 전문이 그대로 한 곳에 — 버전마다 코멘트를 요구한다
- 누가 언제 승인했는지까지 — 승인 표식(3-5)이 그 일부를 준다

</details>

### 3-4. 비교의 기준

**선택: 직전 게시본.** 승인 여부와 무관하게 바로 앞 판 대비다. (인터뷰, 2026-10-14)

### 3-5. 승인 표식

**선택: 적는다.** 채팅 승인이 오면 agent가 코멘트 머리에 `승인 v<n> — YYYY-MM-DD` 한 줄을 더한다. 편집 이력에서 어느 판이 승인본인지 바로 보인다. (인터뷰, 2026-10-14)

### 3-6. 머리의 산문 변경 요약

**선택: 없애고 기계가 만든 변경 블록으로 대체한다.** 요약과 실제가 어긋날 여지를 없앤다. (인터뷰, 2026-10-14)

<details><summary>버린 안</summary>

- 누적 변경 로그(v2·v3·v4 한 줄씩) — 산문이라 실제와 어긋날 수 있다
- 현행 한 줄만 — 같은 이유

</details>

### 3-7. 채팅에 보이는 것

**선택: 링크만.** 사람은 GitHub 브라우저에서 표를 읽는다. 채팅에는 코멘트 URL과 판 번호. (인터뷰, 2026-10-14)

### 3-8. 범위 밖

**선택: 관문의 코멘트 피드 · 착수 요약 · red 완료 코멘트 · 검수 코멘트의 반복은 이번에 다루지 않는다.** 시나리오 표 하나만. (인터뷰, 2026-10-14)

## 4. 열린 축 — 논의

### 4-1. 변경을 보이는 수단과 입도

실측: v3→v4 같은 보통의 갱신은 변경이 거의 행(번호 있는 줄)이다.
v1→v2 같은 재구성(행 일곱 삭제 · 번호 재배열)은 어떤 모양으로도 읽기 어렵다.
GitHub 편집 이력은 작은 문구 수정에서는 그대로 읽히고, 행의 추가·삭제가 섞이면 읽히지 않는다.

- **A. 행 단위 렌더 표 + 행 밖은 단어 diff fence** — 코멘트 머리에 `변경 — 추가 #21, #22 · 삭제 없음 · 수정 #6` 한 줄과 바뀐 행만 담은 표(바뀐 칸은 `~~옛~~ **새**`), 번호 없는 줄(선언 블록 · 산문 · AC 커버리지)의 변경은 그 아래 단어 diff fence로.
  이기는 조건: 갱신이 행 중심일 때 — 실측된 보통의 경우. 승인 뒤에는 `<details>`로 접어 뒤 독자(verifier)의 소음을 줄인다.
  지는 조건: 선언·타입 블록이 크게 바뀌는 판에는 fence가 길어진다. 행 번호를 재배열하면 대응이 깨진다 — 번호를 영구로 두고 삭제는 결번으로 남겨야 산다.
- **B. 줄 diff fence 하나** — 직전 본문과 새 본문의 unified diff를 ` ```diff `로 머리에. 도구가 가장 단순하고 GitHub가 색을 입힌다.
  이기는 조건: 구현을 최소로 두고 싶을 때, 변경이 행 단위로만 읽혀도 될 때.
  지는 조건: 749자짜리 행에서 바뀐 단어 하나를 찾는 일이 그대로 남는다 — 증상의 절반만 푼다.
- **C. 단어 diff fence 하나** — `[-옛-]{+새+}` 표기의 monospace 블록.
  이기는 조건: 단어 수준이 꼭 필요하고 렌더는 포기할 때.
  지는 조건: 표 기호 사이에 마커가 끼어 A보다 읽기 거칠고, 추가·삭제 행의 목록이 한눈에 안 보인다.
- **D. 안 한다 — 제자리 수정만 하고 변경은 GitHub 편집 이력에 맡긴다.** 전문 반복과 컨텍스트 비용은 사라지고 도구는 PATCH만 한다.
  이기는 조건: 갱신이 행 몇 개의 문구 수정에 그칠 때 — 이력 모달의 단어 diff가 그대로 읽힌다.
  지는 조건: 행의 추가·삭제가 섞이면 모달이 정렬을 잃어 벽이 된다(v1→v2 실측). 어느 행이 더해지고 빠졌는지의 요약이 없고, `edited`를 눌러 모달을 열어 160줄을 스크롤해야 바뀐 곳에 닿는다.
  A·B·C 어느 쪽을 골라도 이력은 그대로 남는다 — D는 그 위에 아무것도 더하지 않는 선택이다.

입도의 답은 측정이 말한다 — 행 단위만으로는 749자 행 안의 변경이 안 보이고, 단어 단위만으로는 행의 추가·삭제 구조가 안 보인다.
A가 둘을 겹친다.

**판정(사람, 2026-10-14): D. 지금은 GitHub 코멘트의 편집 이력만으로 충분하다.**

## 5. 반대편 — 이 설계가 틀리는 조건

- 제자리 수정은 코멘트 스트림의 시간순을 깬다.
  뒤에 올라온 red 완료·검수 코멘트가 가리킨 "그때의 표"는 편집 이력 속에만 있다.
  승인 표식 줄과 판 번호가 그 연결이고, 모든 참조(red 커밋 · PR 본문 · 완료 코멘트)가 URL에 `v<n>`을 함께 적어야 산다.
- 재번호 수준의 재구성에는 어떤 diff도 약하다.
  행 번호를 영구로 두고 삭제를 결번으로 남기지 않으면 A의 대응이 깨진다 — 번호 규칙이 함께 바뀌어야 한다.
- 편집 이력은 코멘트 저자가 판을 지울 수 있다.
  복원 보장은 GitHub의 기능에 기댄다 — 지워지면 되돌릴 길이 없다.
- 변경 블록도 기계가 만든 것이지 검증된 것은 아니다.
  행 밖 변경을 잡는 보조 fence가 빠지면 산문 요약과 같은 "안 적힌 변경"이 다시 생긴다.
- 코멘트 ID를 세션이 기억해야 하는 한 새 세션은 새 코멘트를 낸다.
  도구가 마커(`### TDD 시나리오 — <repo>`)로 코멘트를 찾지 않으면 제자리 수정 규약은 재개에서 깨진다.

## 6. 버린 것

- 표의 정본을 PR(본문·코멘트)로 옮기는 틀 — PR은 허용 범위지만 승인 자리가 티켓이라 둘로 갈라진다.
- 시나리오를 지식 플레인 문서로 두는 틀 — 수명이 작업의 것이고(ADR-0001), engineer가 쓰지 못한다.
- 관문의 코멘트 피드를 고쳐 중복을 거르는 틀 — 범위 밖. 제자리 수정이면 중복 자체가 사라진다.

## 7. 임계선 — ADR감인가

아니다.
2026-09-30 결론 §5의 판정이 그대로다 — 집행 흐름은 되돌리기 한 시간대, 하네스 하나.
바꾸는 것은 tdd-loop의 게시·수정 절차와 그것을 구동하는 스크립트 하나다.
되돌리는 자리는 이 문서 §8이 말한다 — `pilots.md`는 정책 ADR의 델타 원장이라 이 변경의 자리가 아니다.

## 8. 다음

판정이 나면 ticket-engineer 하네스 델타 — steward가 쓰고 사람이 승인해 커밋한다.

- 게시 스크립트 하나(`tdd-loop` 스킬 아래) — 마커로 그 티켓·target의 시나리오 코멘트를 찾고, 없으면 만들고, 있으면 PATCH한다.
  변경 블록은 만들지 않는다 — 변경은 GitHub 편집 이력이 보인다(판정 D).
  `--approve`가 승인 표식 줄을 더한다.
  새 코멘트를 손으로 내는 길은 스킬에서 지운다 — 강제는 구조로.
- `scenarios.md` §4·§5, `red.md` §5-2, `verify.md` "표가 틀렸다" 행 — "새 코멘트 · v<n> · 앞 코멘트를 대체"를 스크립트 호출로 바꾼다.
  머리의 산문 변경 요약은 없앤다(3-6).
  행 번호는 영구, 삭제는 결번 — 편집 이력이 행 삭제에서 벽이 되는 것(§2)을 줄인다.
- 참조의 모양 — red 커밋 메시지 · PR 본문 · 완료 코멘트 · 검토자·verifier 호출 프롬프트의 "시나리오 코멘트 URL"에 `v<n>`을 붙인다.
- 되돌리는 자리: 위 네 파일의 해당 절과 스크립트.
- 같은 델타에 **코멘트의 단위 분할**이 함께 들어갔다(채팅 결정, 2026-10-14 — 문서 없음).
  단위 = 기능 하나(세로 조각) · 둘 이상이 쓰는 것만 공통 · 색인 · 승인 · red · green · verify 전부 단위마다 · AC 커버리지와 가드는 단위에.
