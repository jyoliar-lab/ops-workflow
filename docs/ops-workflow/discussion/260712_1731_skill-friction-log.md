# skill 초판 마찰 로그

문서·티켓 skill 초판(ADR 저작 · 인덱스 생성 · Issue 조작)을 만들면서 드러난 것을 남긴다.

**skill은 편의 도구가 아니라 관측 장비다.** 어떤 인자를 묻고 무엇을 자동으로 채우는지가 곧 *"우리가 무엇을 결정했다고 착각하는지"* 를 드러낸다. 그래서 **skill을 고칠 때마다 고친 이유를 여기 적는다** — 그 이력이 규약을 확정하는 근거이고, 규약이 skill에 관성으로 끌려가는 것을 막는 유일한 장치다.

이 문서는 **열려 있다**(`status: active`). ADR을 실제로 써 보는 단계에서 계속 덧붙인다.

---

## 1. 지금까지 한 것

`.claude/skills/` 아래 3종을 저작했다. 각 skill은 **판단을 유도하는 `SKILL.md`** 와 **결정론적 기계인 `scripts/`** 의 2층이다.

| skill | 스크립트 | 하는 일 |
|---|---|---|
| **adr** | `next-id.py` · `freeze-check.py` · `list-subjects.py` · `supersede.py` | 전역 번호 발급 · 동결 사전 검사 · 어휘 제시 · supersede |
| **docs-index** | `build-index.py` | frontmatter 스캔 → `docs/_index/` 생성 |
| **ticket** | `create.py` · `link-sub.py` · `adr-gate.py` | Issue 발행·타입 지정 · 계층 연결 · 컨테이너 티켓의 ADR 게이트 |

**없는 것도 설계다.** 티켓 skill에 **close 하는 함수가 없다**(규약 §5 — PR 머지 ≠ 티켓 종료. 그 사이에 사용자 검수가 산다). discussion **생성 skill을 만들지 않았다** — 순수 판단 영역이고, 생성 의식(ritual)이 생기면 빈 문서를 양산한다. 린터도 아직 없다 — *무엇이 위반인가*가 굳기 전에 만들면 정상 커밋을 막아 실사용을 방해한다.

## 2. 무엇이 실제로 막히는가 (실행 검증)

거부는 프롬프트가 아니라 **exit code**다. exit 1 = 거부이고, agent는 우회하지 않는다.

| 시도 | 결과 |
|---|---|
| `accepted` ADR · `frozen` postmortem 본문 수정 | **거부** (§3 동결) |
| `proposed` ADR을 근거로 컨테이너 티켓 생성 | **거부** (§5 — 굳지 않은 결정으로 일하지 않는다) |
| 근거 ADR 없이 epic 생성 | **거부** |
| 이미 superseded 된 ADR을 다시 supersede | **거부** |
| ADR id 중복 상태에서 번호 발급 | **거부** (전역 유일성이 깨진 채로 더 발급하지 않는다) |
| 리프 티켓(task·bug)을 부모로 하위 이슈 연결 | **거부** (계층은 3층에서 멈춘다) |
| 4종 밖의 Issue Type | **인자 스키마가 값 자체를 받지 않는다** |

**아직 실증하지 못한 것**: Issue 발행·타입 지정·sub-issue 연결의 **쓰기 경로**. 이슈를 실제로 만들어야 확인되므로 dogfood 단계로 미뤘다. 읽기 경로(Issue Type 4종의 노드 해석)는 실 저장소에서 확인했다.

## 3. skill을 고친 이유

**① 콜드스타트를 에러로 취급했다.** 인덱스 스크립트가 *"문서가 0건"* 을 exit 1로 냈다. 그런데 exit 1은 이 하네스에서 **거부**를 뜻한다 — 정상 상태를 거부로 표현한 셈이다. exit 0으로 고쳤다.
→ **미결 해소**: "문서 0건"은 **정상 경로**다. 첫 문서를 쓰는 순간에도 도구가 돌아야 한다.

**② 동결 검사만 있으면 데드락이 생긴다.** `accepted` 문서의 편집을 전부 거부하면, *허용된* 편집(`status` · `superseded_by`)까지 막힌다. supersede를 할 방법이 사라진다.
→ **미결 해소**: 동결은 "아무것도 못 고침"이 아니라 **"본문만 못 고침"**이다. 그래서 `supersede.py`를 추가했다 — **본문에 손댈 방법이 자체가 없는** 스크립트다. 합법 편집도 사람 손이 아니라 기계가 한다. 그래야 동결이 규율이 아니라 구조가 된다.

**③ 어휘 목록의 원본을 인덱스로 잡았다가 바꿨다.** 애초 설계는 *"ADR skill이 `_index/by-subject/`를 읽어 기존 어휘를 제시한다"* 였다. 그러나 인덱스는 **파생물**이고 인덱스 skill을 돌려야 갱신되므로, 문서를 쓰고 인덱스를 안 돌리면 **어휘 목록이 낡는다.**
→ **미결 해소**: 원본은 **문서의 frontmatter**다. 그것을 직접 읽고, `_index/`와 어긋나면 *"인덱스가 낡았다"* 고 **경고한다.** 드리프트를 감추지 않는 쪽을 골랐다.

**④ 스크립트 언어 경계를 뒤집었다.** 초안은 *"외부 CLI를 부르면 bash, 아니면 python"* 이었고 번호 발급·동결 검사·게이트를 bash로 썼다. 그런데 이 셋은 **외부 CLI를 부르지 않는다 — 하는 일은 frontmatter 파싱이다.** 규칙과 실제 배치가 어긋나 있었고, 그 결과 파서가 5벌(python 3 + bash awk 2)이 됐다. bash의 awk 파서는 블록 리스트(`subjects:` 다음 줄 `- loki`)를 읽지 못했다.
→ **전부 python(표준 라이브러리)으로 통일**하고 파서를 **공용 모듈 1벌**로 합쳤다. `gh` 호출은 `subprocess`로 감쌌다.
→ **미결 해소**: 진짜 위험은 언어가 아니라 **같은 문서를 스크립트마다 다르게 읽는 것**이었다. 동결 검사와 컨테이너 게이트가 서로 다른 `status`를 볼 수 있었다.

**⑤ 버그 1건.** 결정 로그 생성이 `parent` 컬럼에서 터졌다(테이블 헤더 누락). 고쳤다.

## 4. skill이 물었는데 답할 근거가 없던 것 = 규약의 결손

**★ 파일명 규약이 없다.** frontmatter 스키마는 정해져 있는데 **파일 이름 규칙이 없다.** 잠정으로 `{ID}-{슬러그}.md`로 두고 skill이 슬러그를 **묻는다.** discussion·postmortem의 파일명은 여전히 미정이다(이 문서도 임의로 지었다).

**★ 날짜 필드가 없다 — 그런데 결정 로그는 "시간순"이다.** 규약은 `_index/decisions-log.md`를 *"accepted ADR만, 시간순"* 이라 했지만, frontmatter에 날짜가 없다. 수명주기 필드를 두지 않기로 한 결정의 부수 효과다.
→ 초판은 **ADR id 순**으로 대체하고 그 한계를 인덱스 본문에 적어 뒀다. id가 전역 순차이므로 *저작* 순서와는 일치하지만 **accept 순서와는 어긋날 수 있다.**
→ **조용히 `accepted_at` 필드를 추가하지 않았다.** 필요한지는 실제로 여러 건을 accept해 봐야 안다. **미결로 남긴다.**

**★ 컨테이너 티켓을 Project의 어느 Status로 넣을지 정해진 게 없다.** 그래서 Project 필드 조작을 **구현하지 않았다.** 기본값을 몰래 넣지 않고 미결로 드러낸다.

**★ founding / sub 판정의 근거가 얇다.** epic은 founding ADR을, feature는 sub-ADR을 전제한다. 기계가 가진 단서는 `parent` 필드 하나뿐이라, 어긋나면 **거부하지 않고 경고만** 한다. 거부로 올릴지는 실제로 티켓을 만들어 보고 정한다.

## 5. 결손 4건 → 규약 개정 (2차)

위 §4에서 드러난 결손이 규약으로 확정됐고, skill이 그것을 강제하도록 고쳤다.

**① 파일명 규약이 정해졌다.** ADR은 `adr-0012-<slug>.md` — **id가 선두**이고(인용키로 바로 찾는다) **날짜 prefix가 없다**(id가 생성순과 단조 일치하므로 날짜는 중복이다). discussion·postmortem은 `YYMMDD_HHmm_<slug>.md`이며, **postmortem의 날짜는 장애 발생일**이다(작성일이 아니다 — 장애를 찾을 때 사람이 기억하는 건 터진 날짜다).
→ `doc-path.py`를 신설해 슬러그를 검증한다(소문자 kebab, 3~6 단어, 한글·대문자 거부).
→ **미결이 남았다**: discussion·postmortem에는 skill이 없으므로 그 파일명을 **기계가 강제할 지점이 없다.** 지금은 프롬프트 층위 규칙일 뿐이다. 린터가 생기면 거기서 잡는다.

**② 동결이 경로에도 걸린다는 것을 뒤늦게 알았다.** 본문만 얼리고 파일을 옮기면 그 문서를 가리키던 **인용이 전부 깨진다** — 얼린 의미가 없다. 동결은 *"본문 + 경로"* 다.
→ `freeze-check.py`에 **경로 변경 검출**을 넣었다. HEAD의 경로와 대조해, 옮겨진 동결 문서를 찾아 거부한다. 인자 없이 돌리면 전량을 훑는다.
→ 그 결과 **accept가 마지막 관문**이 됐다: 얼기 전에 파일명이 규약에 맞는지 검사하고, 어기면 거부한다. 나쁜 이름으로 얼면 되돌릴 방법이 없다(새 ADR로 supersede하는 수밖에).

**③ `accepted_at`을 추가했다 — 단, 권위 없는 필드로.** 결정 로그의 "시간순"을 세우려면 날짜가 필요했다. 그러나 **진실 원본은 git**(accept 커밋)이고, frontmatter의 값은 읽기 편하라고 둔 **편의 필드**다. 어긋나면 **git이 이긴다.**
→ 그래서 **사람이 손으로 적지 않는다.** `accept.py`가 채운다.
→ 그리고 **인덱스는 어긋남을 경고만 하고 실패시키지 않는다.** 권위 없는 필드를 도구가 강제하면 **그건 권위를 준 것이다.** 이 구분을 흐리면 나중에 git과 파일이 싸울 때 누가 이기는지 아무도 모르게 된다.

**④ ★ accept 전이가 유일하게 기계를 안 거치고 있었다.** 동결선을 넘는 문이 셋인데(accept · supersede · 본문 편집 거부) — supersede는 스크립트고, 본문 편집은 스크립트가 거부하는데, **accept만 사람이 `status:` 줄을 손으로 고치고 있었다.** 가장 중요한 문이 열려 있었던 셈이다.
→ `accept.py`를 신설했다. `supersede.py`와 같은 형태다 — **본문에 손댈 능력이 없는 스크립트.**
→ 이로써 **동결 게이트를 넘는 문이 전부 기계가 됐다.** 동결이 규율이 아니라 구조가 되는 것은 이 지점부터다.

## 6. 공동무효 테스트를 실제로 돌려봤다 (ADR 경계 분해)

첫 ADR을 쓰기 전에, 지금까지의 결정 전량을 놓고 입도 규칙(§4③)을 적용했다. **규칙 자체에서 두 가지가 걸렸다.**

**① ★ 테스트를 문자 그대로 읽으면 판정이 안 된다 — 대칭으로 읽어야 한다.**
규약은 *"X가 뒤집힐 때 Y도 반드시 함께 무효가 되는가?"* 라고 **한 방향으로** 적혀 있다. 그런데 그대로 적용하면 **가장 근본적인 결정을 뒤집을 때 아래 것이 전부 죽으므로**, 답이 전부 "예"가 되어 **모든 결정이 한 ADR로 뭉친다.** 명백히 틀린 결과다.

→ 올바른 읽기는 **상호 무효**다: X가 Y를 죽이고 **Y도 X를 죽일 때만** 한 ADR이다. 한쪽만 죽이면 그것은 **하위 축**이다.
→ 이 읽기는 규약이 sub-ADR을 정의한 방식(*"founding과 공동무효가 **아닌**, 독립적으로 뒤집힐 수 있는 하위 축"*)과 정확히 맞는다. **즉 규약은 이미 대칭을 전제하고 있었고, §4③의 문장만 비대칭으로 적혀 있다.** 문장을 고칠 문제다 — 규칙이 틀린 게 아니라 **서술이 판정 절차로 쓰기에 부정확**했다.
→ 대칭으로 바꾸자 경계가 즉시 갈렸다. 애매해서 임의로 그은 경계는 **없었다.**

**② 2단 계층이 의존 그래프를 눌러 편평하게 만든다.**
분해해 보면 축들 사이에 실제 의존이 있다 — 예를 들어 *ADR 저작 규약*은 논리적으로 *문서 3종*에 딸린 하위 축이다(3종에서 ADR을 빼면 저작 규약은 무효). 그러나 계층이 2단이므로 **둘 다 founding의 자식으로 나란히 놓인다.**

→ 그래서 **`parent:`는 의존 관계가 아니라 계층 위치를 표현할 뿐이다.** 이걸 의존 그래프로 오해하면 안 된다.
→ 지금은 이것이 비용이 아니다(계층이 얕아 읽기 쉽다). 축이 더 늘어 편평한 목록이 길어지면 그때 재검토할 일이다. **지금 3단으로 늘리지 않는다.**

**③ 임계선(§4②)이 결정 두 건을 걸러냈다.** *자동 close 미사용*과 *`accepted_at`의 비권위성*은 **되돌리는 데 한 시간이면 된다.** 규약은 그런 것을 ADR로 만들지 말라고 한다. → **별도 ADR을 세우지 않는다.** 규약(CLAUDE.md)에 적힌 것으로 충분하다.
→ 관찰: **임계선 테스트는 실제로 작동한다.** ADR 후보를 줄이는 방향으로.

**분해 결과**: founding 1건(두 개의 플레인 — 작업 추적과 결정 기록의 분리) + 독립 하위 축 9건. 첫 ADR은 founding 하나만 저작한다 — 한 세션에 10건을 쓰면 dogfood가 아니라 문서 공장이 된다.

## 7. 하네스 발견 — agent 정의는 세션 시작 시 로드된다

`docs-tickets` agent를 **만든 그 세션에서 호출할 수 없었다.** 에이전트 레지스트리가 세션 시작 시점에 읽히기 때문이다(`Agent type 'docs-tickets' not found`).

→ **agent를 저작한 세션과 그 agent로 일하는 세션은 반드시 분리된다.** 하네스를 만든 다음 이어서 쓰려면 세션을 새로 띄워야 한다.
→ 우회로(범용 agent에 정의 파일을 프롬프트로 주입)는 **관측 장비를 가짜로 세우는 것**이다 — 로딩 경로·도구 권한·컨텍스트가 진짜와 다르므로, 그렇게 얻은 "잘 되더라"는 아무것도 보증하지 않는다. 쓰지 않았다.

## 8. 실제로 문서와 티켓을 통과시켜 봤다 (dogfood 본편)

agent가 첫 ADR을 저작·accept하고, 그 ADR을 근거로 epic을 발행했다. **픽스처가 아니라 진짜를 통과시키자 규약의 모순 세 개가 한꺼번에 드러났다.**

**① ★ `ticket:` 필드는 애초에 채울 수 없었다 — 삭제했다.**
스키마는 문서 frontmatter의 `ticket:`으로 브리지를 놓는다고 약속했다. 그런데:

- 컨테이너 티켓은 **accepted ADR을 전제한다**(§5) → 티켓은 accept **이후에** 생긴다
- accept 이후 허용 편집은 **`status`·`superseded_by` 둘뿐**이다(§3)

→ **적을 수 있는 시점이 존재하지 않는다.** founding ADR의 `ticket:`은 영구히 빈칸이다. 스키마가 약속한 브리지의 한 방향이 **원리적으로 불가능**했다.

뿌리는 더 깊다. **`ticket:`은 살아 있는 필드다** — ADR 하나가 시간이 지나며 여러 티켓을 낳으므로 계속 갱신해야 한다. **동결 문서는 살아 있는 필드를 담을 수 없다.** `lifecycle`·`last_verified`를 지운 것과 **정확히 같은 논리**인데, 그때 이 필드는 함께 지우지 못했다.

→ **`ticket:`을 스키마에서 뺐다.** 브리지는 **이슈가 문서를 가리키는 단방향**이 된다. 역방향 조회는 **Project의 `ADR` 필드**가 담당한다(아래 ②).
→ **동결선에 구멍을 내지 않았다.** 허용 편집을 셋으로 늘리는 선택지가 있었지만, `accepted`가 문서 전체에 대해 참/거짓 이분이어야 agent가 신뢰할 수 있다.
→ 덧: 이 ADR이 스스로 적은 무효화 조건이 *"브리지가 실제로 놓이지 않는다면"* 이었다. **그 조건이 발행 즉시 참이었다.** 무효화 조건 필드가 자기 문서의 결함을 짚어냈다 — 이 필드를 채택하는 쪽으로 기운 근거다.

**② 역방향 조회를 어디에 둘 것인가 — 이슈의 스키마는 고정돼 있다.**
이슈에는 임의 필드를 붙일 수 없다(title·body·labels·milestone·type·sub-issues가 전부). 라벨은 **다중·평면**이라 "이 티켓의 근거 ADR"이라는 **단일 값 속성**을 담기엔 성격이 안 맞고, ADR마다 늘어난다. 마일스톤은 릴리스용이라 자리를 뺏는다.

→ **Project의 커스텀 필드 `ADR`**(텍스트)에 담는다. 단일 값 속성이라 성격이 맞고, 보드는 어차피 컨트롤 플레인의 뷰다.
→ 대가: **모든 티켓이 Project에 등록돼야 한다.** 그래서 초기 Status 미결을 지금 풀었다 — **`Backlog`**.

**③ 강제에는 사정거리가 있다 — Status는 강제할 수 없다.**
타입별로 쓰는 Status가 다르다(계획된 일은 `Backlog→Todo`, 터진 일은 `Triage→Diagnosed`). 그런데 **GitHub은 타입별 허용 상태나 전이 규칙을 강제할 수단을 주지 않는다.** 보드에서는 누구나 아무 카드나 아무 칸으로 끌어다 놓는다.

→ **인정한다.** 도구는 **초기값만** 넣고, 이후 전이는 사람의 것이다.
→ 발견: *"규율이 아니라 구조로 강제한다"* 는 원칙은 **우리가 매개하는 문**(스크립트·스키마)에서만 성립한다. 플랫폼이 열어둔 문(보드 UI)에서는 성립하지 않는다. **그 경계를 인정하는 것이, 강제할 수 없는 것을 강제하려 드는 것보다 정직하다.**

**④ ★ 게이트가 잘못된 사본을 보고 있었다.**
`adr-gate.py`는 **워킹 트리**의 파일을 읽어 `accepted`를 확인했다. 그런데 **워킹 트리에만 있는 결정은 아무도 볼 수 없는 결정**이다. 그 상태로 발행된 epic의 문서 링크는 **죽은 링크로 태어났다**(실제로 그렇게 됐고, 그래서 작업이 중단됐다).

→ **게이트가 `origin/main`의 사본을 읽도록 고쳤다.** 공표되지 않았으면 거부한다.
→ *"굳었다"* 는 **accept 했다**는 뜻만이 아니라 **공표됐다**는 뜻이다. 이 구분이 없으면 게이트는 자기 디스크만 보고 통과시킨다.
→ **커밋을 도구가 대신하지 않는다**(§6). 다만 **공표 전에는 그 결정으로 일을 시작하지 않는다.**

**⑤ 이슈 본문의 문서 링크는 두 개다.** `blob/HEAD`(주)와 발행 시점 커밋의 permalink(보조).
SHA만 걸면 **supersede된 결정이 `accepted`인 채로 영원히 보인다** — 티켓을 여는 사람이 알아야 할 것은 *"이 결정이 지금도 유효한가"* 이므로 주 링크는 HEAD다. permalink는 *"이 티켓이 어느 시점의 문서를 근거로 발행됐나"* 에 답한다. **서로 다른 질문이라 링크도 둘이다.**

**⑥ 실제로 뮤테이션을 쏘기 전에는 드러날 수 없던 버그 둘.**
- `gh.py`가 GraphQL 변수를 전부 `-F`로 넘겼다. `-F`는 값을 **형에 맞춰** 넘기는데, Project의 SingleSelect 옵션 id가 **숫자꼴 문자열**이라 Integer로 변환되어 `String!`이 거부했다. 파이썬 타입으로 갈라 `int`·`bool`만 `-F`로 보낸다.
- 이슈 본문의 **상대 경로 링크는 이슈 URL 기준으로 풀린다**(저장소 루트가 아니다) → 404. 절대 URL로 고쳤다.
- **관찰**: 픽스처 테스트는 이 둘을 잡을 수 없었다. **쓰기 경로는 실제로 써 봐야 검증된다.**

**실증된 쓰기 경로**: Issue Type 지정(`updateIssueIssueType`) · Project 등록 · `Status: Backlog` · `ADR` 필드 · 본문 링크 — 전부 동작. **sub-issue 연결(`addSubIssue`)과 계층 거부는 아직 미실증**이다(중단됨).

**⑦ agent 정의는 행동을 규정했다.** 거부를 만났을 때 우회를 시도하지 않았고, 커밋하지 않았으며, 막힌 사실을 보고했다. 다만 **skill 문서가 자기 도구에 대해 거짓말하고 있는 것**을 발견해 고쳤다(인덱스 정렬 설명이 코드와 어긋나 있었다). **`.claude/`의 문서에는 rot 방지 장치가 없다** — 동결형 문서와 달리 낡을 수 있고, 낡으면 다음 agent를 오도한다.

**⑧ ★ 동결이 *언제* 발효하는지가 규약에 없었다.**
①의 수정으로 `ticket:`이 스키마에서 사라지자, **이미 accept된 ADR-0001의 본문이 존재하지 않는 메커니즘을 결정으로 적고 있는 상태**가 됐다. 그런데 동결 규약은 accept 이후 본문 수정을 금한다. 그러면 발행 당일에 첫 ADR을 supersede해야 하는가?

여기서 규약이 침묵하고 있다는 것이 드러났다 — **동결은 `accept.py`를 돌린 순간 발효하는가, accept 커밋에서 발효하는가?**

→ **공표(push) 시점으로 정했다.** 근거는 이미 저장소 안에 있었다: `accepted_at`의 진실 원본은 **git**이고(§7), 게이트도 방금 *"워킹 트리는 공표가 아니다"* 로 고쳤다(④). **동결에만 다른 잣대를 쓰면 두 기준이 충돌한다.** 아무도 보지 못한 결정을 무를 수 없다고 우기는 것은 규율이 아니라 **형식**이다.
→ `freeze-check.py`도 **공표된 사본**을 읽도록 고쳤다(④와 같은 버그가 여기 남아 있었다).
→ **`unaccept.py`를 신설했다** — 공표 전에만 accept를 되돌린다. 공표됐으면 거부한다. 되돌리기도 손이 아니라 기계가 한다(accept·supersede와 같은 형태: **본문에 손댈 능력이 없는 스크립트**). 이로써 status를 사람이 손으로 고칠 이유가 완전히 사라졌다.
→ ADR-0001은 공표 전이므로 **되돌려 본문을 바로잡고 다시 accept했다.** 첫 ADR이 발행 당일 폐기되는 사태를 피했고, 규약에는 빈틈 하나가 메워졌다.

**⑨ ★ 입도 오류는 "관련 있는 것을 모으는 쪽"으로 끌린다 — 두 번 겪었다.**

첫 ADR을 얼리기 직전, 본문에 **독립적으로 뒤집힐 수 있는 결정이 섞여 있는지** 검사했다. 두 개가 나왔다.

- **구현 도구 이름**(이슈 트래커·문서 도구의 제품명) — 도구는 독립적으로 갈아치울 수 있다. 이름을 본문에 박으면 도구를 바꿀 때 **이 결정까지 함께 들춰내야 한다.** → 지웠다. 남긴 것은 각 플레인에 **요구되는 성질**이다. 성질은 결정이고, 제품은 결정이 아니다.
- **브리지의 방향**(*"이슈가 문서를 가리킨다"*) — 근거가 오로지 *"문서가 얼기 때문"* 이다. 즉 **동결과 공동무효**인데, 동결은 이 ADR의 결정이 아니라 별개 축이다. 이대로 얼렸다면, 나중에 동결이 뒤집힐 때 **두 플레인 분리까지 함께 폐기**해야 했다. → 덜어냈다.

그리고 그것을 담을 두 번째 ADR을 쓰면서 **같은 오류를 더 크게 저질렀다.** 문서 3종 · "동작"은 문서가 답하지 않는다 · 동결선 · 허용 편집 · 부분 폐기 불허 · 브리지 방향 — 여섯을 한 문서에 넣었다. 그런데 이들은 **독립적으로 뒤집힌다**(생존형 문서를 도로 들여도 부분 폐기 불허는 살아남고, 부분 폐기를 허용해도 동결 자체는 남는다). 초안을 **폐기했다.**

→ **발견**: 입도 오류의 기본 인력은 **묶는 쪽**이다. 그리고 그 인력의 정체는 *"공동무효"* 가 아니라 ***"주제가 비슷하다"*** 이다. 둘은 전혀 다른 기준인데, 쓰는 사람에게는 같은 느낌을 준다.
→ **부분 폐기를 금지했기 때문에**, 입도 판정은 사후 교정이 불가능하다 — **작성 시점의 의무**가 된다. 뭉쳐 놓고 나중에 쪼개는 길이 없다.
→ 다행히 **공표 전이라 되돌릴 수 있었다**(⑧). 동결 발효 시점을 공표로 정한 결정이 **첫날부터 값을 했다.** accept를 두 번 되돌렸다.

**⑩ "어느 사본을 보는가" — 세 번째 사례.**
`build-index.py`는 **워킹 트리**를 스캔한다. 지금은 그게 옳다(인덱스는 커밋 직전에 만드는 파생물이다). 그러나 규칙이 하나 붙는다 — **인덱스는 자기가 가리키는 문서와 같은 커밋에 들어가야 한다.** 문서를 붙들면 인덱스도 함께 붙들어야 한다. 아니면 공표된 인덱스가 없는 파일을 가리킨다(④의 죽은 링크와 같은 실패인데, 저장소 안이라 더 조용히 깨진다).

→ 세 번 다 같은 물음이었다: **게이트는 어느 사본을 보는가 · 동결은 어느 사본을 보는가 · 인덱스는 어느 사본을 담는가.** 워킹 트리와 공표된 사본의 구분이 **하네스 전체를 관통하는 축**이라는 것이 뒤늦게 드러났다.

## 9. 아직 답하지 못한 질문 (dogfood 이후)

- **공동무효 테스트가 실제로 판정 가능한가** — 애매해서 임의로 그은 경계가 생기는가
- **"무효화 조건" 필드**를 채울 수 있는가, 아니면 지어내게 되는가 → 채택/폐기 판정
- **`superseded_by` 다대다**(discussion 1건에서 ADR 여러 건이 파생)를 실제로 마주치는가 → 리스트 허용 vs 별도 필드
- **자족적으로 쓰기**(외부 문서를 인용하지 않기)가 실제로 비용이었는가
- **판단해야 했던 지점 vs 기계가 처리한 지점**의 실제 경계

## 10. 저작 규약 하나 — 경계 명시의 절제 (adr skill 개정)

`adr` 스킬에 규칙을 넣었다: *"X는 여기서 정하지 않는다 · 별도 결정이다"* 를 반사적으로 적지 않고, **모호한 침묵을 명시적 배제로 바꾸는 값이 있을 때만**(X가 인접·실재하는 결정 영역일 때) 둔다.

계기: ADR-0004에 이런 disclaimer가 넷까지 쌓였다 — 둘은 서로 **중복**(표현 형식·색인을 각각 두 번), 하나는 순수 **punt**(*"무엇이 지키는가는 별도 결정"*)였다. *"이 문서가 안 정하는 것"* 은 무한하므로 전부 적으면 **의식(ritual)**이 된다 — ADR-0003이 경계한 *"빈칸을 지어내 채운다"* 의 사촌이다.

0004에서 중복·punt를 걷어냈다(넷 → 둘: 인접·실재하는 **포맷**·**색인** 경계만 각각 한 번 남김). 규칙은 **동결 문서(ADR-0003)를 건드리지 않으려** 규약이 아니라 **판단 heuristic으로 스킬에** 두었다. 강제는 없다 — 린터가 잡을 것도 아니고, 사람·agent의 저작 판단이다.

## 11. 하네스를 새 동결 모델에 정합 (conformance)

ADR-0006을 다시 써서 동결을 좁혔다 — **본문(결정의 의미)** 만, **proposed 밖 전부**(accepted·rejected·superseded), **경로·포맷은 얼음 밖**. ADR-0004는 메타데이터 가변성을 역할로 갈랐다(출처=`references`는 굳고, 분류=`topic`·`subjects`는 확정 후에도 가변). 여기에 하네스를 맞췄다:

- `opsdoc.FROZEN` += **`rejected`** (본문이 어는 상태 = accepted·rejected·superseded).
- `freeze-check.py`: **경로-스캔(무인자) 모드·`moved()` 제거** — 경로는 얼지 않는다. 거부 메시지를 *"얼음: 본문·id·type·parent·references / 얼음 밖: topic·subjects·생명주기·경로·포맷"* 로 바꿨다.
- `accept.py`·`doc-path.py`·`supersede.py`·adr SKILL §2·§3·§4: *"rename 금지 · 경로도 얼어붙는다 · 허용 편집은 두 필드뿐"* 을 걷어내고 본문(의미) 스코프로.
- docs-tickets 에이전트: *"rename·이동 금지"* 항목 제거.

관찰: 이번엔 **정책(ADR)이 먼저 굳고 도구가 따라갔다** — 마찰 로그가 원래 막으려던 방향(*규약이 skill에 관성으로 끌려감*)의 반대다. 두 방향 다 정상이며, 어느 쪽이든 **둘이 어긋난 채로 두지 않는 것**이 요점이다.

★ **최상위 규약(CLAUDE.md)까지 정합됨** — 처음엔 `$OPS_WORKFLOW_ROOT/CLAUDE.md`가 steward 쓰기 경계 밖(hook 차단)이라 §3·§7을 못 고쳤다. **사람이 hook를 열어**(`guard-write.py`에 ops `CLAUDE.md` 허용 추가) §3(동결선 → 본문/의미, 경로·분류는 얼음 밖)·§7(*rename 금지·동결은 경로에도* 삭제, 역할 기반 가변성 추가)까지 맞췄다. 이제 **코퍼스(0002·0004·0006) · 하네스(스크립트·스킬·에이전트) · 최상위 규약(CLAUDE.md)** 셋이 모두 일치한다.

관찰: steward 쓰기 경계는 사람이 hook로 넓혔다 — 자유의 원천은 사람이라는 설계(§0·§5) 그대로다. 경계를 코드가 아니라 규율로 두었다면 이 조정이 조용히 새어 들어왔을 것이다.

## 12. 저작 규약 둘 — 나열되는 섹션의 항목 리스트 (adr skill 개정)

`adr` 스킬 §2에 규칙을 넣었다: **Alternatives·Consequences·무효화 조건은 항목 하나를 불릿 하나로 세우고, 그 항목의 "왜"는 불릿 아래 산문으로 이어 쓴다.** 권장이지 강제가 아니다.

계기: 사람이 `careerhub-front` ADR-0013을 가리키며 *"이 모양이 읽기 좋다"* 고 했다. 산문 덩어리로 이어 붙이면 **몇 개인지·어디서 갈리는지**가 훑어지지 않는다. 제목을 완결 문장으로 쓰라는 규약(ADR-0003)이 딛고 선 전제 — *"읽기는 훑고 고르는 두 단계"* — 가 섹션 안에서도 그대로 성립한다.

**★ 다섯 부분이 두 종류였다는 것이 이번에 드러났다.** 처음엔 사람이 말한 대로 Alternatives·Consequences 둘에만 걸려 했는데, 정작 사람이 가리킨 ADR-0013은 **무효화 조건도** 리스트였다. 다시 보니 갈리는 축은 섹션 이름이 아니라 **하나인가 여럿인가**다 — Context·Decision은 **한 흐름으로 읽는 산문**이고, 나머지 셋은 **독자가 훑고 고르는 목록**이다(버린 선택지들 · 받아들인 대가들 · 깨질 전제들). 규칙을 그 축으로 다시 적었다. ADR-0003은 다섯을 **각각의 역할**로 갈랐지, 이 **읽기 방식의 이분**을 적어두지 않았다.

**★ 위험은 리스트 자체가 아니라 "왜"의 증발이었다.** *"리스트로 써라"* 만 주면 버린 이유가 불릿 조각으로 잘린다 — ADR-0005가 표에 대해 이미 막아둔 실패다(*"결정의 '왜'는 표 셀에 쪼개지 않는다 · 표는 인과를 정렬하는 도구이지 생략하는 도구가 아니다"*). 같은 문장이 리스트에도 그대로 적용된다는 것이 이번에 드러났다: **ADR-0005의 그 규칙은 표에 대한 규칙이 아니라 "본문의 시각적 장치 일반"에 대한 규칙이었다.** 지금은 표에만 걸려 있다. 그래서 스킬 문구를 **항목은 리스트 / 근거는 산문**으로 갈라 적고, 그 명분을 0005에 명시적으로 걸어 두었다.

부수 규칙 둘을 함께 넣었다 — **항목이 하나면 리스트가 아니다**(불릿 한 개짜리 목록은 서식 노이즈), **이미 accept된 문서를 이 모양으로 고쳐 쓰지 않는다**(본문은 얼었다 · ADR-0006. 서식 통일은 동결을 깨는 명분이 못 된다).

**규약(CLAUDE.md)이 아니라 스킬에 두었다** — §10과 같은 이유다. 강제가 아니고 린터가 잡을 것도 아니며, *"여기는 리스트가 나은 자리인가"* 는 저작 판단이다. 그리고 강제로 만들면 **리스트를 채우려고 없는 항목을 세우게 된다** — ADR-0003의 무효화 조건 ①(*빈칸을 지어내 채운다*)이 정확히 경계한 실패다.

관찰: **이 개정은 ADR을 낳지 않았다.** *"되도록 ~하면 좋다"* 는 ADR-0003 §Decision이 요구하는 능동 문장(*"~한다"*)으로 적을 수 없고, 되돌리는 값이 템플릿 몇 줄이라 임계선(§4②) 아래다. **모든 저작 규약이 ADR이 되는 것은 아니다** — 이것이 §10에 이은 두 번째 사례이며, 스킬이 *"영수증이 안 붙는 판단 heuristic"* 의 서식장이라는 것이 굳어지고 있다.

남은 물음 둘:

- **ADR-0005의 "왜를 쪼개지 마라"가 표에만 걸려 있는 것이 맞는가.** 지금은 스킬이 그 결핍을 메우고 있다. 같은 누수가 다른 장치(인용문·중첩 리스트·강조)에서 또 나타나면, 그때는 0005의 전제가 좁았던 것이므로 supersede 거리다 — **한 번은 예외, 반복될 때만.**
- **"산문으로 읽는 둘 / 목록으로 훑는 셋"이 ADR-0003에 없는 것이 결핍인가.** 지금은 서식 heuristic으로 스킬에 있다. 그러나 이것이 서식이 아니라 **각 섹션이 무엇을 담는지(구조=계약)에 딸린 성질**이라면 0003의 몫이다 — 0003은 아직 `proposed`라 고칠 수 있다. 판정은 이 규칙이 실제로 저작을 바꾸는지 보고 내린다.

## 13. 코드가 있는데 열지 않았다 — 발산에는 묻는 지점이 없다

careerhub-front 리뉴얼 발산에서 *"기존 프론트는 디렉터리 관례가 문서로까지 정리돼 있었지만 지켜지지 않았고, 그러므로 문서화된 컨벤션은 강제가 아니다"* 라는 진단이 반복 인용됐다. **사람이 이의를 제기했고**(*"저는 그런 관례를 만든 적이 없습니다"*), 코드를 열어보니 거짓이었다 — 근거로 지목된 문서는 `/init` 이 생성한 관찰 기록이고, 코드보다 9개월 늦으며, 관례는 실제로 지켜지고 있었다. (반증 전문: careerhub-front discussion `260722_1510`.)

**반증 비용은 `git log` 한 번이었다.** 그런데 아무도 돌리지 않았다. §6이 `CODE_ROOT` 를 주입해 둔 이유가 정확히 이것인데(*"결정을 논하려면 코드를 읽어야 한다"*), 읽지 않고 단언했다. CLAUDE.md §2가 *"desired 는 코드가 답한다"* 고 정한 바로 그 지점에서 어긋났다.

★ **skill의 부재가 관측된 첫 사례다.** 지금까지 마찰은 전부 *skill이 무엇을 묻는가*에서 나왔다. 이번 것은 **아무 skill도 없는 구간**에서 나왔다 — discussion 발산에 생성 skill을 일부러 두지 않았고(§1 — 생성 의식이 빈 문서를 양산한다), 그래서 *"이 주장을 코드에서 확인했나"* 를 물을 지점 자체가 없었다. 그 판단은 옳았다고 아직 보지만, **묻지 않는 구간이 곧 관측되지 않는 구간**이라는 대가가 이번에 청구됐다.

★ **동결 게이트도 이것을 못 잡는다.** `freeze-check.py` 는 형식만 본다. accept 심판 넷(임계선 · 입도 · "왜"만 · 자족성)에도 *"본문의 사실 주장이 확인됐나"* 가 없다 — **넷 다 문서 안만 본다.** 자족성은 *"이 파일만으로 이해되나"* 를 묻지 *"이 파일이 참인가"* 를 묻지 않는다. 그래서 거짓 논거가 넷을 전부 통과했고, ADR-0012는 그것을 실은 채 accept·공표까지 갔다.

관찰: **사람이 걸렀다.** §6의 *"지식 루프는 반드시 사람을 통과한다"* 가 설계대로 작동한 실증이다 — 자기오염 차단이 추상적 원칙이 아니었다. 다만 걸린 지점이 **accept 이전이 아니라 이후**였다. 사람은 최후의 그물이지 첫 그물이어야 하는 것은 아니지만, 동결 뒤에 걸리면 값이 비싸다 — 이번엔 Decision이 멀쩡해 supersede를 면했을 뿐이고(부분 supersede 불허 · §3), Decision이 그 줄에 얹혀 있었다면 accepted ADR 하나를 통째로 죽여야 했다.

남은 물음: **이것을 구조로 만들 수 있나.** *"이 주장이 코드와 맞나"* 는 기계가 판정할 수 없어 exit 1 로 만들 수 없다 — §8이 선호하는 형태가 안 나온다. 남는 것은 **게이트 지점에 놓인 규율**뿐이다: docs-tickets 심판에 다섯째를 더하는 것(*"본문이 코드·이력에 대해 주장하는 사실을, 그 출처를 실제로 열어 확인했나"*). 규율은 §8이 최소화하라 한 것이지만 **판정 불가능한 축을 구조로 위장하는 것보다는 낫다.** 지금은 사례가 하나다 — §12의 원칙대로 **한 번은 예외, 반복될 때 넣는다.**

## 14. frontmatter 가 헤딩으로 변형돼도 경고가 없다

ADR-0015 의 frontmatter 가 깨진 채 커밋 직전까지 갔다. 마크다운 포매터가 `id: ADR-0015` 를 `## id: ADR-0015` 헤딩으로 바꾸고 종료 구분자 `---` 까지 먹었다.

재현해 보니 `build-index.py` 는 **경고를 하나도 내지 않는다.** 나머지 필드(`type`·`topic`·`subjects`·`status`·`parent`)는 전부 살아남고 `id` 하나만 사라지므로, ADR 이 **id 칸이 `—` 인 채로 인덱스에 정상 등재된다** — discussion 과 구분되지 않는 모습으로. 조용히 사라지는 것이 아니라 **조용히 잘못된 모습으로 실린다.**

★ **경고 목록이 "없으면 이상한 것"을 타입별로 묻지 않는다.** 현재 검사 셋(`subjects 비었다` · `accepted 인데 accepted_at 없다` · `superseded 인데 superseded_by 없다`)에 **`type: adr` 인데 `id` 가 없다** 가 빠져 있다. `id` 는 discussion·postmortem 에는 원래 없는 필드라 "비었음"이 정상인 경우가 있고, **그 정상 케이스에 가려 ADR 의 이상이 안 보인다.** 뒤의 둘이 이미 *"이 status 면 저 필드가 있어야 한다"* 는 조건부 검사인데, type 축에는 같은 검사가 없다.

이건 §13과 달리 **기계가 판정할 수 있다** — `type == "adr" and not id` 는 판단이 없다. 그러므로 규율이 아니라 스크립트의 몫이고, **고쳤다**: `build-index.py` 에 경고 하나를 더했다(*"adr 인데 id 가 없다 — frontmatter 가 깨졌을 수 있다"*). 파손된 ADR-0015 를 재현해 발화를 확인했고, **id 가 원래 없는 discussion 에는 침묵**하는 것도 함께 확인했다.

여전히 **경고이지 거부가 아니다.** 이 스크립트는 검증하지 않는다는 초판의 선(§1 — *인덱스가 커밋을 막으면 dogfood 가 막힌다*)을 넘지 않았다. 게이트가 필요하다면 그것은 아직 없는 린터의 몫이다.

관찰: **이 파손은 사람이 쓴 것이 아니라 도구가 만들었다.** frontmatter 는 YAML 이고 본문은 마크다운인데, 마크다운 포매터에게 그 경계는 보이지 않는다 — `id: ADR-0015` 는 마크다운으로 읽으면 그냥 텍스트 줄이다. **`---` 하나가 두 문법의 경계 전부를 지고 있고, 그것이 지워지면 아무 층도 이상을 못 느낀다.** §2의 "실행 검증" 표는 *agent가 무엇을 시도하면 거부되는가*만 담았지 **도구가 조용히 망가뜨리는 경우**를 담지 않았다. 거부 게이트는 의도적 위반을 막지, 사고를 막지 않는다.
