# TDD 집행 흐름 — ticket-engineer 하네스에 red·green 을 어떻게 세우나

## 0. 사람이 가져온 것

테스트 코드를 가진 모든 저장소(프론트엔드 · 백엔드 · obs-toolkit)에 TDD 를 적용한다.
하네스 개선의 개략(2026-09-30):

| 단계 | 무엇 | 제약 |
|---|---|---|
| **tdd-scenarios** | 테스트로 구현할 시나리오 목록 — 시그니처(API · 함수 · CLI) + 정상 · 경계 · 예외 케이스 | 티켓 AC 에서 도출하되, 필요한 시나리오는 AC 와 무관하게 추가 |
| **tdd-red** | 시나리오를 테스트 코드로 | 비즈니스 로직은 테스트 컴파일에 필요한 **최소 stub 외 변경 금지**. 작성된 테스트는 **모두 실패** |
| **tdd-green** | 테스트를 통과시키는 비즈니스 로직 | **테스트 코드 변경 금지**. 구현 불가면 보고 |
| **AC-verifier** | 티켓 AC 충족 여부 확인 | **subagent** 로 |

그리고 인프라 관리 코드에는 적용이 어려우므로, 하네스에 `.claude/ref-repos.txt` 처럼 **TDD 적용 저장소 목록**을 두고 `ticket-run.py` 가 대상 여부를 판별한다.
주 대상은 ticket-engineer, 필요하면 ops-workflow 도.

**추가 방향(같은 날, 첫 검토 뒤)** — 단계 제약(red 의 소스 수정 금지 · green 의 테스트 수정 금지)은 **규약으로만** 둔다. 구조 강제(hook · 상태 파일 · 전이 스크립트)는 하지 않는다 — 구현이 지나치게 복잡해진다. 남는 고민은 **대상 구분**이다: Terraform · Ansible · k8s manifest 와 백엔드 · 프론트엔드 · 플러그인 도구를 가르는 것을 **agent 의 순수 판단**에 맡길 수 있는가.

이 문서는 그 방향을 **현 하네스에 대입**해 — 각 단계가 어느 자리에 서고, 규약으로 무엇이 남는지 — 를 벌리고, 방향이 틀리는 조건을 찾는다.
정하지 않는다 — §9 의 답 뒤다.

## 1. 문제 다시 말하기 — 무엇이 불편해서

앞선 세 discussion 이 같은 병목을 세 번 짚었다.

- `260910_1817` §8 — 사람이 소유하려는 것은 **약속**이고 그것을 담은 인공물은 **테스트**인데, 둘이 연결되지 않는다. 수렴한 모양: *착수 시 약속↔테스트 표를 사람이 승인 → 구현 → 반증 subagent → 사람은 약속 테스트만 읽는다.*
- `260910_1900` — 그 절차는 "약속 인공물 = 테스트" 를 전제하며, 저장소 부류에 따라 전제가 서지 않는다. §7 의 질문 넷이 답 없이 열려 있다.
- `260923_2005` — obs-toolkit 에서 테스트를 세 티어로 재편하고 메타테스트로 지켰다(#106 · #107 완료). 구조로 못 거는 것 둘을 남겼다 — **"이 테스트가 정말 약속인가"** 와 **"약속이 빠졌나"**.

지금 하네스의 집행 흐름은 이렇다(`ticket-start/SKILL.md` · `ticket-report/SKILL.md`):

```
ticket-start   티켓 읽기 → AC · Requirements 추출 → 근거 읽기 → ticket-run.py 정렬 → 착수 요약
(작업)         규약 없음 — 코드와 테스트를 agent 가 임의 순서로
ticket-report  preflight.py(PR · 참조 · close 키워드 · 체크) → AC 대조표(agent 의 의미 판정) → 게시
```

테스트에 대해 이 흐름이 말하는 것은 **없다.**
비용은 셋이다.

| 비용 | 실물 |
|---|---|
| **테스트가 구현 뒤에 쓰인다** | 구현을 통과하도록 맞춰진 테스트는 실패해 본 적이 없다 — 동어반복인지 알 수 없다. `260923` §2-3 C 군집(재녹화가 테스트를 조용히 약화)이 그 결과 |
| **AC 판정이 자기 검수다** | `ticket-report` 2단계의 대조표는 구현한 agent 가 같은 컨텍스트에서 쓴다. 근거 칸은 코드 위치라 사람이 코드를 읽어야 한다(`260910_1817` §1 의 병목 그대로) |
| **소유의 시점이 없다** | 사람이 개입하는 자리는 착수 요약(계획)과 보고(결과)뿐 — *무엇을 검사할 것인가* 는 그 사이에서 agent 혼자 정한다 |

TDD 가 이 셋에 답하는 방식은 **순서**다.
red 는 "이 테스트는 실패할 수 있다" 를 실행으로 증명하고(동어반복 배제), 시나리오 표는 소유의 시점을 만들며, 테스트 이름이 대조표의 근거가 된다.
**TDD 의 값은 테스트의 양이 아니라 실패를 먼저 본 테스트만 남는다는 것이다** — agent 가 쓴 테스트 양은 해결률과 무관하다는 반증(`260910_1817` §2-3)이 순서에는 걸리지 않는다.

## 2. 실측 — 지금 하네스의 자리들

네 단계를 세울 자리와 강제 수단을 `$TICKET_ENGINEER_ROOT` 에서 읽었다.

| 지점 | 실물 | TDD 에 주는 것 |
|---|---|---|
| **착수 요약** | `ticket-start/SKILL.md` 6단계 — "경계 2절 + 스크립트 상태 + 작업 계획. 어긋날 소지가 보이면 진행 전에 묻는다" | 시나리오 표가 설 자연스러운 자리. 지금은 **게이트가 아니다** — 묻는 것은 agent 의 판단 |
| **exit 코드 규약** | `_lib/_common.py` `EXIT_PROCEED/REJECT/APPROVAL/HUMAN` = 0/1/2/3, `Reject` 예외, `run_cli` | red→green 전이 검사 · green 의 "구현 불가" 보고가 그대로 얹힌다 — 2(승인 대기) · 3(보고만)이 이미 있다 |
| **쓰기 가드** | `hooks/guard-write.py` — **경로만** 본다(`workspace/target/**` 허용 · `ref/**` · `.bare/**` 거부). Bash 는 `gh issue close` · `gh pr merge` · `gh pr create` · force push 네 패턴만 | 단계별 쓰기 제한(red 는 소스 금지 · green 은 테스트 금지)을 얹으려면 **① 지금 어느 단계인가(상태)** 와 **② 이 경로가 테스트인가(저장소별 패턴)** 둘 다 없다 |
| **Bash 우회** | 같은 hook 가 Write/Edit 은 경로로 막지만 `sed` · heredoc 은 안 본다 | ops-workflow 마찰 로그(`reindex-hook-misses-bash-writes` 3회)와 같은 구멍 — hook 만으로는 단계 제한이 **새지 않는다고 말할 수 없다** |
| **완료 preflight** | `ticket-report/scripts/preflight.py` ①~⑥ — PR · 참조 · close 키워드 · 체크 · target↔worktree | "red 커밋이 있다" · "테스트 실행 결과" 같은 항목이 들어갈 자리. AC 판정은 명시적으로 제외("의미 판정") |
| **코멘트 모듈** | `_lib/comments.py` — ticket-run · preflight 가 코멘트 전문을 다시 보인다 | 시나리오 표를 **티켓 코멘트**로 남기면 재개 · 보고 · verifier 가 같은 경로로 읽는다 |
| **참조 목록** | `ref-repos.txt` 는 **ops-workflow** 에 있다(design-partner 용). ticket-engineer 의 `refresh-refs.py` 는 목록 없이 "있는 것을 pull" | 사람이 말한 "ref-repos 처럼" 은 ops-workflow 쪽 패턴이다 — ticket-engineer 에는 저장소 목록 파일이 **없다**. 처음 두는 것이다 |

## 3. 네 단계를 자리에 놓기

### 3-1. tdd-scenarios — 소유의 시점

**자리**: 착수 요약(ticket-start ⑥) 직후, 코드 전.
**산출물**: 표 하나 — `시나리오 | 시그니처 | 종류(정상·경계·예외) | 출처(AC-n · 추가) | 테스트 이름(예정) | 티어(단위·통합·e2e) | 의존성 처리(실제 · 녹화 replay · fake · mock/stub)`.
마지막 두 열은 이 티켓의 검수를 위한 것이 아니라 **§8 의 테스트 정책 ADR 을 위한 증거**다 — 티켓마다 agent 가 무엇을 골랐고 왜 골랐는지가 코멘트로 남아야 "여러 시도" 가 기억이 아니라 기록이 된다.

여기서 갈리는 것 셋.

- **승인 게이트다 — 둘이다.** 첫 안에는 승인 언급이 없었고, `260910_1817` §8 답 4 는 "계획 승인 왕복 1회를 감수한다" 였다. 사람의 답(§9 답 1)은 왕복 **둘**이다: **시나리오 표 승인 → red 승인**. 표를 승인하면 *무엇을 검사할 것인가* 를 소유하고, red 를 승인하면 *그 검사가 실제로 무엇을 단언하는가* 를 소유한다 — "이 테스트가 정말 약속인가" 가 사후 읽기가 아니라 green 전에 답해진다. 그 뒤 green → refactor → verifier 는 멈춤 없이 흐르고, verifier 의 보고 뒤 다음 절차를 사람이 확인 · 승인한다. 게이트는 착수 게이트의 "보고하고 기다린다" 와 같은 문장이다 — **표를 내고 멈춘다 · red 커밋을 내고 멈춘다.** 스크립트가 아니라 규약이다(§0 추가 방향).
- **어디에 남기나.** 티켓 코멘트(`260910_1900` 의 흐름이 그랬다) · `tmp/` · PR 본문. 코멘트면 재개 시 `ticket-run.py` 가 다시 보이고, verifier 가 `comments.py` 로 읽고, 사람은 GitHub 에서 승인한다(코멘트 답글 또는 반응). **하네스가 이미 실어 나르는 경로**라 새 배관이 없다. `tmp/` 는 세션 밖에서 안 보이고, PR 본문은 red 전엔 PR 이 없다.
- **AC 밖 시나리오의 경계.** "필요한 시나리오는 AC 와 무관하게 추가" 는 옳다 — AC 는 사람이 쓴 것이고 경계 · 예외는 코드를 읽어야 나온다. 다만 CLAUDE.md §3(범위 밖의 축은 멈추고 묻는다)과 맞닿는다. 경계값 · 예외 처리 · 입력 검증은 **같은 약속의 가장자리**라 범위 안이고, 새 동작을 시나리오로 더하는 것은 범위 확장이다. 표의 출처 열이 "추가" 인 행은 그 판정을 사람이 승인 때 한다 — 게이트가 있으면 이 경계가 공짜로 생긴다.

### 3-2. tdd-red — 실패를 먼저 본다

**제약 둘**: 소스는 stub 만 · 테스트는 전부 실패.
둘 다 **규약**이다(§0 추가 방향) — 하네스가 막지 않고, agent 가 지키고, 지켰는지는 **읽어서** 안다.

| 제약 | 규약 문장 | 지켰는지 어떻게 보이나 |
|---|---|---|
| **테스트 전부 실패 + 기존 테스트는 통과** | 저장소의 테스트 명령을 돌려 신규(시나리오 표의 이름) 전부 fail · 나머지 pass 를 확인한 뒤 green 으로 간다. 통과해 버린 신규 테스트는 동어반복 후보 — 고치고 다시 red | 실행 결과를 시나리오 코멘트에 답글로 남긴다(테스트 이름 · fail/pass). verifier 가 읽는다 |
| **소스는 stub 만** | 시그니처 + `raise NotImplementedError` / `panic("TODO")` / `throw new Error("TODO")` 까지. 본문을 쓰지 않는다 | **red 를 커밋으로 닫는다**(`test(#N): red — 시나리오 k개`). 그 커밋의 소스 diff 가 곧 stub 목록이라 verifier 와 사람이 한눈에 읽는다. 커밋 경계는 강제가 아니라 **읽기 단위**다 — 비용이 커밋 메시지 한 줄이라 규약으로 충분하다 |

"전부 실패" 의 뜻을 하나 더 가른다 — **컴파일 실패도 실패인가.**
Beck 은 그렇다고 한다.
그러나 Go · TypeScript 는 컴파일이 안 되면 **패키지 전체**가 돌지 않아 "기존 테스트 통과" 를 검사할 수 없다.
사람이 stub 을 허용한 이유가 정확히 이것이다 — stub 은 컴파일을 살리기 위한 최소이지 구현이 아니다.
Python 은 import 오류가 파일 단위라 stub 없이도 red 가 성립한다.
**언어마다 "최소 stub" 의 하한이 다르다** — 규약 문장은 "컴파일이 살고, 신규 테스트만 실패하며, 나머지는 통과" 로 두고 그 밑은 저장소의 것이다.

### 3-3. tdd-green — 테스트를 건드리지 않고 통과시킨다

**제약**: 테스트 코드 변경 금지 · 구현 불가면 보고.

- **테스트 변경 금지는 규약이다.** 지켰는지는 **green 커밋의 테스트 경로 diff 가 0** 인가로 보인다 — red 와 같은 이유로 green 도 커밋으로 닫는다. 구조로 걸 수도 있었다(상태 파일 + hook)지만 §0 추가 방향으로 버렸다 — §7.
- **"구현 불가" 는 시나리오가 틀렸거나 AC 가 틀렸다는 뜻이다.** 둘 다 agent 가 닫을 수 없다 — CLAUDE.md §3 의 "멈추고 묻는다" 와 같은 모양이고, 테스트를 고치는 길은 **사람에게 보고하고 red 로 되돌아가는 것**뿐이어야 한다. 조용히 테스트를 고쳐 통과시키는 것이 TDD 를 무너뜨리는 정확한 경로다 — 규약 문장이 이것을 가장 또렷하게 말해야 한다.
- **green 을 속이는 길**은 하나 더 있다 — 테스트 입력에만 맞춘 하드코딩. red 가 막지 못하는 것이고, verifier 의 일이다(3-4).
- **refactor 는 green 바로 뒤의 별도 단계다**(§9 답 1·8). 첫 안은 red · green 둘이었고 첫 판은 "green 의 제약 안에서 이미 가능하다" 고 했으나, 사람이 단계로 세웠다 — Beck 의 세 번째. 제약은 green 과 같다: **테스트 불변 · 전부 pass 유지.** 다른 것은 목적이다 — green 은 통과가 목적이라 소스가 거칠어도 되고, refactor 는 그 거친 것을 정리한다. 커밋도 따로 닫는다(`refactor(#N): …`) — verifier 가 "정리가 동작을 바꾸지 않았나" 를 테스트 결과로 본다.
- **green · refactor 는 주 대화 밖 subagent 에서 돈다**(§9 답 4) — 모델은 opus. red 를 쓴 컨텍스트가 green 을 쓰지 않으므로 테스트의 의도를 모른 채 구현한다 — 그것이 "테스트가 정말 검사하나" 의 독립성이다. subagent 가 받는 것은 worktree · red 커밋 · 테스트 명령뿐이다 — 티켓 본문도 시나리오 표도 아니다(사람 지적: 의존성 처리 선택은 이미 테스트 코드에 있다 — 표를 읽히면 의도가 새어 격리의 값이 준다).

### 3-4. AC-verifier — 다른 컨텍스트가 읽는다

**자리**: refactor 뒤, ticket-report 의 대조표를 대신 쓴다. 그 보고를 사람이 읽고 다음 절차를 승인한다(§9 답 1).
**독립성**: subagent 는 새 컨텍스트에서 돈다 — 구현한 대화의 "이건 됐다" 를 상속하지 않는다. `260910_1817` §8-3 의 반증 subagent 가 이것이다. 모델은 green · refactor(opus)와 다른 Fable 이다(§9 답 4) — 같은 모델이 쓰고 같은 모델이 검사하면 같은 맹점을 공유한다.
**읽는 범위와 하는 일은 §10-2 에서 정해졌다**(§9 답 7): 읽기 + **직접 실행** + **반증 테스트** + 저장소에 도구가 있으면 **커버리지**로 부족한 시나리오 탐지. 아래 표는 그중 "읽기" 의 첫 안이다 — 전체는 §10-2 의 표.

무엇을 읽느냐가 값을 정한다.

| 읽는 것 | 잡는 것 |
|---|---|
| 티켓 AC ↔ 시나리오 표 | **약속이 빠졌나** — AC 항목에 시나리오가 없다(`260923` §6 이 구조로 못 건다고 한 둘 중 하나) |
| 시나리오 표 ↔ 실제 테스트 | 승인된 이름이 없거나, 이름은 있는데 단언이 성질이 아니다(약화) |
| red 커밋의 소스 diff | stub 이 stub 인가 |
| green 커밋의 소스 diff ↔ 테스트 입력 | 테스트 입력에만 맞춘 하드코딩 · 분기 |
| 테스트 실행 결과 | red 에서 fail · green 에서 pass 의 기록 |

코드 전체를 읽게 하면 `260910_1817` §1 의 병목이 subagent 로 옮겨갈 뿐이다.
**verifier 는 표 · 테스트 · 두 커밋의 diff 를 읽지, 저장소를 읽지 않는다** — 읽는 양이 약속의 수에 비례해야 사람의 검수와 같은 원칙에 선다.
결과는 대조표의 **근거 칸 = 테스트 이름**(§8-3)으로 나가고, 사람은 그 이름의 테스트만 읽는다.

TDD 가 서면 verifier 의 일이 **줄어든다** — "실패할 수 있는 테스트인가" 는 red 가 이미 증명했다.
남는 것은 위 표의 첫 줄과 넷째 줄이다.

## 4. 대상 판별 — 어느 저장소에서, 어느 변경에서 켜나

첫 안은 하네스 목록 파일(`ref-repos.txt` 꼴)이었고, 추가 방향은 **agent 의 순수 판단으로 가능한가** 를 묻는다.

구조 강제를 버리면(§0 추가 방향) 판별의 조건이 가벼워진다.
강제하려면 저장소별 **테스트 경로 패턴 · 실행 명령**이 하네스에 있어야 했고, 그것은 이름 목록이 아니라 설정이라 저장소가 바뀌면 조용히 낡는 문제가 있었다(`260910_1900` 이 옵션 E 에 적은 반대편이 커지는 경우).
규약만 남으면 agent 는 저장소를 읽고 평소처럼 테스트를 돌린다(`go test` · `pytest` 는 이미 허용 목록에 있다) — 하네스가 알아야 하는 것은 **"이 티켓에 TDD 를 적용하나"** 하나로 준다.

### 판별은 두 질문이다

`260910_1900` §3 이 이미 갈랐다.

1. **이 저장소에서 약속은 테스트에 담기나** — 저장소의 성질. Terraform · Ansible · k8s manifest 는 아니오(약속이 렌더 · 플랜 · 실행 상태에 있다). 백엔드 · 프론트엔드 · 플러그인 도구는 예.
2. **이번 변경의 약속을 테스트로 쓸 수 있나** — 변경의 성질. 같은 백엔드 저장소라도 설정 1줄 · 의존성 갱신 · 삭제는 시나리오 표가 비거나 한 줄이다.

저장소 목록은 1 만 답한다.
agent 판단은 **둘 다** 답할 수 있다 — 그것이 판단에 맡길 때의 값이다.

### agent 판단이 가능한가 — 실측으로 답한다

`260910_1900` §1 의 부류 표 자체가 **agent 가 16개 저장소를 읽고 판정한 결과**다.
①(테스트 스위트 + CI) · ③(선언형 인프라) · ⑤(e2e)의 구분은 파일 트리에서 자명했다 — `*_test.go` + `go-test.yaml`, `kustomization.yaml` + ArgoCD, `playwright.config`.
판단이 흔들린 곳은 둘이다.

| 흔들리는 곳 | 실물 | 왜 |
|---|---|---|
| **② 테스트가 거의 없는 코드 저장소** | careerhub-front 0 · incident-agent 0 · skillscanner 2 · review-crawler 3 | "테스트 파일이 있다" 로 판정하면 skillscanner 는 대상이고 front 는 아니다 — 둘 다 TDD 를 돌릴 인프라가 없다는 점에서 같은데 |
| **인프라 저장소의 테스트 파일** | jyoliar-k8s 의 `smoke_test.py` 1개 · onpremise-k8s 의 `smoke-test.yaml` playbook | "테스트가 있다 → TDD" 로 오판할 수 있다. 저 파일들은 배포 뒤 실측이지 변경 전에 쓸 약속이 아니다 |

즉 판단은 가능하되 **기준이 "테스트 파일 존재" 여서는 안 된다.**
기준은 한 문장으로 규약에 적힌다 — *변경 전에 · 저장소 안에서 · 이번 변경의 약속을 · 실패하는 테스트로 쓸 수 있는가.* 하나라도 아니면 비대상이다: 렌더 · 플랜 · 배포 뒤에야 검증되면(③) 아니고, 테스트 러너 · CI 가 없으면(②) 아니고, 약속이 한 줄이면(변경의 성질) 아니다.

### 옵션

- **J 순수 판단 — 판정을 착수 요약에 적는다.** 규약: 착수 요약(ticket-start ⑥)에 **"TDD: 대상 / 비대상 — 근거 한 줄"** 이 고정 자리로 있다. 적지 않으면 착수 요약이 아니다 — ADR-0016 이 target 에 요구한 "지정 XOR 명시적 부재" 의 규약판. 사람이 그 줄을 보고 뒤집을 수 있다 — 판단이 **보이고 고쳐진다.** 반대편: 매 티켓 판단 = 규율. 틀려도 하네스는 모른다. 그러나 틀린 판정은 시나리오 표에서 드러난다 — ③ 에서 표를 쓰려 하면 "kustomize build 가 성공한다" 같은 실측 명령이 시나리오로 들어오고, ② 에서는 첫 행이 "테스트 러너 설치" 가 된다. 표를 사람이 보는 한(§9-1) 오판은 조용하지 않다.
- **L 하네스 목록 — 이름만.** `$TICKET_ENGINEER_ROOT/.claude/tdd-repos.txt`. 설정이 아니라 이름이므로 낡는 속도가 느리다(저장소 추가 · 성질 변화 때만). 반대편: 변경의 성질(질문 2)을 답하지 못한다 — 설정값 1줄에도 켜진다. 저장소 지식이 하네스에 산다(E 의 반대편은 약해졌지만 남는다). ② 부류를 넣는 순간 "테스트 인프라부터" 가 되는데 목록은 그 사정을 모른다.
- **D 저장소 선언.** 각 저장소 `CLAUDE.md` 한 절 — "이 저장소의 약속은 X 에 담긴다". 저장소 지식이 저장소에 산다. 반대편: 저장소 8곳 커밋. 강제가 없으므로 기계가 읽을 필요도 없다 — 그러면 이것은 J 의 **판단 근거를 저장소가 미리 적어 둔 것**이지 별개 옵션이 아니다.
- **J + L 하이브리드** — 목록은 "확실히 아니오"(③)만 적고 나머지는 판단. 반대편: 원천이 둘이다. ③ 는 파일 트리에서 자명하므로 목록이 더해 주는 것이 없다. 버린다.

### 판정

**J 가 선다 — 조건 둘 아래에서.**
(a) 판정 기준이 "테스트 파일 존재" 가 아니라 위 한 문장으로 규약에 적힌다.
(b) 판정이 착수 요약의 고정 자리에 근거와 함께 적혀 사람이 본다.
둘 다 규약이고 강제는 없다 — 추가 방향과 같은 무게다.
D 는 J 를 돕는 선택 사항으로 남는다: 판단이 흔들리는 저장소(② 부류)에 사람이 한 절을 적어 두면 agent 가 그것을 읽는다.

J 가 **틀리는 조건**: 착수 요약을 사람이 읽지 않게 될 때. 그때 판정은 아무도 안 보는 자기 선언이 되고, L 이 낫다.

## 5. 규약으로 둔다 — 무엇이 남고 무엇이 읽히나

§0 추가 방향으로 상태 파일 · 전이 스크립트 · hook 단계 제한은 없다(버린 이유는 §7).
그러면 네 단계는 **스킬 문장**이고, 지켜졌는지는 **읽어서** 안다.
규약이 실효를 가지려면 "읽을 것" 이 정해져 있어야 한다 — 읽을 것이 없는 규약은 자기 선언이다.

| 단계 | 컨텍스트 | 규약이 남기는 것 | 누가 읽나 | 멈추나 |
|---|---|---|---|---|
| scenarios | 주 대화 | 착수 요약의 **TDD 판정 한 줄**(§4) + **시나리오 표** — 티켓 코멘트 | 사람 · verifier | **멈춤 — 사람 승인** |
| red | 주 대화 | **red 커밋** 1개(`test(#N): red — …`) + 실행 결과 답글(신규 전부 fail · 기존 pass) | 사람(테스트 본문) · verifier(소스 diff = stub 인가) | **멈춤 — 사람 승인** |
| green | subagent(opus) | **green 커밋**(들) + 실행 결과 답글(전부 pass) | verifier(테스트 경로 diff = 0 · 하드코딩) | 흐름 |
| refactor | subagent(opus) | **refactor 커밋**(들) + 실행 결과 답글(전부 pass 유지) | verifier(테스트 경로 diff = 0 · 동작 불변) | 흐름 |
| verify | subagent(Fable) | 대조표 — 근거 칸 = 테스트 이름 — 티켓 코멘트 | 사람 | **멈춤 — 사람이 다음 절차 승인** |

커밋 경계는 강제가 아니라 **읽기 단위**다.
그것 없이는 verifier 가 "어디까지가 red 인가" 를 diff 에서 복원해야 하고, 그러면 verifier 도 코드를 읽게 된다 — §3-4 가 피하려는 것.
squash 머지로 히스토리는 사라지지만 PR 안에는 남고, 보고 시점엔 있다.

하네스 델타는 그래서 작다 — `ticket-start/SKILL.md` 에 판정 자리 + 시나리오 절차, red · green 문장(같은 파일의 연장 또는 스킬 하나), `ticket-report/SKILL.md` 의 근거 칸 규약, agent 정의 하나.
스크립트 변경은 **없어도 된다.** `preflight.py` 에 "TDD 대상이면 red 커밋이 있다" 를 넣을 수는 있지만(커밋 제목 grep 한 줄), 그것도 강제의 시작이므로 §9 에 둔다.

**규약만으로 무엇을 잃나** — 정직하게 적는다.
red 에서 소스를 써 버리거나 green 에서 테스트를 고치는 것을 **그 자리에서** 막는 것이 없다. 발견은 verifier · 사람의 diff 읽기에서고, 그것은 사후다.
마찰 로그의 교훈(*"검사 실체가 없으면 그 보호는 agent 의 자율 준수로 격하된다"* — `260806-freeze-check-script-absent`)이 여기 그대로 적용된다.
받아들이는 이유는 복잡도다 — 상태 파일 · 저장소별 경로 패턴 · Bash 우회 대응까지 얹으면 하네스가 TDD 보다 커진다.
**먼저 규약으로 돌리고, 마찰 로그가 "규약이 새더라" 를 보이면 그때 그 지점만 구조로 올린다** — 이 저장소의 방식(하네스가 먼저, 영수증이 나중)과 같다.

## 6. 사람의 반대편에 서서

**다섯 단계가 다섯 스킬이면 "지금 어느 스킬인가" 가 매번 판단이다.**
`260910_1900` §5 가 인프라 전용 절차를 버린 이유와 같다.
사람의 답(§9 답 4)이 경계를 정했다 — **scenarios · red 는 주 대화의 같은 컨텍스트, green · refactor · verifier 는 각각 subagent.**
그러면 스킬은 하나(주 대화의 절차 — scenarios → red → 승인 뒤 subagent 호출 순서)이고, agent 정의가 셋이다.
"지금 어디" 는 마지막 커밋 제목(red / green / refactor)과 코멘트가 말한다 — 구조 강제가 없으므로 상태는 따로 살지 않고 산출물에서 읽힌다(§5 표). 재개 시 `ticket-run.py` 가 진행 커밋과 코멘트를 이미 보여 준다.
컨텍스트를 가르는 값은 독립성이다 — red 를 쓴 컨텍스트가 green 을 쓰면 테스트의 의도를 알고 구현하므로 "테스트가 정말 검사하나" 가 약해진다. 비용은 subagent 가 티켓 · 표 · worktree 를 다시 읽는 것이고, 사람이 감수했다.

**작은 변경에 네 단계는 과하다 — 그러나 Bug 는 작은 변경이 아니다.**
`260910_1900` §3 이 이미 갈랐다 — *이 저장소에서 약속은 무엇에 담기나*(저장소의 성질)와 *이번 변경에 표가 필요한가*(변경의 성질)는 다른 질문이다.
저장소 목록은 첫째만 답한다.
설정값 1줄 · 의존성 갱신 · 삭제 · 문서에 시나리오 표 → red → green 을 돌리면 게이트 회피가 시작된다(ADR-0017 의 무효화 조건 *"무의존 선언이 반사적 통과 의례가 된다면"* 과 같은 붕괴).
첫 판은 여기에 "Bug 긴급 복구" 를 넣고 티켓 타입(Bug 는 생략)을 판정자 후보로 두었다 — **틀렸다**(사람 지적, 2026-09-30).
코드 저장소에서 **버그는 곧 시나리오다**: 재현 테스트가 red 이고 수정이 green 이다 — TDD 의 가장 전형적인 경우이지 예외가 아니다.
Bug 가 생략되는 것은 저장소가 ③(IaC · GitOps)일 때뿐이고, 그것은 변경의 성질이 아니라 저장소의 성질(질문 1)이 답한 것이다.
생략의 판정은 agent 가 착수 요약에서 하고, 사람이 읽고 승인 또는 방향을 제시한다(§9 답 5).

**"테스트 코드를 갖고 있는 모든 프로젝트" 는 ② 부류를 포함한다.**
`260910_1900` §1 실측: careerhub-front 0 · incident-agent 0 · skillscanner 2 · review-crawler 3.
여기서 TDD 를 켜면 첫 티켓이 "테스트 인프라부터" 가 된다 — 그 discussion §5 가 *"게이트에 얹지 않는다, 별개 투자 판단이다"* 로 버린 것이다.
목록(또는 선언)에 넣기 전에 테스트 러너 · CI 가 서는 Task 가 먼저다. §9-6.

**인프라 제외는 `260910_1900` §7 을 닫는 것이 아니다.**
③ 부류를 당분간 밖에 두는 것은 맞다 — 그러나 그 discussion §4 는 "GitOps 는 테스트를 못 쓴다 가 반쯤 틀리다" 고 했고, 인프라 약속의 인공물이 렌더 단언인지 알림 규칙인지는 여전히 열려 있다.
이 문서는 ① ⑤(그리고 ② 의 인프라가 선 뒤)에 한정하고, ③ 은 그 문서에 남긴다.

**red 가 증명하는 것은 "실패할 수 있다" 까지다.**
"이 테스트가 약속인가" 는 여전히 사람이 시나리오 표에서 판단한다.
승인 게이트 없이 red · green 만 넣으면 순서는 서지만 소유는 생기지 않는다 — `260910_1817` 이 찾은 병목은 순서가 아니라 소유였다.
**시나리오 승인이 핵심이고 red · green 은 그 승인이 구현에서 지켜졌음을 구조로 보이는 장치다.** 둘의 무게가 뒤집히면 안 된다.

## 7. 버린 것

- **집행 흐름을 정책 ADR 로.** 스킬 문장 · agent 정의 · 판정 자리 — 전부 되돌리는 데 한 시간대다(CLAUDE.md §4②). ADR 이 아니다. 첫 판은 여기서 멈춰 "TDD 는 ADR 없음" 이라 했는데, 그것은 대상을 하나만 본 것이었다 — **테스트 정책**(티어 · 범위 · 의존성 처리)은 별개의 대상이고 ADR 감이다. §8 이 둘을 가른다. 인접 후보(*"검수 = 승인된 약속 목록과 그것을 검사하는 테스트를 읽는 것"* — `260910_1817` §8-6)는 여전히 이 문서 밖에 있고, 이 흐름은 그 후보의 **집행 형태**다.
- **테스트 정책 ADR 을 지금 쓰는 것.** ADR 감이지만 방향이 없다 — Alternatives 를 못 채우는 초안은 발산이 덜 된 것이다. 시도로 답을 모은 뒤다(§8). 사람 판정, 2026-09-30.
- **단계 제약의 구조 강제 — 상태 파일 · 전이 스크립트 · hook 단계 제한.** 첫 검토는 이것을 세웠다(red→green 전이 검사 · green 커밋의 테스트 diff = 0 검사 · hook 조기 경고). 버렸다 — 사람의 추가 방향. 필요한 것이 상태 파일 위치 · 저장소별 테스트 경로 패턴 · 테스트 명령 · Bash 우회 대응까지 이어져 하네스가 TDD 자체보다 커진다. 되살리는 조건은 §5 마지막 — 마찰 로그가 규약이 새는 지점을 보일 때, 그 지점만.
- **하네스에 테스트 러너 내장.** 저장소의 명령을 그대로 부른다 — 하네스가 pytest · go · playwright 를 알면 저장소 지식이 스며든다(§4).
- **"테스트 파일 존재" 를 판정 기준으로.** ② 부류와 인프라 저장소의 smoke 테스트를 오판한다(§4).
- **하네스 목록 + 저장소 선언 하이브리드.** 원천이 둘이면 한쪽만 고쳐진다(§4).
- **네 단계 전부 subagent.** 컨텍스트 격리가 값인 곳은 verifier(그리고 아마 red↔green)뿐이다. scenarios 는 티켓 · 근거 · 코드를 읽은 주 대화가 써야 한다.
- **mutation testing 지금.** `260923` §8 답 5 그대로 — 열어 둔다. red 가 동어반복을 걸러내므로 필요가 줄어드는지 먼저 본다.

## 8. 임계선 — 대상이 둘이다

이 문서에 결정 대상이 둘 섞여 있다. 첫 판은 첫 줄만 보고 "ADR 없음" 이라 했고, 사람이 둘째 줄을 짚었다(2026-09-30).

| 대상 | 무엇 | 되돌리기 | 영향 범위 | 판정 |
|---|---|---|---|---|
| **집행 흐름** | 네 단계 · 판정 자리 · verifier — ticket-engineer 하네스의 절차 | 한 시간대 — 스킬 문장 · agent 정의 | 하네스 하나 | **티켓** |
| **테스트 정책** | 어느 테스트를(단위 · 통합 · e2e) **언제** · **어느 범위**로 쓰나. **의존성**은 실제 연결인가 Mock · Stub · Fake · 녹화인가 — 프론트엔드→백엔드 API · 백엔드→DB · obs-toolkit→모니터링 백엔드 | **어렵다** — 정책 위에 저장소마다 스위트가 쌓이고, 뒤집으면 저장소 수만큼 다시 쓴다 | 테스트를 가진 모든 저장소 | **ADR 감 — 그러나 지금은 아니다** |

**왜 둘째가 ADR 감인가.**
`260923` §10 이 obs-toolkit 의 세 티어를 "한 시간대" 로 판정한 것은 **한 저장소의 배치**였기 때문이다.
같은 것을 **모든 개발에 범용으로** 요구하는 순간 성질이 바뀐다 — 각 저장소가 그 위에 스위트를 쌓고 나면, 예컨대 "백엔드 테스트는 DB 를 Mock 한다" 에서 "실제 DB(컨테이너)로 돈다" 로 방향을 바꾸는 비용은 저장소 수에 비례하고, 쌓인 테스트가 곧 매몰이다.
CLAUDE.md §4② 의 곱(되돌리기 어려움 × 영향 범위)이 둘 다 크다.
그리고 이것은 하네스가 아니라 **개발의 규약**이다 — ticket-engineer 는 그 정책을 *따르는* 쪽이지 정하는 쪽이 아니다.

**왜 지금 아닌가.**
방향이 없다.
Decision 에 쓸 문장이 없고, Alternatives 를 못 채우는 초안은 발산이 덜 된 것이다 — 초안을 접고 discussion 으로 돌아간다(design-partner 의 규칙).
답은 시도에서 나온다.
그때까지 **각 티켓의 시나리오 표가 그 자리에서 정한다**(§3-1 의 티어 · 의존성 열) — 티켓마다 다른 답이 나올 것이고, 그 다름이 ADR 의 Context 다.

**그 ADR 이 답해야 할 것** — 지금 보이는 만큼만 적는다. 시도가 늘면 질문이 바뀔 것이다.

- **티어의 축이 무엇인가.** obs-toolkit 은 *"실패하면 사람이 무엇을 하나"* (contracts · format · infra)로 갈랐고, 통례는 *범위 · 의존성* (단위 · 통합 · e2e)으로 가른다. 두 축은 직교한다 — contracts 테스트가 단위일 수도 통합일 수도 있다. 범용 정책은 어느 축으로 세우나, 둘 다인가.
- **의존성 경계마다의 기본값.** 실제 연결 / **녹화 replay**(obs-toolkit 의 선례 — Mock 과 실제 사이의 셋째 길: 나간 요청 == 녹화 요청 검사가 "낡은 응답으로 통과" 를 막는다) / Fake(손으로 만든 최소 구현) / Mock · Stub. 저장소 부류마다 다른가 — 프론트→API 는 녹화가 자연스럽고, 백엔드→DB 는 컨테이너 실제 연결이 싸졌고, 도구→모니터링 백엔드는 obs-toolkit 이 이미 답했다.
- **언제 e2e 인가.** careerhub-web 의 *"e2e 명세를 재작성 전에 쓴다"* (#9)가 선례 — 프론트엔드에서 약속은 e2e 에 담겼다. 그것이 프론트의 기본값인가, #9 의 사정(재작성)이었나.
- **사람이 읽는 것은 어느 티어인가.** `260910_1817` 의 "약속 테스트만 읽는다" 가 어느 축의 어느 값에 대응하나.
- **지속성.** 저장소에 남는 것만 약속 인공물로 인정하나(`260910_1900` §1-2 · §7-2) — 1회 실측은 밖인가.

**시도가 증거를 남기게 하는 장치**는 §3-1 에 넣었다 — 시나리오 표의 티어 · 의존성 처리 열.
비용은 열 둘이고, 없으면 "여러 시도" 가 기억으로만 남는다.
ADR 을 쓸 때 읽을 것은 그 코멘트들이다.

**집행 흐름(첫 줄)은 그 ADR 을 기다리지 않는다.**
`260923` §10 이 리프 셋을 ADR 없이 발행할 수 있다고 한 것과 같은 구조 — 흐름은 정책의 집행 형태이지 전제가 아니다.
산출물은 **ticket-engineer 하네스 델타**이고, steward 가 사람과 고친다(`ops-workflow-steward` 관할).
ops-workflow 쪽 델타는 §9 답에 따라 둘 중 하나가 생길 수 있다 — 티켓 필드(생략 표식)를 발행 도구에 넣는 것, `design-partner` 의 쪼갬 기준에 "한 Task 의 시나리오 수" 를 더하는 것.

쪼갬의 뼈대(답 뒤에 발행). 구조 강제가 없으므로 델타는 문서 셋 + agent 정의 하나다 — 스크립트는 건드리지 않는다:

| | 무엇 | 선행 |
|---|---|---|
| **T1 절차 규약** | `ticket-start/SKILL.md` — 착수 요약의 TDD 판정 자리(§4 의 한 문장 기준) · 시나리오 표 형식(티어 · 의존성 열 포함) · 코멘트 게시 · **승인 대기 둘**(표 · red) · red 문장(stub 하한 · 실행 결과 답글 · 커밋 경계) · subagent 호출 순서 · `ticket-report/SKILL.md` — 근거 칸 = 테스트 이름 · `CLAUDE.md` §2 한 줄 | 없음 |
| **T2 agent 정의 셋** | `.claude/agents/tdd-green.md` · `tdd-refactor.md`(opus — 테스트 불변 · "구현 불가 → 보고") · `ac-verifier.md`(Fable — §10-2 표: 읽기 · 직접 실행 · 반증 테스트 · 커버리지 탐지 · 출력 = 대조표 + 발견 코멘트) | T1 |
| **T0 ② 부류 테스트 인프라** | 저장소별 Task — 러너 · CI. 그 저장소가 TDD 대상으로 판정되기 위한 선행 | 없음 (저장소마다) |

T1 은 하루 규모다.
한 티켓의 첫 TDD 집행은 obs-toolkit 이 맞다 — contracts 티어 · 메타테스트 · 규약 파일이 이미 있어 저장소 쪽 준비가 0 이다(#108 — `260923` §7 의 T3 "누락 채우기" — 가 그 후보).
T1 전에 #108 을 **수동 절차**로 돌려 마찰을 먼저 보는 것도 된다 — 규약 문장은 마찰에서 나오는 편이 정확하다.

## 9. 사람에게 묻는다 — 코드에 없는 것

1. **시나리오 표를 사람이 승인하나.** 왕복 1회(`260910_1817` 답 4 는 "감수"). 승인이면 agent 는 표를 코멘트로 올리고 **멈춰서 기다린다**(규약 — 착수 게이트의 "보고하고 기다린다" 와 같은 문장). 아니면 표는 게시만 하고 red 로 간다 — 소유의 시점은 보고 때로 미뤄지고, §4 의 J(판정을 표에서 본다)도 약해진다.
2. **대상 판정을 J(agent 판단 + 착수 요약 고정 자리)로 하는 데 동의하나.** 판정 기준 한 문장(§4 — *변경 전에 · 저장소 안에서 · 이번 변경의 약속을 · 실패하는 테스트로 쓸 수 있는가*)이 충분한가. 부족하면 어느 저장소가 걸릴지 말해 달라 — ② 부류가 아니라면 아마 없다.
3. **judgment 가 틀렸을 때의 되돌림** — 사람이 착수 요약에서 "TDD 아님/맞음" 한마디로 뒤집는 것으로 충분한가, 아니면 저장소 `CLAUDE.md` 에 선언(D)을 미리 적어 두고 싶은 저장소가 있나.
4. **red 와 green 을 같은 컨텍스트에서 하나.** 갈라야 하면 스킬 분리 또는 subagent — 비용은 컨텍스트 재구성(티켓 · 표 · 코드 다시 읽기).
5. **생략은 누가 판정하나.** J 면 agent 가 변경의 성질까지 판정한다(Bug 1줄 → 비대상). 그것으로 충분한가, 아니면 티켓 타입(Bug 는 항상 생략) 같은 고정 규칙을 원하나.
6. **② 부류(careerhub-front · incident-agent · skillscanner · review-crawler)** — 테스트 인프라 Task(T0)를 먼저 내나, 당분간 밖인가.
7. **verifier 가 읽는 범위** — §3-4 표(표 · 테스트 · 두 커밋 diff)로 한정하는 데 동의하나. 저장소 전체를 읽게 하면 병목이 옮겨갈 뿐이라는 판단이다.
8. **refactor 단계** — 넣나. green 의 제약 안에서 이미 가능하므로 기본은 "없음" 이다.
9. **`preflight.py` 에 "TDD 대상이면 red 커밋이 있다" 한 줄** — 넣나. 구조 강제의 최소 단위(커밋 제목 grep)라 §0 추가 방향에 닿는다. 기본은 "안 넣는다".
10. **첫 집행을 obs-toolkit #108 로** — 동의하나. T1 전이면 수동 절차로 돌려 마찰을 먼저 본다.

### 답 — 2026-09-30

1. **승인은 둘** — 시나리오 표 승인 → red 승인. 이후 green → refactor → verifier 는 멈춤 없이. verifier 보고 뒤 다음 절차는 사람이 확인 · 승인. **refactor 를 green 바로 뒤에 단계로 넣는다.**
2. J — 동의.
3. 판정이 틀리면 사람이 착수 요약을 읽고 진행 방향을 제시한다.
4. scenarios · red 는 같은 세션의 같은 컨텍스트. green · refactor · verifier 는 별도 subagent — green · refactor 는 opus, verifier 는 Fable.
5. 생략도 agent 판정 — 착수 요약을 사람이 읽고 승인 또는 방향 제시. **단, Bug 는 생략 후보가 아니다** — IaC · GitOps 가 아닌 한 버그가 곧 시나리오이고, 재현 테스트가 red 다(§6 정정).
6. 테스트 골격(러너 · 설정 · CI 잡)이 없는 저장소는 **TDD 비대상**. careerhub-front · incident-agent 는 사장됐거나 prototype 이다 — ② 부류의 "표를 요구하면 첫 테스트를 세우라가 된다" 는 문제는 실재하지 않는다(§10-1).
7. verifier 는 **(c) 읽기 + 직접 실행 + 반증 테스트**. 추가: 저장소에 **커버리지 도구**가 있으면 적극 활용해 **부족한 시나리오**가 있는지도 검토한다(§10-2).
8. 답 1 — refactor 단계 있음.
9. preflight 한 줄 — 안 넣는다.
10. 집행 대상은 사람이 정한다.

1·4·5·8·9 는 §3 · §5 · §6 · §8 본문에 반영했다. 6·7 이 남았다.

## 10. 남았던 둘 — 논의와 판정

### 10-1. "테스트 인프라" 가 무엇을 말했나 — 골격과 환경을 가른다

첫 판이 "테스트 인프라" 라 부른 것은 **테스트를 돌릴 골격**이다 — 러너 · 프레임워크 설정(jest/vitest · pytest) · `npm test`/`make test` 스크립트 · CI 잡.
실측(`260910_1900` §1): careerhub-front 는 테스트 0 · CI 는 `create-tag` 뿐, incident-agent 는 0.
red 는 "실패하는 테스트를 **실행**한다" 이므로 러너가 없으면 red 가 성립하지 않는다.

사람이 "dev 환경?" 이라 되물은 것은 아마 다른 층 — 테스트가 붙는 **의존성 환경**(DB · 백엔드 API · 모니터링 백엔드를 실제로 연결하나) — 으로 들렸기 때문이다.
둘은 다르다.

| | 테스트 골격 (첫 판이 말한 것) | 테스트 의존성 환경 (사람이 물은 것?) |
|---|---|---|
| 무엇 | 러너 · 설정 · 스크립트 · CI 잡 | 통합 테스트가 붙는 DB · API · 백엔드 — 실제(dev 환경 · 컨테이너)인가 fake · mock · 녹화인가 |
| 없으면 | **red 자체가 성립 안 함** | 단위 테스트는 되고 통합 · e2e 만 막힘 |
| 누가 답하나 | 저장소 하나의 첫 Task — 한 시간대 | §8 **테스트 정책 ADR** 의 질문 — 지금 쓰지 않기로 했다. 그때까지 시나리오 표의 의존성 열이 티켓마다 답한다 |

골격 없는 저장소에서의 선택지:

- **(a) 첫 TDD 티켓의 red 가 골격 설치를 포함한다** — 시나리오 표 첫 행이 "러너가 돈다". 반대편: 러너 · 컴포넌트 테스트 라이브러리의 선택은 저장소의 결정인데 티켓 하나에 묻어가면 보이지 않는다.
- **(b) 별도 Task 를 먼저 낸다** — "테스트 골격 세우기". 저장소 결정이 티켓 제목으로 보인다. TDD 대상 판정은 그 뒤.
- **(c) 비대상으로 둔다** — J 판정이 "러너 없음" 을 근거로 적고, 사람이 결정한다. 답 3 · 답 10 으로 이미 덮인다.

**판정(사람, 2026-09-30): (c) — 골격이 없으면 비대상.**
그리고 실측의 정정 — careerhub-front 와 incident-agent 는 **사장된 저장소이거나 prototype** 이다. `260910_1900` §1 이 ② 부류로 분류하며 걱정한 "표를 요구하면 첫 테스트를 세우라가 된다" 는 저 둘에는 해당하지 않는다 — 집행 대상이 될 일이 없다.
② 에 남는 것은 skillscanner(2) · review-crawler(3) 뿐이고, 러너는 있으므로 J 판정은 "대상" 쪽이다 — 시나리오 표가 작을 뿐.
J 의 판정 기준 문장에서 "저장소 안에서(러너 · CI 가 있나)" 가 이 답의 자리다.

### 10-2. verifier 가 무엇을 읽고 무엇을 하나

첫 안(§3-4 표): 표 · 테스트 · red/green/refactor 커밋 diff · 실행 결과 답글. 저장소 전체는 읽지 않는다.
축: **무엇을 잡나** · **읽는 양** · **무엇을 믿나** · **쓰기를 하나**.

| 옵션 | 하는 것 | 잡는 것 | 믿는 것 | 반대편 |
|---|---|---|---|---|
| **(a) 읽기만** — 첫 안 | 표 · 테스트 · 세 커밋 diff · 답글 | AC↔표 누락 · 표↔테스트 이름 · 단언 약화 · stub 범위 · 테스트 경로 diff · green diff 안의 하드코딩 | 구현 agent 의 **실행 결과 답글** | 답글이 틀리거나 환경이 다르면 모른다 |
| **(b) 읽기 + 직접 실행** | (a) + 테스트를 스스로 돌린다 | (a) + 답글 불일치 · 환경 차이 | 자기 실행 | 비용은 명령 한 줄 — 반대편이 거의 없다 |
| **(c) (b) + 반증 테스트** | 하드코딩이 의심되면 입력을 바꾼 테스트를 하나 써서 돌려 본다(커밋하지 않는다) | (b) + **테스트 입력에만 맞춘 구현** — red 가 못 잡는 유일한 것 | 자기 실행 | verifier 가 쓰기를 한다 · 저장소 테스트 규약을 알아야 한다 · 반증이 실패하면 어디로 가나(아래) |
| (d) 저장소 전체 읽기 | 소스 전체 | (c) 와 같음 | — | 병목이 subagent 로 옮겨갈 뿐 — 버린다 |

`260910_1817` §8-3 이 "반증 subagent" 라 부른 것은 (c) 다.
첫 판의 권고는 **(c)** — 다만 반증 테스트가 실패했을 때(하드코딩 발견)의 경로는 답 1 과 맞춘다: verifier 는 **보고**하고, 그 반증 테스트를 시나리오에 더해 red 로 되돌리는 것은 사람이 승인한다. verifier 가 스스로 red 를 다시 열지 않는다.

verifier 의 출력은 둘이다 — **대조표**(AC | 충족 | 근거 = 테스트 이름 · PR 링크)와 **발견**(약화 · 하드코딩 의심 · 표에 없는 테스트). 둘 다 티켓 코멘트로, 사람이 읽고 승인한다.

**판정(사람, 2026-09-30): (c).** 그리고 하나 더 — **저장소에 커버리지 도구가 있으면 적극 활용해 부족한 시나리오를 찾는다.**

커버리지의 자리를 정확히 둔다.
`260923` §4 O4 는 coverage 를 게이트로 먼저 넣는 것을 버렸다 — *agent 가 쉽게 채운다*.
여기서는 게이트가 아니라 **verifier 의 탐지 신호**다: 숫자가 아니라 **이번 변경이 건드린 소스에서 어느 분기가 어느 테스트에도 안 도는가**의 목록이고, 그것이 "약속이 빠졌나"(`260923` §6 이 구조로 못 건다고 한 둘째)에 대한 답의 재료다.
`260923` §2-3 A 군집(한 번도 실행되지 않는 CLI 분기)이 정확히 이 방법으로 잡혔다.
verifier 가 그 목록을 **발견** 칸에 "시나리오 후보" 로 적고, 시나리오에 더할지는 사람이 판단한다 — 커버리지 100% 가 목표가 아니다.
도구가 없는 저장소에서는 생략한다 — verifier 가 도구를 설치하지 않는다(그것은 저장소의 결정이다).

verifier 가 하는 것을 한 자리에 모으면:

| 입력 | 검사 | 출력 칸 |
|---|---|---|
| 티켓 AC ↔ 시나리오 표 | 약속 누락 | 발견 |
| 시나리오 표 ↔ 테스트 코드 | 이름 일치 · 단언이 성질인가(약화) | 대조표 근거 · 발견 |
| red 커밋 소스 diff | stub 범위 | 발견 |
| green · refactor 커밋 | 테스트 경로 diff = 0 · 하드코딩 의심 | 발견 |
| **직접 실행** | 전부 pass · 답글과 일치 | 대조표 |
| **반증 테스트**(하드코딩 의심 시) | 입력을 바꿔도 통과하나 | 발견 — 실패하면 red 되돌림 제안, 사람 승인 |
| **커버리지**(도구 있을 때) | 변경 소스의 안 도는 분기 | 발견 — 시나리오 후보 |

남은 사소한 것: 반증 테스트를 worktree 안(미커밋)에 쓰나 `tmp/` 에 쓰나. 러너가 찾으려면 worktree 안이어야 하고, 보고 뒤 지운다 — 가 첫 판의 기본값이나 정한 것은 아니다.

## 11. PR 을 언제 여나

사람이 덧붙인 것(2026-09-30): 단계마다 커밋이면 **PR 을 미리 열어 두고 커밋을 올려야 진행이 PR 에서 보인다.** 그러면 PR 본문을 언제 쓰나.

제약 — `ticket-pr.py` 는 새 커밋 없이는 PR 을 열지 않는다(exit 1). 그러니 가장 이른 시점은 red 커밋 직후다. `--draft` 는 없다. `gh pr edit` · `gh pr ready` 는 hook 가 막지 않는다.

| | 여는 시점 | 반대편 |
|---|---|---|
| **A. red 직후 · Draft** | red 커밋 → Draft PR. green · refactor 가 쌓인다. verifier + 사람 승인 뒤 `gh pr ready` | `--draft` 추가. red 커밋의 CI 는 빨강 — 의도된 것 |
| B. red 직후 · 일반 PR | 같음 | 미완성 시점에 리뷰 요청이 간다 — Draft 가 정확히 이 구분이다 |
| C. green 뒤 | red 는 브랜치에만 | red 승인 자리가 PR 밖이 된다 |
| D. 끝에(현행) | — | 진행이 안 보인다 |

**판정: A. 본문은 링크로.**
red 커밋의 CI 빨강은 부작용이 아니라 **증거**다 — "신규 테스트가 실제로 실패했다" 를 답글이 아니라 CI 실행 기록이 말한다. verifier 가 그 런을 읽으면 §10-2 의 "답글을 믿는다" 가 하나 더 준다. 보고 시점엔 마지막 커밋의 런이 초록이라 preflight ④ 는 그대로 통과한다.
본문 — 열 때: 시나리오 코멘트 링크 + 단계 체크리스트. 단계마다 체크 갱신. verifier 뒤: verifier 코멘트 링크. 대조표를 PR 본문에 복사하지 않는다(사본은 낡는다).
red 승인은 PR diff(테스트 본문)에서, 시나리오 승인은 티켓 코멘트에서 — *무엇을* 검사하나는 티켓의 것, *어떻게* 검사하나는 코드의 것.
