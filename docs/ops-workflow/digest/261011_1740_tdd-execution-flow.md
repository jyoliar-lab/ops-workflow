# TDD 집행 흐름 — ticket-engineer가 티켓 하나를 테스트부터 끝까지 집행하는 모양 (2026-10-11 시점)

## 개요

ticket-engineer는 ops-workflow의 티켓을 받아 대상 코드 저장소에서 일하고 보고하는 agent 하네스다.
이 설계는 그 agent가 코드를 만지기 전에 밟는 순서다 — 시나리오 표를 사람이 승인하고, 실패하는 테스트를 먼저 쓰고, 다른 컨텍스트가 그 테스트를 보강하고, 또 다른 컨텍스트가 통과시키고, 또 다른 컨텍스트가 검수한다.
사람은 두 자리에서만 개입한다 — 시나리오 표를 승인할 때와 검수 보고를 읽고 다음을 지시할 때.
단계 제약은 전부 규약이다.
막는 것은 없고, 지켰는지는 커밋 diff와 티켓 코멘트를 읽어서 안다.

## 어휘

- **시나리오 표** — 무엇을 검사할 것인가. 시그니처 + Given / When / Then 행 + AC 커버리지. 티켓 코멘트 하나.
- **red** — 시나리오를 테스트로 옮기고 실패를 본 상태. 소스는 stub까지만.
- **green** — 테스트를 건드리지 않고 통과시킨 상태. **refactor**는 그 뒤 테스트 불변으로 소스를 정리한 상태.
- **verify** — 구현과 무관한 컨텍스트가 AC ↔ 표 ↔ 구현을 대조한 보고.
- **주 세션** — 티켓을 받은 대화. **subagent** — 주 세션이 부르는 격리 컨텍스트. 셋이 있다: `tdd-red-reviewer`(red 검토·보강, opus) · `tdd-green`(green + refactor, opus) · `ac-verifier`(verify, Fable).
- **변별력** — 테스트가 Then을 만족하지 않는 결과를 거르는 힘. 기준 파일은 `tdd-loop/strength.md`.

이 글은 사례 하나를 끝까지 따라간다.
**obs-toolkit 티켓 #120(Task)** — service graph 출력에서 idle 호출과 미확인 callee를 표기한다.
AC는 셋이다.
AC-1 edges가 비어도 idle이 있으면 "데이터 없음"이 아니라 알려진 호출 idle개가 창 안에서 0건이라고 말한다.
AC-2 callee가 None인 엣지는 그 자리에 "미확인"을 쓴다.
AC-3 server p95가 None이면 숫자 대신 "서버 —"를 쓴다.
target 저장소는 `jyoliar-lab/obs-toolkit` 하나, worktree는 `workspace/target/obs-toolkit/ticket-120/`.

## 1. 착수 — 이 티켓에 TDD를 적용하나

사람이 "#120"을 지정하면 주 세션이 `ticket-start`로 티켓·근거 문서를 읽고 worktree를 정렬한 뒤 착수 요약을 쓴다.
착수 요약에는 고정 자리 하나가 있다 — `TDD: 대상 / 비대상 — 근거 한 줄`.
적지 않으면 착수 요약이 아니다.

판정 기준은 한 문장이다 — 변경 전에 · 저장소 안에서 · 이번 변경의 약속을 · 실패하는 테스트로 쓸 수 있는가.
하나라도 아니면 비대상이다.
렌더 · 플랜 · 배포 뒤에야 검증되는 변경(Terraform · Ansible · k8s manifest)은 아니다.
테스트 골격(러너 · 설정 · CI 잡)이 없는 저장소는 아니다.
이번 변경에 약속이 없으면(설정값 한 줄 · 의존성 갱신 · 삭제 · 문서) 아니다.
Bug 티켓은 생략 사유가 아니다 — 코드 저장소에서 버그는 곧 시나리오이고, 재현 테스트가 red다.
"테스트 파일이 있다"는 기준이 아니다.

#120은 대상이다 — obs-toolkit은 pytest · CI가 있고, 변경은 `service_graph_lines`의 출력 약속 셋이다.
착수 요약에 `TDD: 대상 — 출력 약속 3건, contracts 티어에 실패 테스트로 쓸 수 있음`이 적힌다.
사람이 착수 요약을 읽고 판정을 뒤집을 수 있다.
target이 여럿이면 판정 · 표 · 이후 흐름은 target마다다.

## 2. 시나리오 표 — 사람이 "무엇을 검사하나"를 소유한다

주 세션이 코드 전에 쓴다.
먼저 시그니처를 고정한다 — 테스트가 부를 것의 이름 · 파라미터 · 반환 · 오류를 기존 코드의 관례대로.
#120에서는 기존 함수 `service_graph_lines(graph: ServiceGraph, window: Window) -> list[str]`은 그대로이고, 타입 `ServiceGraph`에 `idle: int` 필드가 더해진다.
타입은 맨 위 `#### 타입 · 상수` 블록에, 함수 선언은 그 시나리오 블록 머리에 fence 한 줄로 — 한 선언은 한 곳에만.
층은 변환 하나라 층 지도는 없다.

그 다음 행을 뽑는다.
한 행이 결과 하나이고 테스트 하나가 된다.
종류는 넷이다 — 정상 · 경계 · 예외 · 가드.
가드는 이미 되는 동작의 유지이고, red에서 통과가 기대되는 유일한 종류다.
AC 항목마다 최소 한 행, AC 밖의 경계 · 예외도 출처 `추가`로 더한다.
새 동작은 더하지 않는다.

| # | 종류 | Given | When | Then | 출처 | 테스트 이름 | 티어 | 의존성 |
|---|---|---|---|---|---|---|---|---|
| 1 | 정상 | edges 없음 · idle 3 | `service_graph_lines(g, W)` | "데이터 없음"이 없고 · 알려진 호출 3개가 0건이라는 줄 하나 | AC-1 | `test_service_graph_lines_say_idle_not_no_data_when_rows_have_zero_calls` | contracts | fake(`_graph`) |
| 2 | 정상 | 엣지 하나 · callee None · server None | 같음 | 머리줄에 "미확인" · 엔드포인트 줄에 "서버 —" | AC-2 · AC-3 | `test_service_graph_lines_mark_unknown_callee_and_missing_server_p95` | contracts | fake |
| 3 | 가드 | 엣지 둘 · 전부 값 있음 | 같음 | 기존 렌더 그대로 | 기존: `test_service_graph_lines_render_edges` | — | contracts | fake |

티어 · 의존성 두 열은 이 티켓의 검수용이 아니다.
티켓마다 agent가 무엇을 골랐는지가 코멘트로 남아, 나중에 테스트 정책을 정할 때 읽을 기록이 된다.
AC 커버리지 표가 끝에 붙는다 — AC-1 → 1, AC-2 → 2, AC-3 → 2.
모든 AC가 한 행 이상이어야 한다.

주 세션이 이 표를 티켓 #120에 코멘트 하나로 게시하고 코멘트 ID를 기록한 뒤 **멈춘다**.
사람이 시그니처 · 행 · 커버리지를 한 번에 읽고 "승인"을 말한다.
수정 요청은 새 코멘트가 아니라 기록한 ID로 지정 수정한다.
승인의 흔적은 남지 않는다 — 다음 산출물이 흔적이다.

## 3. red — 주 세션이 실패를 먼저 본다

승인된 표가 입력이다.
순서는 stub 일괄 → 시나리오 하나씩 → 전체 실행.

stub은 표의 타입 블록과 선언 fence를 그대로 옮긴 것이다 — `ServiceGraph.idle: int` 필드 추가.
함수는 기존 것이라 stub이 없다.
stub의 하한은 "컴파일이 살고 · 신규 테스트만 실패하고 · 나머지는 통과"이고, 본문은 쓰지 않는다 — `if`도 `return`도 없이 마지막 줄은 raise다.

행 1을 쓴다.
테스트 이름은 표 그대로, Given / When / Then을 주석 한 줄씩으로 구분해 보이게, docstring은 Then을 현재형으로.
쓸 때 `strength.md`의 "쓸 때" 절을 따른다 — 단언은 Then의 성질마다 한 줄, `and`로 잇지 않고, Given은 표대로, 대역은 손으로 만든 최소 입력, 그리고 알려진 약함의 패턴을 피한다.
행 1만 돌린다 — `pytest -k test_service_graph_lines_say_idle`.
실패의 종류를 본다.
단언 실패(`expected … got "데이터 없음"`)다 — 기존 코드가 시나리오와 다르게 동작하는 의도된 red.
행 2도 같은 길이다.
행 3은 가드라 쓰지 않는다 — 기존 테스트가 덮는다.

전체를 돌린다 — 신규 2 fail · 기존 545 pass.
가드 아닌 신규가 통과했으면 동어반복 후보라 단언을 구체화하고, 그래도 통과하면 시나리오가 틀린 것이다.
`ImportError` · collect 실패는 red가 아니다 — stub을 보강한다.

커밋 하나 — `test(#120): red — 시나리오 2개 (가드 1개)`.
이 커밋의 소스 diff가 곧 stub 목록이다.
여기서 push도 PR도 코멘트도 아직 없다.
red의 끝은 다음 절이다.

## 4. red 검토 — 다른 컨텍스트가 테스트를 보강한다

주 세션이 `tdd-red-reviewer`를 부른다.
넘기는 것은 넷이다 — 시나리오 코멘트 URL · red 커밋 sha · worktree 경로 · 테스트 명령.
티켓 AC는 넘기지 않고, 주 세션이 red를 쓰며 가졌던 의도 설명도 넘기지 않는다.
표가 명세다.

검토자는 표와 red 커밋의 diff만 읽는다.
먼저 대조한다 — 표의 테스트 이름이 전부 있나 · 각 테스트의 given / when / then이 표의 세 칸과 맞나 · 위 층 테스트가 아래 층의 경우를 다시 열거하나 · red 커밋의 소스 변경이 stub 범위뿐인가 · 가드 아닌 테스트가 통과하지 않았나.
그 다음 테스트마다 변별력을 판정한다 — `strength.md`의 "판정할 때" 절.
**Then이 약속한 성질 하나를 깬 결과를 머리로 떠올리고, 단언이 그 결과를 여전히 통과시키면 약하다.**
깬 결과를 Given으로 만들 수조차 없으면 Given이 약하다.
깬 결과가 떠오르지 않으면 Then이 성질을 말하지 않은 것이다.

#120의 행 1 — 주 세션의 초안은 `assert any("3" in line and "0" in line for line in lines)`였다.
Then은 "알려진 호출 3개가 0건"이다.
성질을 깬 결과를 떠올린다 — idle 줄이 없고 `p95 30ms · 0 errors` 한 줄만 있는 출력.
원래 단언은 그것을 통과시킨다.
약하다 — 알려진 패턴 "우연히 맞는 짧은 토큰"이다.
행 2 — 초안은 `assert any("미확인" in line …)`과 `assert not any("30" in line …)`였다.
"서버 —"가 없고 그 자리가 빈칸인 결과를 떠올리면 부정 단언은 통과한다.
약하다 — 패턴 "부정 단언만"이다.

검토자가 고친다.
행 1은 "0건"이 든 줄을 골라 그 줄이 하나이고 거기 "3개"가 있다고 단언한다.
행 2는 머리줄을 골라 "미확인"을, 엔드포인트 줄을 골라 "서버 —"를 긍정으로 단언한다.
고치는 범위는 테스트 본문과 stub이다 — 표의 행 · 테스트 이름 · 소스 본문은 건드리지 않는다.
더하기만 한다 — Then 밖의 단언이나 픽스처 값을 그대로 비교한 줄이 있어도 버리지 않는다.
보강 뒤 전체를 한 번 돌린다 — 신규 2 fail · 가드 pass · 기존 545 pass여야 한다.
보강한 단언이 stub에서 통과하면 그것이 동어반복이다.

커밋 하나 — `test(#120): red 보강 — 행 1 토큰 단언 · 행 2 긍정 단언`.
고칠 것이 없었으면 커밋하지 않는다.
검토자는 push하지 않는다.
돌려주는 것은 고정 블록 하나다 — 결과(ok / blocked) · 보강 커밋 sha 또는 없음 · 실행 결과 · 멈춤 사유.

**검토자가 멈추는 경우**는 표의 문제일 때다 — 선언과 행이 어긋난다 · Given을 손으로 만들 수 없다 · 단언을 구체화해도 통과한다(가드 아닌데) · stub을 채워도 red가 서지 않는다.
#120에서 AC-3의 "서버 —"가 선언의 오류 주석에 없었다면 검토자는 그것을 blocked로 돌려주고, 주 세션은 표를 새 코멘트(`v2 — … · 앞 코멘트를 대체`)로 다시 내고 사람의 재승인을 기다린다.
표를 고치는 것은 검토자의 일이 아니다.

## 5. red의 끝 — 주 세션이 닫고 흐른다

검토자가 ok로 돌아오면 주 세션이 테스트 명령을 한 번 더 돌린다 — subagent의 보고를 그대로 믿지 않는다.
그 다음 Draft PR을 연다 — `ticket-pr.py 120 --draft`.
본문은 링크와 체크리스트뿐이다.

```markdown
TDD — 시나리오: <시나리오 코멘트 URL>

- [x] red
- [ ] green
- [ ] refactor
- [ ] verify
```

red 커밋들의 CI는 빨강이다 — 의도된 것이고 "신규 테스트가 실제로 실패했다"의 증거다.
머지 게이트는 마지막 커밋의 런을 본다.

티켓에 red 완료 코멘트 하나를 쓴다 — 수와 예외만, 한 화면.
검토 뒤의 최종 수다.

```markdown
### red — jyoliar-lab/obs-toolkit

커밋 `a1b2c3d` · `d4e5f6a` · PR <URL> (Draft)
실행: `python -m pytest` → 신규 2: fail 2 · pass 0(가드) · 기존 545 pass
stub: obs/graph.py — ServiceGraph.idle 필드 1개

예외: 없음
```

보강 여부는 코멘트에 따로 말하지 않는다 — 커밋이 흔적이다.
사람 승인은 없다.
주 세션은 바로 다음 절로 간다.

## 6. green + refactor — 테스트만 보고 통과시킨다

주 세션은 구현하지 않는다.
`tdd-green`을 부른다 — 넘기는 것은 티켓 번호와 타입 · target · worktree · red 커밋 sha들(보강 커밋 포함) · 테스트 명령.
티켓 본문도 표도 시나리오 코멘트 URL도 넘기지 않는다.
테스트가 명세의 전부다.

`tdd-green`은 시작 상태를 확인한다 — 신규 fail · 나머지 pass.
collect가 안 되면 stub 누락분만 채운다.
신규가 이미 통과하면 받은 red가 red가 아니라 멈추고 보고한다.
그 다음 실패 테스트를 정상 → 경계 → 예외 순으로 하나씩 통과시킨다.
#120의 행 1 — `edges`가 비고 `idle > 0`이면 "알려진 호출 3개가 창 안에서 0건" 줄을 만든다.
그 테스트 하나를 통과시키는 가장 단순한 코드, 전체 실행으로 회귀 확인, 다음.
행 2 — callee None에 "미확인", server None에 "서버 —".
한 시나리오를 다섯 번 시도해도 못 통과시키면 멈춘다 — 테스트 의도 오해 · stub과 테스트 불일치 · 모킹 누락 중 하나이고, subagent가 닫을 결정이 아니다.
테스트는 고치지 않는다.
전부 통과하면 커밋 · push — `feat(#120): green — idle · 미확인 · 서버 — 표기`.

refactor는 이 브랜치가 바꾼 파일에서 테스트 파일을 뺀 것만 본다.
중복 · 네이밍 · 단일 책임 · 불필요한 복잡도 · 저장소 컨벤션의 다섯 축으로 후보를 뽑아 하나씩 적용하고 전체 테스트를 돌린다.
실패하면 그 항목만 되돌린다.
#120에서는 "0건" 줄 포맷과 "서버 —" 포맷을 한 헬퍼로 모은 항목 하나 — `refactor(#120): 빈 값 표기를 _dash로`.
후보가 없으면 건너뛴다 — 빈 커밋은 없다.
돌려주는 것은 고정 블록 하나다 — result · green sha · refactor sha 또는 skipped · 실행 결과 · 실패한 것 · blocked 사유.

주 세션은 복귀 뒤 커밋이 원격에 있는지 보고, 테스트를 한 번 더 돌리고, PR 체크리스트의 green · refactor를 `[x]`로 갱신한다.
티켓 코멘트는 없다 — 체크리스트와 커밋이 흔적이다.
blocked면 멈춘다 — 실패한 것만 적은 코멘트를 티켓에 남기고 사람에게 묻는다.
사람의 답이 "시나리오가 틀렸다"면 표를 새 코멘트로 다시 내고 재승인 → red → 검토 → green의 길을 다시 간다.
"구현이 부족했을 뿐"이면 힌트를 프롬프트에 넣지 않고 다시 부른다 — 힌트가 필요하면 테스트가 명세로 부족한 것이고, 그 힌트는 테스트에 들어가야 한다.

## 7. verify — 구현과 무관한 눈이 사슬을 대조한다

주 세션이 `preflight.py 120`으로 기계 확인을 지난다 — Draft PR이 열려 있고 · 마지막 커밋의 체크가 초록이고 · target마다 worktree가 있다.
red 커밋의 빨강은 지나간 런이라 보지 않는다.

`ac-verifier`를 부른다 — 이번에는 맥락을 전부 넘긴다: 티켓 번호 · target · worktree · 시나리오 코멘트 URL · red/green/refactor 커밋 sha · PR URL · 테스트 명령.
대조가 일이기 때문이다.

verifier는 약속의 사슬 — AC → 표 → 테스트 → 구현 — 에서 어느 고리가 끊겼나를 본다.
테스트 본문의 변별력은 보지 않는다 — 그것은 red 검토자가 닫았다.
보는 것은 다섯이다.
티켓 AC(다시 읽는다) ↔ 표의 AC 커버리지 — 약속 누락.
green · refactor 커밋 diff — 테스트 경로의 변경이 0인가 · 테스트 입력값으로 분기하거나 기대값을 되돌려주는 코드가 있나 · refactor가 브랜치 범위 밖을 건드렸나.
직접 실행 — 테스트 명령을 자기가 돌려 전부 통과하는지.
반증 테스트 — 하드코딩이 의심될 때만, 입력을 바꾼 테스트를 worktree 안에 써서 돌리고, 커밋하지 않고, 보고 뒤 지운다.
커버리지 — 저장소에 도구가 이미 있을 때만, 이번 변경이 건드린 소스에서 어느 테스트도 안 도는 분기의 목록.
도구를 설치하지 않는다.

#120에서 verifier는 `idle` 값으로 분기하는 코드가 없어 반증을 쓰지 않는다.
커버리지가 `edges`도 `idle`도 비는 분기가 안 돈다고 말한다.
대조표와 발견을 **한 코멘트**로 티켓에 직접 게시한다.

```markdown
### 검수 — jyoliar-lab/obs-toolkit · PR <URL>

| AC | 충족 | 근거(대표 테스트) |
|---|---|---|
| AC-1 idle 0건 표기 | ✅ | `test_service_graph_lines_say_idle_not_no_data_when_rows_have_zero_calls` |
| AC-2 미확인 | ✅ | `test_service_graph_lines_mark_unknown_callee_and_missing_server_p95` |
| AC-3 서버 — | ✅ | 같은 테스트 |

실행: `python -m pytest` → 통과 547 / 실패 0 (red a1b2c3d · d4e5f6a · green 7g8h9i0 · refactor j1k2l3m)

### 발견

**시나리오 후보** — 커버리지
- edges 0 · idle 0 분기가 어느 테스트에도 안 돈다 — "데이터 없음"이 유지되는지 행 추가 후보
```

근거 칸은 표의 테스트 이름 열에서 오고, 직접 실행이 그것이 통과함을 확인한다.
발견은 되돌아갈 곳마다 묶인다 — 표가 틀렸다 · 구현이 틀렸다 · 사람에게 · 시나리오 후보 · 기록.
비는 묶음은 절째 없다.
돌려주는 것은 코멘트 URL 한 줄이다.

주 세션은 코멘트가 게시됐는지, 반증 테스트가 worktree에 남지 않았는지 보고, PR 체크리스트의 verify를 `[x]`로 갱신하며 본문에 검수 코멘트 링크를 더한다.
그리고 **멈춘다**.

## 8. 사람의 지시 — 결론은 사람이 낸다

대조표의 ✅는 "테스트가 있고 통과한다"의 기록이지 검수의 결론이 아니다.
사람이 verifier 코멘트를 읽고 다음을 정한다.

| 지시 | 주 세션이 하는 것 |
|---|---|
| **ready** | `gh pr ready` — Draft를 푼다. 그 뒤 `ticket-report`의 게시 후 검수 · 지정 수정 단계부터. 대조표 작성 · 게시는 verifier 코멘트가 대신했다 |
| **표가 틀렸다** | 표를 새 코멘트로 다시 내고 승인 → red 커밋 추가 → 검토자 → green 재호출. PR은 Draft 그대로 |
| **구현이 틀렸다** | 반증을 행으로 더해 표 재승인 → red → 검토자 → green. 테스트가 통과하는 구현을 "고쳐 달라"고만 보내지 않는다 — 고칠 근거는 테스트에 있어야 한다 |
| **사람에게** 묶음 | AC · Technical Notes 갱신은 사람과. 갱신 뒤 시나리오부터 |

#120은 사람이 시나리오 후보를 다음 티켓으로 보내고 ready를 말한다.
`gh pr ready` 뒤 머지와 Issue close는 사람의 것이다.

red로 되돌아가는 길은 어디서 들어와도 같다 — 주 세션이 red를 쓰고 · 검토자가 보강하고 · 조건부로 멈추고 · green으로 흐른다.
red에서 사람 승인은 어디에도 없다.

## 9. 재개 — 새 세션이 진행 중인 티켓을 받았을 때

승인의 흔적은 남지 않으므로 새 세션은 산출물에서 현황을 읽는다.
시나리오 코멘트 · red 커밋 · red 완료 코멘트 · Draft PR과 체크리스트 · green/refactor 커밋 · 검수 코멘트.

red 완료 코멘트의 유무가 "검토까지 끝났다"를 말한다.
red 커밋은 있는데 완료 코멘트가 없으면 검토자부터다.
완료 코멘트가 있고 체크리스트의 green이 비어 있으면 green부터다.
표 승인과 verify 뒤의 지시는 흔적이 없으므로 사람에게 묻는다 — 지금 어느 단계이고 무엇이 승인됐는가.
답을 받은 단계부터 이어간다.

## 변별력의 기준 — 한 파일, 두 역할

`tdd-loop/strength.md`는 두 절이다.

**쓸 때** — 주 세션이 red를 쓰며 따른다.
단언은 Then의 성질마다 한 줄 · 조건을 `and`로 잇지 않는다 · 단언은 성질이지 값의 복사가 아니다 · Given은 표대로, 대역은 손으로 만든 최소 입력 · 모킹은 테스트마다 격리.
그리고 알려진 약함의 패턴 일곱을 피한다.

| 패턴 | 모양 |
|---|---|
| 결과를 특정하지 않는 포함 단언 | `any(tok in line for line in lines)` — 어느 줄이든 통과 |
| 우연히 맞는 짧은 토큰 | `"3" in line` — `30ms`도 맞는다 |
| 부정 단언만 | "없다"만 있고 맞는 것이 있다는 단언이 없다 |
| Then의 성질 누락 | Then이 둘을 약속하는데 단언은 하나 |
| Given이 성질을 가르지 못함 | 동률 · 경계를 약속하는데 Given에 그 경우가 없다 |
| 대역이 일을 대신함 | fake가 창을 잘라 줘 구현 없이도 Then이 성립 |
| 동어반복 | 항상 참 · stub이 우연히 만족 · 아무것도 부르지 않음 |

**판정할 때** — 검토자가 테스트마다 수행한다.
Then이 약속한 성질 하나를 깬 결과를 떠올리고, 단언이 그것을 거르는지 읽는다.
패턴 목록은 이 원리의 예시다 — 새 모양도 원리로 잡고, 목록은 발견될 때마다 자란다.
주 세션은 이 원리를 알되 테스트마다 수행하지는 않는다.

하드코딩은 이 기준의 밖이다.
기대값을 돌려주는 구현은 이 입력에서 Then의 성질을 하나도 깨지 않는다.
그것이 깨지는 것은 다른 입력에서이고, verifier의 반증 테스트가 잡는다.

## 이 체계가 하지 않는 것

- 단계 제약을 구조로 막지 않는다 — hook · 상태 파일 · 전이 스크립트가 없다. red 뒤 소스 본문을 쓰거나 green 뒤 테스트를 고치는 것은 커밋 diff에서 읽힌다.
- `preflight.py`는 red 커밋의 존재를 검사하지 않는다.
- 하네스가 테스트 러너 · 커버리지 도구를 내장하거나 설치하지 않는다 — 저장소가 핀한 것을 `tmp/venv-<repo>/`에서 돌린다.
- 테스트 정책(티어 · 범위 · 의존성을 실제 · 녹화 · fake · mock 중 무엇으로)을 정하지 않는다 — 시나리오 표의 티어 · 의존성 열이 티켓마다 기록으로 남는다.
- 주 세션이 구현하거나 대조표를 쓰거나 검수 결론을 내지 않는다.
- subagent가 PR 본문 · 티켓 코멘트를 쓰지 않는다 — verifier의 검수 코멘트만 예외다.
- 머지 · Issue close · `gh pr ready` 전의 Draft 해제를 하지 않는다.
- 하네스 자신을 고치지 않는다 — 개정은 steward가 사람과 밖에서 한다.
