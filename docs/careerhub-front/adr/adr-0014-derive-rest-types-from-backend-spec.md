# ADR-0014 — 프론트가 쓰는 REST 타입을 백엔드 스펙에서 생성한다 (손으로 선언하지 않는다)

## Context

프론트를 TypeScript로 개발하기로 했다. 그러면 **REST 응답 타입을 어디서 얻는가**가 곧바로 남는다.

현재 프론트가 사용하는 REST 응답 계약은 명시적으로 존재하지 않는다. 업스트림 gRPC용 proto는 있으나 프론트가 소비하는 REST 계약은 아니고, 실제 계약은 백엔드 Go 구조체와 직렬화 태그에만 존재한다. 프론트는 그 응답의 형태를 추측하여 타입을 손으로 선언하거나 그대로 사용한다.

이 상태에서는 계약 위반이 조용히 발생한다. 백엔드가 응답 필드명을 변경하거나 제거해도 프론트는 컴파일과 배포를 모두 통과하고, 런타임에서야 화면이 비거나 일부 기능이 동작하지 않는 것으로 드러난다.

문제를 TypeScript가 해결해 주는 것은 아니다. 프론트가 REST 계약 타입을 손으로 선언하면, 백엔드 계약이 바뀌는 순간 타입은 실제 계약과 어긋난다. 컴파일러는 실제 계약이 아니라 **손으로 작성한 선언**을 신뢰하므로, 잘못된 계약을 올바른 것처럼 보증하는 **거짓말하는 타입**이 된다.

## Decision

**REST 계약의 단일 원천(Single Source of Truth)을 백엔드에 둔다.**

백엔드는 자신이 제공하는 REST 응답 계약을 기계가 읽을 수 있는 스펙으로 제공하고, 프론트는 그 스펙에서 REST 계약 타입을 생성하여 사용한다. **REST 계약 타입은 프론트에서 손으로 선언하지 않는다.**

이렇게 하면 프론트가 참조하는 계약 표현이 항상 같은 원천에서 생성된다. 백엔드 계약이 변경되면 생성된 타입도 함께 변경되고, **프론트가 실제로 의존하는 계약이 깨진 경우에는 컴파일 단계에서 드러난다.**

이는 계약 위반을 런타임까지 숨겨 두는 대신 가능한 한 이른 시점에 발견하도록 만드는 것이다.

## Alternatives

- **프론트가 REST 계약 타입을 손으로 선언한다**
  가장 빠르게 시작할 수 있다. 그러나 선언과 실제 계약은 언제든 서로 어긋날 수 있으며, 그 사실을 자동으로 알 수 없다. 타입은 실제 계약을 반영하지 못하는 **거짓말하는 타입**이 된다.

- **런타임 검증만 사용한다**
  응답과 기대한 형태가 다른 경우를 런타임에서 발견할 수 있다. 그러나 계약 자체를 컴파일 단계에서 공유하지는 못하며, 계약 변경을 사용하는 코드가 미리 드러나지는 않는다. 런타임 검증은 계약 생성을 대체하기보다 보완하는 수단이다.

- **계속 추측해서 사용한다 (현재)**
  현재 방식이다. 계약 위반은 런타임에서만 드러나며, Context에서 설명한 문제가 그대로 유지된다.

## Consequences

- 이 결정을 위해서는 백엔드(api-composer)가 REST 계약 스펙을 제공해야 한다. 현재는 REST 계약 스펙이 존재하지 않으며, 이를 추가하는 작업은 별도 저장소에서 수행되고 이미 티켓으로 관리된다.

- 프론트는 실행 중인 백엔드 서비스가 아니라 **버전된 계약 스펙**에 결합한다. 스펙으로부터 타입을 생성하면, 프론트가 사용하는 계약이 변경된 경우 컴파일 단계에서 드러난다. 이는 런타임에서 발견하던 계약 위반을 더 이른 시점으로 이동시키는 효과다.

- 타입 생성 시점이나 생성물을 저장소에 포함할지 여부(예: CI에서 생성, 이미지 빌드에서 생성, 생성물 커밋)는 구현상의 선택이다. 이러한 결정은 되돌리기 쉽고 계약의 원천에는 영향을 주지 않으므로 이 ADR의 범위에 포함하지 않는다.

- 백엔드가 계약 스펙을 제공하기 전까지 런타임 검증을 추가하는 등의 임시 방편은 별도의 구현 판단으로 다룬다. 이 ADR이 고정하는 것은 **REST 계약 타입의 원천을 백엔드 스펙으로 한다**는 원칙이다.

## 무효화 조건

다음 중 하나가 성립하면 이 결정을 다시 검토한다.

- 백엔드가 REST 계약 스펙을 현실적으로 제공할 수 없다고 판단되는 경우
- 계약 스펙이 실제 REST 계약을 충분히 표현하지 못해 신뢰할 수 없는 경우
- 계약 스펙을 유지하는 비용이 얻는 효과를 지속적으로 초과한다고 판단되는 경우

그 경우에는 계약의 단일 원천을 백엔드에 둔다는 전제를 폐기하고, 런타임 검증 중심 접근 등 다른 대안을 다시 평가한다.
