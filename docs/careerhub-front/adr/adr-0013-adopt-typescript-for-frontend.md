# ADR-0013 — careerhub-front를 TypeScript로 짓는다 (순수 JavaScript로 짓지 않는다)

## Context

새 프론트엔드는 사람이 아니라 agent가 구현한다. 이 프로젝트에서는 **사람의 코드 리뷰를 품질 보증의 근거로 두지 않는다.** 앞선 스택 결정이 받아들인 전제다.

지금 코드는 순수 JavaScript라 타입 검사가 없다. agent가 존재하지 않는 필드를 읽거나 함수의 인자를 잘못 넘겨도, 린트는 의미를 모르고 런타임까지 간다. 화면에는 `undefined`만 남고, 오류는 실행 이후에야 드러난다.

사람 리뷰를 안전망으로 둘 수 없다면, **가능한 많은 오류를 실행 전에 기계가 막아야 한다.** 앞선 스택 결정이 "타입·계약·테스트를 선택이 아니라 전제로 둔다"고 한 이유도 여기 있다.

이 문서는 그 전제 가운데 **타입 검사를 무엇으로 구현할 것인가**를 정한다.

## Decision

**TypeScript로 짓는다.** 순수 JavaScript도, JSDoc 기반 `checkJS`도 선택하지 않는다.

이 프로젝트에서 타입은 "있으면 좋은 것"이 아니라 **사라진 리뷰어를 대신하는 가장 앞단의 검증 장치**다.

타입 검사는 가능한 한 agent가 가장 잘 다루는 형태여야 한다. 현재 프론트엔드 생태계의 표준은 TypeScript이며, 주요 라이브러리와 예제, 타입 정의, 관용구 역시 TypeScript를 중심으로 축적되어 있다. agent 역시 그 문법과 패턴을 전제로 가장 안정적으로 코드를 생성한다.

따라서 타입 검사를 도입한다면, 생태계와 agent 모두의 기준인 TypeScript를 그대로 채택한다.

## Alternatives

- **순수 JavaScript로 남는다**
  기존 JavaScript 자산을 유지해야 할 때는 의미가 있다.  
  이 프로젝트는 기존 프론트를 유지하지 않고 다시 작성한다. 따라서 JavaScript를 유지할 이유는 자산 보존이 아니라 타입 검사를 포기하는 것뿐이다.  
  사람 리뷰를 안전망으로 삼지 않는다는 전제와도 모순된다.

- **JSDoc + `checkJS`**
  JavaScript 문법을 유지하면서 타입 검사를 얻는 선택이다.  
  그러나 이 결정의 목적은 **최소한의 타입 검사**가 아니라 **사라진 리뷰어를 최대한 대체하는 것**이다.  
  `checkJS`는 TypeScript보다 표현력이 제한되고, 라이브러리와 예제 역시 TypeScript를 기준으로 제공된다. agent가 가장 많이 학습한 패턴 역시 TypeScript 문법이다.  
  타입 검사를 도입하면서도 가장 널리 쓰이는 표현과 생태계를 일부러 포기할 이유가 없다.

## Consequences

- **타입이 코드베이스 전체의 일부가 된다.**
  되돌리려면 대부분의 코드를 다시 수정해야 한다. 따라서 처음부터 결정한다.

- **타입의 원천은 별도로 정해야 한다.**
  TypeScript는 타입을 검사할 뿐, REST API의 실제 계약을 만들어 주지는 않는다. 백엔드와 별도로 손으로 선언하면 계약이 바뀌는 순간 거짓 타입이 된다.
  API 타입의 원천(OpenAPI, 코드 생성 등)은 별도의 결정으로 다룬다.

- **TypeScript는 계약 자체를 보장하지 않는다.**
  컴파일러는 형식의 일관성을 검사하지만, 서로 다른 저장소에서 실행되는 백엔드와 실제 런타임 계약까지 증명하지는 못한다.
  따라서 타입 검사와 별도로 계약 관리와 통합 테스트는 계속 필요하다.

## 무효화 조건

다음 전제가 깨지면 이 결정을 다시 검토한다.

- 사람의 코드 리뷰를 품질 보증의 핵심 수단으로 다시 둘 수 있게 되는 경우
- TypeScript가 더 이상 프론트엔드 생태계의 사실상 표준이 아니게 되는 경우
- agent가 TypeScript보다 다른 타입 시스템을 일관되게 더 잘 생성·수정하는 것이 입증되는 경우
