# 아픔을 무엇이 "할 수 없게" 만드나 — 린트·토큰·테스트, 그리고 빠져 있던 둘

---

> ⚠ **§1·§6의 한 논거는 이후 코드로 반증됐다** — *"관례가 문서화됐는데 지켜지지 않았다"* 는 거짓이다. 문서가 코드보다 9개월 늦고, 관례는 실제로 지켜지고 있다.
> 아래 원문은 사고의 기록으로 그대로 둔다. **인용 전에 `260722_1510_documented-convention-premise-refuted.md` 를 먼저 읽는다.**
> 결론(구조로 강제하라)은 서지만, 근거는 *"관례를 어겼다"* 가 아니라 *"관례가 아픈 축을 덮지 않았다"* 로 교체됐다.

---

## 1. 이 문서가 열린 경위 — 프레임워크는 곁가지였다

프레임워크 선택(축 C)에 여러 라운드를 썼다. **그것이 곁가지였음이 반증으로 드러났다.**

주장은 *"프레임워크의 관례가 구조를 강제하고, 지금 코드의 병이 그 가드레일의 부재였다"* 였다. **거짓이다.** 지금 코드에 이미 관례가 있다:

```
src/view/job_posting/postingId/index.svelte    ← 파일 기반 라우팅과 사실상 같은 구조
src/view/job_posting/postingId/api.js
src/view/job_posting/store.js
```

그리고 `careerhub-front/CLAUDE.md` 에 **문서화까지 되어 있다** — *"각 페이지 디렉토리에 index.svelte(뷰), api.js(API 호출), store.js(상태 관리)가 함께 위치한다."*

> **관례는 있었다. 문서화도 됐다. 그리고 스파게티가 됐다.**

프레임워크가 정해주는 것은 **라우팅과 파일 배치**뿐이고, **그건 안 아팠다.** 아픈 것은 다른 셋이다.

**★ 그러므로 진짜 축은 여기다.** 이 저장소의 관통 원칙이 이미 답을 가리키고 있었다 — ***"규율이 아니라 구조로 강제한다. '하지 마세요'라고 적어두는 규칙을 최소화하고, 할 수 없게 만든다."*** front CLAUDE.md 의 컨벤션은 **정확히 "하지 마세요"였고, 그래서 안 지켜졌다.**

---

## 2. 아픔 셋 — 무엇이 각각을 막나

| 아픔 | 증거 | 프레임워크가 막나 |
|---|---|---|
| **컴포넌트 비대** | `Detail.svelte` 914줄 · `JobPostingItem.svelte` 479줄 | ❌ |
| **스타일 흩어짐** | 전역 CSS 71줄 · 토큰 없음 · 32개 중 23개에 하드코딩 | ❌ |
| **회귀를 못 잡음** | 테스트 프레임워크 없음 | ❌ |

**하나도 안 막는다.** 프레임워크는 이 표에 등장하지 않는다.

---

## 3. ★ 빠져 있던 것 ① — 타입

**프론트는 순수 JavaScript다.** `scripts/setupTypeScript.js` 는 템플릿이 준 미사용 스크립트이고, `tsconfig` 도 없다.

**이것이 다른 결정과 정면으로 충돌한다.** 프론트엔드 구현을 agent 에 맡기기로 했고, 그 결정이 스스로 받아들인 대가가 이것이다:

> **"사람이 코드 리뷰로 품질을 보증하지 못한다."**

**사람이 못 잡는데 컴파일러도 없으면, 아무도 안 잡는다.**

agent 가 `postingDetail.reviewInfoo` 라고 쓰면? 사람은 못 읽고, 린트는 오타를 모르고, **런타임에 조용히 `undefined`** 가 된다. 화면이 비어 보이고, 왜인지는 아무도 모른다.

**★ 타입은 이 프로젝트에서 "있으면 좋은 것"이 아니라 사라진 리뷰어의 대체재다.**

---

## 4. ★★ 빠져 있던 것 ② — 계약이 없다. 더 깊은 병이다

타입을 도입해도 **그 타입을 어디서 얻는가**가 남는다.

`careerhub-api-composer` 에 proto 가 넷 있다 — `restapi.proto`, `review.proto`, `matchJob.proto`, `scrapJob.proto`. **전부 업스트림 gRPC 용이지 프론트용이 아니다.** 프론트가 받는 REST 응답의 계약은 `common/domain/` 의 Go 구조체(`jobposting.go`·`review.go`·`userinfo.go`)의 json 태그에만 존재한다.

> **REST 계약이 어디에도 명세돼 있지 않다. 프론트는 추측해서 쓴다.**

`Detail.svelte` 는 `postingDetail.reviewInfo` · `postingDetail.firstPageReviews` 를 읽는데, **그게 맞는지 검증할 수단이 없다.** Go 구조체를 열어보는 것 말고는.

**결과 — 계약 위반이 조용하다.** 백엔드가 필드명을 바꾸면 프론트는 컴파일도 통과하고 배포도 되고, **화면만 비어 보인다.**

**★ 손으로 타입을 선언하면 이 문제가 안 풀린다.** 손으로 쓴 타입은 백엔드와 어긋나는 순간 **거짓말하는 타입**이 된다. 없는 것보다 나쁠 수 있다 — 컴파일러가 틀린 것을 보증하니까.

---

## 5. ★ 강제의 계층 — 이를수록 강하다

| 시점 | 장치 | 성질 |
|---|---|---|
| **작성 중** | 타입 | agent 가 쓰는 순간 막힌다. **가장 이르다** |
| **커밋 시** | 린트 · 포매터 | 들어오기 전에 막힌다 |
| **CI** | 테스트 | 들어온 뒤 잡는다 |
| **런타임** | 스키마 검증 · 관측 | **터진 뒤에 안다** |
| — | 문서화된 컨벤션 | **아무도 안 지킨다** ← §1 이 증명 |

*"할 수 없게 만든다"* 를 문자 그대로 읽으면 **위로 갈수록 강하다.** 아래로 갈수록 "일어난 일을 알려주는 것"에 가까워진다.

**둘 다 필요하다** — 타입은 계약 위반을 못 잡고(백엔드는 다른 저장소·다른 언어다), 런타임 검증은 오타를 못 잡는다.

## 6. 축

### A. 타입

| | 되돌리기 | 트레이드오프 |
|---|---|---|
| **A0. JS 그대로** | — | §3. 사람도 컴파일러도 안 잡는다. **재작성하는 마당에 이 선택은 이상하다** |
| **A1. TypeScript** | **어렵다 — 전 코드에 스며든다** | 사라진 리뷰어를 대체. agent 가 가장 많이 아는 형태이기도 하다. **one-way door → ADR감** |
| A2. JSDoc + checkJS | 쉽다 | 문법 도입 없이 타입 검사. 가볍지만 표현력·생태계가 얇다 |

### B. 계약 — REST 타입을 어디서 얻나

| | 되돌리기 | 트레이드오프 |
|---|---|---|
| **B0. 추측한다** (지금) | — | 계약 위반이 조용하다 |
| **B1. 손으로 선언** | 쉽다 | **거짓말하는 타입의 위험.** 어긋나도 아무도 모른다 |
| **B2. 백엔드에서 생성** | **어렵다 — 인터페이스·계약** | 진실이 하나가 된다. 백엔드 변경이 프론트 빌드를 깨뜨린다. **api-composer 에 스펙을 붙이는 작업이 선행 — 프론트 밖의 티켓이다.** one-way door → **ADR감** |
| **B3. 런타임 스키마 검증** | 쉽다 | 손으로 쓰되 **위반이 즉시 터진다.** B1 의 조용함을 없앤다. B2 와 배타적이지 않다 |

**★ B2 는 이 저장소의 경계를 넘는다.** api-composer 는 Gorilla Mux 로 REST 를 손으로 만들고 스펙이 없다. 스펙을 붙이는 것은 **백엔드 결정**이고, 프론트 리뉴얼이 그것을 기다릴지가 판단거리다.

### C. 구조 — 컴포넌트 비대를 막는 것

| | 되돌리기 | 트레이드오프 |
|---|---|---|
| C0. 안 막는다 | — | §1 이 결과를 보여준다 |
| **C1. 줄 수 린트** (`max-lines` 등) | 쉽다 | **★ 함정: 쪼개기를 강제하지만 잘 쪼개기를 강제하지 않는다.** 914줄을 100줄 × 10개로 쪼개도 엉망일 수 있다 |
| C2. import 경계 린트 | 쉽다 | 계층 역전을 막는다. 규칙을 우리가 정해야 한다 |

**되돌리기가 싸다 → ADR 감이 아니다. 티켓이다.**

### D. 스타일 — 토큰을 강제하는 것

| | 되돌리기 | 트레이드오프 |
|---|---|---|
| D0. 없음 (지금) | — | 하드코딩 |
| **D1. 토큰만** (CSS 변수) | 쉽다 | **정의할 뿐 강제하지 않는다.** 하드코딩이 여전히 가능 → §1 의 재발 |
| **D2. 토큰 + 스타일 린트** | 쉽다 | 하드코딩된 색·간격을 거부한다. **"할 수 없게" 만든다** |
| **D3. Tailwind** | **중간 — 마크업에 스며든다** | **토큰이 문법에 내장.** 밖으로 나가려면 명시적으로 써야 하고 그것도 린트로 막힌다. 가장 강한 강제 |
| D4. 컴포넌트 라이브러리 | 어렵다 | 선택지가 좁아 일관성이 딸려온다. 디자인 자유도를 잃는다 |

### E. 테스트

| | 트레이드오프 |
|---|---|
| E0. 없음 (지금) | — |
| **E1. e2e** (Playwright) | 사용자 관점. **★ 인프라 비용이 크다** — 전체 스택(auth · api-composer · 3개 코어 서비스 · MongoDB 3개)이 떠야 하고, **로그인이 Google OAuth 뿐이라 우회 경로를 백엔드에 만들어야 한다.** 12개 라우트 중 8개가 인증 필요 |
| E2. 컴포넌트 테스트 | 인프라가 싸다. 사용자 관점은 아니다 |
| E3. 시각 회귀 | **★ 디자인을 바꾸는 것이 목적인 동안에는 노이즈다.** 리뉴얼이 끝난 뒤에 값이 생긴다 |

## 7. 트레이드오프 축

- **★ 언제 막나** — 작성 중 > 커밋 > CI > 런타임 > 문서 (§5). 이를수록 강하다
- **강제인가 권고인가** — 토큰 정의(D1)와 토큰 강제(D2)는 다른 물건이다. §1 이 그 차이를 증명했다
- **되돌리기 비용** — A1·B2·D3 만 비싸다. 나머지는 티켓
- **경계를 넘는가** — B2 는 백엔드 변경을 요구한다. E1 도 (OAuth 우회)
- **누가 떠안나** — 강제가 강할수록 agent 가 막히고, 약할수록 나중에 사람이 디버깅한다

---

## 8. 미결

① **★ 재작성 전에 무엇을 세우나** — 린트·토큰·타입은 **재작성 전에 세워야 효과가 있다.** 나중에 붙이면 이미 쌓인 것을 고쳐야 한다. 그런데 세우는 동안 재작성이 멈춘다

② **B2(계약 생성)를 기다리나** — api-composer 에 스펙을 붙이는 것은 백엔드 작업이다. 프론트 재작성이 그것을 기다릴 가치가 있나, 아니면 B3(런타임 검증)로 시작하고 나중에 B2 로 갈아탈 것인가

③ **E1(e2e)의 OAuth 우회를 누가 만드나** — auth-service 변경이다. 프론트 밖이고, 이 저장소는 코드를 고치지 않는다. **티켓이다**

④ **D3(Tailwind)가 과한가** — 가장 강한 강제이지만 마크업에 스며든다. 되돌리기가 중간이다

## 9. 지금까지의 관찰

- **★ 프레임워크는 아픔 셋 중 하나도 안 막는다**(§2). 여러 라운드를 곁가지에 썼다. **아픔의 표를 먼저 그렸으면 알았을 것이다** — 그 표는 첫날 이미 있었다
- **★★ 문서화된 컨벤션은 강제가 아니다.** front CLAUDE.md 에 관례가 적혀 있었고, 지켜지지 않았고, 스파게티가 됐다. **이 저장소의 §8("규율이 아니라 구조로")이 프론트에는 적용되지 않았고 그 결과가 지금 아픈 것이다**
- **★★★ 논의에서 타입과 계약이 통째로 빠져 있었다.** "린트·토큰·테스트" 셋으로 문제를 규정한 것 자체가 좁았다. **가장 이른 시점에 막는 장치가 논의에 없었다**
- **★ 계약이 없다는 것이 가장 깊은 병일 수 있다.** 타입을 손으로 쓰면 거짓말하는 타입이 되고, 그건 없는 것보다 나쁠 수 있다. **그리고 이 병의 치료는 프론트 밖에 있다**
- **토큰을 정의하는 것과 강제하는 것은 다른 결정이다.** D1 은 §1 의 재발이다 — 적어두고 안 지키는 것
- **ADR 감은 A1(타입)·B2(계약)·D3(Tailwind) 셋뿐이다.** 나머지는 되돌리는 데 한 시간이면 되니 티켓과 코드의 관할이다
