# 토큰 저장 — 서버가 생긴 뒤에 다시 여는 축 D

앞선 발산(`260717_1456` §3-D)은 이 축을 **열어둔 채로** 닫았다 — *"지금 하지 않는다. 언젠가의 one-way door."* Epic #6 이 그 판단을 그대로 실었다.

**그 판단의 근거가 스택 결정으로 약해졌다.** 이 문서는 그것을 확인하고 축을 다시 벌린다.

> **개정 이력.** 초판(§5)은 D2 의 범위를 **과소평가**했고(api-composer 를 빠뜨렸다) D1 의 대가도 **과소평가**했다(공개 화면까지 프록시 대상이 된다). 둘 다 코드를 더 읽고서야 드러났다. 그리고 그 과정에서 ***"축 D 는 축 B 와 독립"*** 이라는 앞선 판정이 무너졌다(§7). 초판의 잘못된 수치는 남기지 않고 고쳤다 — 아직 아무 결정도 여기 얹히지 않았으므로.

## 1. 코드에서 읽은 것

추측이 아니라 인용이다. 경로는 `$CODE_ROOT` 기준.

### 저장 방식

| 사실 | 근거 |
|---|---|
| 토큰이 **JS가 쓰고 JS가 읽는 쿠키**에 산다 | `careerhub-front/src/cookie.js` — `document.cookie` 로 심고 읽는다 |
| `HttpOnly`·`Secure`·`SameSite` 가 **한 군데도 없다** | `setCookie` 의 기본 옵션은 `path: "/"` 뿐 |
| access·refresh·grantType·**authorities** 가 전부 쿠키에 | `src/httputils.js` — `set*ToCookie` 6종 |
| auth-service 는 **쿠키를 굽지 않는다.** JSON 바디로 준다 | `auth_service/restapi/ctrlr/dto/dto.go:61-64` |
| auth-service 전역에 `SetCookie`·`HttpOnly` **0건** | grep (vendor 제외) |
| 프론트가 받아서 직접 심는다 | `src/view/login/index.svelte:36-37` |
| OAuth 콜백이 **브라우저를 거쳐** 토큰을 넘긴다 | `auth_service/.../after_auth.html` — `window.opener.postMessage({authToken}, "*")` |
| 원 저자도 알고 있었다 | `src/httputils.js:4` — `//TODO: jwt token 및 유저정보 등의 정보 저장에 대한 다른 방법을 찾아보자.` |

### 소비 방식 — 누가 토큰을 읽나

| 사실 | 근거 |
|---|---|
| 백엔드는 쿠키를 안 본다. **`Authorization` 헤더를 본다** | 아래 4곳 |
| 헤더를 읽는 지점 **넷** | api-composer `middleware/middleware.go:20` · `jwtresolver/jwtresolver.go:142` · auth-service `middleware/middleware.go:20` · `jwtresolver/jwtresolver.go:142` |
| 토큰 소비자는 **브라우저 하나뿐** | 비-브라우저 클라이언트 없음. 서비스 간 통신은 gRPC |
| 프론트가 헤더를 직접 채운다 | `src/httputils.js` — `setAccessTokenToHeader` |
| 게이트웨이는 **경로 분기만** 한다 | `jyoliar-k8s/.../gateway/httproute.yaml` — `/`·`/api`·`/auth` 가 같은 호스트, 필터 없음 |

### ★★ 인증 선택적(optional auth) API — 공개 화면까지 퍼져 있다

| 사실 | 근거 |
|---|---|
| `withAccessToken` 을 쓰는 파일이 **10개** | `src/` 전수 grep |
| 그중 **공고 목록·공고 상세**(공개 라우트)가 포함된다 | `view/job_posting/api.js` · `view/job_posting/postingId/api.js` |
| 백엔드가 클레임 유무로 **응답을 가른다** | `api-composer/.../jobposting_controller.go:66-71` — `JobPostingsWithClaims` vs `JobPostings` |
| 상세도 같다 | 같은 파일 `:123-131` — `JobPostingDetailWithClaims` vs `JobPostingDetail` |

> **★ "공개 4 / 인증 8" 이라는 라우트 구분은 *화면 접근*의 구분이지 *API 호출*의 구분이 아니다.** 앞선 발산은 그 둘을 같은 선으로 취급했다. 코드는 그렇지 않다 — **가장 트래픽이 많은 공개 화면이 인증 선택적 API 를 부른다.**

## 2. 아픔

**① XSS 한 방에 refresh token 까지 털린다.** 주입된 스크립트가 `document.cookie` 를 읽어 보내면 끝이다. access token 만이면 만료를 기다리면 되지만, refresh token 은 **무기한 갱신 열쇠**다 — `/auth/refresh` 에 바디로 넣으면 새 access 가 나온다(`auth_controller.go:263`). 피해자가 브라우저를 닫아도, 로그아웃해도 **공격자 손의 문자열은 유효하다.** JWT 라 "이 토큰만 무효화"할 자리도 없다.

**★ 탈취된 토큰은 이식 가능하고(공격자 기계에서 쓴다) 지속적이다(무기한).**

**② 클라이언트가 자기 권한을 선언한다.** `getAuthoritiesFromCookie()` 로 화면 권한을 판단한다. 서버가 헤더의 JWT 로 다시 검증하므로 데이터가 새지는 않지만, 재작성에서 그대로 옮길 모양이 아니다.

**③ `postMessage(..., "*")`** — 타깃 오리진이 와일드카드다. 별개 취약점이고, 재작성이 이 흐름을 다시 쓴다.

**④ 이 앱은 서드파티 스크립트를 의도적으로 넣는다.** 수익 모델이 AdSense 게재다(`careerhub/discussion/260717_1853`). 광고 로더는 **iframe 이 아니라 페이지 컨텍스트에서** 돌고, 따라서 `document.cookie` 에 도달할 수 있다. **고전적 XSS 취약점을 우리가 안 만들어도, 남의 코드가 1st-party 권한으로 실행되는 것을 우리가 결정으로 초대한다.**

**⑤ CSP 가 없다.** `public/index.html` 전문과 gateway 설정에 `Content-Security-Policy` **0건**. 주입된 스크립트의 외부 전송을 막을 층이 없다.

## 3. HttpOnly 가 실제로 주는 것 — 과장하지 않는다

**HttpOnly 는 XSS 를 막지 않는다.** XSS 가 나면 여전히 당한다. 바뀌는 것은 ***털렸을 때 무엇을 잃느냐*** 다.

브라우저가 그 쿠키를 `document.cookie` 반환값에서 제외하므로 **JS 에 읽을 API 가 없다.** 동시에 브라우저는 그 쿠키를 요청에 자동으로 붙인다 — **"쓰되 읽지는 못한다."**

| | **지금 (D0)** | **HttpOnly** |
|---|---|---|
| 토큰 문자열을 가져가나 | ✅ | ❌ |
| 공격자 기계에서 쓸 수 있나 | ✅ **된다** | ❌ |
| 피해자 브라우저에서 요청을 보낼 수 있나 | ✅ | ✅ **여전히 된다** |
| 언제까지 | **refresh 가 사는 동안 무기한** | 스크립트가 도는 동안만 |
| 탭을 닫으면 | 무관 | **끝난다** |
| 우리가 탐지·차단할 수 있나 | 공격자 IP 의 정상 요청 | 피해자 세션의 이상 행동 → rate limit 이 먹힌다 |

**남는 공격을 세션 라이딩이라 한다** — 토큰을 훔치는 대신 피해자 브라우저를 원격 조종한다. 심각하지만 **그 탭 안에, 그 시간 동안**으로 갇힌다.

> **무기한·이식 가능한 계정 탈취 → 일시적·국소적 조종.** 없어지는 게 아니라 반경이 줄어든다.

**층으로 보면 HttpOnly 는 예방이 아니라 피해 한도(blast radius) 설정이다:**

| 층 | 무엇을 하나 | 지금 |
|---|---|---|
| XSS 를 안 만든다 | React/Next 의 기본 이스케이핑 | 재작성이 얻는 것 |
| CSP | 주입돼도 외부 전송을 막는다 | ❌ 없다 |
| **HttpOnly** | 뚫려도 **토큰이 못 나간다** | ❌ 없다 |
| 짧은 수명 + 회전 | 나가도 창이 좁다 | refresh 무기한 |

## 4. 옵션

### D0. 현행 복제

JS 쿠키에 access·refresh 저장. **정하지 않으면 이게 된다**(§6).

### D1. 프론트 서버가 굽는다

Next 라우트 핸들러가 auth-service 로부터 JSON 으로 토큰을 받아 HttpOnly 쿠키로 심고, 서버에서 꺼내 `Authorization` 헤더로 변환해 api-composer 를 부른다.

**바뀌는 것:** 프론트(새 코드) + auth-service 의 **OAuth 콜백 착지점**(`postMessage` → 리다이렉트. HttpOnly 와 정면 충돌하므로 불가피).
**안 바뀌는 것:** api-composer. 헤더를 **누가 채웠는지** 신경 쓰지 않는다(§1).

### D2. auth-service 가 직접 굽는다

`Set-Cookie` 로 브라우저에 심는다. 프론트는 토큰을 아예 만지지 않는다.

**★ 여기에 함정이 있다.** 브라우저는 HttpOnly 쿠키를 못 읽는다 — 그러면 **그 토큰을 `Authorization` 헤더에 넣어줄 주체가 없다.** `setAccessTokenToHeader` 가 작동 불가능해진다. 따라서 **소비 쪽 4곳이 전부 쿠키를 읽도록 바뀌어야 한다.**

게이트웨이가 변환해주지도 못한다. Gateway API 의 `RequestHeaderModifier` 는 **리터럴 값만** set/add 하므로 "쿠키에서 꺼내 헤더에 넣어라"를 표현할 수 없다. NGINX Gateway Fabric(`gatewayClassName: nginx`)의 `SnippetsFilter` 로는 기술적으로 가능하지만, **인증 배선을 GitOps 저장소의 nginx 스니펫에 넣는 것**이 되고 표준 밖 탈출구다.

**요구하는 것 다섯:**

| # | 무엇 | 어디 |
|---|---|---|
| ① | sign-in·sign-up·agree·refresh 응답을 `Set-Cookie` 로 | auth-service |
| ② | OAuth 콜백을 리다이렉트 착지로 재설계 | auth-service `after_auth.html` |
| ③ | 인증 미들웨어가 쿠키를 읽도록 | **api-composer 2곳 + auth-service 2곳** |
| ④ | refresh 가 바디 대신 쿠키를 읽도록 | `auth_controller.go:263` |
| ⑤ | CSRF 방어 (`SameSite` + 오리진 검증) | 양쪽 |

### D3. BFF 세션

서버에 세션 상태를 둔다. 상태 저장소 도입 — 홈랩 1인 운영에 과하다.

## 5. D1 vs D2 — 무엇이 가르나

| | **D1 — 프론트 서버** | **D2 — auth-service** |
|---|---|---|
| **XSS 로부터의 이득** | **동일** | **동일** |
| 바뀌는 저장소 | 프론트 + auth-service(콜백만) | auth-service + **api-composer** |
| Next 없이 성립하나 | ❌ | ✅ |
| 재작성 전에 할 수 있나 | ❌ | ✅ **병렬 가능** |
| 브라우저의 직접 API 호출 | ❌ **전부 Next 경유 (BFF 화)** | ✅ 그대로 |
| ADR-0012 와의 관계 | 사실상 딸린 축 | **독립 축** |
| CSRF | 생긴다 | 생긴다 |

**★ XSS 방어 효과는 둘이 같다.** 토큰이 JS 에서 안 보인다는 성질은 누가 굽든 동일하다. **가르는 것은 보안이 아니라 — 어느 저장소가 바뀌고, 무엇에 의존하고, 언제 할 수 있느냐다.**

### ★★ D1 의 진짜 대가 — 초판이 과소평가한 것

D1 에서 토큰이 **Next 서버만 아는 쿠키**라면, 브라우저의 클라이언트 컴포넌트는 `/api` 를 직접 부를 수 없다. 헤더를 채울 수 없으니까. **모든 인증 API 호출이 Next 를 경유한다 — 즉 Next 가 API 프록시(BFF)가 된다.**

그 대가가 관리 화면에만 붙는다면 작다. **그런데 §1이 보여주듯 공개 화면이 인증 선택적 API 를 부른다.** 공고 목록에서 **필터를 만질 때마다, 페이지를 넘길 때마다** 브라우저 → Next → api-composer 로 간다. **인터랙션이 가장 잦은 메인 화면에 +1 홉이 붙는다.**

**렌더링이 강제되는 것은 아니다.** D1 이 강제하는 것은 *"인증이 얽힌 데이터 접근이 서버를 경유한다"* 이지 *"HTML 을 서버가 그린다"* 가 아니다. 화면은 여전히 CSR 로 둘 수 있고 라우트별 렌더링 스위치는 유효하다.

> **정확히는 — 스위치는 남지만 CSR 쪽 끝의 값이 깎인다.** CSR 의 장점은 *"라우팅과 데이터 요청에 서버 왕복이 없다"* 인데 D1 이 그 왕복을 되살린다. 선택지가 사라지는 게 아니라 **한 선택지가 더 이상 그만큼의 값을 못 낸다.**

**얻는 것도 있다.** BFF 가 되면 토큰 갱신 로직이 한 곳에 모이고, 응답을 화면에 맞게 조립할 자리가 생기며, **서버가 아는 사실이 늘어난다**(계측 축 H 의 §2.6 이 말한 그 성질).

### D2 의 대가

백엔드 4곳 수정 + 테스트. 전부 이 저장소 밖이므로 **티켓 둘**(auth-service · api-composer)이 되고, 그 둘이 프론트 인증 화면을 막는다.

### 공통 대가 — CSRF 표면

지금은 프론트가 토큰을 **직접 헤더에 넣으므로**(`setAccessTokenToHeader`) 다른 사이트가 요청을 유발해도 그 헤더를 채울 수 없다 — **이 앱은 오늘 CSRF 에 구조적으로 면역이다.** 쿠키 자동 첨부로 옮기면 그 면역이 사라진다.

`SameSite=Lax` + 상태 변경 요청의 메서드·오리진 검증이 **같이 와야 한다.** 덤이 아니라 조건이다. → **이 결정은 XSS 노출을 CSRF 표면과 맞바꾸는 것**이고, 후자가 훨씬 잘 알려진 표준 방어로 덮인다는 점이 교환을 성립시킨다.

### 권장 속성

| 속성 | 무엇을 막나 |
|---|---|
| `HttpOnly` | JS 가 값을 읽는 것 |
| `Secure` | 평문 HTTP 로 새는 것 |
| `SameSite=Lax` | CSRF |
| `Path=/auth/refresh` (refresh 만) | refresh 가 모든 요청에 딸려 나가는 것 |

**우선순위를 하나만 꼽으면 refresh token 이다** — access 는 수명이 짧아 창이 좁지만 refresh 는 무기한 열쇠다.
**`localStorage` 는 더 나쁘다** — JS 에 완전 노출인데 자동 전송 이점도 없다.

## 6. 왜 "나중에"가 위험한가

**안 정하면 결정이 사라지는 게 아니라, 구현 시점에 기본값으로 내려진다.**

재작성은 인증 배선을 처음부터 새로 쓴다. 로그인 화면을 만드는 agent 는 토큰을 어딘가에 넣어야 하고, 결정이 없으면 참조할 것은 기존 코드뿐이다 → **D0 가 복제된다.** ADR-0015 가 스타일에 대해 말한 것과 같은 실패다 — 아무도 정하지 않은 것이 관례가 되어 굳는다.

**SSR-safe 규율과도 얽힌다.** Epic #6 이 지키기로 한 *"컴포넌트 최상위에서 `window`·`document`·`localStorage` 를 만지지 않는다"* 인데, 지금 인증은 정확히 `document.cookie` 를 최상위에서 읽는 구조다. ADR-0012 Consequences 가 이미 지목했다.

## 7. ★★ 앞선 판정이 무너졌다 — 축 D 는 축 B 와 독립이 아니다

`260717_1456` §3-D 는 이렇게 적었다:

> *"★ D 는 B2 를 고를 때만 강제된다. B1 이면 독립 축으로 남아 나중에, 따로 결정할 수 있다."*

**그 판정은 "공개 화면은 인증과 무관하다"를 전제한다.** §1 이 그 전제를 깼다 — 공고 목록·상세가 인증 선택적 API 를 부른다. **로그인 상태를 서버에서 그리지 않아도, 데이터 자체가 이미 개인화된다.**

따라서:

- **D0 가 아닌 어떤 선택도 데이터 접근 경로에 영향을 준다.** "B1 이면 D 가 빠진다"는 성립하지 않는다.
- **D1 은 특히 얽힌다** — 공개 화면의 클라이언트 호출까지 프록시 대상이 되므로.

### 덤 — 축 B 의 화면 배정표도 흔들린다

`260717_1550` §7 은 **공고 상세를 SSG/ISR** 로 배정했다. 그런데 그 엔드포인트가 개인화된다(`JobPostingDetailWithClaims`). **SSG 로 구우면 개인화가 안 된다.**

치명적이진 않다 — 공고 본문은 굽고 개인화 조각만 클라이언트에서 채우면 된다. 그러나 **그건 §7 표가 말한 것과 다른 설계**다. 같은 문서 §8 이 *"개인화하면 캐시가 죽는다"* 를 축으로 적어놓고도, **어느 화면이 실제로 개인화되는지를 확인하지 않은 채** 배정했다.

---

## 8. 미결 — 채우지 않고 남긴다

① **재작성에서 인증 화면이 언제 오나.** 코드가 아니라 사람이 답한다.

② **D1 인가 D2 인가.** §5 가 축을 놓았다. 남은 것은 *"백엔드 둘을 지금 건드릴 것인가"* 와 *"메인 화면의 +1 홉을 감수할 것인가"* 다.

③ **`authorities` 를 어떻게 다룰 것인가.** 토큰 저장과 공동무효인가, 별개인가.

④ **이것이 ADR 인가.** D1·D2 의 되돌리기 비용이 다르고, D2 는 재작성과 병렬로 갈 수 있어 임계선 판정이 갈릴 수 있다.

⑤ **축 B 를 다시 열어야 하나.** §7 의 덤이 화면 배정표를 흔들었다. 별도 문서인지 이 축에 딸린 것인지 아직 안 정했다.

## 9. 지금까지의 관찰

- **★ 결정을 미룬 근거(되돌리기 비용)가 낡았다.** ADR-0012 가 프론트에 서버를 만들면서 D1 의 비용이 재계산됐다. **열어둔 축은 방치하면 낡은 가격표를 달고 있다.**
- **★★ "공개 4 / 인증 8" 은 화면의 구분이지 API 의 구분이 아니었다.** 이 하나가 축 D 의 분리 판정과 축 B 의 배정표를 동시에 흔들었다. **라우트 목록은 읽었으나 그 라우트가 무엇을 부르는지는 안 읽었다** — `260722_1510` 이 기록한 것과 같은 종류의 어긋남이다.
- **★ HttpOnly 는 XSS 를 막지 않는다.** 막는 것은 **탈취**이고 남는 것은 **악용**이다. "안전해진다"고 말하면 거짓이고, 그 거짓이 CSP·짧은 수명 같은 다른 층을 안 세우게 만든다.
- **★ D2 의 범위는 auth-service 하나가 아니다.** 브라우저가 HttpOnly 를 못 읽는다는 바로 그 성질이 **헤더를 채울 주체를 없앤다** → 소비 쪽 4곳이 따라온다. 보안 이득을 주는 성질이 곧 배선 비용을 만든다.
- **★ D1 의 대가는 렌더링 강제가 아니라 CSR 의 값 하락이다.** 스위치는 남는다. 다만 한쪽 끝이 예전만큼 좋지 않다 — **선택지의 소멸과 값의 하락을 구분하지 않으면 논거가 과장된다.**
- **오늘 이 앱은 CSRF 에 면역이다.** 헤더 방식의 유일한 장점이고, 어느 옵션으로 가든 그것을 잃는다. 잃는 것을 세지 않으면 이동이 공짜로 보인다.
- **AdSense 결정과 이 축이 같은 페이지에서 만난다.** 두 결정은 각각 내려졌고 이 교차는 어디에도 안 적혀 있었다.
