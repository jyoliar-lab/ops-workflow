# 공통 UI 요소와 외부 디자인 프레임워크

Epic jyoliar-lab/ops-workflow#6의 공개 화면(채용공고 목록·상세) 착수 전에 제기된 질문.

## 문제

원 질문은 "버튼 같은 공통 요소를 먼저 잡고 가야 하나, 잡는다면 어디까지가 공통 요소인가"였다.
논의 중 질문이 한 층 내려갔다 — "공통 컴포넌트를 직접 만드나, 외부 디자인 프레임워크를 들여오나."

밑에 있는 불편: 기존 프론트는 스타일이 흩어져 일관성을 잃었다(ADR-0015 Context — Svelte 컴포넌트 32개 중 23개가 자체 스타일 블록).
같은 일을 반복하고 싶지 않다.

## 코드 관찰

- `careerhub-web`은 Tailwind v4(CSS-first `@theme`) + `eslint-plugin-tailwindcss` 배선이 끝나 있다 (`src/app/globals.css`, `package.json`).
  `@theme` 토큰은 현재 brand 4색뿐이다.
- ADR-0015가 값 수준 일관성(색·간격 하드코딩)은 이미 구조로 막았다.
  남은 것은 패턴 수준 — 같은 요소가 화면마다 다르게 생기는 것.
- 두 공개 화면이 실제로 공유하는 요소를 기존 앱(`workspace/ref/careerhub-front`)에서 읽으면: Header · 페이지네이션(목록 하단, 상세 리뷰) · 태그/뱃지 · 별점 표시.
  **"버튼"은 이 두 화면에서 의외로 공통 요소가 아니다** — "공통 요소 = Button·Input·Card"는 디자인 시스템의 관습적 상상이고, 실재하는 반복과 달랐다.
- Epic #6은 디자인 토큰을 "되돌리기 쉬운 구현 판단, 하위 Task"로 이미 분류해뒀다.

## 경계 교정 — ADR-0015가 고정한 것과 안 한 것

agent가 처음에 "컴포넌트 라이브러리는 ADR-0015에서 기각됐으므로 지나간다"고 경계를 넓게 그렸고, 사람이 교정했다.

- ADR-0015의 **Decision**이 고정한 것: 토큰을 Tailwind 유틸리티로 소비하고, 이탈은 린트가 막는다는 구조.
- 고정하지 **않은** 것: "컴포넌트는 직접 만든다."
  Alternatives에서 기각된 것은 *Tailwind 대신* 쓰는 자체 CSS 체계의 라이브러리(MUI·Bootstrap류)다.
- 기각 사유였던 "디자인 자유도 상실"은 사람의 실제 선호로 무게가 사라졌다: **디자인은 무난하면 되고, 차별화가 필요 없다.**

여기서 판별 기준이 나왔다: **Tailwind 토큰 구조 안에서 사는 프레임워크는 ADR-0015와 양립하고, 자체 CSS 체계를 들여오는 것은 충돌한다.**

## 옵션

### 축 1 — 공통 요소를 언제 잡나

- **A. 디자인 모듈 선구축** — 화면 전에 프리미티브를 만든다.
  이기는 조건: 확정된 시각 기준이 있고 남은 화면이 많을 때.
  시각 기준 없이 만들면 근거 없는 모양이 되어 두 번 만든다.
- **B. 화면 우선 + 두 번째 사용에서 추출** — 목록을 먼저 짓고, 상세를 지으며 실제 반복된 것만 추출.
  여기선 두 번째 사용처가 이미 코드로 보이므로(위 공유 요소 표) 통상적 약점("언제가 두 번째인지 모른다")이 없다.
  토큰+린트가 하한을 깔아둬 추출 전 표류 비용도 작다.
- **C. 안 한다 — 공통화를 끝까지 미룬다** — 전 화면 후 일괄 정리.
  비용: 복붙이 화면 수만큼 자라고, 회귀망(#9)이 공개 라우트만 덮어 후반 일괄 리팩토링은 사람 눈에만 의존한다.

### 축 2 — 직접 만드나, 외부에서 들여오나

- **D. 외부 디자인 프레임워크 도입** — 처음엔 "ADR-0015 기각, 지나간다"로 접었다가, 경계 교정 + "무난하면 된다" 선호로 **재개봉**됐다.
  후보 조사 진행 중: shadcn/ui · daisyUI · HeroUI · Flowbite · Catalyst · Base UI · Preline · Park UI/Ark UI.
  판별 항목: Tailwind v4(CSS-first) 지원 · React 19/Next 16 호환 · 배포 모델(npm 의존 vs 코드 복사 vs CSS 플러그인 — 제거 비용 차이) · 동작(a11y·포커스) 포함 범위 · `@theme` 토큰으로 테마 가능한가 · 린트와의 충돌 · 라이선스.

## 버린 것

- **Bootstrap·MUI류(자체 CSS 체계)** — ADR-0015 Decision과 실충돌.
  토큰의 단일 원천이 둘이 된다.
- **"Button·Input·Card부터 만든다"는 관습적 선구축 목록** — 두 공개 화면의 실재 반복(Tag·Rating·Pagination·Header)과 다르다.
  코드를 읽지 않은 공통 요소 목록은 상상이다.
- **완전한 토큰 팔레트 사전 설계** — 디자인 원천이 없는 상태에서는 근거가 없다.
  값이 마크업에 적히려는 순간마다 `@theme`에 승격하는 lazy 방식을 택한다(`globals.css` 주석의 기존 규칙).

## 조사 결과 — 축 2의 후보 비교 (260818 추기)

2026-08-18 기준, 버전·릴리스 날짜를 검증한 조사.
전제 스택: Next.js 16 App Router · React 19 · Tailwind v4 CSS-first `@theme` · eslint-plugin-tailwindcss 4.x.

### 판정 (agent 제안)

**shadcn/ui.**
copy-in 모델이라 채택의 실체가 저장소에 코드가 생기는 것이고, ADR-0015가 우려한 "컴포넌트 API가 마크업에 스며들어 못 뺀다"가 구조적으로 완화된다.
daisyUI의 whitelist 관리는 ADR-0015의 강제 장치(린트)에 손으로 구멍을 뚫는 일이라 감점.
Catalyst는 토큰 순수성이 최고이나 밑단(Headless UI)의 활력 열세와 좁은 컴포넌트 폭이 리스크.

부수 효과: 축 1(공통 요소를 언제 잡나)이 소멸한다 — 선구축할 것이 없어지고, 화면을 지으며 필요한 컴포넌트를 `shadcn add`로 끌어오는 것이 기본 경로가 된다.
두 공개 화면의 필요 요소(Card·Badge·Pagination)는 기본 세트에 있고, 별점 표시만 직접 만든다.

## ADR 판정 — ADR감이 아니다 (260818 2차 추기)

agent가 "의존성 도입 = one-way door 후보이므로 proposed ADR을 쓴다"고 했고, 사람이 반문했다: copy-in이면 직접 만드는 것과 구조가 같지 않은가.
임계선(§4② — 되돌리기 어려움 × 영향 범위)을 실제로 돌리면 반문이 맞다.

- shadcn 채택의 결과물은 `src/components/ui/*.tsx` — 소유한 일반 React+Tailwind 코드다.
  그만 쓰기로 해도 되돌릴 것이 없다 — CLI를 더 안 부르면 끝이고, 받은 코드는 내 코드로 남는다.
- 유일한 런타임 의존(`@base-ui/react`)은 컴포넌트 단위로 국소적이라 교체 비용이 낮다.
- 구조적 약속은 ADR-0015가 이미 지고 있다.
  shadcn은 그 토큰 구조 안의 소비자일 뿐 새 구조를 세우지 않는다.

**후보 선택이 ADR 여부를 갈랐다** — HeroUI(런타임+compound API 침투)나 daisyUI(린트 whitelist로 ADR-0015의 강제 장치 변형)였다면 문서화 대상이었다.
shadcn이 이긴 이유(제거 비용 최저)가 곧 ADR이 필요 없는 이유다.
"의존성 도입"은 휴리스틱이지 판정이 아니다 — **배포 모델이 임계선을 가른다.**

이 결론은 Epic #6의 기존 분류("디자인 토큰·마이그레이션 경로 — 되돌리기 쉬운 구현 판단. 하위 Task로 다룬다")와 일치한다.

## 수렴 (260818)

사람이 shadcn/ui로 확정했다.
ADR 없이 Epic #6 하위 Task 3장으로 파생됐다 — 셋업 / 목록 화면 / 상세 화면, 순차 선행.

쪼갬에서 버린 것 둘:

- **"셋업을 첫 화면 Task에 포함"** — agent의 처음 제안.
  사람이 분리를 택했다: 셋업(토큰 브리지·린트 설정)의 검증을 화면 구현과 섞지 않고 먼저 굳힌다.
- **"검색/필터 패널을 목록에서 별도 Task로 뗀다"** — agent의 제안이었으나 폐기.
  회귀망(#9)의 목록 시나리오가 검색·필터·페이지네이션을 한 여정으로 명세하므로, AC를 시나리오 통과로 걸려면 Task 단위가 명세 단위를 따라야 한다.
  **티켓의 크기는 취향이 아니라 검증 단위가 정한다** — 이 논의가 남긴 일반 교훈.

상세를 목록 뒤에 거는 이유: e2e 상세 시나리오가 목록을 경유해 진입하고("어느 공고를 열지는 목록이 알려준다"), 공유 요소가 목록에서 먼저 생긴다.

### 추기 — 시각 검증 게이트 (사람 제안)

"무난한 디자인"은 조사로 확정했지만 그 룩을 실제 화면에서 본 적이 없다는 공백을 사람이 짚었다.
이미 구현된 최소 화면(로그인)에 shadcn을 먼저 적용해 룩을 판정하는 Task를 셋업과 목록 사이에 끼웠다.
**되돌리기 판정은 되돌리기가 가장 싼 시점에 한다** — 새 화면이 shadcn 위에 지어지기 전이 그 시점이다.
느낌이 아니면 채택을 여기서 접는다 — copy-in 모델이라 접는 비용도 화면 하나 되돌리기뿐이다.
