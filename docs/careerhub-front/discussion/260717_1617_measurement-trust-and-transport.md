# 계측 — 무엇을 신뢰할 수 있고, 어디서 보내나 (축 H)

> # ⚠ 이 문서는 잘못된 전제 위에 서 있다 — `rejected`
>
> **전제:** *"careerhub 가 Google Ads 로 광고를 집행하고, 그 전환을 최적화한다."*
> **사실:** careerhub 의 수익 모델은 **광고 게재(AdSense)** 다. **광고주가 아니라 게시자다.**
>
> **Google Ads 는 돈을 쓰는 도구이고, 돈을 버는 도구는 AdSense 다.** 둘은 같은 네트워크의 양쪽 끝이다 — Ads 가 광고를 넣고, AdSense 가 그것을 게시자의 사이트에 뿌리고 게시자에게 지불한다. **"Ads 로 돈을 번다"는 성립하지 않는다.**
>
> **그래서 이 문서의 결론 대부분이 무의미하다:**
> - **AdSense 는 전환 추적을 요구하지 않는다** — 페이지뷰와 광고 노출·클릭으로 지불한다. 최적화할 입찰이 없다
> - → H1(서버 직접 전송) · 이중 계수 · 진실의 원천 · `/go/` 리다이렉트 · 유령 스팸 방어가 **전부 "우리가 광고주다"에 매달려 있었다**
> - → **GA 는 "어느 콘텐츠가 PV 를 만드나"를 보는 내부 판단 도구로 내려간다. H0 로 충분하다**
> - → **조작 걱정은 무의미하다** — GA 가 오염돼도 AdSense 수익은 안 변한다. 그것은 Google 이 따로 센다
>
> **살아남는 것 (§2·§2.5·§2.6·§3):** 클라이언트 계측이 원천적으로 신뢰 불가라는 것, SST 가 광고 차단을 못 막는다는 것, **렌더링 구조가 무엇을 서버가 아는 사실로 만드는가**, 사실의 출처가 신뢰를 정한다는 것. 이것들은 전제와 무관하게 참이다.
>
> **왜 이렇게 됐나 — 요구에 적힌 말을 검증 없이 받았다.** 요구사항이 *"Google Analytics/Google Ads 추후 추가"* 였고, 나는 "Ads = 광고주 도구"라는 뜻으로 읽고 **그 전제 위에 세 라운드를 쌓았다.** 사람이 *"실은 Ads 로 어떻게 돈을 버는지조차 모른다"* 고 정직하게 말하기 전까지 아무도 그것을 묻지 않았다.
>
> **★ 교훈: 요구에 적힌 고유명사를 검증하지 않았다.** 코드는 읽었으면서 **말은 안 읽었다.** *"desired 는 코드가 답한다"* 는 규율이 코드 밖의 전제에는 적용되지 않았고, 그 틈으로 잘못된 전제가 세 라운드를 끌고 갔다.
>
> **후속:** 수익 모델과 그 실현 가능성(AdSense 승인 · 광고 차단)은 프론트엔드의 관할이 아니다. 별도로 다룬다.

---

렌더링 논의(축 B)에서 두 번 튀어나오고, *"브라우저에서 보내면 조작 가능한 것 아닌가"* 라는 물음으로 세 번째 불려 나온 축. **축 B와 독립이다** — 렌더링을 무엇으로 하든 이 결정은 그대로고, 이 결정이 렌더링을 바꾸지도 않는다.

## 1. 세 개를 구분한다 — 이 축의 혼동은 전부 여기서 나온다

| | 무엇 | 무엇을 준다 |
|---|---|---|
| **SSR** (축 B) | HTML을 서버가 만든다 | 크롤러 · 미리보기 · 초기 렌더 |
| **SST** (Server-Side Tagging) | 계측 이벤트를 **내 서버가 받아** GA로 전달한다 | ID 은닉 · 검증 지점 (~~광고 차단 우회~~ — §2.5 정정) |
| **MP** (Measurement Protocol) | **내 서버가 GA로 직접** 이벤트를 보낸다 | **위조 불가능 · 차단 불가능한 사실** |

*"서버 사이드"* 라는 말이 셋에 다 붙어 있어서 계속 뭉쳐진다.

> **정정.** 이 문서의 초판은 *"SSR은 이 문서의 어느 문제도 풀지 못한다"* 고 단언했다. **틀렸다** — 광고 차단 앞에서는 **SSR이 관련된다**(§2.6). 다만 GA 태그를 통해서가 아니라, **렌더링 구조가 어떤 사실을 서버가 알게 만드느냐**를 통해서다.

---

## 2. 클라이언트 계측은 원천적으로 신뢰할 수 없다 — 그리고 생각보다 나쁘다

**Measurement ID는 페이지 소스에 평문으로 있어야 한다.** 스크립트가 발화하려면 필요하므로 감출 방법이 없다.

그것을 긁어 GA의 수집 엔드포인트로 **직접** 쏘는 것이 ghost spam이다. 결정적인 성질:

> **공격자는 사이트를 방문조차 하지 않는다.** 요청이 우리 서버·CDN에 **하나도 오지 않는다.** 접근 로그에 아무것도 안 남고, 세션은 **GA의 DB 안에만** 존재한다.

→ **WAF·IP 차단·GA의 봇 필터가 구조적으로 못 막는다.** 우리를 거치지 않는 것을 우리가 막을 수는 없다. 동기는 스팸 도메인 유인, 클릭 사기 정탐, 무작위 ID 대량 발사다.

**★ SSR은 여기에 아무것도 하지 않는다.** HTML을 서버가 만들어도 Measurement ID는 페이지에 있어야 하고, 스팸은 우리 서버를 안 거친다.

## 2.5. ★ 정정 — SST는 광고 차단을 우회하지 못한다

이 문서의 초판과 축 B 문서는 SST의 이점으로 *"광고 차단 우회"* 를 적었다. **과장이었다.**

> **uBlock Origin은 기본 설정으로 서버 사이드 GTM 요청도 차단한다.** Brave·Ghostery·AdGuard도 같다. **도메인이나 경로 prefix를 바꿔도 소용없다** — EasyPrivacy 필터가 패턴을 잡고, 그 리스트는 거의 모든 차단기에 들어 있다.

**왜 — SST도 결국 브라우저에 의존하기 때문이다.** 브라우저가 JS를 실행하고, 쿠키를 심고, 네트워크 요청을 보내야 한다. **그것이 정확히 차단기가 노리는 것이다.** 도메인을 내 것으로 바꿔도 URL·JS 패턴은 남는다. 차단기는 URL 패턴 차단, HTML·스크립트의 텍스트 치환, JS API 후킹까지 한다.

→ **SST는 완화이지 해법이 아니고, 군비 경쟁이다.**

### ★ careerhub에서는 특히 안 통한다

**사용자가 개발자다.** Wanted·JumpIt 공고에 스킬 스캐너가 붙은 서비스다. **개발자는 광고 차단기 사용률이 가장 높은 집단이고, 그중 uBlock Origin의 비중이 크다.**

→ 일반 사이트에서 SST가 회복시키는 몫이 여기서는 훨씬 작다. **H2의 값은 이 도메인에서 낮다.**

## 2.6. ★★ 차단 앞에서는 SSR이 관련된다 — 처음으로

차단기는 **브라우저 안에 산다.** 그러므로 **브라우저를 거치지 않는 것은 건드릴 수 없다.** 이것이 유일하게 확실한 성질이고, 여기서 렌더링 구조가 개입한다.

| | 화면 조회는 누가 아나 | 차단 |
|---|---|---|
| **CSR SPA** | **브라우저만 안다.** 화면 전환에 서버 요청이 없다 — JS가 라우팅한다 | 차단되면 그 사실이 **영영 사라진다** |
| **SSR / SSG** | **서버도 안다.** 화면마다 요청이 발생하고, 전환 시에도 서버에서 데이터를 받는다 | **차단 불가능** — 막으면 페이지 자체가 안 뜬다 |

> **즉 SSR은 "화면 조회"를 §3의 위 칸(브라우저만 아는 것)에서 아래 칸(백엔드가 아는 것)으로 옮긴다.**

**이것이 *"SSR은 시스템 측에서 직접 제어할 여지가 많다"* 의 정체다.** GA 태그의 문제가 아니라 — 그 층위에서는 SSR이 여전히 무관하다(§2) — **렌더링 구조가 어떤 사실을 서버가 아는 것으로 만드느냐**의 문제였다. 축 B와 축 H가 여기서 한 번 만난다.

**서버가 심는 first-party 쿠키**를 더하면 식별자도 JS 차단과 무관해진다 — 서버가 응답을 만들며 심으므로.

**정직한 단서:**
- 서버가 아는 것은 *"요청이 왔다"* 이지 *"사람이 봤다"* 가 아니다. **봇·크롤러를 걸러야 한다**
- 세션 봉합(§3)은 그대로 남는다
- 이것이 축 B를 SSR로 밀 근거가 되는가는 별개다 — **SSG도 요청을 남긴다.** 필요한 건 "요청마다 서버 렌더"가 아니라 **"화면 전환이 서버를 거치는 구조"** 다

## 3. ★ 진짜 축 — "그 사실을 누가 아는가"

조작 가능성은 전송 방식의 문제가 아니라 **사실의 출처**의 문제다.

| 사실의 출처 | 신뢰 | 보내는 곳 | 조작 |
|---|---|---|---|
| **브라우저만 아는 것** — 스크롤·체류·클릭·화면 조회 | ❌ **원천적으로 불가** | 클라이언트 | 감수한다. 어떤 구조로도 못 막는다 |
| **백엔드가 아는 것** — 스크랩 생성·가입·조건 등록·탈퇴 | ✅ | **서버에서 MP + `api_secret`** | **불가능** |

**careerhub의 진짜 전환은 전부 아래 칸이다.** 스크랩(북마크), 가입, 매칭 조건 등록 — 모두 `userinfo-service` 와 `api-composer` 가 아는 사실이고, **브라우저가 알려줄 필요가 애초에 없다.** 서버에서 보내면 위조가 성립하지 않는다.

> **위 칸을 신뢰하려는 노력은 헛수고다.** 사용자의 기기에서 일어난 일을 그 기기의 말로만 아는 이상, 어떤 아키텍처도 그것을 진실로 만들지 못한다. **할 수 있는 것은 신뢰하지 않을 자리를 두는 것뿐이다.**

**함정 — 세션 봉합(stitching).** 서버 이벤트를 사용자 경로에 붙이려면 브라우저의 `client_id` 를 잡아 저장해 두어야 한다. 서버에서 임의 ID를 만들면 **끊어진 경로**가 생겨 전환이 유입과 연결되지 않는다. 즉 **서버 전송은 클라이언트 전송을 대체하는 것이 아니라 그것을 필요로 한다.**

## 4. 옵션

### H0. 아무것도 안 한다 — 표준 클라이언트 계측만

| | |
|---|---|
| 이길 때 | GA를 내부 판단용으로만 쓸 때. 유령 스팸은 노이즈일 뿐 치명적이지 않다 |
| 잃는 것 | 광고 차단으로 인한 **손실**. 유령 스팸으로 인한 **오염**. 전환 위조 가능 |
| 비용 | 0 |

### H1. 백엔드가 아는 전환만 서버에서 보낸다 (MP)

| | |
|---|---|
| 이길 때 | 전환의 정확성이 중요할 때 — 특히 Ads에 먹일 때 |
| 얻는 것 | **위조 불가능한 전환.** 광고 차단과도 무관(브라우저를 안 거침) |
| 비용 | `api-composer` 나 각 서비스에 전송 코드. `client_id` 를 받아 저장하는 배선 |
| 되돌리기 | 쉽다 — 보내기를 멈추면 된다 |

### H2. Server-Side Tagging — 모든 이벤트를 내 엔드포인트로 받는다

| | |
|---|---|
| 얻는 것 | **Measurement ID가 페이지에서 사라진다** → 유령 스팸(§2)의 진입점이 닫힌다. 검증·가공 지점 |
| 한계 ① | **광고 차단을 못 막는다**(§2.5). 개발자 사용자에겐 특히 |
| 한계 ② | 브라우저가 보낸 이벤트의 **진위는 여전히 모른다.** 다만 위조가 **내 서버를 거치므로** WAF·rate limit이 먹힌다 — 유령 스팸과 결정적으로 다르다 |
| 비용 | 태깅 서버를 운영한다. **운영 표면이 늘어난다** |
| 되돌리기 | 중간 |

**★ H2의 값은 §2.5 이후 크게 깎였다.** 남은 값은 **유령 스팸 차단(ID 은닉)** 과 **검증 지점**이지 광고 차단 회복이 아니다. 그 둘을 위해 태깅 서버를 운영할 값어치가 있는지는 미결이다.

**★ 전제는 이미 갖춰져 있다** — `gateway/httproute.yaml` 에서 `/`·`/api`·`/auth` 가 **같은 오리진**이다. 차단기가 first-party로 보고 통과시킬 엔드포인트를 이미 갖고 있다. 새 도메인이 필요 없다.

### H1 + H2

서로 배타적이지 않다. **H1은 전환의 진실성**을, **H2는 수집의 완전성과 ID 은닉**을 담당한다. 다른 문제를 푼다.

## 5. 트레이드오프 축

- **무엇을 지키려는가** — **손실**(광고 차단으로 안 옴)인가 **오염**(가짜가 들어옴)인가 **위조**(전환이 조작됨)인가. 셋은 다른 문제이고 해법도 다르다
- **운영 표면** — H1은 안 늘린다. H2는 늘린다
- **되돌리기 비용** — 둘 다 낮다. **→ ADR감이 아닐 가능성이 높다**(§4② 임계선)
- **누가 떠안나** — 오염된 전환이 Ads 입찰에 먹이면 **돈이 떠안는다**

---

## 6. 미결

① **★ GA 데이터를 무엇에 쓸 것인가** — 이 축 전체가 여기 걸려 있다.
- **내부 판단용** (어느 화면이 쓰이나) → H0로 충분하다. 노이즈는 감수한다
- **Google Ads 최적화** → 전환 오염이 **입찰을 왜곡해 돈을 태운다**. H1이 사실상 필수가 된다
- **외부 보고** → 신뢰성 요구가 높다

② **무엇을 전환으로 볼 것인가** — 스크랩? 가입? 외부 지원 링크 클릭? **마지막 것은 브라우저만 아는 일이라 §3의 위 칸이다** — 하필 가장 중요한 전환이 가장 못 믿을 자리에 있을 수 있다

③ **실무에서 조작과 손실 중 무엇이 큰가** — 악의(조작)보다 구조(광고 차단 손실)가 더 많이 깎는다는 보고가 흔하다. 우리 트래픽에서 실제로 어떤지는 **재보기 전엔 모른다**

## 7. 지금까지의 관찰

- **★ "광고 차단 영향을 최소화하려면?" 의 답은 H1 하나다.** H2(SST)는 완화이지 해법이 아니고(§2.5), careerhub의 사용자가 개발자라 특히 안 통한다. **차단기는 브라우저 안에 살고, 브라우저를 안 거치는 것만이 안전하다.**
- **★ 차단을 이기려 하지 말고, 차단이 닿지 않는 곳의 사실을 써라.** 스크랩·가입·조건 등록은 백엔드가 안다 — H1로 **100%** 얻는다. 차단기가 무의미해진다. 도메인·경로를 위장하는 군비 경쟁보다 이쪽이 싸고 확실하다.
- **★★ 그리고 렌더링 구조가 "무엇이 서버가 아는 사실인가"를 바꾼다**(§2.6). CSR SPA는 화면 조회를 브라우저만 알게 만들고, SSR/SSG는 서버도 알게 만든다. **이것이 "SSR은 제어 여지가 많다"의 정체였다** — 세 번의 오해 끝에 나온 진짜 연결고리다.
- **"서버 사이드"라는 말이 세 개의 다른 것에 붙어 있다** — Rendering · Tagging · Measurement Protocol. 이 논의에서 SSR이 계속 불려 나온 것은 대체로 그 말이 겹쳤기 때문이지만, **§2.6에서는 진짜로 관련됐다.** 초판이 *"SSR은 어느 문제도 풀지 못한다"* 고 단언한 것은 성급했다 — **말이 겹친다는 발견에 취해 실제 연결까지 부정했다.**
- **조작 가능성은 전송 방식이 아니라 사실의 출처가 정한다.** 브라우저만 아는 일은 어떤 아키텍처로도 진실이 되지 않는다. 반대로 백엔드가 아는 일은 애초에 브라우저에게 물을 필요가 없었다.
- **유령 스팸은 우리 서버를 거치지 않는다** — 이 한 가지 성질이 방어 수단 대부분을 무력화한다. 막는 게 아니라 **긁을 것을 없애는 것**(H2)이 유일한 접근이다.
- **되돌리기 비용이 둘 다 낮다** — 이 축은 ADR이 아니라 **티켓과 코드**의 관할일 가능성이 높다. 미결 ①이 닫히면 그냥 하면 된다.
