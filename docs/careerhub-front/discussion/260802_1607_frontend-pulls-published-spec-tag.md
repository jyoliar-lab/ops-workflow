> **결말(2026-08-02)** — 축 A2(로컬 생성 + 산출물 커밋 + CI 드리프트 게이트) · 축 B1(핀 범프는 사람) · 축 C1(핀 파일에 좌표 전체)로 수렴했고, 전부 #12 본문으로 옮겼다. 자동화 형제 티켓은 내지 않는다. 결정은 ADR-0014·0020이 이미 세워 놓았고 여기서 정한 것은 전부 two-way door라 ADR을 파생시키지 않는다.
# 프론트가 공표 태그에서 TS 타입을 만드는 방법 — 소비자가 당긴다

## 아픔 — 문제가 옮겨 앉았다

`260730_1524`에서 벌린 문제는 *"백엔드 스펙 변경을 프론트에 어떻게 **전파**하는가"* 였다. 그 논의는 ADR-0019·0020으로 수렴했고, #30이 REST 축의 공표 좌표(`spec/api-composer/v0.2.0` 태그)를 실제로 세웠다.

**그러면서 문제의 모양이 바뀌었다.** ADR-0020이 *"consumer가 결합하는 것은 원천이 아니라 공표물이며, 어느 공표 버전에 언제 올라탈지는 consumer가 자기 저장소의 핀으로 선택한다"* 고 정했으므로, 백엔드의 역할은 **태그 발행에서 끝난다**. 남은 것은 전파가 아니라 **소비자 저장소 안의 소비 방법**이다:

> **careerhub-web이 공표 태그 하나를 핀하고, 그 태그의 `openapi.yaml`에서 TS 타입을 만들어 쓰는 파이프라인을 어떤 모양으로 세울 것인가.**

이것이 #12의 실체다. #12는 아직 *"백엔드 스펙에서 생성한다"* 는 방향만 적고 있고, **어디에 결합하는지**(가변 브랜치가 아니라 불변 좌표)를 말하지 않는다 — ADR-0020 이전에 발행됐기 때문이다.

## 코드에서 확인한 현재

- **공표물**: `spec/api-composer/v0.2.0` 태그(#30이 발행). 그 태그의 `spec/api-composer/openapi.yaml` — OpenAPI **3.0.3** · 1,161줄 / 32.7 KB · **연산 20개** · `bearerAuth`(JWT) · 경로는 `ROOT_PATH` prefix 아래 마운트 가능.
- **좌표 규약**: 태그 prefix = 계약 디렉터리, 파일명은 고정 관례. **좌표 하나에서 파일 위치가 파생된다** — 소비자에게 별도 경로 지식이 불요(api-composer README).
- **소비자(careerhub-web)**: Next.js 16.2(App Router) · TS **strict + `noUncheckedIndexedAccess`** · npm · Node 24 · CI는 `g1-check.yml`(typecheck·lint)뿐. `src/app`에 3파일 — **화면이 아직 없다.** 타입 생성 파이프라인 없음.
- **★ 자격증명 지형**: 두 저장소 모두 **private**이고, careerhub-web·api-composer·조직 어디에도 **Actions 시크릿이 0개**다.

## 제약 — 조사에서 확인한 사실

### ① 소비자 CI는 provider를 읽을 수 없다

`GITHUB_TOKEN`은 **자기 저장소로 한정**된다(GitHub 문서 명문: *"The token's permissions are limited to the repository that contains your workflow"*). cross-repo private read에는 별도 자격증명이 필요하고, 필요한 권한은 정확히 **`Contents: read`** 하나다. 수단은 셋:

| | 회전 | 비고 |
|---|---|---|
| fine-grained PAT | 만료 관리 필요 | 가장 적은 의식 |
| GitHub App installation token | 자동(1시간) | GitHub이 권하는 방향 · 좌석 불요 |
| deploy key | **만료 없음** | GitHub이 App 쪽을 권함 |

**로컬(개발자 머신)에서 당기면 이 자격증명이 필요 없다** — 사람은 이미 두 저장소에 접근한다. 즉 **"생성이 어디서 도느냐"가 시크릿 하나를 만들거나 없앤다.**

### ② 좌표 규약이 전달 수단을 고른다

우리 태그는 슬래시를 품는다(`spec/api-composer/v0.2.0`). 이것이 수단을 걸러낸다:

- ✅ **Contents API** — `gh api "repos/O/R/contents/spec/api-composer/openapi.yaml?ref=spec/api-composer/v0.2.0" -H "Accept: application/vnd.github.raw"`. ref를 **데이터**로 넘기므로 모호성이 없다.
- ✅ **`actions/checkout` + `sparse-checkout`** — `repository:`·`ref:`·`token:`·`sparse-checkout: spec/api-composer`. CI 전용이고 네이티브 입력이라 손으로 partial clone을 짤 필요가 없다.
- ❌ **`raw.githubusercontent.com`** — 토큰은 받지만 ref를 **경로에** 담는다. 슬래시 품은 태그가 파일 경로와 구분되지 않는다.
- ❌ **`git archive --remote`** — GitHub이 HTTPS·SSH 양쪽에서 막아뒀다.

### ③ 도구 — 우리 브리프에서는 한 곳으로 수렴한다

실제 스펙으로 다섯 도구를 돌려 본 결과:

| 도구 | 산출 | 파일/줄 | strict+`nUIA` | 판정 |
|---|---|---|---|---|
| **openapi-typescript** (+`openapi-fetch`) | **타입만**(런타임 0) | **1파일 · 1,086줄** | ✅ (`eOPT`·TS7까지 clean) | **적합** |
| @hey-api/openapi-ts | 타입+SDK+런타임을 **저장소에 심는다** | 16파일 · 3,180줄 | ⚠️ `exactOptionalPropertyTypes`에서 **52 에러** | 부적합 |
| orval | 타입+react-query 훅 | 6파일 · 2,917줄 | — | 부적합(훅이 본체) |
| kubb | 플러그인식(타입만도 가능) | **88파일** · 1,509줄 | — | 부적합(디프 붕괴) |
| swagger-typescript-api | 타입+클라이언트 클래스 | — | — | **실격**(OpenAPI 3.1 미지원) |

수렴 이유는 브리프의 각 조항이 같은 곳을 가리키기 때문이다 — **타입만**(런타임 0인 유일한 도구) · **커밋 가능한 디프**(1파일 1,086줄은 읽히는 계약 디프, 88파일은 아니다) · **도구 선택권 유지**(산출물이 평범한 `paths` 타입이라 `openapi-fetch`→raw `fetch`→나중에 react-query로 갈아타도 재생성 불요) · **App Router 적합**(훅은 클라이언트 컴포넌트 전용이라 서버 경로는 어차피 손으로 쓴다).

> ⚠️ **TypeScript 7이 생성기를 깨뜨린다.** `typescript@7.0.2`(2026-07)에서 openapi-typescript는 설치가 막히고(peer `^5.x`), 강제 설치하면 크래시한다. hey-api는 peer 범위가 거짓말을 해서 **설치는 되고 크래시한다** — 더 나쁜 실패다. 반면 **생성된 `.d.ts`는 TS 7에서 깨끗하게 컴파일된다.** 즉 깨지는 것은 산출물이 아니라 생성기이고, `npx -y openapi-typescript@7.13.0`처럼 **격리 실행**하면 소비자의 의존성 그래프에 생성기가 들어오지 않는다.

### ④ 생성물 커밋은 관행이다 — 우리가 발명하는 것이 아니다

공개 GitHub 코드 검색에서 생성기 배너로 잡히는 커밋된 산출물이 수천~수만 건이다(openapi-typescript 4,772 · hey-api 17,248). "재생성 후 디프 검사" 게이트도 마찬가지다 — OpenAPI Generator 공식 문서가 그 패턴을 명시하고, openapi-typescript는 그 용도의 `--check` 플래그를 갖고 있다(다만 원격/인증 스펙 경로에서 쓰는 `redocly.yaml` 구동 시 **오탐 버그**가 열려 있어, `git diff --exit-code`가 안전하다).

전체 파이프라인(태그에서 fetch → 생성)을 실측하니 **1.5초**다. 게이트 비용은 사실상 0이다.

## 옵션 — 축으로 나눈다

### 축 A. 생성이 어디서 도나 (= 시크릿이 생기나)

- **A1. 로컬 생성 + 산출물 커밋 · CI는 지금 그대로**
  개발자가 `npm run gen`으로 당기고 생성하고 커밋한다. **시크릿 0.** CI는 `g1-check`(typecheck·lint)만 돈다 — 앱 코드가 커밋된 타입과 어긋나면 여기서 깨진다.
  *지는 조건*: 누가 생성물을 손으로 고치거나, 핀만 올리고 재생성을 잊으면 **아무도 모른다**. ADR-0014가 없애려던 "거짓말하는 타입"이 다른 문으로 돌아온다.
- **A2. A1 + CI 드리프트 게이트** (PR마다 핀 좌표에서 재생성 → `git diff --exit-code`)
  A1의 유일한 구멍을 막는다. 비용은 **시크릿 1개**(`Contents: read`)와 1.5초.
- **A3. 커밋하지 않고 빌드마다 생성**
  *기각 후보*: 모든 CI 잡·모든 프리뷰 배포·모든 로컬 `npm ci`가 cross-repo 자격증명을 요구하고, 생성기가 소비자 의존성 그래프에 들어와 **TS 7 문제를 정면으로 맞는다**. 얻는 것(디스크 1,086줄)이 잃는 것보다 작다.

### 축 B. 핀을 무엇이 올리나

- **B1. 사람 손** — 지금은 백엔드 머지도 같은 사람이 한다. 새 좌표를 아는 사람이 바로 그 사람이다. 비용 0.
  *지는 조건*: 잊는다. 무음.
- **B2. Renovate** — `customManagers`(regex) + `github-tags` 데이터소스로 **접두 태그를 추적할 수 있다**(확인됨). 단 함정이 있다: **태그 prefix를 `currentValue` 캡처 밖에 두어야 한다.** 안 그러면 Renovate가 `SPEC_TAG=0.3.0`으로 써서 **핀을 파괴한다**. 그리고 `hostRules`로 두 저장소에 읽기 자격증명이 필요하다.
- **B3. 폴링 워크플로** — `gh api repos/O/R/git/matching-refs/tags/spec/api-composer`가 접두 태그만 정확히 돌려준다(확인됨). cron → 핀 수정 → PR. 부품이 Renovate보다 적고 자격증명은 같다.
- **B0(기각). provider가 `repository_dispatch`** — 초 단위로 빠르지만 **백엔드가 소비자 저장소에 쓰기 권한을 갖는다.** "백엔드 역할은 태그 발행까지"를 정면으로 되돌린다.

**Dependabot은 이 일을 못 한다.** `package-ecosystem`이 닫힌 집합이라 평범한 핀 파일을 읽는 설정이 없고, `gitsubmodule`은 태그가 아니라 브랜치 최신 커밋으로 올린다.

### 축 C. 핀을 어떤 모양으로 적나

- **C1. 좌표 전체** (`spec/api-composer/v0.2.0`) — 파일에 적힌 것이 곧 공표 좌표다. 사람이 읽고 바로 `gh api`에 넣는다. B2를 쓸 때 위 함정을 조심해야 한다.
- **C2. 버전만** (`0.2.0`) — 워크플로가 `spec/api-composer/v${VERSION}`으로 조립한다. Renovate 함정이 원천적으로 없다. 대신 핀 파일이 **공표 좌표를 그대로 담지 않는다**(prefix가 스크립트에 흩어진다).

## 검토하고 버린 것 — 수단 쪽

여기가 이 논의에서 가장 값진 부분이다. *"태그를 패키지처럼 당긴다"* 는 직관이 **npm에서는 성립하지 않는다.**

- **npm git 의존 (`github:org/repo#tag`)** — 네 가지 독립적 이유로 기각:
  ① 서브디렉터리 지정(`::path:`)이 2026-02에 들어가 **Node 24 패치 버전에 따라 있고 없다**(npm 11.16+ 필요) ② 반쯤만 동작한다 — 서브디렉터리에서 이름·버전은 읽지만 **저장소 전체를 패킹**하고 lockfile의 `resolved`에서 경로 조각이 **사라진다**(핀이 거짓말한다) ③ `prepare`가 **저장소 루트에서** 돈다 — Go 저장소 루트에서 npm 스크립트가 도는 상황이고 `--ignore-scripts`로도 막히지 않는다 ④ **npm 12가 git 의존을 기본 비활성화한다**(`allow-git="none"`) — 다음 메이저 업그레이드에 만료 예정인 전략.
- **git submodule** — superproject가 기록하는 것은 **SHA-1 gitlink**이고 `.gitmodules`의 `branch=`는 브랜치만 받는다. "태그에 핀"이 "그 태그가 가리키던 SHA를 커밋"으로 격하되어, **#30이 일부러 만든 감사 가능한 좌표가 소비자 쪽에서 뭉개진다.**
- **`raw.githubusercontent.com` · `git archive --remote`** — 위 제약 ②.
- **백엔드가 npm 패키지를 발행한다(축 A의 상위 대안)** — 업계 다수형(octokit·Stripe)이고 lockfile·봇을 공짜로 준다. 그러나 **"백엔드 역할은 태그 발행에서 끝난다"를 되돌린다**. 소비자가 하나뿐인 지금 레지스트리+발행+인증이라는 부품 셋이 스크립트 하나와 같은 일을 한다. 소비자가 늘면 재검토.
- **프론트 CI가 태그를 읽어 스스로 npm 패키지를 발행하고 자신이 소비한다** — ①의 부품을 소비자 쪽으로 옮긴 것뿐이고, 자기가 발행해 자기가 먹는 순환이라 얻는 것이 없다.
- **CI가 생성해서 되커밋한다(봇 푸시)** — 사람이 `npm run gen`을 안 쳐도 된다는 것 하나를 얻자고 PR 브랜치 write 권한이 늘고 사람 커밋과 경합한다.
- **스펙 파일 사본도 함께 커밋한다** — 매력적으로 보인다: 자격증명 없이 "타입 = 커밋된 스펙"을 검사할 수 있다. 그러나 **검사가 약해진다**(사본끼리의 정합만 보고 "커밋된 스펙 = 핀한 태그"는 못 본다) · **사본이 하나 는다**(ADR-0020의 자세와 어긋나고 drift의 씨앗) · 드리프트 게이트를 두기로 한 이상 **얻는 것이 없다**. 커밋하는 것은 생성된 `.d.ts` 하나다.

> ★ **Go는 공짜로 받는 것을 npm은 못 받는다.** gRPC 축(#31~#38)이 고른 "태그 = 패키지 좌표"는 Go 모듈이 접두 태그를 그대로 좌표로 해석하기 때문에 성립한다(`go.mod` 한 줄이 핀). npm에는 그 해석기가 없다 — **같은 태그가 Go 소비자에게는 패키지 좌표이고 TS 소비자에게는 그냥 git ref다.** 이 비대칭이 이 논의가 필요했던 이유다.

## 범위 밖 — 명시해 둔다

- **미구현(501) 대응** — `260801_1806`이 수렴시킨 것: **소비자 코드는 분기하지 않는다.** 방어는 소비자 배포 게이트 한 자리에만 서고, 그것은 별도 티켓의 관할이다. #12에서 501 분기를 짜 넣지 않는다.
- **mock(Prism·MSW)** — 병렬 개발용 응답. 화면이 아직 없어 지금은 아프지 않다.
- **oasdiff breaking 게이트** — provider 측 독립 축(`260730_1524` 축 B).

## 축 D — 빌드 결과물이 어느 좌표로 만들어졌는지 무엇이 말하나

논의 중 제기된 질문이고, **처음에 층을 넷으로 세운 것이 틀렸다.** ①(커밋된 핀 파일)과 ②(배포 체인)는 같은 것이다 — 핀을 파일로 커밋하는 순간 ②는 추가로 하는 일이 **0**이다. 층은 둘이었다: **(가) 핀이 git에 있다** vs **(나) 산출물·런타임이 스스로 말한다.**

**(가)가 왜 공짜인가 — 사슬이 이미 닫힌다.** 조직 공용 빌드 워크플로(`jyoliar-careerhub/.github`)가 `IMAGE_TAG: ${{ inputs.image-tag || github.ref_name }}` — **이미지 태그 = git 태그명 그대로**다. 그래서 GitOps `newTag` → careerhub-web의 그 태그 → 그 커밋의 핀 파일 → 계약 좌표까지 **전 hop이 git 사실**이 된다. `260801_1806`이 Go 소비자에 대해 확인한 사슬과 같은 모양이고, **프론트에서는 핀 파일이 `go.mod`의 자리를 대신한다.** (전제: careerhub-web도 `v*` 태그로 이미지를 굽는 관례를 따를 것 — 지금 Dockerfile·워크플로가 없다. 이는 배포 파이프라인 티켓의 몫이지 이 논의가 만든 일이 아니다.)

**(나)를 지금 사지 않는 이유**: 어긋남의 *방어*는 소비자 배포 게이트가 하고 그 재료는 런타임 값이 아니라 git 핀이다 · 화면도 배포도 아직 없다 · 대조 상대인 백엔드 `GET /contract/version`은 이미 서 있어 나중에 붙여도 늦지 않다. (나)가 사는 자리는 **조사 편의와 관측**이지 결손이 아니다.

남는 정직한 반론 하나: git 사슬은 *배포가 GitOps를 통했다*는 전제에 의존한다 — 손으로 `kubectl set image`를 하면 **사슬이 조용히 거짓말한다.** 다만 그건 계약 좌표만의 병이 아니라 GitOps 우회 일반의 병이라, 좌표를 자기서술로 바꾼다고 해결되지 않는다.

| 축 | 선택 | 왜 |

| **C** | **C1** — 핀 파일에 좌표 전체 | B를 자동화하지 않으므로 Renovate 함정이 성립하지 않는다. 파일에 적힌 것이 곧 공표 좌표다 |
| **D** | **(가)** — git 핀으로 충분 | 추가 작업 0. (나)는 아플 때 산다 |

**형제 티켓을 내지 않는다** — B1을 골랐으므로 전파 자동화 티켓이 없고, 좌표 노출은 배포 파이프라인 티켓의 몫이며, mock·oasdiff·소비자 배포 게이트는 각각 별개 계기로 선다.

### 모범 방안이 되려면 챙길 다섯

1. **생성기를 의존성에 넣지 말고 버전 고정해 격리 실행** — TS 7 공존 불가 문제가 사라지고, 생성기 업그레이드가 산출물을 재포맷해 디프 게이트를 노이즈로 터뜨리는 것도 막는다.
2. **게이트는 `git diff --exit-code`** — `--check`는 원격·인증 스펙 경로에서 오탐 이슈가 열려 있다.
3. **한 스크립트, 두 호출자** — 로컬과 CI가 다른 경로로 생성하면 게이트가 자기 자신을 검사하게 된다. 백엔드의 `make openapi`와 동형.
4. **PR 게이트는 재생성 diff와 typecheck 둘 다** — diff만으로는 "타입은 최신인데 앱이 안 맞음"을, typecheck만으로는 "타입이 낡음"을 못 잡는다.
5. **산출물에 손대지 마라를 신호로** — 배너 + `.gitattributes`의 `linguist-generated=true` + 린트 제외. 막는 것은 게이트의 일이고, 이건 리뷰가 계약 변경에 집중되게 하는 장치다.

> ★ **이 모양의 진짜 값은 백엔드와 동형이라는 것이다.** `make openapi`(로컬 생성) + CI 신선도 게이트(재생성 후 diff) — 정한 것은 그걸 프론트 언어로 옮긴 것뿐이다. 두 저장소가 같은 규율을 쓰면 배울 것이 하나다.
