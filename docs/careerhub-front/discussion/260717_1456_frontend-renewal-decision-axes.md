# careerhub-front 리뉴얼 — 결정 축 벌리기

"프론트 리뉴얼"로 들어온 요구를 **독립적으로 뒤집힐 수 있는 축들**로 분해하고, 각 축의 옵션·트레이드오프를 벌린다. 결론을 내는 문서가 아니다.

---

## 1. 현재 상태 — 코드에서 읽은 것

추측이 아니라 인용이다. 경로는 `$CODE_ROOT` 기준.

| 사실 | 근거 |
|---|---|
| Svelte 3 + rollup, 프레임워크 없음 | `careerhub-front/package.json` |
| **해시 라우팅** — `svelte-spa-router` | `src/App.svelte`, `src/view/index.js` |
| 라우트 12개. 공개 4 (`/`, `/job_posting`, `/job_posting/:site/:postingId`, `/login`) · 인증 8 (`/my/*`, `/admin/*`) | `src/view/index.js` |
| JWT access/refresh를 **JS에서 읽는 쿠키**에 저장. HttpOnly·SameSite·Secure 없음 | `src/cookie.js`, `src/httputils.js` |
| auth-service는 토큰을 **JSON 바디로** 반환. 쿠키를 굽지 않음 | `auth-service/` 전역에 `SetCookie`·`HttpOnly` 없음 |
| `@media` 쿼리가 **전체에서 2줄** — `withdrawal` 한 파일에만 | `src/view/my/withdrawal/index.svelte:81,112` |
| 모바일 분기 코드 없음 (`matchMedia`·`innerWidth` 부재) | `src/` 전역 grep |
| 전역 CSS 71줄, 디자인 토큰 없음. 스타일은 32개 컴포넌트 중 23개에 흩어짐 | `public/global.css` |
| 거대 컴포넌트 — `Detail.svelte` 914줄, `JobPostingItem.svelte` 479줄 (총 ~4,950줄) | `src/view/job_posting/postingId/`, `src/components/jobPostingList/` |
| 테스트 프레임워크 없음 | `careerhub-front/CLAUDE.md` |
| 빌드 산출물을 `sirv`로 **정적 서빙**. 컨테이너 기동 시점에 build | `Dockerfile`, `package.json` |
| 환경변수를 문자열 치환으로 주입 (`__BACKEND_URL_VARIABLE__`) | `src/const.js`, `rollup.config.js` |
| 프론트·API·auth가 **동일 오리진** (`/`, `/api`, `/auth`) | `jyoliar-k8s/gitops/base/services/careerhub/apps/gateway/httproute.yaml` |
| replicas 1, arm64 노드 | `jyoliar-k8s/.../apps/frontend/deployment.yaml` |

**규모는 작다.** ~5,000줄 / 32 컴포넌트 / 12 라우트. 재작성이 비현실적인 크기가 아니다 — 이 사실이 뒤의 마이그레이션 축을 좌우한다.

## 2. 요구를 다시 말한다 — 전제 검증

### ⚠ "GA를 위해 SSR" — 근거가 약하다

GA4는 브라우저에서 도는 클라이언트 태그다. SSR은 GA4 수집의 전제가 아니다. **GA를 지금 망가뜨리는 건 SSR의 부재가 아니라 해시 라우팅이다** — `careerhub.jyo-liar.com/#/job_posting/wanted/123` 에서 `#` 뒤는 **서버로 전송되지 않고**, GA4 기본 `page_view`도 경로를 `/` 하나로 뭉갠다. 12개 라우트가 한 페이지로 보인다.

Google Ads도 마찬가지로, 심사에서 필요한 건 **크롤러가 읽을 수 있는 URL**이지 SSR 그 자체가 아니다.

→ **해시 → history 라우팅**이 GA·Ads가 요구하는 것의 대부분을 준다. SSR은 그 위에 얹는 **별개 결정**이다. 둘을 한 덩어리로 묶으면 큰 쪽(SSR)이 작은 쪽(라우팅)을 인질로 잡는다.

### ⚠ SEO 목표 자체가 위태로울 수 있다

공고 본문은 Wanted·JumpIt에서 **수집한 것**이다(`careerhub-posting-provider`). 원본이 이미 색인돼 있으므로, 같은 본문을 SSR로 뿌리면 구글에는 **중복 콘텐츠**다 — 렌더링을 아무리 잘해도 원본을 이기지 못한다.

careerhub가 원본에 없는 것: **리뷰 점수 결합**(`review-service`), **스킬 추출**(`skillscanner`), **교차 사이트 집계**. SEO 가치가 있다면 거기다.

→ **SSR을 결정하기 전에 "무엇으로 검색에 걸릴 것인가"를 먼저 정해야 한다.** 이게 안 정해지면 SSR은 값을 못 내는 비용이다.

### ⚠ "모바일/PC 다른 디자인 틀"은 SSR과 충돌할 수 있다

서버에서 User-Agent로 분기해 다른 마크업을 주면(dynamic serving) 응답이 UA에 종속돼 **캐시 키가 갈라지고**, 구글도 이 방식을 권장하지 않는다. "다른 틀"의 강도에 따라 SSR 설계가 달라진다 — §4 미결 ①.

## 3. 축 — 무엇이 실제로 갈라지나

"리뉴얼" 하나로 보이던 것은 **최소 6개 축**이다. 공동무효 관계를 따로 적었다.

### A. URL 체계 — 해시 → history

| 옵션 | 되돌리기 | 영향 범위 | 누가 떠안나 |
|---|---|---|---|
| **A0. 안 한다** (해시 유지) | — | SEO·GA 영구 포기. Ads 심사 난항 | 사업 |
| **A1. history 라우팅** | 쉬움 (서버 rewrite 한 줄) | HTTPRoute·정적 서버 fallback 설정 | 인프라 소폭 |
| A2. history + 기존 해시 URL 리다이렉트 | 쉬움 | A1 + 클라이언트 리다이렉트 shim | — |

**one-way door 아니다.** 되돌리는 데 한 시간. → ADR감이 아닐 수 있다. **다른 모든 축의 전제**라는 점에서만 중요하다.

### B. 렌더링 전략 ★one-way door★

라우트별로 요구가 다르다 — `/job_posting/*`만 SEO가 필요하고, `/my/*`·`/admin/*`은 **검색에 걸리면 안 된다**.

| 옵션 | 되돌리기 | 트레이드오프 |
|---|---|---|
| **B0. CSR 유지** + prerender 없음 | — | SEO 0. §2의 "중복 콘텐츠" 우려가 맞다면 잃는 게 없을 수도 |
| **B1. 공개 라우트만 SSR**, 나머지 CSR | 어려움 (프레임워크·인증에 얽힘) | 요구를 정확히 만족. 인증 없이 SSR 가능 → 축 D를 **분리**해준다 |
| **B2. 전면 SSR** | 어려움 | 개인화 헤더까지 서버 렌더 → 축 D가 **강제로 딸려온다**. 캐시 불가 |
| **B3. 공고 상세를 SSG/ISR**로 사전 생성 | 중간 | 공고는 수집 후 거의 안 변함 → 궁합 좋음. 공고 수만큼 빌드 시간·스토리지 |

**★ B1의 값어치**: 로그인 상태를 서버에서 렌더하지 않으면(헤더는 클라이언트에서 채움) **SSR이 토큰을 알 필요가 없다.** 그러면 축 D(인증 재설계)가 이 리뉴얼에서 **빠진다.** 축을 쪼개 얻는 이득의 실례다.

### C. 프레임워크 ★one-way door★

| 옵션 | 되돌리기 | 트레이드오프 |
|---|---|---|
| **C0. 현행 유지** (Svelte 3 + rollup) + 직접 SSR 배선 | — | 라우터·SSR·하이드레이션을 손으로. 홈랩 1인 운영에 지속 불가능 |
| **C1. SvelteKit** | 매우 어려움 | Svelte 지식 보존. Svelte 3→5 마이그레이션 동반. 라우팅·SSR·prerender·env 주입이 전부 내장 → §1의 해킹 3개(`__VARIABLE__` 치환·기동 시 build·sirv)를 한 번에 제거 |
| **C2. Next.js (React)** | 매우 어려움 | 생태계·자료 최대. **32개 컴포넌트 전량 재작성**. GA/Ads 예제가 가장 흔함 |
| **C3. Nuxt (Vue)** | 매우 어려움 | C2와 같은 비용에 생태계는 더 작음 → 굳이? |

**C는 B에 대해 공동무효가 아니다** — SvelteKit을 채택하고도 렌더링 전략은 나중에 갈아탈 수 있다. 별개 ADR이다.

### D. 토큰 저장 ★one-way door · 백엔드 계약 변경★

현재: 토큰이 **JS로 읽히는 쿠키**에 산다(`src/cookie.js`). XSS 한 방에 refresh token까지 털린다 — 이건 리뉴얼과 무관하게 이미 존재하는 부채다.

| 옵션 | 되돌리기 | 트레이드오프 |
|---|---|---|
| **D0. 안 한다** | — | B1을 고르면 SSR과 충돌하지 않는다. 부채는 남는다 |
| **D1. HttpOnly 쿠키** | 어려움 | **auth-service 변경 필요** — 지금은 JSON 바디로만 반환. 동일 오리진이라 배선은 단순 |
| D2. BFF에 세션 | 매우 어려움 | 상태 도입. 홈랩 규모에 과함 |

**★ D는 B2를 고를 때만 강제된다.** B1이면 독립 축으로 남아 **나중에, 따로** 결정할 수 있다.

### E. 반응형 전략 ★one-way door★

요구가 "모바일/PC에 따라 **다른 디자인 틀**"이라 CSS 브레이크포인트로 끝나지 않을 수 있다.

| 옵션 | 되돌리기 | 트레이드오프 |
|---|---|---|
| **E1. 단일 트리 + CSS 반응형** | 쉬움 | 한 벌만 유지. "틀이 다르다"가 레이아웃 수준이면 충분 |
| **E2. 공용 로직 + 분기된 프레젠테이션** | 중간 | 정보구조가 갈릴 때. 컴포넌트 두 벌 유지 |
| **E3. 서버 UA 분기 (dynamic serving)** | 어려움 | 캐시 키 분화, 구글 비권장, B3(SSG)와 충돌 |
| E4. 별도 도메인 (`m.`) | 매우 어려움 | 사실상 앱 두 개 |

**E는 C·B와 얽힌다** — E3는 B3를 죽인다. 하지만 E1↔E2는 프레임워크와 무관하게 뒤집을 수 있다.

### F. 디자인 시스템

"디자인이 임의적"의 실체는 §1이 말해준다 — **토큰이 없다.** 색·간격·타이포가 23개 컴포넌트에 하드코딩돼 있어 일관성을 강제할 지점이 없다.

| 옵션 | 되돌리기 | 트레이드오프 |
|---|---|---|
| **F1. 디자인 토큰만** (CSS 변수) + 손으로 컴포넌트 | 쉬움 | 최소 비용으로 일관성. 컴포넌트는 여전히 직접 |
| **F2. Tailwind** | 중간 | 토큰이 강제됨. 마크업에 스타일이 섞임 |
| **F3. 컴포넌트 라이브러리 채택** | 어려움 | 빠름. 프레임워크 선택(C)에 종속 — Svelte 생태계는 얇다 |

**one-way door 아니다** (F3 제외). → **F는 ADR감이 아닐 가능성이 높다.** 티켓과 코드에 남긴다.

### G. 마이그레이션 경로

| 옵션 | 트레이드오프 |
|---|---|
| **G1. 재작성 (big-bang)** | ~5,000줄이면 가능한 크기. 테스트가 없어(§1) 회귀를 잡을 그물도 없다 → 그물이 없다는 게 오히려 점진 이전의 값을 깎는다 |
| **G2. Strangler — 공개 라우트 먼저, `/admin/*` 나중** | 라우트 단위로 갈라 붙일 수 있다(HTTPRoute path 분기). 두 스택 동시 운영 비용 |

**G는 결정이 아니라 결과일 수 있다** — B·C가 정해지면 대개 따라온다.

## 4. 미결 — 코드가 답하지 않는 것

**채우지 않고 남긴다.** 그럴듯한 기본값을 넣으면 결정이 숨는다.

① **"다른 디자인 틀"의 강도** — 레이아웃만 다른가(E1), 정보구조·기능도 다른가(E2+)? 이게 정해져야 E가 닫힌다.

② **SEO의 목표가 무엇인가** — §2의 중복 콘텐츠 지적이 맞다면, 원본 공고 복제가 아니라 **집계·리뷰 결합**으로 걸려야 한다. 어떤 검색어로 들어오길 원하나? 이게 없으면 B는 값을 못 매긴다.

③ **"리팩토링이 어렵다"의 구체적 사건** — 무엇을 하려다 막혔나? `Detail.svelte` 914줄인가, store 패턴인가, 디자인 일관성인가? 아픔이 특정돼야 성공을 판정할 수 있다.

④ **Svelte를 유지할 이유가 있나** — 취향인가, 이미 아는 것이라서인가? C1과 C2를 가르는 건 기술이 아니라 이 답이다.

⑤ **토큰 부채(D)를 이 리뉴얼에 넣나** — B1이면 안 넣어도 된다. 넣으면 auth-service까지 범위가 커진다.

## 5. 지금까지의 관찰

- **"프론트 리뉴얼" 하나가 아니라 최소 6개 축이고, 대부분 공동무효가 아니다.** 한 ADR로 뭉치면 하나가 뒤집힐 때 전부 죽는다.
- **one-way door는 B·C·D·E 넷.** A·F·G는 되돌리는 데 한 시간 — 티켓과 코드의 관할이다(CLAUDE.md §4②).
- **B1(공개 라우트만 SSR)을 고르면 D가 이 리뉴얼에서 빠진다.** 축을 쪼개서 범위를 줄이는 실례.
- **요구에 들어온 "GA를 위한 SSR"은 SSR을 정당화하지 못한다.** 해시 라우팅 제거가 그 값의 대부분을 준다.

## 6. 1라운드 — 닫힌 것과 뒤집힌 것

### 축 E 닫힘 — "다른 디자인 틀"은 반응형 CSS였다

**답: 레이아웃만 다르다.** 정보구조·기능은 동일.

→ **E1**(단일 컴포넌트 트리 + CSS 반응형). E3(서버 UA 분기)가 죽고, 그와 함께 **§2의 세 번째 우려가 소멸**한다 — 캐시 키 분화도, 구글 비권장 문제도 없다. E는 B·C 어느 쪽과도 충돌하지 않는다.

**E는 ADR감이 아니다.** 되돌리는 데 한 시간이고, 요구가 "레이아웃만"이면 축이 아니라 **구현**이다. → 티켓.

> 요구가 "모바일/PC에 따라 **다른 디자인 틀**"로 들어왔지만 실체는 반응형 CSS였다. 해법의 모양을 한 요구를 문제로 되돌려 물으니 축 하나가 통째로 사라졌다.

### ★ 아픔은 SSR·SEO와 아무 관련이 없다

**답: ① 회귀를 못 잡는다(테스트 전무) ② 스타일이 흩어짐 ③ 거대 컴포넌트.**

셋 다 **CSR로도 해결되는 내부 구조 문제**다. SSR도, SEO도, 프레임워크 교체조차 요구하지 않는다.

→ **이 리뉴얼은 서로 다른 것을 요구하는 두 반쪽이었다:**

| | 아픔 (지금 아프다) | SEO/GA (앞으로 하고 싶다) |
|---|---|---|
| 정체 | 테스트 그물 · 디자인 토큰 · 컴포넌트 분해 | 해시 제거 · 렌더링 전략 |
| 근거 | **확실하다** — 코드가 증명한다(§1) | **미정** — 미결 ②가 안 닫혔다 |
| one-way door | 아니다 | B는 그렇다 |

**두 반쪽을 한 ADR에 담으면 안 된다.** 공동무효가 아니다 — SEO 목표가 뒤집혀도 거대 컴포넌트는 여전히 아프다.

### ★ 의존 순서가 뒤집혔다

들어온 요구의 순서는 *"SSR을 정한다 → 그에 맞는 프레임워크를 고른다"* 였다. 따져보니 **반대다.**

- **C1(SvelteKit) vs C2(Next)는 미결 ②(SEO 목표)와 무관하다** — 둘 다 SSR·SSG를 준다. ②가 가르는 건 **B**(렌더링 전략)이지 C가 아니다.
- **C0(현행 유지)는 ②를 기다릴 것도 없이 이미 밀려났다** — 아픔 ①③(테스트·구조)과 §1의 빌드 해킹 3개가 C0를 죽인다.
- **그런데 C가 안 닫히면 아픔을 고칠 수 없다** — 지금 컴포넌트를 분해하고 테스트를 붙여봐야 C2로 가면 **전량 폐기**다.

→ **C가 병목이다. 그리고 C는 ②가 아니라 ④에 걸려 있다.**

### 축 C — ④를 사실 문제로 좁혔다

C1(Svelte 유지)의 핵심 논거는 "기존 자산 보존"이다. 실제로 얼마나 보존되나 — 세어봤다.

| | 줄 수 | 비중 |
|---|---|---|
| **Svelte 종속** (`.svelte` 4,950 + store 4개 344 + `httputils.js` 158) | **5,452** | **93%** |
| 이식 가능 (순수 JS — `api.js` 11개 ~281, `cookie.js` 53, `utils.js`·`const.js`·`initEvent.js` 17) | 395 | 7% |
| 합계 | 5,847 | |

**★ "Svelte 유지 = 자산 보존"은 사실이 아니다.**

- 93%가 Svelte에 묶여 있고, **그 93%가 바로 아픔 ②③이 지목한 것** — 거대 컴포넌트와 흩어진 스타일. **보존하고 싶지 않은 바로 그것이다.** 어차피 분해하고 다시 스타일링할 거라면 사실상 재작성이다.
- 살아남는 7%(395줄)마저 얇은 `fetch` 래퍼다. 어느 프레임워크로 가든 다시 쓸 만한 분량.
- `cookie.js` 53줄은 축 D(HttpOnly)를 언젠가 하면 어차피 죽는다.

→ **C1의 이점에서 "코드 재사용"이 빠진다. 남는 건 "사람이 Svelte에 익숙한가" 하나다.**

이건 조사로 좁힐 수 없다. **취향·역량·이 앱을 얼마나 오래 끌고 갈 것인가**의 문제이고, 그건 사람이 답한다.

## 7. 다음 라운드 — 미결 갱신

| 미결 | 상태 |
|---|---|
| ① 디자인 틀의 강도 | **닫힘** — 레이아웃만. E1 |
| ② SEO 목표 | **열림 · 조사 필요** — 어떤 검색어에 수요가 있나. **B를 막고 있다.** 별도 Task로 뗀다 |
| ③ 리팩토링의 아픔 | **닫힘** — 테스트·토큰·컴포넌트 분해. SSR과 무관 |
| ④ Svelte 유지 이유 | **열림** — 사실 문제(자산 보존)는 위에서 소거됨. 남은 건 취향·역량. **C를 막고 있고, C가 나머지 전부를 막고 있다** |
| ⑤ 토큰 부채(D) 포함 여부 | 열림 — B1이면 빠진다. B가 닫힌 뒤 |

### ★ B는 C가 닫히면 one-way door가 아니게 된다

§3에서 B(렌더링 전략)를 one-way door로 적었다. **다시 보니 그건 C0(현행 유지 + 직접 배선) 세계에서만 참이다.**

SvelteKit도 Next.js도 **렌더링 전략이 라우트별 설정**이다 — SvelteKit은 `export const ssr` / `prerender`, Next는 라우트 단위 static/dynamic. B0↔B1↔B3 사이를 **플래그로 오간다.**

→ **C를 SSR 가능한 프레임워크로 닫아두면, B는 결정이 아니라 스위치가 된다.** ②(SEO 목표)가 안 닫혀도 리뉴얼이 막히지 않는다. 조사 결과가 나오면 그때 라우트별로 켠다.

**공짜는 아니다.** 나중에 켜려면 처음부터 **SSR-safe 규율**을 지켜야 한다 — 컴포넌트 최상위에서 `window`·`document`·`localStorage`를 만지지 않는 것. 지금 코드는 그 반대다(`src/cookie.js`가 `document.cookie`를 직접 읽고, `httputils.js`가 그 위에 얹혀 있다). **이 규율을 처음부터 지키는 것이 SSR을 나중으로 미루는 값이다.** 미루되 문은 열어둔다.

이 관점에서 **B는 ADR감이 아닐 수 있다** — 플래그를 되돌리는 데 한 시간이면 티켓과 코드의 관할이다(§4②). 남는 진짜 one-way door는 **C 하나**, 그리고 언젠가의 **D**뿐이다.

### 순서

**④ → C → (아픔 작업 + 해시 제거) 착수.** ②는 병렬 조사로 떼고, 결과가 나오면 라우트별로 SSR을 켠다. **②는 더 이상 병목이 아니다.**

## 8. 2라운드 — 수렴

**답: Next.js. 그리고 이 앱을 사업으로 키운다.**

두 답이 서로를 떠받친다 — 수명이 길수록 생태계의 두께가 복리로 값을 내므로, "사업으로 키운다"가 C2의 결정적 근거가 된다. 반대로 "장난감"이었다면 C1(손에 익은 것)이 이겼을 것이다. → **ADR-0011 · ADR-0012 초안으로 넘어갔다.**

### 수렴 신호 점검

- **새 옵션이 더 안 나온다** — C는 네 옵션에서 멈췄고 C0·C3는 근거로 죽었다
- **각 옵션이 어떤 조건에서 이기는지 말할 수 있다** — C1은 "앱의 수명이 짧고 즐거움이 우선일 때" 이긴다. 그 조건이 거짓으로 확정됐다
- **남은 이견(②)이 취향이 아니라 사실 문제로 좁혀졌다** — 논쟁거리가 아니라 조사거리다

### ★ 초안이 판정한 것 — 축 C는 하나가 아니라 둘이었다

첫 초안은 "Next.js 채택 + 전량 재작성"을 **한 문서**에 담았다. 근거는 *"Next를 고르면 재작성이 강제된다(보존 자산 없음)"* 였다. **이 추론이 틀렸다.**

공동무효 테스트가 묻는 것은 그 방향이 아니다 — ***"Next 채택이 뒤집히면 재작성도 반드시 무효가 되는가?"*** **아니다.** Next를 버리고 다른 스택으로 가도 **재작성은 여전히 필요하다.** 보존 자산이 없다는 근거는 스택 선택과 무관하게 성립한다.

첫 초안 안에 반증이 이미 적혀 있었다 — *"잔류하든 이주하든 재작성은 동일하게 발생한다."* 그 문장이 곧 **두 결정이 따로 죽는다는 증거**인데, 묶는 근거로 읽었다. **함의(A면 B다)를 공동무효(A가 죽으면 B도 죽는다)로 착각한 것이다.**

→ 쪼갠다. 관계는 **parent → sub**다:

| | |
|---|---|
| **ADR-0011** 재작성한다 (점진 개선하지 않는다) | 죽으면 → 0012도 죽는다 (안 버릴 거면 스택 선택이 무의미) |
| **ADR-0012** 스택으로 Next.js 채택 · `parent: ADR-0011` | 죽어도 → 0011은 산다 (다른 스택으로 재작성) |

**초안은 판정 도구로 작동했다** — 다만 판정은 초안을 쓸 때가 아니라 **사람이 읽었을 때** 났다. 자기가 쓴 문서의 입도를 자기가 의심하는 데는 한계가 있다.

**나머지 두 점검은 통과했다:**

- **Decision에 수치·리소스명이 비집고 들어오지 않았다** → 코드 관할을 침범하지 않았다(§4①)
- **Alternatives를 각각 채울 수 있었다** → 발산이 충분했다는 신호. 못 채웠다면 초안을 접고 여기로 돌아왔어야 한다
- **ADR-0011의 무효화 조건은 비웠다** — 정직하게 찾지 못했다. 억지로 지어내면 다음 사람이 그 거짓 조건을 근거로 결정을 뒤집는다

### 이 discussion이 남기는 것

**축 6개 중 ADR이 된 건 둘이고, 둘 다 축 C에서 나왔다.**

| 축 | 처분 |
|---|---|
| **C 프레임워크** | → **ADR-0011 · ADR-0012 (proposed)** — 하나로 보였으나 둘이었다 |
| A URL 체계 | Next 채택의 **귀결**. 결정이 소멸했다 |
| B 렌더링 전략 | **스위치로 강등** — C가 닫히자 one-way door가 아니게 됐다. ②의 조사를 기다린다 |
| D 토큰 저장 | **열린 축** — 지금 하지 않는다. 언젠가의 one-way door |
| E 반응형 | **소멸** — "다른 디자인 틀"의 실체는 반응형 CSS였다 |
| F 디자인 토큰 | 티켓 — 아픔이지만 되돌리기 쉽다 |
| G 마이그레이션 경로 | 열린 축 — C를 유지한 채 뒤집을 수 있다 |

**가장 값진 것은 버린 이유다.**

- **"GA를 위해 SSR"은 SSR을 정당화하지 못했다** — GA4는 클라이언트 태그다. 범인은 해시 라우팅이었다. 누가 다시 이 논거를 들고 오면 여기를 보여준다.
- **"Svelte 유지 = 자산 보존"은 실측으로 죽었다** — 93%가 Svelte 종속이고 그 93%가 바로 버리고 싶은 것이었다. 논거가 자기 자신을 무효화했다.
- **"모바일/PC 다른 틀"은 요구의 표현이 해법의 모양을 하고 있던 사례다** — 문제로 되돌려 물으니 축이 통째로 사라졌다.
- **아픔과 요구는 다른 것을 원했다** — 아픔(테스트·토큰·구조)은 SSR을 요구하지 않았고, 요구(SEO/GA)는 아픔과 무관했다. 둘을 한 ADR에 담았다면 SEO 목표가 뒤집힐 때 구조 개선까지 같이 죽었을 것이다.

- **"Next를 고르면 재작성이 강제된다"는 두 결정을 묶는 근거가 아니었다** — 함의는 한 방향이고 공동무효는 양방향이다. 강제된다는 것과 함께 죽는다는 것은 다르다. 이 착각은 ADR을 실제보다 크게 만든다.
