# obs-toolkit 으로 agent 가 트러블슈팅을 얼마나 잘 하나 — 무엇을 재고, 어디서 문제를 내고, 무엇으로 돌리나

## 0. 계기와 문제 다시 말하기

사람이 가져온 것은 "모의 장애를 숨기고 문제를 내서, 정답 개수와 토큰을 센다. 토큰은 구독제 안에서" 다.
방향은 맞다.
다만 그 모양 그대로 돌리면 숫자는 나오되 **그 숫자가 도구에 대해 말해 주는 것이 거의 없다.**
이유를 먼저 적고, 그 위에서 옵션을 벌린다.

**지금 치르고 있는 비용은 "측정이 없다" 가 아니라 "피드백 없이 설계 결정이 쌓인다" 다.**
#97 은 조사 순서를 **고정**했다(범위 → RED → 로그 분포 → 템플릿 → 트레이스 경로).
Finding 규칙은 "신호 둘 이상 일치 → high" 로 confidence 를 정했다.
`Budget` 은 질의 횟수와 응답 바이트에 상한을 건다(`obs/core.py` L434–449).
셋 다 직관에서 나왔고, 셋 다 "agent 가 그걸로 더 잘 맞히나" 를 확인한 적이 없다.
#92 의 AC 중 agent 출력에 관한 것은 *"Finding 만 남는 것을 사람이 확인"* 하나뿐이다 — 격리의 확인이지 품질의 확인이 아니다.
측정의 목적은 "점수" 가 아니라 **이 결정들에 피드백을 다는 것**이다.

그러면 문제는 하나가 아니라 셋으로 갈린다.

| 묻는 것 | 누가 답하나 | 지금 있나 |
|---|---|---|
| **환원 연산이 옳은 숫자를 내나** | 결정론 — `tests/contracts/` · #97 `correlations` 테스트 | 있다(#105) |
| **agent 가 도구를 제대로 쓰고 환원물을 옳게 읽나** | 실행해 봐야 안다 — **이 논의** | 없다 |
| **모델 자체가 얼마나 똑똑한가** | 우리 것이 아니다 | — |

두 번째 줄만 이 논의의 것이다.
세 번째를 두 번째와 섞으면 "7/10" 이 도구의 점수인지 Claude 의 점수인지 모른다.
**가르는 방법은 하나 — 같은 문제를 도구 없이(또는 덜 갖추고) 풀게 하고 차이를 본다.**
도구의 성능은 절대 점수가 아니라 **층 기여** 다 — 한 층을 더했을 때 바로 아래 arm 보다 **얼마나 더 맞혔나**(§3).

## 1. 실측 — 지금 무엇이 있나

`workspace/ref/obs-toolkit` HEAD `37a8070`, `jyoliar-k8s`, 그리고 클러스터(읽기 전용 SA)를 읽었다.

- **도구는 반쯤 있다.** logs(#94) · metrics(#95) 환원과 `obs-query` 스킬은 있고, traces(#96) · `investigate_bundle`(#97) · `red`(#102) · 하네스 도입(#98)은 열려 있다.
  지금 측정하면 측정되는 것은 **`obs-query` 만 가진 agent** 다.
  이건 결함이 아니라 기회다 — 지금 재 두면 #97 이 들어온 뒤의 층 기여 가 곧 #97 의 가치다(§3 arm B → C).
- **fixture 녹화·replay 인프라가 있다**(`tests/record.py` · `tests/replay.py`).
  단, replay 는 *"나간 요청 == 녹화 요청"* 을 호출마다 검사한다 — 정해진 질의 열을 되감는 장치지, 자유 탐색하는 agent 에게 데이터를 주는 장치가 아니다.
  그대로는 시나리오 재생에 못 쓴다(§4 S3).
- **문제를 낼 자리.** `careerhub-dev` 네임스페이스는 있으나 `kubectl get deploy,sts -n careerhub-dev` 에 뜨는 것은 mongodb 둘뿐이다 — 앱은 **prod 에만** 산다(10 deploy · 2 sts).
  **사람의 답(10-03): prod 는 지금 외부에 제공되지 않는 상태이고, 장애를 주입해도 무방하다.**
  그러면 "모의 환경" 은 곧 prod 이고, dev 에 앱을 띄우는 선행은 없다.
  남는 부작용은 둘 — 알럿이 Discord 로 가는 것과 실제 관측 데이터에 가짜 장애가 섞이는 것(S2 의 실제 장애와 구분하려면 주입 창을 truth 에 기록해야 한다).
- **장애 주입 도구가 없다.** `jyoliar-k8s` · `onpremise-k8s` 에 chaos·litmus·toxiproxy 는 한 줄도 없다.
  주입은 `kubectl`·GitOps 변경이 될 것이고, **agent 의 SA 는 읽기 전용이라 주입은 언제나 사람이 한다**(CLAUDE.md §6).
- **데이터 수명.** Prometheus `retention: 30d`(`overlays/baremetal/controllers/prometheus-operator/application-patch.yaml:43`) · Loki `retention_period: 168h`(`base/controllers/loki/application.yaml:37`) · Tempo `retention: 72h`(`base/controllers/tempo/application.yaml:22`).
  실환경에 심은 시나리오는 **트레이스 기준 3일이면 죽는다.**
- **실제 장애 재고.** Bug 티켓 #24(TSDB 디스크 고갈) · #25(kubelet_volume_stats 부재) · #83(vip-watcher crashloop) · #100(Alloy 메모리) · #80(CoreDNS) · #82(zitadel-helm) — 원인이 확정된 사례 여섯.
  전부 retention 밖이라 데이터는 없다.
  앞으로의 장애는 생기는 즉시 문제가 될 수 있다(§4 S2).
- **구독제 경로.** `260817_1512` 가 이미 답했다 — 구독으로 돌릴 수 있는 프로그래머블 경로는 `claude -p`(+ `CLAUDE_CODE_OAUTH_TOKEN`) 뿐이고 Agent SDK 는 API 키 필수(정책).
  거기에 하나가 더 있다 — **`claude plugin eval`** 도 구독 인증으로 돈다(§5 R1).

## 2. 무엇을 재나 — "정답 개수 · 토큰" 을 벌린다

트러블슈팅의 답은 O/X 가 아니다.
Finding 계약(#97)이 이미 claim · evidence · signals · confidence · next_check 로 갈라 뒀으니, 채점도 그 축으로 간다.

| 축 | 무엇 | 어떻게 재나 | 왜 |
|---|---|---|---|
| **국소화** | 원인 컴포넌트(service · pod · 노드)를 맞혔나 | truth 와 문자열 대조 — 기계 | 사람이 "정답" 이라 부르는 것의 실체 |
| **시각** | 변화 시각을 허용 오차 안에 짚었나 | truth 의 주입 시각 ± 허용 — 기계 | #97 `correlations` 의 ±2분과 같은 축 |
| **근거 재실행** | evidence 의 질의·창을 다시 돌리면 같은 값이 나오나 | `manifest.json` 재실행 — 기계 | 근거 없는 claim 은 low 로 강등하는 규칙의 검증 |
| **보정(calibration)** | high 라고 한 것이 맞고, 모를 때 low·판정 불가 라고 했나 | confidence × 정오 2×2 표 | **틀린 high 가 최악**이다 — 티켓 코멘트에 박혀 사람이 믿는다 |
| **무장애 대조** | 아무것도 없는 창에서 "없다" 고 했나 | clean 시나리오 — 기계 | 항상 뭔가를 찾는 도구는 쓸모없다 |
| **비용** | 토큰 · 질의 횟수 · 턴 · 벽시계 | `claude -p --output-format json` 의 `usage` · `modelUsage` · `num_turns` · `duration_ms`(§5-1 실측), `Budget` 카운터 | 사람이 낸 축. 구독이라도 `total_cost_usd` 는 정가 추정(`costBasis: list`)으로 찍힌다 — **과금은 안 돼도 비교값으로는 쓸 수 있다** |
| **구독 창 소모** | 플랜 한도의 몇 % 를 썼나 | stream-json 의 `rate_limit_event` 가 `unifiedWindows.five_hour.utilization` · `seven_day.utilization` 을 낸다(§5-1) — 실행 전후 차 | 사람이 가장 묻는 것. 해상도가 소수 둘째 자리라 **라운드 단위**로 잰다 |
| **오염** | 주 대화에 남은 토큰 vs subagent 에서 쓴 토큰 | `usage`(주 컨텍스트만) 와 `modelUsage`(subagent 포함 전체) 의 차 — §5-1 에서 실측으로 확인 | #92 가 가장 신경 쓴 것. 지금은 "전사 눈으로 확인" 뿐이었다 |
| **분산** | 같은 문제를 3회 돌렸을 때 흔들림 | runs ≥ 3, 평균과 pass@k 둘 다 | 1회 점수는 운이다. `plugin eval` 기본값이 3 인 이유 |

점수는 **비대칭**이어야 한다.
"모르겠다"(판정 불가) 는 0점이지 감점이 아니고, "틀린 high" 는 감점이다.
그래야 도구가 agent 를 **모를 때 멈추는 쪽**으로 민다 — `finding.md` 의 규칙이 그것이다.

truth 는 시나리오마다 파일 하나다 — 원인 컴포넌트 · 종류 · 주입 시각 · 주장하면 안 되는 것 · clean 여부.
사람이 쓴다 — 주입한 사람이 곧 truth 를 아는 사람이다.

## 3. arm — 도구의 점수는 층 기여다

| arm | agent 가 가진 것 | 뜻 |
|---|---|---|
| **A 맨손** | `kubectl`(읽기 SA) + Grafana 프록시에 `curl` 로 직접 PromQL·LogQL | 도구 없음. 모델의 바닥 |
| **B 조회** | A + `obs-query`(지금 있는 것) | 환원 연산의 층 기여 — B 가 A 보다 더 맞힌 만큼 |
| **C 조사** | B + `obs-investigate`(#97 · #98 뒤) | 고정 순서 번들의 층 기여 — C 가 B 보다 더 맞힌 만큼 |

A 가 없으면 B 의 점수는 해석할 수 없다.
C 가 B 보다 못하면 #97 의 고정 순서가 틀린 것이고, 그것은 **측정이 설계에 피드백을 준 첫 사례**가 된다.
`claude plugin eval` 은 with/without 두 arm 을 내장하고 `delta` 를 보고에 넣는다(§5) — A 와 B 의 짝이 그대로다.

## 4. 어디서 문제를 내나 — 시나리오 원천

### 비교 축

- **재생 가능성** — 같은 문제를 다음 달에, 도구가 바뀐 뒤에 다시 낼 수 있나. 측정의 가치는 한 번이 아니라 **반복**에서 나온다(#96 · #97 · #102 가 아직 열려 있다).
- **진실성** — 데이터가 실제 스택이 내는 모양인가. 손으로 만든 데이터는 고정 순서 파이프라인이 "맞게" 설계된 모양 그대로라 **순환 검증**이 된다.
- **사람 비용** — 문제 하나를 내는 데 사람이 얼마나 드나.
- **부작용** — prod 사용자 · Discord 알럿 · 실제 관측 데이터 오염.
- **되돌리기** — 그만두면 무엇이 남나.

### 옵션

| | 원천 | 재생 | 진실성 | 사람 비용 | 부작용 | 메모 |
|---|---|---|---|---|---|---|
| **S0 안 잰다** | 실제 장애 때 써 보고 코멘트에 감상 | — | 최고 | 0 | 0 | 피드백은 있으되 **비교 불가** · 기준선 없음 · 다음 장애까지 기다림 |
| **S1 실환경 주입**(사람의 안) | prod 에 사람이 고장을 심는다 — bad image tag · env 깨기 · limit 조이기(OOM) · NetworkPolicy 차단 · DB 자격 회전 · replicas 0 | **낮다** — 트레이스 72h | 최고 | 건당 10–30분 + 복구 | **작다** — prod 가 외부 제공 중이 아니다(사람의 답). 남는 것은 Discord 알럿과 관측 데이터의 가짜 장애 | 가장 싼 첫 라운드 |
| **S2 실제 장애 재생** | 장애가 나면 retention 안에 그 창을 문제로 등록. truth = Bug 티켓·postmortem | 낮다(같은 72h) | 최고 | 거의 0(이미 조사했다) | 0 | 횟수를 못 정한다. 다만 **공짜**라 S1·S3 와 겹쳐 항상 켜 둘 가치가 있다 |
| **S3 스냅샷 재생** | 주입 또는 실제 장애 창의 백엔드 데이터를 떠서 로컬 Prometheus·Loki·Tempo 에 올린다 | **높다** — 영구 · CI 가능 | 높다(원본) | 초기 구축이 크다 · 건당은 작다 | 0 | Prometheus 는 TSDB snapshot API 가 있다. Loki·Tempo 는 청크를 복사해 로컬에 올려야 하고 **해 본 적 없다** — 스파이크 거리 |
| **S4 합성** | 설계한 장애 모양의 시계열·로그·span 을 생성해 로컬 백엔드에 push | 최고 | **낮다** — 순환 검증 위험 | 건당 중간 | 0 | 시작 환경으로는 가장 싸다. 단독으로는 안 된다 |

### 판정

- **S0 은 버린다.** 기준선 없는 감상은 §0 의 비용을 그대로 둔다. 다만 S2 는 S0 의 좋은 부분(진짜 장애)을 공짜로 가져오니 **항상 켠다**.
- **S1 은 prod 에서 한다.** 처음엔 "prod 엔 안 한다" 고 썼으나 사람이 prod 가 외부 제공 중이 아니라고 답했다 — 선행(dev 앱 기동)이 사라지고 S1 이 바로 **첫 라운드**다.
  주입 창은 truth 에 기록한다 — S2 의 실제 장애와 섞이지 않게.
- **S3 는 두 번째 라운드다.** S1 의 72h 수명이 처음 아프게 느껴지는 순간(두 번째로 같은 문제를 내고 싶을 때)이 착수 시점이다.
  지금 짓는 것은 투기다.
- **S4 는 S3 가 어려운 백엔드(Tempo)에만** 보조로.

제안 — **S1(prod) + S2 로 시작, S3 는 아프면.**
첫 코퍼스는 작다 — 주입 3 + clean 1.
넷으로 arm A·B 의 층 기여 를 처음 본다.

### 판정

R1 과 R2 는 경쟁이 아니라 **층**이다.
R1 은 "도구가 있을 때 없을 때" 를 싸게 반복하는 자리이고, R2 는 Finding 계약을 기계로 채점하는 자리다.
그러나 R1 의 미확인 둘(토큰 주입 · 네트워크)은 **막히면 R1 전체가 죽는** 종류다.
그래서 첫 Task 는 둘 다를 **문제 하나**로 돌려 보는 스파이크다 — 결과가 R1 을 살리면 두 층, 죽이면 R2 하나.

### 5-1. 구독제로 토큰을 잴 수 있나 — 실측 (2026-10-03)

사람이 가장 먼저 물은 것이라 문서로 답하지 않고 돌려 봤다.
이 머신의 로그인은 `claude auth status` 로 `authMethod: claude.ai` · `subscriptionType: max` — API 키 없음.
Claude Code 2.1.288, 빈 디렉터리에서 `claude -p … --output-format json` 세 번(한 턴 · Bash 한 번 · subagent 한 번).

**된다. 공식 문서보다 많이 나온다.**

| 필드 | 값(subagent 프로브) | 뜻 |
|---|---|---|
| `usage.input_tokens` · `output_tokens` · `cache_creation_input_tokens` · `cache_read_input_tokens` | 34 · 166 · 12,293 · 32,550 | **주 컨텍스트**의 토큰 |
| `modelUsage.<model>.{inputTokens, outputTokens, cacheCreationInputTokens, cacheReadInputTokens, costUSD, costBasis}` | 36 · 171 · 25,810 · 32,550 · $0.43 · `list` | **subagent 까지 합친 전체**. `usage` 와의 차가 곧 subagent 몫 — 오염 축(§2)이 공짜로 나온다 |
| `total_cost_usd` | $0.43 | 정가 추정. 구독이라 청구되진 않으나 **비교값**으로 유효 |
| `num_turns` · `duration_ms` · `duration_api_ms` | 2 · — | 문서에 없다고 보고됐으나 있다 |
| `subagent_stats.{spawned, completed, max_depth, by_type}` | 1 · 1 · 1 · `general-purpose: 1` | subagent 호출 수 |
| stream-json `rate_limit_event.rate_limit_info.unifiedWindows.{five_hour, seven_day}.utilization` | 0.12 · 0.30 | **구독 창 소모율** — 사람이 물은 바로 그 숫자. 한 세션 안에서도 여러 번 온다 |

쓰는 법은 단순하다 — 세션 전후의 `utilization` 차로 플랜 소모를, `usage`/`modelUsage` 로 토큰을, `costUSD` 로 비교 단가를 적는다.
`utilization` 은 소수 둘째 자리라 세션 하나의 차는 0 으로 보일 수 있다 — 라운드(세션 24개) 단위로 읽는다.

주의 둘.

- **세션마다 시스템 프롬프트 cache write 약 11.8k 토큰**이 고정비로 붙는다(`cache_creation.ephemeral_1h_input_tokens`). 한 턴짜리 프로브도 $0.24 였다. 문제당 비용을 비교할 때 이 상수를 빼고 봐야 도구의 차가 보인다.
- 프로브는 빈 디렉터리였다. 평가 세션은 플러그인 + 홈랩 접근이 있어 고정비가 더 크다 — 스파이크가 그 값을 잰다.

`claude plugin eval --help`(같은 버전) 도 읽었다.
각 run 은 "a full claude child on your own credential" 이라 같은 한도를 나눠 쓰고, `--json` 이 run 별 점수를 내며, `--ablation with-without` 이 기본이라 §3 의 arm A/B 가 플래그 하나다.
다만 보고에 `utilization` 이 실리는지는 **미확인** — 필요하면 R1 바깥에서 전후로 한 번씩 `claude -p` 를 돌려 읽는다.

### 구독 예산

`claude -p` · `plugin eval` 둘 다 플랜 한도에서 소비된다.
한 문제의 비용은 모른다 — 스파이크가 처음 잰다.
어림만: 문제 4 × arm 2 × runs 3 = 24 세션이고, 조사 한 세션이 수만~수십만 토큰이면 한 라운드가 플랜의 시간 창 하나를 **다 쓸 수 있다.**
`llm` · `baseline` grader 는 추가 토큰이다 — 심판은 `--judge-model` 로 작은 모델을 쓰고, 기계 채점이 되는 축은 `regex` 로 간다.
`--max-cost-usd` 는 정가 추정 기준이라도 **중단 장치**로는 동작한다.
한 라운드가 한 창에 안 들어가면 runs 를 1 로 낮추고 분산은 포기한다 — 그 순서로 깎는다.

## 6. 외부 선례 — 기억에서 끌어왔고 **검증하지 않았다**

- 확인은 스파이크 Task 의 References 에 넣는 일이지 이 문서의 일이 아니다.
