# obs-toolkit 테스트 지우기 — "불필요한 테스트" 의 객관적 기준과 지운 뒤의 증명

## 1. 문제

부모 논의 `261019_1623` 은 ③ 테스트 리팩토링을 "경계 위에서 다시 세운다" 로 그렸고, 그 초안(`tmp/github-issues/obs-toolkit-test-refactor.md`)은 삭제 · 병합 · 재배치를 모듈 단위 제안 하나에 묶었다.
어댑터 쪽 선행 셋(#128 · #129 · #131)이 끝나 ③ 의 자리가 왔다.
사람은 재편에 앞서 **지우기만 먼저** 하기를 원한다 — 재편 전에 읽을 양을 줄이고, 소스를 건드리지 않는 가장 안전한 첫걸음이며, 다음 티켓마다 기존 테스트가 함께 갈리는 churn 을 먼저 걷어내기 위해서다.

그러면 두 질문이 남는다.
"불필요한 테스트" 를 무엇으로 판정하나 — 사람의 인상이 아니라 두 사람이 같은 답을 내는 기준이어야 한다.
지운 뒤 "검증에 문제가 없다" 를 무엇으로 보이나 — 점수 한 줄이 아니라 무엇을 잃지 않았는지가 보여야 한다.

열려 있던 것은 넷이었다 — 지우기의 티어 범위, 증명의 강도, 지우기와 재편의 경계(순수 삭제인가 대체를 쓰나), 그리고 산출물의 모양(티켓 · 코멘트 · 규칙).
넷은 인터뷰에서 닫혔다(§3).
남은 것은 **사전 기준의 부류** — 무엇을 후보로 골라내나 — 와 **대조 루프의 입도**이고, 둘은 코드와 측정 사실에 기대므로 열린 축이다(§4).

## 2. 실측

코드는 `workspace/ref/obs-toolkit`, HEAD `31e7768`(#131 머지 · 2026-10-24) 기준이다.
측정 수치는 #131 완료 보고(https://github.com/jyoliar-lab/ops-workflow/issues/131#issuecomment-6381289373)에서 옮겼다.

**기준선과 비용**

- 기준선 — total 6630 · killed 5896 · survived 715 · no tests 19 · killed/total 88.93 % · 문장 커버리지 97.9 %(2095 stmts).
- 변이 사본(`mutants/`)과 변이 내용 단위 대조 스크립트(`tmp/t131/reconcile.py` · 보고의 zip 첨부)가 남아 있다 — 다음 측정의 입력이다.
- 병렬 측정이 **138 s** 다(#130 이 가짜 killed 를 고친 뒤). 기준선을 단일 워커로 다시 만들면 812 s 다. 모듈마다 다시 재는 것이 비용상 가능해졌다.
- mutation 의 테스트 선택은 **contracts · format 두 티어**다(`pyproject.toml` `[tool.mutmut]` · README). infra 티어는 하네스 검사라 변이 소스를 지나지 않는다 — infra 테스트의 가치는 mutation 으로 잴 수 없다.

**지우기가 killed 를 잃은 실례 — #131**

- `test_main_call_directory_named_by_at` 하나를 지웠더니 `promql_run` 즉시 조회의 kind 문구 변이 3 이 killed → survived 로 돌아섰다.
  그 테스트는 디렉터리 이름 전체(`…Z-promql`)를 단언해 시각과 함께 kind 배선도 보고 있었는데, 지운 쪽은 시각만 보았다.
- 점수는 89.00 → 88.93 % 로 거의 같았고, 잡은 것은 변이 내용 단위 대조의 "killed → survived 3" 행이다.
- 같은 보고에서 "같은 변이 그대로 생존 675 · 사라진 변이 3 · 새 변이 1" 이 함께 읽혔다 — 점수가 아니라 집합의 이동이 지우기의 효과를 말한다.

**killed 집합 불변은 스위트의 성질이다**

- 같은 약속을 보는 테스트 A · B 가 있으면 A 만 지워도 killed 가 그대로이고 B 만 지워도 그대로이지만, 둘을 함께 지우면 빠진다.
- 그래서 "이 테스트는 불필요하다" 는 단독으로 증명되지 않는다 — 증명되는 것은 "이 **삭제 묶음**은 killed 를 잃지 않았다" 이고, 마지막에 전체 한 번은 반드시 돈다.

## 3. 인터뷰에서 닫힌 축

### 3-1. 왜 지우기를 먼저 두나

**선택: 셋 다 — 재편 전에 읽을 양을 줄인다 · 소스를 건드리지 않는 가장 안전한 첫걸음이다 · 다음 티켓에서 기존 테스트가 함께 갈리는 churn 을 먼저 걷어낸다.** 지우기가 끝나면 모듈 제안 코멘트가 다루는 대상 자체가 작아지고, 전 · 후 대조 절차를 소스 변경 없는 자리에서 먼저 익힌다. (인터뷰, 2026-10-24)

<details><summary>버린 안</summary>

- PR 검수 시간 단독 — 지우기만으로 줄어드는 것은 아니다. 재편까지 가야 "무엇이 약속인지 보이는" 상태가 된다.

</details>

### 3-2. 범위 — contracts + format

**선택: mutation 측정이 보는 두 티어, contracts 와 format.** infra 는 이번에 지우지 않는다 — 변별력을 잴 도구가 없어 §3-3 의 증명이 서지 않는다. infra 481 단언의 가치는 ③ 재편의 모듈 제안에서 다른 기준으로 다룬다. (인터뷰, 2026-10-24)

<details><summary>버린 안</summary>

- contracts 만 — `--help` 33 항목 · format 이 contracts 를 다시 보는 2 가 format 에 있다. 두 티어가 같은 약속을 나눠 들고 있어 한쪽만 보면 중복이 보이지 않는다.
- 세 티어 전부 — infra 는 mutation 밖이라 "지워도 됐다" 를 같은 방식으로 증명할 수 없다. 기준이 티어마다 갈려 한 Task 에 두 종류의 증명이 든다.

</details>

### 3-3. 증명의 강도 — killed 집합 불변

**선택: 변이 내용 단위로 killed → survived 가 0 건.** 점수가 같아도 집합이 움직였으면 지우기가 무언가를 잃은 것이다 — #131 의 회귀 3 이 그 실례다. 문구 변이(문자열 리터럴)의 손실도 손실로 친다 — 어느 변이가 "문구라서 괜찮다" 인지는 이 Task 가 아니라 ③ 의 생존 분류가 정한다. 대조는 삭제 묶음 단위이고, 마지막 전체 대조 한 번이 필수다(§2). (인터뷰, 2026-10-24)

<details><summary>버린 안</summary>

- 문구 변이 손실 허용 — 허용선이 생기면 "이건 문구다" 판정이 지우기 안에 들어와 기준이 둘이 된다. 지우기는 기준 하나로 간다.
- 점수 · 커버리지가 낮지 않으면 충분 — #131 이 보였듯 점수는 0.07 pt 차이로 회귀 3 을 가린다.

</details>

### 3-4. 지우기와 재편의 경계 — 순수 삭제만

**선택: 이 Task 는 삭제만 한다. 지우려는 테스트가 어느 mutant 의 유일한 killer 라 §3-3 에 걸리면 복구해 남기고, "지우면 X 를 잃는다" 를 기록한다.** 그 성질을 경계 위의 한 테스트로 옮기는 일은 ③ 재편의 것이다. 범위가 가장 좁고 되돌리기 쉽다. (인터뷰, 2026-10-24)

<details><summary>버린 안</summary>

- 걸리면 경계 위에 대체 테스트를 쓴다 — 지우기와 재편이 섞이고, 새 테스트가 생겨 검수 대상이 늘어난다. 3-1 의 "읽을 양을 줄인다" 와 어긋난다.
- 모듈 제안 코멘트에서 건별 판정 — 유연하지만 승인 항목이 많아진다. 기준 하나(killed 불변)로 기계가 가를 수 있는 것을 사람에게 되묻는다.

</details>

### 3-5. 산출물 — 지우기 Task 하나와 판정 기준 코멘트

**선택: ③ 초안과 별개로 지우기 Task 를 먼저 낸다. 완료 보고에 "불필요한 테스트" 의 판정 기준을 남기고, 사람이 그것을 읽어 추후 ticket-engineer 의 tdd-loop 규칙으로 증류한다.** 저장소 규칙 · 메타테스트에 지금 박지 않는다 — 기준이 증거 위에 선 뒤의 일이다(CLAUDE.md §6 — 티켓 코멘트는 원자료, 규칙은 증류물). (인터뷰, 2026-10-24)

<details><summary>버린 안</summary>

- ③ 초안의 첫 단계로 흡수 — 한 티켓이지만 "지우기만의 증명" 과 "재편의 증명" 이 한 완료 보고에 섞인다. 지우기의 효과를 따로 읽을 수 없다.
- 기준을 지금 저장소 규칙으로 — 아직 사례가 없다. 규칙이 먼저 서면 지우기가 규칙을 맞추는 일이 된다.

</details>

### 3-6. 코멘트의 모양 — 기준 목록 + 삭제 장부 + 남긴 사례

**선택: 셋을 한 코멘트에 둔다.** ① 기준 목록 — 부류마다 뜻 · 판별법. ② 삭제 장부 — 지운 테스트마다 이름 · 적용한 기준 · 속한 삭제 묶음. 묶음마다 killed 대조 결과 한 줄. ③ 남긴 사례 — 기준에 걸렸지만 §3-3 에 걸려 남긴 테스트와 "지우면 빠지는 변이". ③ 이 없으면 뒷날의 규칙이 "이 패턴은 지운다" 로만 쓰여 과하게 지운다 — #131 의 at 단언이 kind 배선을 겸하고 있던 것이 그 예다. (채팅, 2026-10-24)

<details><summary>버린 안</summary>

- 기준 목록만 — 어느 테스트에서 그 기준이 나왔는지 따라갈 수 없다.
- 기준 목록 + 장부만 — "지워도 됐다" 만 남고 "지우면 안 됐다" 가 없다. 규칙의 예외 조건이 비어 간다.

</details>

## 4. 열린 축 — 논의

### 4-1. 사전 기준의 부류 — 무엇을 삭제 후보로 골라내나

§3-3 은 지운 **뒤**의 증명이다.
무엇을 지워 볼지 고르는 **사전** 기준이 따로 있어야 작업자가 359 + 48 함수를 하나씩 지워 보지 않는다.
후보 부류는 §2 의 표에서 나왔다.
부류마다 뜻 · 판별법 · 예시 · killed 집합에 미칠 영향의 예상을 적는다.
판정은 "어느 부류를 이 Task 의 후보로 삼나" 다 — 여러 개를 고를 수 있다.

**A. 동어반복 · 단언 없음** — 어떤 구현에서도 거짓이 될 수 없는 문장.

- 뜻 — 테스트가 비교하는 양쪽이 같은 코드에서 나오거나, 아무것도 비교하지 않는다.
- 판별법 — (a) `assert X == f(…)` 에서 `f` 가 `X` 를 만든 바로 그 함수다 · (b) 함수 본문에 `assert` · `pytest.raises` · `assert_snapshot` 이 없다 · (c) 상수를 그 상수의 리터럴과 비교한다.
- 예시 — `assert _params(t.calls[0])["query"] == metrics.summarize_query(CPU_QUERY, W, "60s")`(`test_metrics.py:447`) · `json.loads(to_json(_run(client, op)))`(`test_metrics.py:437`, 예외만 안 나면 통과) · `assert metrics.DEFAULT_BASELINE == "1d"`(`test_metrics.py:135`).
- killed 영향 예상 — 거의 없다. (a) 는 조립 함수의 변이를 양쪽이 같이 받아 못 잡고, (b) 는 예외 변이만 잡는다. 단, (b) 의 `_no_physical` 호출형 둘은 헬퍼 안에서 `assert` 하므로 단언 없음이 아니다 — 판별법 (b) 는 헬퍼 안의 assert 를 세야 한다.
- 수량 — 13 + 3 + 1 = 17 단언 · 그중 테스트 함수 전체가 지워지는 것은 소수(동어반복 단언은 대개 다른 단언과 한 함수에 있다 — 단언만 지우면 함수가 남는다).

**B. 인자 → 필드 통과 단언** — 넣은 값이 그대로 나왔다는 단언.

- 뜻 — `k=2` 를 넘기고 결과의 `.k == 2` 를 본다. 계산이 아니라 대입을 검사한다.
- 판별법 — 단언의 우변이 호출 인자에 쓴 리터럴과 같고, 좌변이 결과 dataclass 의 같은 이름 필드다.
- 예시 — `assert ev.value.k == 2`(`test_traces.py:538`) · `assert v.limit == 2`(`test_logs.py:528`).
- killed 영향 예상 — **있을 수 있다.** #129 가 `k=` · `limit=` 인자 제거 변이 16 을 죽인 행이 바로 이 꼴이다(`test_metrics_run_top_passes_k_and_by` 등). 통과 단언이 "인자가 core 에 닿는다" 는 배선의 유일한 증거인 자리가 있다.
- 수량 — 7.

### 4-2. 대조 루프의 입도 — 언제 다시 재나

실측 — 전체 측정이 138 s 다. mutmut 은 바뀐 함수의 mutant 만 다시 돌리는 증분 실행과 이름 패턴 실행(`mutmut run "obs.core.x_load_config*"`)을 지원한다(README). 그러나 테스트를 지웠을 때 어느 mutant 를 다시 재야 하는지는 "그 테스트가 지나던 함수" 로 좁힐 수 있고, 그 표가 어디 있는지는 4-1 F 의 확인 사항과 같다.

- **A. 삭제 묶음(모듈)마다 전체 재측정 + 변이 내용 대조** — 묶음마다 138 s 와 `reconcile.py` 한 번. 가장 단순하고 증명이 묶음 단위로 선다 / 묶음 수만큼 측정 코멘트가 쌓인다.
- B. 영향 함수만 재측정 — 지운 테스트가 지나던 함수의 mutant 만 패턴으로 다시 돈다. 빠르다 / "지나던 함수" 표를 먼저 확보해야 하고, 패턴 실행의 결과를 전체 기준선과 합치는 절차가 든다. 마지막 전체 한 번은 어쨌든 필요하다.
- C. 끝에 한 번 — 전부 지운 뒤 한 번 대조. 가장 싸다 / 회귀가 나오면 어느 묶음이 잃었는지 이분 탐색해야 한다. §3-6 의 장부가 "묶음마다 대조 결과" 를 요구하므로 C 로는 장부를 채울 수 없다.

**판정(사람, 2026-10-24): A — 다만 묶음은 모듈이 아니라 삭제 기준(4-1 의 부류)이다.** 기준마다 선별 → 제거 → 전체 재측정 → killed → survived 를 낳은 테스트 복구 → 재측정(회귀 0 까지) → 코멘트(제거 목록 · 복구 목록) → 다음 기준.

절차의 제약 — 판정에서 따라오는 것.

- 재측정은 누적이다 — 매 측정은 "지금까지 지운 전부" 위에서 돈다. 앞 기준에서 지운 A 와 이번 기준의 B 가 같은 변이를 나눠 들고 있었다면 회귀는 이번에 보이고, 복구는 이번 묶음의 B 다. 그래서 마지막 측정이 곧 전체 대조이고 따로 한 번 더 돌 필요가 없다.
- 복구의 단위는 테스트 함수다. 회귀한 변이의 함수 이름으로 그 함수를 지나던 삭제 테스트를 고르고, 둘 이상이면 전부 복구한 뒤 하나씩 다시 지워 본다.
- 기준의 순서는 싼 것부터다 — A(17 단언) → B(7) → C → E → D(81 사이트). D 는 복구가 가장 많이 나올 자리라 마지막에 두면 앞 기준의 삭제가 D 의 측정에 섞이는 양이 적다.
- E 는 전부 복구될 것이 §2 에서 이미 보인다 — 한 번의 측정으로 "남긴 사례" 가 되는 셈이고, 그 비용(138 s)은 받아들인다.

## 5. 반대편 — 이 설계가 틀리는 조건

- killed 집합 불변은 mutmut 이 만든 변이에 대한 불변이다. 변이가 겨냥하지 않는 결함(동시성 · 외부 응답의 형태 변화 · 성능)을 잡던 테스트는 지워도 집합이 그대로다. mutation 이 표본인 한 "잃지 않았다" 는 표본 안에서의 말이다.
- 같은 변이를 죽이는 두 테스트 가운데 하나를 지울 때, 남는 쪽이 실패 메시지의 국소성이 나쁜 쪽(연산 층 · Given 이 큰 쪽)이면 변별력은 같아도 진단 시간이 늘어난다. 어느 쪽을 남기나는 killed 가 아니라 부모 3-1 의 경계 표가 정해야 한다.
- 지우기를 재편보다 먼저 하면 D 부류(경계 아래 단언)는 대부분 남는다. 지우기가 끝난 뒤에도 contracts 의 `*_lines` 32 · 조립기 49 가 그대로라 "읽을 양" 의 감소가 기대보다 작을 수 있다.
- §3-3 이 문구 변이 손실도 손실로 치므로, 한국어 안내 문구 하나를 유일하게 보는 테스트는 지울 수 없다. 그런 테스트가 많으면 지우기의 산출이 작고, ③ 의 생존 분류(문구 · 선언 예외)가 먼저 와야 했던 것이다.
- 코멘트의 기준 목록이 tdd-loop 규칙으로 갈 때, 규칙은 "지우기" 가 아니라 "쓰지 않기" 의 규칙이 된다. 지우기에서 안전했던 기준이 쓰기 단계에서도 옳다는 보장은 없다 — 예를 들어 B(통과 단언)는 지우기에선 위험하지만 쓰기에선 "배선의 유일한 증거" 로 필요할 수 있다.
