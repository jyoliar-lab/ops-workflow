# 생존 mutant 를 어떻게 쓰나 — mutant 가 잘못된 구현 위에 있을 때를 가려내는 법 · 조사 (2026-10-24)

## 질문

지우기(#132) 다음은 생존 mutant 를 죽이는 테스트를 더하는 일이다.
그 일에는 지우기에 없는 위험이 있다 — 생존 mutant 가 앉아 있는 원본 코드가 **이미 잘못된 구현**이면, 그것을 죽이려고 쓴 테스트가 잘못된 동작을 명세처럼 굳힌다.
뒤에 그 구현으로 버그가 나면 테스트가 "의도된 동작" 이라고 증언하므로 원인을 특정하기 어려워진다.

이 조사는 아직 열지 않은 논의(생존 mutant 처리 — 테스트 추가의 기준과 절차)의 열린 축을 겨냥한다.
묻는 것은 둘이다.
외부에서는 mutation testing 의 결과(생존 mutant)를 어떻게 쓰는가 — 테스트를 더하는 것 말고 어떤 처분이 있고, 어떤 비율로 일어나는가.
생존 mutant 의 자리가 테스트 공백이 아니라 **코드 결함**임을 어떻게 알아내는가 — 원본과 mutant 중 어느 쪽이 맞는지를 무엇으로 가르는가.

용어(mutant · killed · survived · 동치 · 점수)의 1차 출처는 `261019_1640` §1 이고, 생존의 1차 분류(누락 · 동치 · 선언 · 미실행)는 `261021_1310` §3 이다.
이 문서는 그 위에 "테스트를 쓸 때의 오라클" 한 겹을 더한다.

## 조사

### 1. 생존 mutant 의 처분 — 테스트 추가는 하나의 길일 뿐이다

**Google — 코드 리뷰에서 떠오른 mutant 를 개발자가 어떻게 해소하나.** Petrović · Ivanković · Fraser · Just, *Please fix this mutant: How do developers resolve mutants surfaced during code review?*, ICSE-SEIP 2023. PDF https://homes.cs.washington.edu/~rjust/publ/mutation_testing_resolution_icse_2023.pdf · 조회 2026-10-24.

- 리뷰어가 "Please fix" 로 지지한 mutant 가운데 해소된 51건을 손으로 분류했다 — **테스트 추가 33 · 리팩토링 뒤 테스트 13 · 토론 3 · 불명 2.**
  인용: "in 33 cases, the code author added or modified a test to detect the mutant; (2) in 13 cases the code author refactored the code, to improve testability, and added tests; (3) in 3 cases, the mutants prompted a discussion".
- 리팩토링 길 — mutant 가 "테스트할 수 없거나 따라가기 어려운 코드 블록" 에 떠오르면 먼저 코드를 고쳤다.
  인용: "Often it was the case that the mutant could not be detected without the refactoring."
- 토론 길 — **문장 삭제 변이**가 "이 코드가 불필요한가, 가드가 더 필요한가" 의 토론을 낳았고, 결과는 문서화 또는 **불필요 절의 제거**였다.
  인용: "Another resolution path is the removal of clauses that are deemed redundant as the result of the discussion."
  즉 mutant 가 가리킨 자리에서 바뀐 것이 테스트가 아니라 코드인 경우가 있다.
- 해소되지 않은 60건의 이유 — **반박 27**("그 테스트가 실제 버그를 잡겠는가" 를 의심) · 보류 16 · 측정 밖 테스트 3 · 도구 한계 14.
  인용: "Code authors questioned the importance of the test a surfaced mutant would have elicited, and its ability to detect actual bugs ... We rely on the expertise of developers to make these decisions."
- 전체 해소율은 38 %, 리뷰어가 지지한 것은 60 % 다.
  인용: "Overall, our analysis demonstrates that 38% of all surfaced mutants are resolved via code changes or test additions."
- 선행 연구를 끌어 "동치 mutant 도 코드의 모호함을 드러내면 생산적일 수 있다" 고 적었다.
  인용: "equivalent mutants can be productive, if they advance code quality, and that non-equivalent mutants can be unproductive, if they represent test goals that lead to undesirable tests."

**Google — 생산적 · 비생산적 mutant 와 "변경 감지기" 테스트의 경고.** Petrović · Ivanković · Fraser · Just, *Practical Mutation Testing at Scale: A view from Google*, TSE 2021(arXiv 2102.11378). https://arxiv.org/pdf/2102.11378 · 조회 2026-10-24.

- 비생산적 mutant 의 정의 — 동치이거나, 죽일 수는 있지만 그 테스트가 스위트를 좋게 하지 않는 것.
  인용: "An unproductive mutant is either trivially equivalent to the original program or it is detectable, but adding a test for it would not improve the test suite".
- **이 조사의 질문에 가장 가까운 문장** — 그런 테스트는 "명세가 아니라 지금의 구현을 검사하는 변경 감지기" 라 해롭다.
  인용: "these tests, if written and added, would even have a negative impact because their change-detector nature (specifically testing the current implementation rather than the specification) violates testing best practices and causes brittle tests and false alarms."
- 비생산적 부류는 사람의 "Not useful" 피드백을 모아 **arid node 규칙**(백 개 넘는 손 규칙)으로 생성 단계에서 뺀다 — 분류를 매번 다시 하지 않는다.
  인용: "The expert function that flags simple nodes as arid is developed over time to incorporate developer feedback on reported 'Not useful' mutants. This process is manual".

**Google — mutant 는 실제 버그와 결합돼 있나.** Petrović · Ivanković · Fraser · Just, *Does mutation testing improve testing practices?*, ICSE 2021. https://homes.cs.washington.edu/~rjust/publ/mutation_testing_practices_icse_2021.pdf · 조회 2026-10-24.

- 고우선 버그 1502건의 수정 이력을 되감아, 버그를 넣은 변경에 mutation testing 을 돌렸다면 **70 %** 에서 그 버그와 결합된 생존 mutant 가 보고됐을 것이다.
  인용: "for 1043 (70%) of the bugs, mutation testing would have reported a fault-coupled mutant in the bug-introducing change. Recall that each bug-introducing change was covered by the existing tests".
- 뜻 — 생존 mutant 는 "테스트가 비어 있다" 의 신호이면서, 그 자리 **열에 일곱은 실제 버그가 숨을 수 있는 자리**다. 다만 이것은 "원본이 틀렸다" 가 아니라 "이 자리의 결함을 지금 테스트가 못 잡는다" 다.

**학술 — 결합 효과의 크기.** Just 외, *Are Mutants a Valid Substitute for Real Faults in Software Testing?*, FSE 2014. https://homes.cs.washington.edu/~mernst/pubs/mutation-effectiveness-fse2014.pdf · 조회 2026-10-24.

- 실제 결함 357건 중 **73 %** 가 흔한 변이 연산자의 mutant 와 결합돼 있고 27 % 는 아니다.
  인용: "73% of real faults are coupled to the mutants generated by" / "For 95 out of 357 real faults (27%), none of the triggering tests".
- 결합되지 않은 27 % 는 변이 연산자가 흉내 내지 못하는 결함이다 — mutation 이 표본인 한계의 수치.

**실무 사례 — 생존 mutant 가 코드 결함으로 판명난 셋.**

- *Trail of Bits — Use mutation testing to find the bugs your tests don't catch*(2025-09-18). https://blog.trailofbits.com/2025/09/18/use-mutation-testing-to-find-the-bugs-your-tests-dont-catch/ · 조회 2026-10-24.
  감사 중 **한 줄을 주석 처리한 변이**가 살아남았고(인용: "'cmdsToExecute.last().value = _cmd.value' ==> '//cmdsToExecute.last().value = _cmd.value' --> UNCAUGHT"), 뿌리를 좇자 입력 검증 누락(고위험 TOB-ARK-10)이었다.
  권하는 절차는 "생존 mutant 마다 뿌리 원인을 먼저 분석한다" 이다 — 인용: "Discovering the root cause is important to determine the impact and recommended solution for the issue."
  생존의 원인 셋을 든다 — 결과 상태 검사 누락 · 현실과 다른 mock · 케이스 부재.
- *dev.to — My test suite had 100% coverage. Mutation testing still found real bugs.*(Node.js 라이브러리 breakwater · Stryker · 게시 8월 3일, 연도 미표기). https://dev.to/pinceladasdaweb/my-test-suite-had-100-coverage-mutation-testing-still-found-real-bugs-2man · 조회 2026-10-24.
  생존 199 를 **다섯 묶음**으로 갈랐다 — 코드 결함 1(이름 있는 정책이 두 이름으로 집계) · 죽은 코드(timeout 정책의 도달 불가 경로) · 테스트 결함 1(무엇을 넣어도 통과) · 테스트 공백(문서된 계약 중 단언 없는 것) · 동치(수용 · 문서화).
  죽은 코드는 "옛 버전을 다시 빌드해 모드 · 순서 · 거부 종류를 바꾼 **차등 실행**에서 0 차이" 를 보여 지웠다 — 테스트가 아니라 **독립 오라클(옛 버전)** 로 판정한 예다.
  코드 결함은 "그 자리를 죽이려고 테스트를 쓰는 과정에서" 드러났다 — 문서의 규칙("명시 이름이 항상 이긴다")을 기대값으로 삼았기 때문에 구현과 어긋남이 보였다.
- *awesome-testing — Mutation testing for agent-written code*(2026-08-02). https://www.awesome-testing.com/2026/08/mutation-testing-for-agent-written-code · 조회 2026-10-24.
  인용: "A mutant is a counterexample—a way to challenge a claim—not the source of truth." / 생존 mutant 는 "does not automatically mean that the production code contains a bug."
  절차 — 생존마다 **관찰 가능한 피해를 먼저 서술**하고, 비이슈(동치 · 진단용 · 러너 특성)를 가르고, 의미 있는 생존에는 "원본에서 통과하고 고정된 mutant 에서 실패하는 계약 테스트" 를 더한다. 기대값을 구현에서 베끼지 말라고 적는다 — 인용: "The goal is not to game a score or generate assertions that merely mirror the implementation."
  같은 모델이 코드와 테스트를 둘 다 쓰면 같은 가정을 반복한다 — 인용: "A test suite can grow very quickly while still repeating the same assumptions as the implementation."

**정리 — 처분의 지도.** 생존 mutant 하나는 다섯 처분 가운데 하나로 간다.

| 처분 | 뜻 | 출처 |
|---|---|---|
| 테스트 추가 | 명세에서 기대값을 끌어와 그 자리를 검사한다 | Google 33/51 · 실무 셋 |
| 코드 리팩토링 뒤 테스트 | 테스트할 수 없는 모양이면 먼저 고친다 | Google 13/51 |
| **코드 수정** | mutant 가 가리킨 원본이 틀렸거나 죽은 코드다 | Google 토론 3(불필요 절 제거) · Trail of Bits · breakwater |
| 비생산 판정 · 억제 | 동치 또는 죽일 가치 없음 — 규칙 · pragma 로 다음 측정에서 뺀다 | Google arid · Stryker |
| 반박 · 보류 | 그 테스트가 실제 버그를 잡겠는가를 의심해 쓰지 않는다 | Google 27/60 |

### 2. 질문의 핵심 — 잘못된 구현을 명세로 굳히는 테스트에는 이미 이름이 있다

**특성화 테스트(characterization test) — Feathers.** InfoQ 팟캐스트 *Michael Feathers: Looking Back at Working Effectively with Legacy Code*(2021-03-15). https://www.infoq.com/podcasts/working-effectively-legacy-code/ · 조회 2026-10-24.

- 인용: "the tests aren't really defining correct behavior, they're really defining actual behavior for the codebase." / "You don't really take those tests as being a definition of correctness, but rather definition of actuality."
- 그래서 특성화 테스트가 놀라운 결과를 내면 "Is that good behavior or bad behavior?" 를 묻는다 — 결과를 그대로 기대값으로 받지 않는다.
- Wikipedia *Characterization test*(https://en.wikipedia.org/wiki/Characterization_test · 조회 2026-10-24)는 "legacy code 의 기존 동작을 의도치 않은 변경에서 지키는" 용도로 적는다 — 버그를 포함해 **지금의 동작**을 고정하는 것이 목적인 기법이다.
- 생존 mutant 를 죽이려고 "원본을 돌려 나온 값" 을 기대값으로 쓰는 테스트는 정확히 특성화 테스트다 — 그 기법의 목적(기존 동작 보존)과 지금의 목적(약속 검증)이 다르다.

**동어반복 테스트(tautological · self-test · ugly mirror).**

- Fabio Pereira, *TTDD — Tautological Test Driven Development (Anti Pattern)*(2010-05-27). http://fabiopereira.me/blog/2010/05/27/ttdd-tautological-test-driven-development-anti-pattern/ · 조회 2026-10-24.
  테스트가 "구현의 거울" 이 되는 꼴에 이름을 붙였다.
- J. B. Rainsberger, *The Curious Case of Tautological TDD*(2014-05-14 · 2019-06-18 갱신). https://blog.thecodewhisperer.com/permalink/the-curious-case-of-tautological-tdd · 조회 2026-10-24.
  동어반복은 "알고리즘으로 자기 자신을 검사하는" 것이라 테스트와 코드가 같은 실수를 공유한다 — 치료는 mock 제거가 아니라 **본질적 상호작용**을 검사하는 것.
- Open Catalog of Test Smells 의 *Self-Test* — "결과를 기대값이 아니라 결과 자신과 비교한다". 기계 판별은 "기대값은 상수 또는 상수 참조이고 테스트 안에서 계산되지 않는다"(Rwemalika 외, 아래 Canedo 가 인용).

**오라클 앵커링(oracle anchoring) — 2026 의 가장 직접적인 연구.** Arquimedes Canedo, *Oracles That Cannot Fail: Anchoring and the Expectation That Moves With the Fault*, arXiv 2608.17214(2026-08-17). https://arxiv.org/abs/2608.17214 · 조회 2026-10-24.

- 핵심 — 인용: "A test oracle that obtains its expected value from the system it is judging cannot fail. If a fault moves measurement and expectation together the comparison cancels exactly, and no generated input will reveal it. The defect is in the oracle and not in the input space."
- 두 종류의 기대값 — 인용: "An expectation is specification-anchored when composed from values fixed outside the code under mutation, and state-anchored when it flows, directly or transitively, from that code."
- **판별은 정적이다** — 인용: "Anchoring is binary, decidable without running anything, and relative to a declared mutate target."
  기대값이 상수 · 공표된 절차 · 변이 대상 밖의 값으로만 조립됐는가를 코드에서 읽는다.
- 효과의 크기 — 한 오라클을 "공표된 절차" 로 다시 앵커링하자(코드 무변경) 46 생존 중 8 이 죽었고, 건강한 오라클을 상태 앵커링으로 바꾸자 19 중 4 가 살아났다.
  인용: "Re-anchoring one holding oracle on published procedure, changing no production code, recovers 8 of 46; state-anchoring a healthy debounce oracle costs 4 of 19".
- **빠진 오라클을 명세 앵커로 쓰자 배포가 못 잡던 결함 둘이 드러났다** — 인용: "Writing the oracle this analysis said was missing then exposed two defects deployment had not surfaced."
  즉 "원본이 틀렸나" 는 기대값을 구현 밖에서 끌어올 때만 드러난다.
- 한계 — 인용: "All measurements come from one system by one author."

**정리.** 질문의 위험은 문헌에서 세 이름으로 불린다 — 특성화 테스트(의도된 용법) · 동어반복 테스트(안티패턴) · 상태 앵커 오라클(측정 가능한 결함).
셋이 가리키는 판별 하나 — **기대값의 출처가 변이 대상 안인가 밖인가.**

### 3. 원본과 mutant 중 어느 쪽이 맞나 — 오라클의 출처

**오라클 문제의 분류.** Barr · Harman · McMinn · Shahbaz · Yoo, *The Oracle Problem in Software Testing: A Survey*, TSE 41(5), 2015. https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf · 조회 2026-10-24.

- 네 부류 — **specified**(명세 · 계약 · 모델에서) · **derived**(다른 산출물 — 이전 버전 · 다른 구현 · 메타모픽 관계 · 문서에서) · **implicit**(크래시 · 예외처럼 설명 없이 틀린 것) · **없음**(사람).
  인용: "the final source of test oracle information remains the human".
- **의사 오라클(pseudo-oracle)** — 독립적으로 만든 다른 구현과 결과를 비교한다.
  인용: "A pseudo-oracle is an alternative version of the program produced independently, e.g. by a different programming team or written in an entirely different programming language."
  N-version 프로그래밍이 같은 발상이다.
- **메타모픽 관계** — 값이 아니라 실행 사이의 관계를 단언한다.
  인용: "The key idea is that reasoning about the properties of f will lead us to relations that its implementation p must obey."
  설문은 이것을 derived 에 둔다 — 실무에서는 "SUT 를 들여다보고" 관계를 끌어내기 때문이다.
- **회귀 테스트는 이전 버전을 오라클로 삼는다는 암묵 가정 위에 있다** — 인용: "It rests on the implicit assumption that the previous version can serve as an oracle for existing functionality."
  이 가정이 깨지는 자리가 바로 질문의 자리다 — 원본이 틀렸으면 이전 버전은 오라클이 아니다.

**명세 쪽의 같은 문제 — 형식 명세도 약할 수 있다.** Amaral · Mendes · Campos, *MutDafny: A Mutation-Based Approach to Assess Dafny Specifications*, ICSE 2026(arXiv 2511.15403 · v2 2026-04-12). https://arxiv.org/abs/2511.15403 · 조회 2026-10-24.

- 테스트 대신 **형식 명세**에 mutant 를 돌린다 — 변이해도 검증이 통과하면 명세가 약하다는 신호다.
  인용: "If a program with a mutant verifies, this may indicate a weakness in the specification."
- 그러나 생존이 곧 약한 명세는 아니다 — 인용: "an alive mutant may not always indicate the presence of a weak specification; i.e., the mutant might just be equivalent to the original program".
- 손 분석 비용 — 생존 284 를 한 사람이 8 시간(**mutant 당 약 1.7 분**)에 보고 약한 명세 5 를 찾았다.
  인용: "This took eight hours of one person's effort (≈ 1.7 minutes per mutant)".
- 뜻 — 기대값의 출처를 명세로 올려도 명세가 틀릴 수 있다. 오라클을 올리는 것은 위험을 없애는 게 아니라 **틀린 자리를 테스트에서 명세로 옮겨 사람이 읽을 수 있는 곳에 두는 것**이다.

**pseudo-tested — 돌지만 단언이 없는 메서드를 개발자는 어떻게 보았나.** Vera-Pérez · Danglot · Monperrus · Baudry, *A Comprehensive Study of Pseudo-tested Methods*, EMSE 2019(arXiv 1807.05030). https://arxiv.org/pdf/1807.05030 · 조회 2026-10-24.

- 표본 101 중 개발자가 테스트할 가치가 있다고 본 것은 **30(30 %)**.
  인용: "We found that developers consider only 30 of them worth spending time improving the test suite."
- 가치 없음의 기준 — 자동 생성 코드 · 디버그 · 로그 문구 · 드물게 쓰는 기능 · 사소한 메서드 · 인터페이스 채우기 · 위임 메서드.
  가치 있음의 기준 — 핵심 기능 · 널리 쓰임 · 외부 클라이언트가 씀 · **입력 전제조건 검사**.
  인용: "are involved in core functionalities, are widely used in the code base, are used by external clients or verify preconditions on input data."
- 뜻 — "어느 생존을 죽일 가치가 있나" 의 기준이 **코드의 자리(핵심인가 · 밖에서 보이는가)** 로 주어졌다. mutant 의 종류가 아니다.

**정리 — 원본이 맞는지 가르는 다섯 출처.** 질문 "mutant 가 잘못된 구현 위에 있는가" 는 "원본이 맞다" 를 무엇으로 말하나로 바뀐다.

| 출처 | 무엇으로 가르나 | 비용 · 한계 |
|---|---|---|
| **명세 앵커**(specified) | 문서 · 계약 · 외부 상수에서 기대값을 조립한다. 구현을 돌려 얻은 값은 쓰지 않는다 | 명세가 없거나 모호하면 멈춘다 — 그 자체가 발견이다. 명세도 틀릴 수 있다(MutDafny) |
| **의사 오라클**(derived) | 독립 구현 · 실 시스템의 응답 · 옛 버전과 비교한다 | 독립성이 핵심 — 같은 사람 · 같은 모델이 둘 다 쓰면 독립이 아니다(awesome-testing) |
| **메타모픽 · 성질**(derived) | 값 대신 관계를 단언한다 — 단조 · 합 · 멱등 · 대칭 | 관계가 구현에서 읽혀 나오면 상태 앵커가 된다(Barr · Canedo) |
| **암묵 오라클**(implicit) | 크래시 · 예외 · 타입 오류 — 설명 없이 틀린 것 | 좁다. 잘못된 값은 못 잡는다 |
| **사람**(토론) | 코드 리뷰에서 "이 절이 불필요한가" 를 묻고 문서화 또는 제거 | Google 51 중 3. 비용은 mutant 당 분 단위(MutDafny 1.7 분) |

### 4. 절차 — 외부 사례가 권하는 순서

출처들이 겹쳐 말하는 순서를 한 줄로 모았다.
판정은 이 문서의 것이 아니다 — 논의 문서가 고른다.

1. **뿌리 원인부터**(Trail of Bits) — 생존 mutant 마다 "이 변이가 살아남은 이유" 를 적는다. 테스트를 쓰기 전이다.
2. **관찰 가능한 피해를 서술**(awesome-testing) — 변이가 밖에서 보이는 무엇을 바꾸나. 바꾸는 것이 없으면 동치 후보다.
3. **분류**(breakwater · Google) — 테스트 공백 · 약한 단언 · 동치 · 도달 불가(죽은 코드) · 테스트 결함 · **코드 결함**. 뒤의 둘은 테스트 추가가 아니다.
4. **기대값의 출처를 먼저 정한다**(Canedo · Feathers) — 명세 · 문서 · 외부 상수 · 독립 오라클 가운데 어디서 오나. 구현을 돌려 얻은 값이면 쓰지 않는다. 출처가 없으면 **그 자리가 발견**이고, 테스트 대신 질문(코멘트)이 산출물이다.
5. **테스트는 원본에서 통과하고 고정된 mutant 에서 실패해야 한다**(awesome-testing) — 둘 다 확인한다. 전자만 확인하면 특성화 테스트다.
6. **테스트할 수 없는 모양이면 먼저 리팩토링**(Google 13/51) — 테스트가 구조를 뚫고 들어가면 변경 감지기가 된다.
7. **죽이지 않을 권리**(Google 27/60 · Vera-Pérez 70 %) — "이 테스트가 실제 버그를 잡겠는가" 에 아니오면 쓰지 않고 이유를 적는다. 점수를 위해 쓰지 않는다 — 인용: "do not game the score or change production code solely to satisfy the tool."

### 조사에서 찾지 못한 것

- **"원본 vs mutant" 를 가르는 형식 규칙**은 어느 출처에도 없다. 전부 "기대값의 출처를 밖에서" 와 "사람이 읽는다" 로 귀결한다.
- 산업 데이터에서 **"생존 mutant 의 자리가 실제로 틀린 구현이었던 비율"** 은 없다. Google 2023 은 테스트 33 · 리팩토링 13 · 토론 3 으로 갈랐고 "코드 버그 수정" 을 따로 세지 않았다. 사례 셋은 각 1건이다.
- Python · mutmut 에 특정한 지침은 없다. 도구 문서(Stryker · PIT)는 동치와 생존을 가르는 법을 "손으로" 라고만 적는다 — Stryker, *Equivalent mutants*, https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/ · 조회 2026-10-24. 인용: "There is no definitive way for Stryker to find and ignore them."
- Canedo 의 앵커링 판별이 **단일 시스템 · 단일 저자**의 측정이라 일반화 근거가 약하다. 개념은 쓰되 수치는 옮기지 않는다.

## 논의 문서로 가져가는 것

- 생존 mutant 의 처분은 다섯이다 — 테스트 추가 · 리팩토링 뒤 테스트 · **코드 수정** · 비생산 판정(억제) · 반박. Google 의 해소 51건 중 테스트만 더한 것은 33 이고, 지지된 mutant 의 40 % 는 해소되지 않았다.
- 질문의 위험은 이름이 셋 있다 — 특성화 테스트 · 동어반복 테스트 · 상태 앵커 오라클. 판별은 하나다 — **기대값이 변이 대상 밖에서 조립됐는가.** 코드를 읽어 정적으로 가를 수 있다(Canedo).
- "원본이 맞다" 의 출처는 넷 + 사람이다 — 명세 · 독립 구현(의사 오라클) · 관계(메타모픽) · 암묵. 출처가 없으면 테스트 대신 질문이 산출물이다.
- 명세로 올려도 명세가 틀릴 수 있다(MutDafny). 올리는 뜻은 틀린 자리를 **사람이 읽는 곳**으로 옮기는 것이다.
- 가치 판정의 기준은 mutant 의 종류가 아니라 **코드의 자리**다 — 핵심 기능 · 밖에서 보이는 것 · 입력 전제조건(Vera-Pérez). obs-toolkit 에서는 공개 경계(부모 3-1) 위의 자리가 그것이다.
- 사람의 비용은 mutant 당 분 단위다(MutDafny 1.7 분 · Google 리뷰). #132 뒤 생존 약 700 을 전부 읽는 것은 20 시간대다 — 자리(경계 위)와 종류(문구 · 선언 제외)로 먼저 줄여야 한다.
- obs-toolkit 이 이미 가진 독립 오라클 — **녹화 fixture**(실 Prometheus · Loki · Tempo 의 응답, format 티어의 replay)와 **서버 측 계산**("계산은 서버가 한다" — 환원 연산이 PromQL 로 서버에 묻는다). 전자는 의사 오라클(실 시스템), 후자는 기대값을 구현 밖에 두는 길이다. 명세 앵커의 후보는 `skills/*/SKILL.md` 의 약속 문장과 docstring 의 "한 테스트 = 한 주장" 이다.
- 절차의 뼈대 — 뿌리 원인 → 관찰 가능한 피해 → 분류 → 기대값의 출처 → 원본 통과 · mutant 실패 둘 다 확인 → 테스트할 수 없으면 리팩토링 → 죽이지 않을 권리. 각 단계가 논의의 축 후보다.
