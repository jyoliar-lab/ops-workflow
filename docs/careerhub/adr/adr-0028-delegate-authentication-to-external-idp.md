# ADR-0028 — 인증은 외부 IdP 제품이 소유하고, 인가·도메인 상태는 앱이 소유한다

## Context

careerhub의 로그인은 소셜 전용(현재 Google, Naver 추가 예정)이고 비밀번호가 없다. 인증은 auth-service가 직접 구현해 왔는데, 그 구현에 구조적 결함이 누적되어 있다: 대칭 서명 키를 api-composer와 공유해 검증자가 곧 발급자가 되는 문제, OAuth 왕복에 PKCE·nonce·유효한 state 방어가 없는 문제, 발급한 토큰을 폐기할 수단(로그아웃·정지)이 없는 문제, 로그인 대기 상태를 만료 없는 암호화 봉투로 브라우저에 맡기는 문제. 이를 자체 재작성으로 고치는 방향이 한 차례 수렴됐고, 그때 기성 IdP 제품 도입은 기각됐다 — 그러나 그 기각의 전제는 **"제품이 인증만 가져가고 사용자 원장·권한·동의는 앱에 남아, 가입·탈퇴가 두 시스템에 걸친다"** 는 프레임이었다.

재검토에서 두 사실이 그 전제를 무너뜨렸다.

첫째, **상용 세계의 표준형이 정확히 반대다.** 결제 기반 서비스조차 기한부 이용 권한을 IdP에 넣지 않는다 — 진실은 앱 DB에 두고, 토큰에 실을 필요가 있으면 **발급 시점 훅**으로 주입한다. 주요 IdP 제품에 롤 만료 기능이 없다는 사실 자체가 그 증거다(만료 있는 권한은 인증이 아니라 비즈니스 도메인이다). careerhub의 권한 모델(`user_authority`의 만료일, 초대티켓의 원자적 사용-부여)은 이미 이 표준형이며, 제품을 들여도 한 줄도 바뀌지 않는다.

둘째, **현행 IdP 제품은 발급 훅을 1급 기능으로 제공한다.** 토큰 발급 시 제품이 외부 endpoint를 호출해 클레임을 받아 싣는 방식이 가능하므로, 인가 데이터를 앱이 소유한 채 인증만 위임하는 경계가 실제로 성립한다.

한편 위임의 극단형은 성립하지 않는다. 사용자의 존재를 제품만 알고 앱에는 사용자별 상태가 없다면 가입·탈퇴가 제품 안에서 원자적으로 끝나겠지만, careerhub는 다른 서비스(userinfo)의 데이터가 사용자 식별자로 인덱싱되어 있고 인가 원장도 앱에 남으므로, 사용자 원장의 사본에 해당하는 상태를 앱 측이 계속 갖는다. 따라서 탈퇴·정지는 여전히 두 시스템에 걸친다. 다만 현재 가입 사용자가 1명이라 식별자 이전 비용이 ~0인 창이 열려 있다(ADR-0027의 비용 비대칭과 동일한 형태). 또한 기존 탈퇴 흐름도 userinfo까지 전파되지 않고 있었으므로, "제품 도입이 원자성을 깬다"던 기각 논거는 실측상 이미 절반만 참이었다.

## Decision

**인증과 인가의 소유권을 다음 경계로 가른다:**

- **외부 IdP 제품이 소유한다** — 회원가입, 로그인(소셜 IdP 브로커링과 그 왕복의 모든 방어), 세션 수명주기(발급·갱신·로그아웃·강제 종료), 탈퇴·정지의 인증 측면.
- **앱(auth-service)이 소유한다** — 권한(만료 포함), 초대티켓, 약관동의의 원장과 그 도메인 규칙. **인가 데이터를 IdP에 넣지 않는다.**
- **시스템 전역 사용자 식별자는 제품이 발급하는 id를 그대로 쓴다** — 앱이 별도 식별자를 발급해 제품 정체성과 매핑하는 층을 두지 않는다.
- **동의 수집과 온보딩은 앱의 게이트로 한다** — 제품 로그인 흐름에 동의·재동의 단계를 만들어 넣지 않는다. 동의 미충족 사용자도 토큰은 발급되며, 충족 여부의 판정은 별도 메커니즘이 아니라 여느 인가와 같은 경로다.

경계의 접합, 곧 앱이 소유한 인가 상태가 각 서비스의 판정에 어떻게 전달되는가는 여기서 정하지 않는다 — 별도 결정으로 가른다.

## Alternatives

- **자체 재작성 (직전 수렴).** 규격 요구 목록(ID Token 검증·PKCE·세션 상태·비대칭 서명·트랜잭션 레코드)을 전부 자체 구현·유지한다. 표준형이 "인증만 위임" 경계를 지지하고 발급 훅이 실재하는 이상, 같은 결과를 더 비싸게 사는 길이다. 기각의 근거였던 원장 분리 비용은 발급 훅과 사후 정합으로 흡수된다.
- **도메인까지 제품에 넣기 (전부 위임).** 동의·권한·티켓을 제품 확장(SPI 등)으로 재작성한다. 도메인 로직이 제품의 언어·배포·업그레이드 주기에 종속되고, 만료 있는 권한과 원자적 티켓 사용은 제품 어휘로 표현되지 않는다. 지워지지 않는 도메인을 옮겨 적는 일이다.
- **권한을 제품 롤로 이관.** 만료를 표현할 수 없고, 티켓 사용(행 잠금 안의 검사-기록-부여)이 앱 트랜잭션과 제품 API 호출로 갈라져 원자성이 깨진다. 만료만 앱에 남기는 절충은 권한의 진실을 둘로 가른다.
- **프로토콜 어댑터(브로커 shim)만 도입.** OIDC 클라이언트 코드·왕복 방어·세션 관리가 전부 앱에 남아 코드가 줄지 않고 홉만 는다. IdP가 둘인 규모에서 이득이 없다.

## Consequences

- **운영물이 하나 는다.** 제품의 배포·백업·업그레이드가 상시 비용이 된다. 이 비용을 수용하는 판단이 이 결정의 일부다.
- **전파 결합이 생긴다.** 제품에서의 탈퇴·정지가 앱 데이터 정리로 저절로 이어지지 않으므로, 둘 사이의 상태 정합 수단이 필요해진다. 주기 조정이든 이벤트 수신이든 방식은 코드 관할이다. IdP 측 연동 해제 통보(Naver 콜백)를 제품에 반영하는 관리 API 호출도 같은 새 일감이다.
- **프론트 로그인 흐름이 재작성된다.** 팝업·postMessage 방식이 표준 리다이렉트로 바뀐다.
- **기존 사용자와 식별자의 이전이 필요하다.** 현재 규모에서 비용은 ~0이나, 이행 전까지 기존 결함 코드가 계속 돈다 — 전환 기간이 길어지면 즉효 결함(토큰 원문 로깅 등)은 별도로 먼저 닫는다.
