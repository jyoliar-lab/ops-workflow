# ADR-0030 — IdP 제품으로 Zitadel을 채택한다

## Context

인증을 외부 IdP 제품에 위임하기로 했으므로(ADR-0028) 제품을 골라야 한다. 요구는 그 결정의 경계에서 도출된다: ① 소셜 브로커(Google 네이티브 + Naver를 generic OIDC로) ② 표준 OIDC 발급자(서비스가 공개키로 로컬 검증) ③ **발급 시점에 외부를 호출해 클레임을 주입하는 훅** ④ arm64 홈랩(8GB 노드)에서의 자원 적합성 ⑤ 수용 가능한 라이선스 ⑥ 개인 프로젝트가 상시로 낼 수 있는 업그레이드 노동.

배치 제약이 하나 있다: 소셜 IdP의 pairwise `sub`는 redirect_uri 호스트(sector identifier) 기준으로 계산되므로, 제품을 무엇으로 하든 **기존 호스트 아래 경로에 두고 기존 client_id를 물려주면** 기존 사용자의 IdP 연결이 보존된다. 따라서 제품 선택에 순서 제약은 없고, 배치 위치가 정체성 결정이 된다.

후보 실측에서 갈린 지점은 ③과 ⑥이었다.

**③ 발급 훅의 실행 모델** — Zitadel의 현행 훅(Actions v2)은 제품이 등록된 **외부 HTTP endpoint를 호출**하는 방식이다: 커스텀 로직이 우리 언어(Go)로 우리 저장소·배포 파이프라인에 살고, 제품 쪽에는 설정만 남는다. ADR-0028의 접합(발급 시 제품→앱 호출)이 이 실행 모델 그 자체다. 반면 Keycloak의 훅(protocol mapper)은 **Java SPI를 빌드해 제품 프로세스 안에 배치**하는 방식이다 — 커스텀 코드의 거주지가 정반대이고, 제품 업그레이드마다 재빌드·호환 검증 대상이 된다.

**⑥ 업그레이드 노동** — Keycloak은 26.x부터 분기별 마이너에 하위호환 보장을 도입해 과거("연 4회 메이저")보다 크게 나아졌으나, LTS 부재는 공식 입장으로 유지된다(최신만 보안 패치). Zitadel은 실측상 메이저가 ~연 1회이고 **직전 메이저에 보안 백포트가 병행**되며(v4 출시 후에도 v3.4.x 패치 지속 확인), GA 기능의 하위호환이 명시 정책이다 — 업그레이드 시점을 고를 수 있다.

그 외 실측: Zitadel은 Go 단일 계열로 앱 메모리 ~512MB(Keycloak Operator 기본 requests 1700MiB), 저장소가 PostgreSQL 단독(v3부터)이라 이미 운용 중인 저장소 종류에 얹히고, 이벤트소싱이라 인증 이벤트(가입·로그인·탈퇴)가 구조적으로 기록된다. 라이선스는 v3부터 AGPL-3.0인데 구성요소별로 갈린다 — core·콘솔·로그인 UI가 AGPL이고 API·SDK·proto·Helm·Terraform은 Apache 2.0이다. 미수정 운용에는 의무가 없고, 연동면이 Apache 2.0이라 앱 코드로의 감염 경로가 없으며, 로그인 UI를 fork·수정해 서비스할 때만 공개 의무가 생긴다(앱 온보딩 게이트 구성에서는 fork가 불필요하다).

## Decision

**IdP 제품으로 Zitadel을 채택한다.** 결정의 핵심 근거는 셋이다:

- **발급 훅이 외부 호출 모델이다** — 커스텀 로직이 앱의 언어·저장소·배포에 남고, 제품 업그레이드가 커스텀 코드의 재빌드를 요구하지 않는다.
- **업그레이드 노동의 곡선이 개인 프로젝트에 맞는다** — 직전 메이저 백포트가 실재해 업그레이드 시점을 선택할 수 있다.
- **자원·저장소가 현 인프라에 맞는다** — Go·~512MB·arm64, PostgreSQL 단독.

훅의 세대 선택(Actions v2 + login v2 조합), 배치 경로, 토큰 수명, 키 회전 방식은 코드·설정의 관할이다.

## Alternatives

- **Keycloak.** 생태계·문서·레퍼런스의 절대 질량이 가장 크고, 26.x의 릴리스 체계 개선으로 과거의 탈락 사유(잦은 메이저)는 상당히 해소됐다. 그래도 버리는 이유: 발급 훅이 Java SPI 인프로세스 배치라 커스텀 코드가 제품의 업그레이드 주기에 종속되고, LTS 부재로 분기 추적이 의무이며, 기본 메모리 요구가 3배 이상이다. 제품이 파는 기능의 큰 몫(비밀번호·MFA·동의 화면)은 소셜 전용 + 앱 온보딩 게이트 구성에서 쓰이지 않는다.
- **Ory Kratos.** 철학(headless — UI를 앱이 소유)은 이 구조와 가장 정합하나, 표준 OIDC 발급자가 아니어서 서비스가 검증할 토큰을 얻는 배선을 직접 조립해야 하고 관리 콘솔이 없다. "더 얇은 제품 + 더 많은 조립"이라는 다른 트레이드이며, 조립을 줄이는 것이 위임의 목적이었으므로 어긋난다.
- **경량 신생(Rauthy·Pocket ID)·Casdoor.** Rauthy는 발급 훅이 없고 실질 1인 유지, Pocket ID는 소셜 브로커 자체가 없다. Casdoor는 커버리지가 넓으나 보안 이력(누적 CVE)·품질 평판이 채택 부담이다.
- **SaaS(Auth0·Clerk 등).** 자체 호스팅 불가, 사용자 데이터 외부 이전, 무료 등급의 소셜 커넥션 개수 제한이 IdP를 늘려갈 계획과 충돌한다.

## Consequences

- **AGPL-3.0을 받는다.** 미수정 운용에는 실질 의무가 없으나, 코어를 수정해 서비스하거나 로그인 UI를 fork하면 공개 의무가 생긴다. 이용 형태가 상업 재배포로 바뀌면 상용 라이선스가 출구다.
- **단일 회사 의존을 받는다.** 회사가 꺾이면 AGPL이라 포크는 가능하지만, 포크를 받아줄 커뮤니티 질량이 Keycloak 계열만 못하다. 이것이 이 선택의 가장 무거운 잔여 리스크다.
- **운영 절차에 masterkey가 들어온다.** 백업이 PostgreSQL 덤프만으로 완결되지 않는다 — masterkey를 함께 보존하지 않으면 암호화 데이터를 잃는다.
- **훅 세대 정렬이 필요하다.** 구세대 조합(login v1 + Actions v2)에 트리거 공백이 있으므로 login v2 + Actions v2로 맞춘다.
- **제품 교체는 원장 이전이다.** 사용자 정체성이 제품 안에 살게 되므로 교체 비용이 크다 — 다만 식별자가 저장소 독립 발급·불변(ADR-0028·ADR-0027)이라 값 보존 이전은 가능하고, IdP 연결은 호스트·client_id 유지로 보존된다.

## 무효화 조건

- **외부 호출형 발급 훅이 제품에서 제거·유료화되는 경우.** 채택 근거의 첫째 기둥이다.
- **프로젝트가 유지보수를 상실하는 경우**(보안 패치 중단 수준). 단일 회사 의존 리스크가 현실화된 상태다.
- **AGPL을 수용할 수 없는 이용 형태가 생기는 경우** — 상용 라이선스 전환 또는 제품 재선정이 필요해진다.
