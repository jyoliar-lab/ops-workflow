# ADR-0027 — 시스템 전역 사용자 정체성은 저장소 독립적으로 발급된 불변 식별자로 한다

## Context

careerhub의 사용자 식별자는 auth-service PostgreSQL `user` 테이블의 `serial` PK다. 이 값은 JWT claim으로 나가고, api-composer가 gRPC 요청 필드로 내려보내며, userinfo-service MongoDB가 스크랩·매칭조건 문서의 유니크 인덱스로 쓴다. 즉 **한 저장소의 PK가 시스템 전역의 사용자 정체성 노릇을 하고 있다.**

다른 서비스가 사용자 식별자로 데이터를 인덱싱하는 패턴 자체는 옳다 — 대안(이메일 키·IdP 정체성 키·매 조회 조인)이 전부 더 나쁘다. 이메일은 가변·재사용 가능해 식별자로 쓸 수 없고, IdP 정체성을 다운스트림에 흘리면 계정 연결·프로바이더 변경마다 데이터 마이그레이션이 터지며, 조인은 서비스 분리를 무의미하게 만든다.

문제는 패턴이 아니라 **발급 방식**이다. `serial`의 값은 *그 테이블에의 삽입 순서*의 함수라서, 시스템 전역 정체성이 특정 PostgreSQL 인스턴스의 시퀀스 상태에 묶인다. user 테이블을 재구축하려면 반드시 값 보존 마이그레이션과 시퀀스 재설정을 해야 하고, 어기면 userinfo의 문서들이 조용히 다른 사람의 것이 된다 — 이 제약은 어디에도 적혀 있지 않고 스키마만 봐서는 보이지 않는다. 부수적으로 순차 정수는 사용자 수를 노출하고 추측 가능하다.

판별 질문은 자료형("정수인가")이 아니라 **"이 값을 그 테이블 없이 재현·보존할 수 있는가"** 다. 독립 발급한 랜덤 값이라면 정수여도 문제 대부분이 없고, DB가 기본값으로 발급하는 UUID라도 발급 주체가 저장소라는 점은 같다.

지금 정하는 이유는 비용 비대칭이다. 현재 가입 사용자가 1명(운영자 본인)이라 식별자 치환 비용이 사실상 0이고, 이 비용은 사용자 수에 단조증가한다. **지금은 가역, 나중은 불가역이다.**

## Decision

**시스템 전역 사용자 정체성은 저장소 독립적으로 발급된 불변 식별자로 한다.**

- **저장소 독립 발급** — 식별자의 값이 특정 저장소 인스턴스의 상태(시퀀스·삽입 순서)의 함수여서는 안 된다. 저장소를 재구축해도 값이 보존·재현될 수 있어야 한다.
- **노출된 식별자는 불변** — 일단 시스템 경계(토큰·타 서비스 데이터)로 나간 식별자는 그 사용자가 존재하는 한 바뀌지 않는다.

식별자의 구체 형식(UUID 버전·ULID 등), 발급 주체(앱·DB·외부 시스템), 그리고 저장소 안에서의 자리(PK로 삼는지, 별도 유니크 컬럼으로 두는지)는 코드의 관할이다 — 위 두 성질을 만족하는 한 어떻게 하든 이 결정은 흔들리지 않는다.

## Alternatives

- **serial 유지 + 재구축 제약 명문화.** 재작성이 user 테이블 스키마를 크게 건드리지 않을 때만 이기는 안이다. 재구축이 가능하고 사용자가 1명인 현재 조건에서는 유일한 매력(마이그레이션 회피)이 소멸한다 — 치환할 문서도 운영자 본인 것뿐이다.
- **이메일·(provider, subject)·조인을 전역 키로.** Context에 적은 대로 각각 가변성·IdP 결합·런타임 결합으로 기각. 패턴 차원에서 성립하지 않는다.

## Consequences

- **치환 마이그레이션을 이행해야 한다.** userinfo MongoDB의 유니크 인덱스 2개 재작성과 문서 `userId` 치환, 토큰 claim의 식별자 교체가 뒤따른다. 현재 규모(N=1)에서 비용은 무시 가능하나, 이행을 미루면 이 결정의 근거였던 비용 비대칭이 반대로 작동한다.
- **식별자에서 정보가 사라진다.** 순차 정수가 주던 가입 순서·규모의 암시는 의도적으로 포기한다.
