# 서류 지원 후 관측할 수 있는 신호 — 무엇을 만들고 어디까지 구분할 것인가

## 1. 문제

서류 지원의 결과는 늦게 오고, 드물게 오고, 자주 오지 않는다.
합격·불합격만으로는 공고 선별 방식이나 이력서 변경이 통했는지 가르는 데 몇 달이 걸린다.
무응답일 때는 서류가 읽히지도 않은 것인지, 읽힌 뒤 탈락한 것인지조차 구분되지 않는다.

그래서 지원한 뒤 결과 통보 전에 관측할 수 있는 신호를 만들려 한다.
출발점은 이력서에 든 두 링크다 — 커리어허브 서비스와 커리어허브 GitHub 조직의 Overview 페이지.
전자는 트래픽을 바로 볼 수 있고, 후자는 README에 넣은 이미지의 요청으로 방문을 관측할 수 있다는 착상이다.

신호의 용도는 넷이다.
무응답을 "읽히지 않음"과 "읽힌 뒤 탈락"으로 가르고, 이력서 버전 사이의 관심 차이를 보고, 공고 선별 방식을 검증할 중간 라벨로 쓰고, 커리어허브 기능으로 이어질 수 있는지를 본다.

열려 있던 것은 셋이다.
어떤 신호를 만들 것인가, 방문을 어느 지원 건의 것으로 돌릴 수 있는가, 지원처에 드러나지 않게 할 수 있는가.

## 2. 실측

경로는 `workspace/ref/` 기준이다.

**커리어허브 쪽에서 지금 보이는 것**

- 운영 중인 프런트는 `careerhub-front`이고 해시 라우팅이다. `#` 뒤는 서버에 오지 않아 서버는 어느 화면을 봤는지 알 수 없다 — `careerhub-front/src/App.svelte:2,7`, `docs/careerhub-front/discussion/260717_1456_frontend-renewal-decision-axes.md:48`.
- 분석 태그(GA 등)와 UTM 처리 코드는 프런트 두 저장소 어디에도 없다.
- 외부 요청은 Cloudflare → 터널 → 공개 Gateway(nginx) → 프런트·API 순으로 닿는다 — `jyoliar-k8s/gitops/base/bootstrap/cloudflare-tunnel/config.yml:9-10`.
- 공개 Gateway의 액세스 로그는 Loki에 수집되고 보존은 7일이다 — `jyoliar-k8s/gitops/base/controllers/loki/application.yaml:37`.
- 그 로그 한 줄에는 클라이언트 주소, 시각, 요청 줄(경로와 쿼리스트링), 상태 코드, Referer, User-Agent가 남는다(Loki, 2026-11-15 03:45Z의 줄에서 확인).
- 클라이언트 주소 칸에 클러스터 내부 주소가 아닌 외부 주소가 찍힌다(같은 줄). 원 주소 복원 설정은 `jyoliar-k8s/gitops/overlays/baremetal/services/careerhub/prod/apps/gateway/public-nginx-proxy-patch.yaml:11-16`이다.
- 같은 시각에 `/env.js`, `/__ENV.js` 같은 경로를 훑는 스캐너 요청이 섞여 있다(같은 조회).
- 트레이스는 3일 보존이고, 메트릭에는 사용자·주소·User-Agent 차원을 의도적으로 넣지 않았다 — `jyoliar-k8s/gitops/base/controllers/alloy/application.yaml:251-276`.
- 프런트의 `public/` 아래 파일은 같은 도메인에서 그대로 서빙된다 — `careerhub-front/package.json:9`. 공개 오브젝트 스토리지는 없다.
- Cloudflare 쪽 로그 내보내기나 분석 리소스는 terraform에 없다. 대시보드에서 무엇이 보이는지는 코드로 확인하지 못했다.

**GitHub 조직 Overview 쪽**

- 조직 Overview의 원본은 공개 저장소 `.github`의 `profile/README.md`다 — `docs/careerhub/discussion/261031_1903_careerhub-org-overview-and-infra-readmes.md:26-27`.
- 그 저장소는 `workspace/ref/`에 없어 게시본을 직접 읽지 못했다.

**조사가 말하는 것** (전문은 `related`의 조사 문서)

- GitHub는 README의 외부 이미지를 자체 프록시로 대신 가져온다. 원 서버에 닿는 요청은 GitHub의 주소와 프록시의 User-Agent로 오고 Referer가 없었다는 관찰이 있다(2019년 개인 실험 1건).
- 같은 실험에서 새로고침은 프록시 캐시에서 처리돼 원 서버에 요청이 오지 않았다.
- `Cache-Control: no-cache`로 매번 요청이 오게 할 수 있는지는 근거가 엇갈린다. 공식 문서는 점검 항목으로만 언급하고, 무시됐다는 커뮤니티 보고가 있다.
- 프로필 방문 카운터 프로젝트는 방문자의 주소·User-Agent를 알 수 없고 세는 것이 고유 방문자가 아니라 요청 횟수라고 스스로 적는다.
- GitHub 저장소 Traffic은 최근 14일의 조회 수·고유 방문자·유입 경로를 보여주고 API로도 받을 수 있다. 조직 프로필 조회가 여기에 집계되는지는 근거를 찾지 못했다.
- 원티드는 기업이 지원서를 열람하면 상태를 바꾸고 알림을 준다는 도움말이 있다(검색 요약 수준, 직접 열람 실패). 점핏은 지원자용 공식 자료를 찾지 못했다.
- 채용 담당자가 이력서의 링크를 얼마나 누르는지, 열람·클릭 신호가 서류 통과와 얼마나 관련되는지에 관한 신뢰할 만한 자료는 찾지 못했다.
- 서류 한 건을 보는 시간이 평균 7.4초라는 벤더 연구가 있다(표본·방법 미공개).

## 4. 열린 축 — 논의

### 4-1. 어떤 신호를 만들 것인가

옵션은 서로 배타적이지 않다.
무엇을 묶음에 넣을지가 판정이다.

- A. **플랫폼이 주는 열람 상태** — 지원 플랫폼의 열람 표시·알림을 지원 건마다 기록한다.
  지원 건별 귀속이 처음부터 되고, 만들 것이 없고, 지원처에 드러날 것이 없다.
  "열람"이 목록에서 눌렀다는 뜻인지 본문을 읽었다는 뜻인지 알 수 없고, 한 플랫폼은 제공 여부부터 확인되지 않았다.
- B. **커리어허브 방문** — 공개 Gateway 액세스 로그에서 이력서 링크로 들어온 방문을 본다.
  링크를 눌렀다는 것은 열람보다 강한 관심이고, 로그는 이미 쌓이고 있다.
  보존이 7일이라 늦은 방문을 놓치고, 스캐너 요청을 걸러야 하며, 화면 단위의 행동은 해시 라우팅 때문에 보이지 않는다.
- C. **GitHub Overview의 이미지 요청** — README에 내 도메인의 이미지를 넣고 그 요청을 센다.
  GitHub 링크를 누른 방문까지 닿는 유일한 수단이다.
  방문자의 주소·User-Agent가 프록시에 가려 시각과 횟수만 남고, 캐시 때문에 방문마다 요청이 온다는 보장이 없다. 캐시 동작은 실측해야 안다.
- D. **GitHub 저장소 Traffic** — 조직의 공개 저장소들의 조회 수·고유 방문자·유입 경로를 주기적으로 받아 둔다.
  만들 것이 적고 고유 방문자 수가 나온다.
  14일이 지나면 사라지고, 지원 건별로 나눌 수 없으며, 조직 Overview 조회가 집계되는지 확인되지 않았다.
- E. **링크가 거쳐 가는 내 자산을 새로 둔다** — 이력서의 모든 링크가 내 도메인의 한 페이지나 경유 주소를 지나게 한다.
  GitHub로 가는 방문도 내 로그에 주소·시각과 함께 남아 C의 한계가 사라진다.
  GitHub 링크가 GitHub 주소가 아니게 되어 눈에 띄고(4-3), 새 자산을 만들고 유지해야 한다.
- F. **만들지 않는다** — 최종 결과만 기록한다.
  신호가 결과와 관련된다는 근거가 없으므로 틀릴 일도 없다.
  무응답은 계속 해석할 수 없고, 선별 방식의 검증은 결과가 쌓일 때까지 기다려야 한다.

### 4-2. 방문을 어느 지원 건의 것으로 돌릴 것인가

지원 건별 구분이 가장 좋지만 비용이 있다.
타협 지점을 정하는 축이다.

- A. **지원 건마다 다른 링크** — PDF마다 링크의 대상 주소에 건별 꼬리표를 붙인다.
  방문이 어느 지원 건의 것인지 정확히 나오고, 꼬리표는 쿼리스트링으로 붙이면 지금의 로그에 그대로 남는다.
  지원마다 PDF를 새로 만들어야 하고, 주소를 손으로 옮겨 치면 꼬리표가 빠지며, 주소에 보이는 꼬리표가 드러난다(4-3).
- B. **이력서 버전마다 다른 링크** — 건별이 아니라 이력서 버전 단위로만 꼬리표를 붙이고, 건별 구분은 시점으로 추정한다.
  버전 비교라는 용도는 정확히 충족하고 PDF는 버전 수만큼만 만든다.
  같은 버전으로 같은 주에 여러 곳에 지원하면 어느 건인지 가르지 못한다.
- C. **링크는 하나, 시점으로 대조** — 방문 시각을 지원 일시와 맞춰 본다.
  이력서를 건드리지 않고 드러날 것이 없다.
  주 3~5건이면 겹치고, 플랫폼 밖 유입(검색·봇)과 구분할 근거가 시각뿐이다.
- D. **합계만 본다** — 지원을 시작한 뒤 방문이 늘었는지만 본다.
  가장 싸다.
  네 용도 가운데 어느 것도 충족하지 못한다.

GitHub Overview 쪽은 이미지 요청에 방문자 정보가 없으므로, 4-1의 E를 택하지 않는 한 A·B를 적용할 수 없고 C·D만 남는다.

### 4-3. 지원처에 어디까지 드러나도 되는가

채용 담당자가 추적을 알아챘을 때의 반응에 관한 자료는 찾지 못했다.
그래서 이 축은 근거가 아니라 감수할 위험의 크기로 정한다.

- A. **보이는 것을 만들지 않는다** — 링크는 지금 그대로 두고 서버 쪽 기록만 본다.
  알아챌 것이 없다.
  귀속은 시점 대조(4-2의 C)까지만 가능하다.
- B. **주소에만 남긴다** — 이력서에 보이는 글자는 그대로 두고 링크의 대상 주소에만 꼬리표를 붙인다.
  읽는 사람 눈에는 띄지 않고 귀속이 정확해진다.
  링크에 마우스를 올리거나 누른 뒤 주소창을 보면 보인다. 꼬리표가 무엇으로 읽히는가는 모양에 달려 있다.
- C. **밝힌다** — 열람 확인용 링크임을 이력서에 적는다.
  숨긴 것이 없어 들켰을 때의 위험이 없다.
  이례적이고, 적어 둔 것 자체가 평가에 영향을 줄 수 있다.
- D. **GitHub 링크까지 내 주소로 바꾼다** — 4-1의 E에 해당한다.
  GitHub 쪽 방문도 귀속된다.
  GitHub 링크가 GitHub 주소가 아닌 것은 가장 눈에 띈다.

## 5. 반대편 — 이 설계가 틀리는 조건

- 서류 심사에서 링크를 누르는 일이 드물면 신호가 거의 생기지 않는다. 그 비율에 관한 자료가 없다.
- 신호는 한쪽으로만 읽힌다. 방문이 있으면 읽혔다는 뜻이지만, 방문이 없다고 읽히지 않았다는 뜻은 아니다.
- 열람·클릭이 서류 통과와 관련된다는 근거가 없다. 중간 라벨로 삼으면 통과가 아니라 클릭을 부르는 이력서와 공고를 고르게 될 수 있다.
- GitHub 쪽 이미지 요청은 캐시에 막혀 실제 방문보다 적게 잡힐 수 있고, 얼마나 적은지 알 수 없다.
- 플랫폼의 링크 미리보기나 보안 스캐너가 사람보다 먼저 링크를 열면 방문으로 잘못 잡힌다.
- 로그 보존이 7일이라, 지원 뒤 한참 지나 열람하는 곳은 놓친다.
- 지원이 주 3~5건이라 버전 비교나 선별 검증에 쓸 만큼 신호가 쌓이는 데 오래 걸린다.
- 커리어허브 기능으로 옮기면 다른 사람의 접속 기록을 다루게 된다. 접속 주소가 개인정보에 해당하는지는 2차 자료만 확인했다.

## 6. 버린 것

- **외부 문서 추적 서비스** — 내 자산만 계측한다(3-2).
- **이메일 열람 추적** — 지원이 플랫폼을 거치므로 지원처에 보내는 메일이 없다.
- **프런트에 분석 태그를 붙여 화면 단위 행동을 본다** — 서류 열람 여부를 가르는 데는 첫 요청이면 충분하고, 분석 태그는 별도 논의에서 이미 다뤘다(`docs/careerhub-front/discussion/260717_1617_measurement-trust-and-transport.md`).

## 7. 임계선 — ADR감인가

ADR감이 아니다.
개인 검증 단계의 신호는 로그 질의와 이력서 파일로 만들고, 그만두면 흔적이 남지 않는다.
임계선은 둘에서 생길 수 있다.
로그 보존 기간을 늘리는 것은 코드 변경이고 티켓이다.
이 신호를 커리어허브가 다른 구직자에게 제공하기 시작하면 제3자의 접속 기록을 처리하는 결정이 되고, 그것은 되돌리기 어렵다.
