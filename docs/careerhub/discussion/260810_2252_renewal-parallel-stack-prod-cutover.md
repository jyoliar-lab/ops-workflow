# 리뉴얼은 prod에 바로 — 병행 스택·컷오버·스키마 동결의 정제

## 문제

careerhub 리뉴얼에 dev/staging 환경 도입을 검토했으나 보류하기로 했다.
근거: 환경 구조를 잡는 공수가 크고, 리뉴얼 방향의 확립이 모니터링·개발·배포 체계보다 선행해야 한다.
따라서 리뉴얼 스택은 prod에 바로 선다.
남는 질문은 셋이다: 공개 전 검증을 어디서 하는가 · 컷오버를 어떻게 하는가 · 그동안 레거시(실사용자)를 어떻게 보호하는가.

제안된 방안: 별도 엔드포인트(`dev-careerhub.jyo-liar.com`)에 리뉴얼 스택을 세워 검증하고, 컷오버 시점에 DNS 레코드를 전환한다.
제약: auth-service의 DB 스키마는 컷오버 전까지 변경 금지.

## 먼저 — 이 방안의 실체를 정확히 부르면 판단이 쉬워진다

이 스택은 dev 환경이 아니다.
같은 클러스터에서 prod 데이터 플레인(auth PG · userinfo Mongo · Zitadel 원장)을 공유하고, 테스트 로그인이 실원장에 실사용자를 만든다.
실체는 **prod의 미공개 면(blue-green의 green)** 이다 — 병행 신스택을 세워 두고 전환식으로 넘어가는 것.

방향 자체는 지지한다.
기존 라우팅 논의(`260810_1801`)의 종착 그림 — "레거시는 손대지 않는다, 경로 기반인 채 컷오버 때 루트째 소멸한다" — 과 정확히 맞물리고, in-place 순차 교체 대비 롤백이 압도적으로 싸다.
아래는 방향 지지 위에서의 반론·정제 4건이다.

## 병행 스택의 실제 구성 — 전부가 이중화되는 것이 아니다

- **이중화되는 것: careerhub-web · api-composer(신버전).**
  web은 새 공개 호스트에 서고, 신 composer는 BFF 판정(`260810_1801`)에 따라 공개 호스트 없이 내부 전용으로 병행 배포된다.
  구 composer는 레거시 루트의 `/api`를 컷오버까지 계속 서빙한다.
- **신설되는 것: Zitadel.** 구버전이 없으므로 병행이 아니라 그냥 신규다.
- **겸직하는 것: auth-service.**
  단일 인스턴스가 레거시 표면(OAuth 왕복·발급)과 신규 표면(공용 모듈 검증·클레임 공급)을 함께 서빙하다가, 컷오버 후 레거시 표면을 철거한다.
  병행 이중화가 아니다 — 그래서 이 서비스의 코드·스키마 변경만 유일하게 레거시를 깨뜨릴 수 있고, 스키마 제약이 여기 걸리는 것이 정확하다.
- **공유되는 것: 게이트웨이(nginx-gateway-fabric) · 데이터 플레인 전부.**
  게이트웨이는 새 리스너·인증서 SAN이 추가될 뿐 별도 인스턴스가 아니다.

## 반론 ① — `dev-careerhub`라는 이름은 이미 다른 것으로 예약되어 있다

`260810_1801`이 환경 네임스페이스를 판정하며 `*.dev-careerhub.jyo-liar.com`을 **미래의 진짜 dev 환경**(형제 네임스페이스)으로 정해 뒀다.
그 판정의 근거는 격리였다 — 환경(prod/dev)은 쿠키 상속 경계가 아니라 격리 경계이므로 제품 네임스페이스 밖 형제로 둔다.
진짜 dev 환경은 별도 데이터 플레인을 갖는 격리 공간이어야 한다.

그런데 이번 스택은 prod 데이터를 공유한다 — 격리의 반대다.
prod 데이터 플레인에 붙은 스택이 dev 이름표를 달면:

- **분류가 거짓말을 한다.** SSM 경로 관례(`/<도메인>/<env>/<용도>`)·매니페스트의 env 축에서 이 스택은 전부 prod인데 이름만 dev다.
- **"어차피 추후 도입"이 성립하지 않는다.** 미래의 dev 환경은 이 스택이 아니다(데이터 플레인이 다르다). 이 호스트를 물려줄 수 없으므로 선점의 실익이 없고, 오히려 진짜 dev가 생길 때 이름의 의미가 이미 오염되어 있다.
- **"dev 환경이 있다"는 거짓 신호가 남는다.** 다음에 이 호스트를 보는 사람(사람이든 agent든)은 격리 환경으로 오인하고 파괴적 테스트를 한다 — prod 원장 위에서.

## 정제 ① — 임시 호스트가 아예 필요 없을 수 있다

리뉴얼 web의 **최종 호스트가 레거시 apex(`careerhub.jyo-liar.com`)와 다르다면**, 신스택을 처음부터 최종 호스트에 세우면 된다.
`260810_1801`은 신규 공개면을 `*.careerhub.jyo-liar.com` 2단 아래로 정했고 web의 호스트명은 컷오버 시 확정으로 열어 뒀다 — 예컨대 `www.careerhub.jyo-liar.com`이 최종이라면:

- 공개 전 검증을 최종 호스트에서 그대로 한다 — 옮겨 세울 일도, 임시 이름을 지울 일도 없다.
- OIDC redirect URI·e2e 설정·env가 처음부터 최종값이다 — 컷오버 때 재설정 항목이 0에 수렴한다.
- 컷오버는 "레거시 apex의 처분"으로 축소된다 — 리다이렉트를 걸거나 루트째 소멸시키거나.
- 비공개 유지가 걱정이면: 공표 전까지 robots/noindex + (원하면) 게이트웨이 수준 basic auth 한 장이면 충분하다 — 사용자 1명 규모에서 비밀 유지가 목적이 아니라 오인 방지가 목적이다.

apex를 최종 호스트로 쓰고 싶다면 그때만 임시 호스트가 필요한데, 그 경우에도 prod 네임스페이스 안의 한시 이름(`next.careerhub.jyo-liar.com` 류)이 실체와 맞다 — dev 이름은 어느 경우에도 맞지 않다.

컷오버의 수단도 정확히는 DNS 레코드가 아니라 **HTTPRoute의 hostname 전환**이다 — 레코드는 external-dns가 HTTPRoute에서 파생하므로(ADR-0034의 방향과도 정합) 매니페스트 커밋이 곧 컷오버가 되고, git revert가 곧 롤백이 된다.

## 반론 ②/정제 ② — 스키마 "동결"은 그대로 두면 리뉴얼 자체와 모순된다

동결의 진의는 "레거시 auth-service가 컷오버까지 죽지 않아야 한다"이고, 이것은 옳다.
그러나 문자 그대로의 변경 금지는 리뉴얼 계획과 모순된다 — 사용자 원장 재편(Zitadel sub 채택)은 스키마 변경 그 자체이고, 신스택은 그것 없이는 prod 데이터로 검증될 수 없다.

**expand/contract로 정제한다:**

- **컷오버 전 — expand만 허용.**
  추가만 한다: 새 컬럼(예: Zitadel sub 매핑)·새 테이블·새 인덱스.
  기존 컬럼·제약·타입은 불변 — 레거시 코드가 읽고 쓰는 표면이 그대로면 레거시는 깨지지 않는다.
  "동결"이 지키려던 것을 전부 지키면서 신스택 검증이 가능해진다.
- **컷오버 후 — contract.**
  레거시 컬럼(`authorized_by`/`authorized_id` 등)·구 식별자 의존을 인증 경로 철거와 같은 국면에서 제거한다.

## 정제 ③ — 진짜 컷오버는 라우팅이 아니라 데이터 치환이다

라우팅 전환은 언제든 되돌릴 수 있다 — 레거시 스택이 살아 있는 한.
되돌릴 수 없는 것은 **식별자 백필**(auth 원장 값 치환 · userinfo `userId` 백필)이다.
백필이 돌면 구 composer→userinfo 경로는 구 식별자로 조회해 빈 결과를 받는다 — 레거시는 그 순간부터 사실상 죽는다.
따라서 롤백 창의 끝은 라우팅 전환이 아니라 백필 실행 시점이고, 절차는 이 순서여야 한다:

1. 신스택 검증 완료(최종 호스트에서, prod 데이터 read 위주로).
2. 레거시 write 정지(사용자 1명 — 실질적으로는 "잠깐 안 쓰기").
3. 식별자 백필 실행 — **여기가 one-way door**(노출 식별자 불변 원칙과 같은 축).
4. 라우팅 전환(HTTPRoute hostname / apex 처분).
5. 관찰 기간 — 레거시 스택은 배포된 채 둔다(롤백은 이제 백필 역치환까지 포함하므로 관찰이 값싸진 게 아니라, 라우팅 문제에 한해 revert가 가능한 상태).
6. contract 국면 — 인증 경로 철거·대칭키 컷오버·레거시 컬럼 제거·레거시 루트 소멸.

## 반전 — 가용성을 버리자 제약이 연쇄로 녹았다

식별자 백필이 one-way door라는 판정(정제 ③)이 서자, 사람이 방향을 반전시켰다: **레거시의 단기간 중단(엔드포인트 접근 불가, 며칠 수준)을 감수한다.**
근거는 규모다 — 실사용자가 운영자 본인 1명이고, 며칠의 접근 불가가 아쉽지 않다.
가용성은 이 시스템에서 지킬 가치가 가장 싼 속성이었는데, 앞의 정제 ②·③은 전부 그것을 지키는 비용이었다.

이 한 판정이 녹인 것들:

- **스키마 expand/contract(정제 ②)가 통째로 불필요해진다.**
  동결도 2단계 분리도 레거시가 같은 DB 위에서 살아 있어야 한다는 전제의 산물이었다.
  레거시가 정지된 창 안에서는 원장 재편·백필을 one-shot으로, 파괴적 변경 포함해서 그냥 하면 된다.
- **전환기 이중 검증(레거시 대칭키 병행 수용)이 불필요해진다.**
  점진 전환이 없으므로 신스택은 Zitadel 토큰만 알면 된다 — 검증 전환 티켓의 이중 수용 요구는 하드 컷오버에서 소멸한다.
- **유통 토큰 만료 대기(24h)가 무의미해진다.**
  레거시가 정지되면 유통 중 대칭키 토큰을 받아줄 표면이 없다 — 대칭키 제거를 만료에 게이트할 이유가 없어진다.
- **임시 호스트·이름 논점(반론 ①·정제 ①)이 소멸한다.**
  레거시 정지가 apex를 비우므로, 최종 호스트가 apex여도 신스택을 바로 거기 세워 검증할 수 있다.
  `dev-careerhub` 이름은 쓸 자리 자체가 없어졌고, 그 네임스페이스는 미래의 진짜 dev 환경 예약분으로 온전히 남는다.
- **write 정지 절차가 별도로 필요 없다.** 정지가 곧 freeze다.

### 반전 후의 절차 — 컷오버 = 중단 창

**0. 사전 국면(레거시 무중단).**
레거시와 무간섭인 모든 것을 먼저 끝낸다: 백업 체계 신설과 복구 실측 · Zitadel 배치(최종 호스트)·초기 구성·소셜 브로커 로그인 검증 · 클레임 공급 endpoint · careerhub-web 개발과 e2e.
Zitadel은 신설이고 web은 새 호스트라 레거시를 건드리지 않는다.

**1. 중단 창 개시 — 레거시 정지.**
HTTPRoute 제거 또는 replica 0 — 매니페스트 커밋 하나다.

**2. DB 백업 — 롤백 지점.**
실측 검증된 백업 체계가 이 시점의 전제다.
롤백 수단이 "라우팅 revert"에서 **"백업 복원 + 레거시 재기동"** 으로 바뀌었다 — 백업 복구 실측이 컷오버의 안전망으로 승격된 것이 이 반전의 숨은 대가다.

**3. 원장 재편·백필 one-shot.**
auth 원장의 sub 치환·userinfo `userId` 백필·레거시 컬럼 정리까지 한 국면에서.

**4. 신스택 통합 검증 — 최종 호스트에서, 며칠 걸려도 된다.**
중단 창의 길이는 이 검증이 정한다.

**5. 공개.**
실패가 크면 2의 백업으로 복원하고 레거시를 재기동한다 — 창 안에서는 언제든 되돌아갈 수 있다.

**6. 이후 여유 국면.**
인증 경로 철거·대칭키 제거·레거시 루트 소멸은 급할 것이 없어졌다 — 레거시는 이미 죽어 있다.

## 감수하는 것 — 공유 데이터 플레인의 검증 잔재

검증 중의 테스트 로그인은 Zitadel 원장·auth DB(동의 등)·userinfo에 실데이터를 남긴다.
사용자 1명 규모에서 격리 비용(별도 DB + 재이전)이 오염 비용을 압도하므로 수용한다.
다만 테스트 계정을 명시적으로 식별 가능하게 만들고(전용 소셜 계정 등), 컷오버 전 정리 목록을 유지한다 — "수용"과 "방치"는 다르다.

## 버린 대안

- **in-place 순차 교체 — 서비스별로 prod 현행 배포를 직접 갈아끼운다.**
  버린 이유: 롤백이 배포 단위 revert의 연쇄가 되고, 검증이 곧 실사용자 노출이다.
  레거시 무변경 원칙(`260810_1801`)과도 어긋난다.
- **dev/staging 환경 선행 도입.**
  이번에 보류로 판정된 것의 기록: 환경 구조의 공수가 크고, 리뉴얼 방향 확립이 선행해야 한다.
  병행 스택 방식이 그 공수 없이 전환식 컷오버의 핵심 이득(검증·싼 롤백)을 취한다.
  진짜 dev 환경(격리 데이터 플레인)은 리뉴얼 이후의 별도 논의로 남는다 — 네임스페이스는 `260810_1801`이 이미 예약해 뒀다.

## 수렴 대기 — 반전 이후 남은 것

- **careerhub-web의 최종 호스트명** — apex 승계든 `*.careerhub` 하위든 이제 자유 선택이다(임시 호스트 제약이 소멸했으므로 순수 네이밍 취향·구조 판단만 남았다).
- **중단 창의 개시 시점** — 사전 국면(0)의 완료가 조건이고, 시점 자체는 사람이 정한다.
- **티켓 조정의 승인** — 검증 전환의 이중 수용 요구 제거 · 대칭키 제거의 만료 대기 제거 · 컷오버 절차의 티켓화 여부.

정제 ②(expand/contract)와 반론 ①·정제 ①(호스트 이름)은 반전으로 무효가 되었으나 본문에 남긴다 — 가용성을 다시 지켜야 하는 날(실사용자가 생기는 날)이 오면 그대로 되살아나는 논리다.
