> **수렴(2026-08-05)** — 패턴(다른 서비스가 로컬 user_id로 인덱싱)은 옳다. 논점은 식별자의 격이었고,
> **"시스템 전역 사용자 정체성은 저장소 독립적으로 발급된 불변 식별자로 하고, 저장소 PK를 외부에 노출하지 않는다"** 로 수렴했다.
> 근거는 원리가 아니라 비용 비대칭이다 — 사용자가 1명(운영자 본인)이라 지금 바꾸는 비용이 ~0이고, 미루는 비용은 사용자 수에 단조증가한다.
> ADR 초안 파생은 사람이 보류했다("기록까지만"). 초안이 나가기 전까지 `active`로 둔다.

# auth-service의 user_id가 다른 서비스의 인덱스로 쓰이는 것은 적절한가

## 물음

`260804_1831_auth-rebuild-implementation-approach.md` §③이 관찰로 남긴 사실 — auth-service의 `user_id`가
userinfo-service MongoDB의 인덱스에 박혀 있어 외부 IdP 도입이 어렵다 — 에서 한 걸음 물러나 묻는다:
**애초에 auth-service의 user_id가 다른 서비스의 인덱스로 쓰이는 것이 적절했나.**

## 질문의 분해 — 하나의 물음 안에 성격이 다른 두 판정이 있다

| | 판정 |
|---|---|
| **A. 다른 서비스가 auth의 사용자 식별자로 데이터를 인덱싱한다** | **적절. 필수에 가깝다** |
| **B. 그 식별자가 auth-service 저장소의 serial PK다** | **여기가 논점이었다** |

## A — 패턴은 옳다. 대안이 전부 더 나쁘다

| 대안 후보 | 왜 지는가 |
|---|---|
| email로 묶는다 | OIDC Core가 명시 배제(*"MUST NOT be used as unique identifiers"*) — 가변이고 재사용된다. 260804_1831 6절 9번에 근거가 있다 |
| (authorized_by, authorized_id) = IdP 정체성으로 묶는다 | IdP 결합이 도메인 데이터까지 내려간다. 계정 연결·프로바이더 변경·IdP 교체마다 다운스트림 문서 전체가 재작성 대상이 된다 — 260804_1831 §9의 `sub` 변동 조건 전부가 데이터 마이그레이션 트리거가 된다 |
| 매 조회를 auth에 조인 | 서비스 분리를 무의미하게 만드는 런타임 결합 |

**로컬 정체성을 다운스트림에 흘리고, IdP 정체성은 auth 안에 가둔다** — 260804_1831 §③이 수렴한 "로컬 원장 소유"의 올바른 귀결이고, 코드도 이 경계를 지키고 있다:

- `authorized_by`·`authorized_id`는 auth-service `user` 테이블에만 있다 — `UNIQUE (authorized_by, authorized_id)` (`auth-service/sql/migrations/00001_init_schema.sql`)
- userinfo-service에는 `userId`만 내려간다 — unique 인덱스 `userId_1`(matchjob), `userId_1_site_1_postingId_1`(scrapjob) (`careerhub-userinfo-service/internal/migration/migrations/001_create_initial_indexes.go`)

**정직한 교정 하나** — §③의 "user_id가 박혀 있어 IdP가 어렵다"는 어려움의 원인은 인덱스로 쓰인 것이 아니라
**로컬 원장을 소유한다는 사실 자체**다. user_id가 UUID였어도, 아예 안 흘렀어도, IdP의 `sub`는 로컬 id를
대체하지 못하고 옆에 붙는 열이 됐을 것이다. 이 패턴을 바꿨더라도 그 논의의 결론은 안 바뀌었다.

## B — 문제의 정확한 이름: "정수"가 아니라 "저장소가 발급한다"

코드가 말하는 실체:

- `user_id serial NOT NULL ... PRIMARY KEY` — PostgreSQL 순차 정수 (`auth-service/sql/migrations/00001_init_schema.sql`)
- JWT claim으로 나가고(`auth_service/restapi/jwtresolver/claims.go`의 `UserId string`), 컨트롤러마다 `strconv.Atoi` 왕복
- api-composer가 토큰에서 꺼내 gRPC로 내려보내고, userinfo-service가 그 값으로 저장·조회한다

**판별 질문은 "정수인가"가 아니라 "이 값을 그 테이블 없이 재현/보존할 수 있는가"다.**
serial의 결함은 자료형이 아니라 발급 방식이다 — 값이 *그 테이블에의 삽입 순서*의 함수라서,
정체성이 특정 PostgreSQL 인스턴스의 시퀀스 상태에 묶인다. 반례 둘로 확인했다:

- 독립 발급한 랜덤 int64였다면 정수여도 문제 대부분이 없다
- DB가 `DEFAULT gen_random_uuid()`로 발급하는 UUID는 자료형이 UUID여도 발급 주체가 저장소라는 점은 같다 (다만 UUID는 순서 무관·전역 유일이라 재구축 제약 자체가 소멸한다)

### serial의 실질 비용 — 과장하지 않는다

- **재구축 시 암묵 제약**: user 테이블을 다시 만들 때 반드시 값 보존 마이그레이션 + 시퀀스 재설정을 해야 한다. 어기면 userinfo의 문서들이 조용히 다른 사람의 것이 된다. 이 제약은 어디에도 적혀 있지 않고 스키마만 봐서는 보이지 않는다.
- **열거 가능성**: 순차 정수는 사용자 수를 노출하고 추측 가능하다. 서명 토큰 뒤에 있어 당장의 위협은 아니다.
- **재사용 위험은 이미 구조로 막혀 있다**: 탈퇴가 삭제가 아니라 익명화 UPDATE(`authorized_by='DELETED', status='DELETED'`, `auth-service/sql/queries/user.sql`)라 행이 남고 serial이 재발급되지 않는다. "탈퇴자의 id를 신규 가입자가 상속"하는 최악 시나리오는 없다.

지금까지 실제로 아팠던 것(§③)은 serial 탓이 아니었다. "serial은 나쁘니 UUID"는 형용사 비교다 —
이 결정을 가르는 것은 식별자의 미덕이 아니라 **재작성이 저장소를 갈아엎는가**라는 다른 결정이다.

## 옵션과 이기는 조건

| | 이기는 조건 | 지는 조건 |
|---|---|---|
| **B1. serial 유지 + 제약 명문화** | 재작성이 user 테이블 스키마를 크게 안 건드릴 때. 비용이 ADR 한 줄("재구축 시 값 보존")로 끝난다 | 재작성이 어차피 테이블을 다시 만들 때 — 값 보존 마이그레이션이라는 일을 하면서 얻는 게 현상 유지뿐 |
| **B2. 저장소 독립 id로 교체** | 재작성이 어차피 user 테이블을 재창조할 때 — 마이그레이션의 증분 비용만 낸다(userinfo unique 인덱스 2개 재작성 + 문서 `userId` 치환 + JWT claim) | 사용자 수가 커서 치환 비용이 크거나, 저장소를 그대로 물려받을 때 |
| **B3. 내부 PK / 노출 id 분리** | 저장 효율과 노출 안전을 정말 따로 최적화할 필요가 있을 때 | careerhub 규모 — 근거가 없다 |

## ✔ 수렴 — 사실 두 개가 들어와 닫혔다

판정에 걸려 있던 사실: ① 재작성이 user 테이블을 재창조하는가 ② 현재 가입자 수.
사람의 답: **① 재창조 가능 ② 1명(운영자 본인).**

- B1의 유일한 매력(마이그레이션 회피)이 소멸한다 — 치환할 문서도 본인 것뿐이고, 극단적으로는 버리고 재로그인해도 된다.
- 미루는 비용은 사용자 수에 단조증가한다. *지금은 가역, 나중은 불가역* — 이 비대칭에서는 지금 정한다.
- → **B2 채택.** 결정 문장: **시스템 전역 사용자 정체성은 저장소 독립적으로 발급된 불변 식별자로 하고, 저장소 PK를 외부에 노출하지 않는다.**

**결정의 경계(§4①)** — UUIDv4/v7/ULID 선택, 발급 주체(앱/DB)는 **코드의 관할**이다. 발급 방식은
되돌리기 쉽다(바꿔도 기존 값은 유효). 되돌리기 어려운 것은 "저장소 독립 발급"이라는 성질과
"노출된 식별자는 불변"이라는 계약뿐이고, ADR은 거기까지만 담는다.

**공동무효 판정(§4③)** — 계정 연결·정체성 저장 모델(260804_1831 열린 질문 5)과 **별개 ADR**이다:
연결 정책이 뒤집혀도 이 결정은 유효하고, 그 역도 같다. 관계는 `references`로 잇는다.
(논의 초반에는 "한 ADR로 묶일 가능성이 높다"고 봤으나 판정을 실제로 돌려 뒤집었다.)

이 수렴은 260804_1831의 **열린 질문 1번을 해소한다** — "현재 가입 사용자가 몇 명인가"의 답이 1이므로,
*"유일하게 시간이 비용을 밀어 올리는 축"* 의 시간 압력은 사실상 없다. 단, 사용자가 늘기 시작하면 되살아난다.

## 검토하고 버린 것

- **email·(authorized_by, authorized_id)·조인을 키로 쓰는 것** — A절의 표. 패턴 자체를 바꿀 이유가 없다.
- **"정수라서 문제"라는 진단** — 자료형이 아니라 발급 방식이 문제다. 랜덤 int64 반례로 기각.
- **B1 (serial 유지 + 제약 명문화)** — 원리적으로 정당한 옵션이었으나, 재창조 가능 + N=1로 이기는 조건이 소멸했다.
- **B3 (내부 PK / 노출 id 분리)** — 복잡도 하나가 늘고, careerhub 규모에서 두 축을 따로 최적화할 근거가 없다.
- **계정 연결 ADR과 한 문서로 묶는 것** — 공동무효 판정 결과 독립. 별개 ADR + `references`.
- **UUID 버전·발급 주체를 결정에 포함하는 것** — 코드의 관할(§4①). ADR에 넣으면 코드가 답할 것을 문서가 참칭한다.
