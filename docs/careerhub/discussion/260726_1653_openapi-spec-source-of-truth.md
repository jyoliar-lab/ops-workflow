# api-composer OpenAPI 스펙의 원천 — code-first vs spec-first

## 발단

티켓 [#5](https://github.com/jyoliar-lab/ops-workflow/issues/5) 착수 중, Requirements가 범위 밖으로 둔 spec-first가 오히려 적합하지 않은가라는 논점이 제기됐다(이슈 코멘트, 2026-07-26). 사람 판정: 임의로 닫지 않고 discussion으로 두 방향을 벌린 뒤 결정한다. **티켓 #5는 수렴까지 보류.**

## 문제 재진술

표면 논점은 "핸들러를 생성하느냐"가 아니다. 진짜 질문은:

> **REST 계약 스펙의 원천을 무엇으로 하는가 — 코드(Go 구조체)인가, 독립 명세(YAML)인가.**

주의 — **ADR-0014는 이 축을 정하지 않았다.** ADR-0014가 고정한 것은 프론트 측 원칙("REST 계약 타입의 원천 = 백엔드 **스펙**")뿐이고, 백엔드가 그 스펙을 코드에서 생성하든 손으로 유지하든 관할 밖이다(Consequences 마지막 단락). "진실 = `common/domain/` 구조체"는 티켓 #5의 Goal이 정한 것이다. 따라서 spec-first로 가더라도 ADR-0014의 supersede가 아니라 **별개의 새 결정**이다.

두 층위의 아픔을 구분한다:

- **지금 실재하는 아픔** — 계약이 어디에도 명세돼 있지 않고, 위반이 조용하다(티켓 #5의 문제).
- **제기된 잠재적 아픔** — ① 계약이 구현의 부산물이 된다 ② 스펙 표현력이 Go 타입계 상한에 갇힌다(enum·nullable vs 생략·에러 응답) ③ 스펙이 서버를 기술할 뿐 구속하지 않는다.

## 사실 확인 (코드에서)

`careerhub-api-composer` 기준:

- 활성 핸들러 **19개** (`careerhub/apicomposer/controller/*.go`, 등록 20건 중 1건 주석)
- 응답 인코딩은 컨트롤러 내 인라인(`json.NewEncoder`), 에러는 `http.Error`(text/plain)
- 미들웨어 체인 실재: `jwtresolver/` · `middleware/`(trace_logger 포함) · otelmux
- → spec-first의 강제력(생성 인터페이스 구현 = 컴파일 구속)을 얻으려면 위 전부의 재서명·재통합이 선행된다. **"사실상 HTTP 계층 재작성"이라는 코멘트의 비용 추정은 과장이 아니다.**

## 사실 확인 2차 (도구·의존)

- **oapi-codegen이 gorilla/mux를 직접 지원한다** (`gorilla-server: true`). `HandlerFromMux(si, r *mux.Router)`가 기존 라우터를 BaseRouter로 받으므로, 생성 핸들러를 **컨트롤러 단위로 손 라우트와 공존**시킬 수 있다 → 빅뱅 재작성 불필요, 되돌림도 컨트롤러 단위. "19개 전면 재서명 선행"이라는 초기 비용 추정은 이 지점에서 **과대**였다.
- 기본 모드의 생성 시그니처는 표준 `(w, r)`라 라우터 레벨 미들웨어(otelmux·JWT context)가 대부분 생존한다. 단, **응답 타입의 컴파일 구속(한계 ③ 해소)은 `strict-server` 모드**가 필요하고 그것이 진짜 재서명이다 — 이것도 컨트롤러 단위 점진 적용 가능.
- **티켓 #12(프론트 타입 파이프라인)가 #5에 블로킹돼 있다**("#5 완료 전 착수 불가"). 스펙이 늦게 존재할수록 프론트 리뉴얼의 타입 계층이 늦어진다 — B의 지연 비용은 백엔드 안에서 끝나지 않는다.

## 옵션

### A. code-first 진행 (현 Requirements)

리플렉션 생성 + 스펙 파일 커밋 + CI 신선도 게이트.

- 지금의 아픔을 즉시 푼다. **가역** — 생성기를 버리면 끝.
- 산출물(커밋된 스펙)은 spec-first 전환 시 **초기 YAML로 승계 가능** — 매몰비용이 아니라 디딤돌. 단 오독 주의: 승계로 절감되는 것은 B의 전환 비용 중 **스펙 저작분뿐**이다. B의 본체 비용(서버 재작성 — 아래)은 그대로 남는다. 즉 "A가 B를 쉽게 만든다"가 아니라 **"A가 B를 방해하지 않는다"**. 승계되는 YAML의 품질도 Go 타입계 상한에 갇힌 채 넘어가므로(빈약한 enum·에러 스키마가 초기 스펙이 됨) 전환 시점에 보강 저작이 필요할 수 있다.
- 스펙을 커밋하는 순간 계약 변경이 PR diff에 드러난다 — "변경 후 감지"가 아니라 **머지 전 리뷰**다. spec-first와의 실질 차이는 "구현 전 설계 합의"뿐인데, 이는 계약의 생산자·소비자가 다른 팀일 때의 가치다.
- 잠재적 아픔 ②③은 내부에서 완화 가능: 보강 선언(enum·nullable·에러 스키마), 라우트→응답 타입 커버리지 테스트.
- 남는 간극: 완화는 완화일 뿐 — 보강 선언이 비대해지면 사실상 손 스펙이 된다.

### B. spec-first 전환

손 YAML을 원천으로, 생성 인터페이스로 서버를 컴파일 구속.

- 잠재적 아픔 ①②③을 구조로 해소 — 표현력·구속력의 상한이 없다.
- **one-way door**: 19 핸들러 재서명 + 미들웨어 재통합 + `common/domain/`↔생성 타입 관계 재설계. 별개 ADR 감.
- 지금의 아픔(명세 부재)은 재작성이 끝나야 풀린다 — 값이 나오는 시점이 가장 늦다.
- 진실이 "손으로 유지하는 YAML"이 된다 — 티켓 #5가 배제한 "사람이 동기화를 기억해야 하는" 지점이 스펙↔구현 사이에서 스펙↔의도 사이로 이동할 뿐이라는 반론 가능. (생성 인터페이스가 구현 쪽 동기화는 강제하므로 대칭은 아니다.)

### D. 하이브리드 — 진실은 즉시 YAML로, 구속은 점진으로

사실 확인 2차가 만든 옵션. 결정("원천 = 독립 스펙")은 B와 같되 실행이 다르다:

1. **부트스트랩**: 일회성 리플렉션 덤프(또는 손 전사)로 현행 계약을 YAML화하고, 그 순간부터 **진실 = YAML**로 선언. 스펙이 즉시 존재하므로 #12가 바로 착수 가능 — A의 "즉시 값"을 B 안에서 얻는다.
2. **점진 구속**: 컨트롤러 단위로 gorilla-server → strict-server 전환. 미들웨어 국면과 실행만 겹칠 수 있다(결정·티켓은 분리).
3. **전환기 게이트**: 아직 생성 인터페이스로 구속되지 않은 컨트롤러에 대해 스펙이 거짓말할 수 있는 구간이 남는다. **A의 생성기를 전환기 검증 도구로 유지** — 코드에서 뽑은 스펙과 YAML을 diff해 미이행 라우트의 표류를 CI가 잡는다. 전 컨트롤러가 구속되면 생성기를 폐기한다.

- 남는 약점: 부트스트랩 YAML의 품질이 Go 타입계 상한에서 출발한다(보강 저작은 전환 중 점진적으로). 전환기 diff 게이트는 A의 구현 비용 일부를 어차피 치른다는 뜻이기도 하다.

### C. 안 한다 (현상 유지)

계약은 계속 Go 구조체에만 산다.

- 비용 0처럼 보이지만, 조용한 계약 위반("화면만 비어 보인다")이 지속되고 프론트 리뉴얼(ADR-0014 이행)이 전제를 잃는다. **현상 유지의 비용이 이미 실증된 상태** — 티켓 #5의 Context가 그 기록이다.

## 판정 축

| 축 | A (code-first) | B (spec-first) | C (안 한다) |
|---|---|---|---|
| 되돌리기 비용 | 낮음 (생성기 폐기) | **높음** (재작성의 역방향) | — |
| 지금의 아픔 해소 | 즉시 | 재작성 후 | 안 됨 |
| 스펙 표현력 | Go 타입계 + 보강 선언 | 상한 없음 | — |
| 서버 구속력 | 커버리지 테스트 수준 | 컴파일 타임 | 없음 |
| 누가 떠안나 | CI·생성기 유지보수 | HTTP 계층 재작성 + YAML 저작 | 프론트(런타임 디버깅) |
| 전환 경로 | A→B: 스펙 저작분만 승계, 재작성 비용은 잔존 | B→A는 사실상 없음 | — |

## 각 옵션이 이기는 조건

- **A가 이긴다**: 소비자가 프론트 하나(같은 운영자) / 계약 변경 리뷰는 PR diff로 충분 / 보강 선언이 소수에 그침.
- **B가 이긴다**: 외부·다중 소비자 등장 / 계약 설계 리뷰가 구현 **전에** 필요해짐 / 보강 선언이 비대해져 사실상 손 스펙 / code-first 감지를 뚫는 계약 위반 실증.
- **C가 이긴다**: 없음 — ADR-0014가 accepted인 이상 C는 그 전제를 방치하는 것.

## 확정된 것 (사람 판정, 2026-07-26)

- **미들웨어 구조 개선은 #5에 포함하지 않는다.** 사람 의도 확인 결과 특정 아픔이 있는 것이 아니라 "spec-first 진행 중 발견되는 구조 이슈를 겸사겸사"였다 → 선행 티켓 없음. 처리 규칙: 기계적·국소적(계약·동작 불변) 발견은 같은 작업에서 커밋 분리로 수행, 구조적 발견은 #5 코멘트로 기록 후 실재해지면 별개 리프 티켓으로. (관찰→코멘트→티켓의 일반 원리 적용)

## 수렴 (사람 판정, 2026-07-26) → ADR-0018 파생

- **B(전면 spec-first) 채택** — 원천 = 독립 YAML 스펙, 서버는 생성 인터페이스로 구속.
- **구속력은 응답 타입 컴파일 구속(strict)까지** — 한계 ③을 해소하지 않으면 B를 택한 이유의 절반이 사라진다는 논거 수용.
- **D(하이브리드) 기각** — 진실 선언은 **구속 완료 후**. 전환 완료 전에 하류(#12)를 병렬 진행할 계획이 없어 즉시 선언의 이득이 없고, 전환기 diff 게이트는 A의 구현 비용을 중복 지불. #12 블로킹 지속을 대가로 받아들임.
- **A(code-first) 기각** — 세 한계가 구조적이고, 전환 비용은 엔드포인트 수에 비례해 커지므로 가장 적은 지금이 가장 싸다. **실증된 아픔이 아닌 선제적 결정임을 ADR Context에 명기.**
- 결정 본문·버린 이유의 정본: **ADR-0018** (`adr/adr-0018-spec-first-rest-contract-source.md`, parent: ADR-0014).
- 티켓 재구성: ADR-0018 accept 후 **Epic + 리프 분해** (부트스트랩·CI / 컨트롤러 그룹별 strict 전환), #5는 재정의해 첫 리프로 편입. 발행은 accept·공표 이후.
