# auth-service가 굳이 필요한가 — Keycloak이 원장까지 갖는 프레임의 재검토

## 0. 경위 — 이것은 `260804_1831`의 재도전이고, 정당하다

`260804_1831`은 **"제품을 들이지 않는다"** 로 `done` 수렴했다. 그런데 그 논의가 평가한 프레임은
**"제품이 인증만 가져가고, 사용자 원장·동의·권한·티켓은 auth-service에 남는다"** 였다 —
거부 근거 ②(원장 분리 시 원자성 파괴)·③(로컬 user_id 잔존)이 전부 *"앱이 원장을 계속 소유한다"* 를 전제한다.

사람이 지금 들고 온 프레임은 다르다: **auth-service 소멸 — Keycloak이 인증·원장·동의까지 갖고,
막히는 것(티켓)은 다른 방향으로 구현한다.** 이 옵션은 평가된 적이 없다.
그리고 그 수렴은 ADR을 파생시키지 않았으므로("현 상태 유지라 되돌리기가 싸다") 다시 여는 비용이 0이다.
"다시 열 트리거" 목록에는 없는 각도지만, 트리거 목록은 닫힌 집합이 아니다.

**단, 1831의 탈락 사유 중 하나는 프레임과 무관하게 남는다** — 운영 비용(§4). 이 문서의 반대편 축이다.

## 1. 사람의 주장 셋 — 검증 결과

### ① "로그인/회원가입 전 필수/선택 동의 여부는 Keycloak이 제공하는 것 같다" — **절반만 맞다**

Keycloak 내장 Terms and Conditions는 **required action 하나 = 단일 수락**이다.
careerhub의 동의는 **4건 개별**이다(`sql/migrations/00002_seed_agreements.sql` — 필수 3: 이용약관·개인정보·만14세, 선택 1: 마케팅, priority 정렬).
개별 체크·선택 동의의 철회·동의 시각 기록은 내장 기능 밖이고, **커스텀**(required action SPI 또는 declarative user profile + 테마)이 필요하다.

### ② "약관 변경 후 재동의, 변경 내역 기록은 SPI로 커스텀 가능한 듯" — **맞다. 단 가격표가 있다**

가능하다 — 커뮤니티에 정확히 이 목적의 required action SPI 구현체가 있다(eddykaya/keycloak-custom-required-action).
그러나 **"전 사용자 재동의 요구"가 내장에 없다는 것이 open feature request로 확인된다**(keycloak#26124) —
즉 이 기능들은 전부 **우리가 Java로 짓고 유지하는 코드**다.
그리고 1831이 Keycloak을 버린 1차 사유가 **연 4회 메이저 릴리스 × 마이너당 30~46개 마이그레이션 항목**이었는데,
**커스텀 SPI는 그 업그레이드마다 재빌드·호환 검증 대상이 하나 더 느는 것**이다. 탈락 사유가 완화되는 게 아니라 가중된다.

### ③ "유일하게 막히는 게 티켓" — **막히는 것은 둘이다**

코드 실측(`auth-service`):

- **티켓**: 3테이블(`ticket`·`ticket_authority`·`ticket_used`) + `ticket_service.go` 361줄.
  `UseTicket`이 `FOR UPDATE` 행잠금 → 사용횟수 검사 → 사용기록 → 권한부여를 **한 트랜잭션**으로 돈다.
- **시간 만료 권한**: `user_authority.expiry_date` + `ticket_authority.expiry_duration_ms` —
  티켓이 *만료일이 있는 권한*을 부여한다. **Keycloak realm role에는 만료가 없다.**
  즉 티켓만 이사하면 되는 게 아니라, **티켓이 부여하는 권한 모델 자체가 Keycloak 어휘로 표현되지 않는다.**
  권한을 Keycloak 밖(앱 DB)에 두면 티켓도 따라 나오고, 안에 두려면 롤 만료 SPI까지 짓는다.

## 2. 구조 논점 — "서비스 삭제"인가 "도메인 3개 분산"인가

auth-service에는 인증 외에 **동의·권한·티켓** 세 도메인이 있다. K1(소멸)이 성립하려면 셋 다 목적지가 필요하다:

| 도메인 | Keycloak 안으로 | 앱에 남기면 |
|---|---|---|
| 동의 (개별·이력·재동의) | Java SPI + 커스텀 저장 | 수신처 필요 |
| 권한 (시간 만료) | realm role로는 불가 → SPI | 수신처 필요 |
| 티켓 (원자적 사용·권한부여) | custom REST resource SPI = 도메인 로직 Java 재작성 | 수신처 필요 |

**전부 안으로** = Go 도메인 코드를 Java SPI로 재작성하고 업그레이드 표면을 최대화.
**일부라도 밖에** = 그 수신처가 필요하다 — api-composer에 넣으면 composer가 DB와 도메인을 갖게 되고,
별도 서비스로 두면 **그것이 곧 축소판 auth-service다.** 서비스가 삭제되는 게 아니라 이사한다.
후자의 극단(인증만 Keycloak, 도메인은 앱)은 1831이 이미 평가하고 버린 프레임으로의 회귀다.

## 3. 공정하게 — 이 방향이 사는 것, 그리고 약화·역전된 옛 논거

**사는 것이 크다.** `260805_1550`의 결정 셋(D1 세션 상태·D2 왕복 소유·D3 비대칭 서명)과
`260804_1831` 6절의 필수 목록 23개가 **통째로 제품 관할이 된다.**
api-composer는 JWKS로 RS256 검증 — 표준 라이브러리 한 벌. 다중 IdP·계정 연결·로그아웃·PKCE·nonce 전부 설정이 된다.
리뉴얼 작업 목록 전체와 맞바꾸는 것이므로, 이 재검토는 사치가 아니다.

**옛 논거 중 둘은 그때보다 약하다** — 정직하게 적는다:

- **원자성 논거(1831 ②)의 약화** — `260805_1550` D-8이 확인했듯 **지금도 탈퇴가 userinfo MongoDB로 전파되지 않는다.**
  "원자적인 것이 깨진다"던 경계는 이미 PostgreSQL 담장 안에서만 원자적이었다. 가입(user+동의)은 Keycloak이 둘 다 가지면 그 안에서 원자적이다.
  남는 원자성 논거는 **티켓 사용 흐름 하나**다(§1③).
- **식별자 논거(1831 ③)의 역전** — `260805_1308`이 *"저장소 독립 불변 식별자"* 로 수렴했다.
  Keycloak의 user id(UUID)는 그 성질을 갖는다. 그리고 **가입자 1명(운영자 본인)** 이라
  userinfo 인덱스의 `userId` 치환 비용이 지금 ~0이다 — *지금은 가역, 나중은 불가역*의 그 창이 이 방향에도 똑같이 열려 있다.

**변하지 않은 반대 논거:**

- **운영 비용** — Operator 기본 requests 1700MiB / limits 2GiB, 연 4회 메이저, 커뮤니티판 LTS 없음. §1②로 SPI 유지가 가중된다.
- **Naver 연결끊기 콜백** — 어느 제품이든 직접 짠다(1831 ④). 받는 곳이 필요하다 → §2의 수신처 문제와 합류한다.
- **1831의 실측에서 조건이 맞는 풀 IdP는 Zitadel이었다**(Go, 512MB, arm64). Keycloak은 그 비교에서 진 쪽이다.
  이번 프레임에서 Keycloak을 지목한 이유가 있는지 — 동의 SPI 생태계? — 확인이 필요하다.

## 4. 옵션 (초기 발산 — 아직 벌리는 중)

- **K0. 안 한다** — 현행 리뉴얼(D1·D2·D3 + 티켓 목록). 비용: 일회성 재작성 + 자체 유지. 이기는 조건: 상시 운영비를 안 내는 쪽이 총비용에서 이길 때.
- **K1. 전부 Keycloak** — 동의·권한·티켓까지 SPI로. 비용: Java 재작성 + 업그레이드마다 SPI 검증. 이기는 조건: SPI 표면이 생각보다 작고 안정적일 때.
- **K2. Keycloak(인증·원장·기본동의) + 잔여 도메인 소형 서비스** — 티켓·시간만료권한·동의이력은 앱 쪽에.
  이기는 조건: "auth-service 소멸"이 아니라 "auth-service에서 인증을 들어내는 것"을 목적으로 받아들일 때.
- **K2'. 제품을 Zitadel로** — K1/K2와 직교하는 제품 선택 축. 1831 실측의 승자.

## 6. 방향 좁힘 (2026-08-05) — K2로: 발급은 제품, auth-service는 잔여 도메인

사람이 방향을 좁혔다: **발급자 = Keycloak 또는 Zitadel / 검증자 = auth-service·api-composer.**
제품이 회원가입·로그인·강제 탈퇴를 갖고, auth-service는 그 외(권한·티켓·…)를 갖는다.
Zitadel도 검토 대상으로 유지한다. 컴퓨팅 리소스는 문제 아님으로 판정(홈랩 사용률 6~36%, 1831 실측과 일치) —
**단 1831의 1차 탈락 사유는 리소스가 아니라 업그레이드 노동이었다**(연 4회 메이저·커뮤니티 LTS 없음). 이 비용의 수용 여부는 여전히 열려 있다.

### ① 검증 사본 문제는 사실상 소멸한다 — 게이트웨이도 introspection도 필요 없다

사람이 *"검증 코드가 두 쪽 사본이 필요하므로 게이트웨이를 둘지, api-composer가 auth-service를 호출할지"* 를 미결로 뒀는데,
**이 걱정은 대칭키 시대의 것이다.** 오늘의 고통(1735 축 A)은 ⓐ 수제 resolver의 복붙 사본이 갈라졌고 ⓑ 대칭키라 사본마다 발급 능력이 딸려갔다는 것이다.
제품 발급 토큰은 **RS256 + JWKS 공개 엔드포인트**이고, 검증은 표준 라이브러리(`go-oidc` 등) + issuer URL 설정이다:

- 사본이 늘어도 **발급 능력이 퍼지지 않는다** — 공개키뿐이다. 1735가 A3(공통 모듈)을 "A1 없이 하면 위험"이라 했던 제약이 풀린다: **비대칭이면 goutils 공통 검증 모듈이 안전하다.**
- **api-composer → auth-service 검증 호출(introspection)은 만들지 않는다** — `260805_1334` 7-3-c가 거부한 바로 그 런타임 결합(지금 0건인 의존을 신설, auth-service가 전 요청 경로의 SPOF)이다. 같은 논리가 게이트웨이 검증에도 적용된다: 각 서비스가 JWKS로 로컬 검증하는 것이 기본형이고, 이 미결은 나중이 아니라 **지금 닫힌다.**

### ② ★ 진짜 이음새는 검증이 아니라 권한 클레임이다

**api-composer는 권한을 실제로 검사한다** — 실측: `apicomposer/controller/strict.go`가 matchJob 연산에 `AUTHORITY_MATCH_JOB`을 요구하고, `common/user_authority/user_authority.go`에 권한 상수 4종이 있으며, 전부 **JWT 클레임 `Authorities`에서** 읽는다.

그런데 K2에서 권한은 앱 DB(`user_authority`, 시간 만료 포함)에 남고, **토큰은 제품이 발급한다 — 제품은 앱의 권한 테이블을 모른다.** 토큰에 `Authorities`가 없어진다. 경로 옵션:

| | 모양 | 비용 |
|---|---|---|
| **P1. 신원만 토큰으로, 권한은 각자 조회** | composer가 요청마다(또는 캐시) `user_authority`를 본다 | 조회 경로 신설 — auth-service API 호출이면 런타임 결합(①에서 거부한 그것), DB 직접 읽기면 저장소 공유 |
| **P2. 제품 토큰에 권한 클레임 주입** | 제품이 발급 시 앱 권한을 얹는다 | 제품이 앱 DB를 읽어야 함 → **SPI**(Keycloak protocol mapper / Zitadel action). 업그레이드 표면 증가 |
| **P3. 권한을 제품 롤로 이관** | composer는 제품 롤 클레임을 읽는다 | **시간 만료 권한이 표현 안 된다**(§1③). 티켓 부여 흐름이 제품 Admin API 호출이 되어 원자성이 깨진다 |
| **P4. composer의 권한 검사를 없앤다** | 검사를 auth-service 경로로 옮기거나 폐지 | 권한 모델 자체의 재설계. matchJob 게이트가 실사용인지가 선행 판정 |

**이 표가 K2의 실질 결정이다.** 검증 방식은 정해져 있고(①), 권한 데이터의 흐름은 정해져 있지 않다.

### ③ 가입의 이음새 — "제품 가입 = careerhub 회원 완성"이 아니다

동의 4건 개별(§1①)이 가입 조건이다. 제품이 가입을 가져가면 동의는:
- **(a) 제품 안 SPI** — 개별 체크·시각 기록을 required action으로. K1 방향의 비용(§1②)이 여기만 남는다.
- **(b) 앱 온보딩 게이트** — 제품 가입은 인증 계정만 만들고, 첫 로그인 때 앱이 JIT로 user 행을 만들며 동의를 요구. 동의 이력·재동의가 전부 앱(Go) 관할로 남는다. 제품 쪽 커스텀이 0에 수렴한다.

(b)면 auth-service의 잔여 도메인에 동의가 포함되고, 사람이 처음 말한 "동의는 Keycloak이 제공" 부분을 **의도적으로 안 쓰는** 것이 된다. 어느 쪽인지가 K1/K2의 실질 경계다.

### ④ 탈퇴·연동 해제의 전파 — 새 결합이 둘 생긴다

- **제품 → 앱**: 강제 탈퇴·계정 삭제 시 앱 데이터(권한·동의·티켓 이력·Mongo 스크랩) 정리. 제품 이벤트(웹훅/admin events) **수신 코드**가 필요하다. 1831 ②가 예고한 "보상·조정 코드"가 이 프레임에서 실제로 생긴다 — 단 D-8(지금도 전파 안 됨)이 보여주듯 **새 문제가 아니라 기존 구멍의 상속**이다.
- **앱 → 제품**: Naver 연결끊기 콜백(1831 ④)을 받은 쪽이 제품의 계정을 정리해야 한다 → auth-service가 **제품 Admin API의 클라이언트**가 된다.

### ⑤ 식별자 — 제품 sub를 전역 id로

제품의 user id(UUID)를 시스템 전역 식별자로 채택하면 `260805_1308`의 수렴(저장소 독립 불변 식별자)과 정합하고, N=1인 지금 userinfo Mongo 인덱스 치환이 ~0이다. 별도 매핑 테이블(제품 sub ↔ 로컬 serial)을 두는 안은 그 수렴이 이미 기각한 모양(저장소 PK 노출)을 연장하는 것이다.

### 이 방향이 서면 결정 지형이 바뀐다

`260805_1550`의 D1(세션 상태)·D2(왕복 소유)·D3(비대칭 서명)은 **전부 제품 관할로 소거**되고, 대신 새 one-way door가 선다:

> **후보 결정 문장 — "인증(가입·로그인·세션·탈퇴)은 외부 IdP 제품이 소유하고, 권한·티켓·동의는 앱이 소유하며, 서비스는 제품 발급 토큰을 로컬(JWKS)로만 검증한다."**

되돌리기 어려운 것: 사용자 원장의 소유권 이전(마이그레이션·프론트 로그인 흐름·전 서비스 검증 변경). 제품 선택(Keycloak vs Zitadel)·클레임 구성은 그 아래 층이다.
하위 미결: 권한 클레임 경로(②) · 동의 위치(③) · 전파 수신 방식(④).

## 7. 좁힘 2 (2026-08-05) — 사람의 답 넷과, 그로부터 갈라진 것

사람의 답: **① 권한 클레임은 P2 또는 P3**(P3면 시간 만료 때문에 별도 서비스가 필요한가 고민) **② 동의는 앱 온보딩 게이트 ③ 제품은 Zitadel도 고려 후 결정 ④ 전파는 주기 조정(reconciliation).**

### ① P3의 "별도 서비스" 우려는 P3 자체를 기각하는 논거다

P3(권한을 제품 롤로) + 만료 별도 서비스는 **권한의 진실을 둘로 가르는 것**이다 — 부여·표현은 제품 롤에, 만료는 앱에.
그러면 티켓 사용(부여)이 앱 트랜잭션 + 제품 Admin API 호출로 갈라져 원자성이 깨지고, 만료 집행은 조정 잡이 제품 롤을 회수하는 지연 경로가 된다.
그리고 "별도 서비스"는 만들 필요가 없다 — **K2에서 auth-service가 이미 권한·티켓의 집으로 남기로 했다.** P3의 유일한 매력(권한 도메인을 앱에서 지운다)이 시간 만료·티켓 원자성 때문에 성립하지 않으므로, **지워지지 않는 도메인을 반쪽만 옮기는 안이다.**

**→ P2로 좁힌다.** P2가 보존하는 것: 티켓 사용의 앱 트랜잭션 원자성 · composer의 클레임 검사 의미론(클레임 이름 매핑만 바뀜) · 권한 회수 지연 = 토큰 수명(오늘의 10분 의미론과 동일).
**덤 — P2가 온보딩 게이트(§6③-b)의 신호를 겸한다**: 미온보딩 사용자는 권한이 비므로(또는 `onboarded` 클레임), composer가 앱 DB를 안 보고도 거를 수 있다.

P3 재고 조건: **시간 만료 권한과 티켓이 실사용이 아니어서 폐기 가능할 때**뿐이다.

### ② ★ P2의 비용이 제품 선택을 기울인다 — 실측

| | Zitadel | Keycloak |
|---|---|---|
| P2 메커니즘 | **Actions — complement token flow.** `preAccessToken` 트리거에서 JS 스크립트가 http fetch로 외부 API를 부르고 `setClaim` | **커스텀 protocol mapper = Java SPI.** JAR 빌드 → providers 배치 → 재시작. 외부 REST에서 클레임을 긁는 서드파티 확장(keycloak-json-remote-claim 등)이 있으나 그것도 추적할 jar다 |
| 유지 비용 | 콘솔 설정 + 스크립트 수준 | **연 4회 메이저 릴리스마다 재빌드·호환 검증** — 1831의 탈락 사유가 정확히 여기 얹힌다 |

**정밀화(사람의 질문으로 확인)** — Zitadel Actions는 세대가 둘이고, 어느 쪽이든 빌드가 없다:

- **v1(구형)**: JS 스크립트를 콘솔에 넣으면 Zitadel **내장 인터프리터가 프로세스 안에서 실행**한다. 빌드·배포 없음. 샌드박스 제약(타임아웃·제한된 모듈·http fetch 모듈).
- **v2(현행, v3/v4의 방향)**: **임베디드 JS가 아니라 외부 HTTP endpoint(Target) 호출**이다 — Zitadel이 조건(Request/Response/**Function**/Event) 충족 시 등록된 endpoint에 POST하고, 로직은 **어느 언어로든 우리 인프라에서** 돈다. payload 서명 검증 지원. Function 타입이 v1의 complement-token 자리를 대체한다.

**→ careerhub에서 P2의 실체는 JS조차 아니다: auth-service 자체가 Target이 된다.** Zitadel이 발급 시 auth-service의 endpoint를 호출하고, auth-service(Go)가 권한·동의 클레임을 돌려준다 — §7③에서 "발급 시 제품 → auth-service 호출"이라 적은 그 의존이 Actions v2의 1급 실행 모델 그 자체다. 커스텀 코드는 전부 우리 Go 저장소에 살고, 제품 쪽에는 설정(Target·Execution)만 남는다.
채택 시 확인 항목: v1→v2 트리거 커버리지가 이행 중이라(login v1 + actions v2 조합에 일부 공백 이슈 존재) **login v2 + actions v2 조합으로 정렬**할 것.

동의를 앱 게이트로 가져오면서(§7③) 제품 쪽 커스텀 요구는 P2 훅 하나로 줄었다. 그 하나의 비용이 Zitadel에서는 설정이고 Keycloak에서는 Java 빌드 파이프라인이다.
1831 실측(Go·512MB·arm64에서 Zitadel이 조건 승자)과 합치면 **Keycloak의 남은 우위는 생태계·문서·"기능 수"뿐인데, 그 기능 대부분(비밀번호·MFA·동의 화면)은 소셜 전용 + 앱 게이트 구성에서 사표다.** Keycloak 반대편 잔여 논거: Zitadel은 AGPL(1831 확인)·상대적으로 작은 생태계.

### ③ P2의 새 의존 하나 — 정직하게 적는다

P2의 권한 출처는 auth-service의 조회 API가 자연스럽다(제품이 앱 DB를 직접 읽는 것보다 경계가 깨끗하다).
그러면 **토큰 발급 시점에 제품 → auth-service 호출**이 생긴다 — §6①에서 거부한 요청 경로 결합과 다르다(로그인·갱신 시에만, 요청마다가 아님). 실패 모드: auth-service가 죽으면 로그인이 실패하거나 권한 없는 토큰이 나온다. 어느 쪽으로 다룰지는 코드 관할이지만, **의존 자체의 수용은 결정의 일부다.**

### ④ 주기 조정(reconciliation)의 귀결

- 조정 잡의 주인은 auth-service(사용자 도메인 잔여의 집)가 자연스럽다. 제품 사용자 목록 ↔ 앱 user 행 ↔ Mongo 문서를 대조한다.
- 강제 탈퇴의 앱 측 정리는 조정 주기만큼 지연된다 — N이 작은 동안 수용 가능하고, D-8(지금도 전파 없음)보다는 개선이다.
- **덤 — 제품이 마지막 로그인 시각을 공짜로 준다.** `260805_1550` D-7(마지막 로그인 시각 기록 티켓)이 제품 관할로 넘어가고, D4(접근수단 0 계정)의 감지 재료가 조정 잡의 입력으로 생긴다.

## 8. 시간 만료 권한은 도입의 장애물이 아니다 — 상용 표준형과의 대조

사람의 물음: *"결제 후 권한 부여 기능이 있다면 결국 그 권한을 인증 솔루션에 입력해야 하고, 유효기간 기능도 필요하지 않나.
티켓 + 시간 만료 권한이 같은 맥락으로 언젠가 필요하다면, 외부 인증 솔루션으로 어떻게 구현하나."*

### 답 — 상용 세계는 그것을 인증 솔루션에 입력하지 않는다

결제 기반 SaaS의 표준형(Stripe 문서·실무 가이드가 수렴하는 모양):

1. **엔타이틀먼트의 진실은 앱 DB(또는 빌링 시스템)다.** 결제 이벤트(webhook)가 앱 DB에 *"user X는 feature Y를 시각 Z까지"* 행을 쓴다.
   Stripe 자신의 지침이 *"앱 DB가 access의 source of truth, webhook 확인된 구독 상태로 접근을 부여, 만료 시각을 앱 DB에 저장"* 이다.
2. **IdP는 인증만 갖는다.** 엔타이틀먼트·만료는 IdP에 넣지 않는다.
3. 토큰에 싣고 싶으면 **발급 훅으로 주입**한다(Auth0 Actions·Zitadel actions·Keycloak mapper) — **= P2.** 아니면 체크타임 조회(P1).

**IdP 제품에 롤 만료가 없는 것 자체가 시장의 답이다.** Keycloak에서 시간 기반 롤/그룹 멤버십은 미지원 feature request로 남아 있고,
그 스레드의 대표 용례가 정확히 *"구독이 만료되면 VIP 롤을 자동 제거"* 다 — 시장이 그 기능을 IdP에 넣지 않는 이유는,
그것이 인증이 아니라 **비즈니스 도메인(인가·빌링)** 이기 때문이다. (1831 ⑥의 OpenFGA 검토도 같은 지형 — 인가는 IdP 밖의 축이다.)

### careerhub 매핑 — 이미 표준형으로 지어져 있다

| 상용 표준형 | careerhub 현재 |
|---|---|
| 결제 이벤트(webhook) → 권한 부여 트리거 | **티켓 사용**(`UseTicket`) |
| entitlement 테이블 `(user, feature, expires_at)` | **`user_authority(user_id, authority_id, expiry_date)`** — 그 자체 |
| 발급 훅이 앱 DB를 읽어 토큰에 주입 | **P2가 하려는 바로 그것** |

**즉 "티켓 + 시간 만료 권한 때문에 외부 인증 솔루션 도입이 어렵다"는 전제가 뒤집힌다.**
어려운 것은 이 도메인을 제품 **안으로** 넣으려 할 때(P3)뿐이고, §7①이 P3를 기각했으므로 장애물 자체가 소멸한다.
외부 솔루션을 들여도 이 도메인은 **한 줄도 안 바뀐다** — P2 훅이 토큰에 실어줄 뿐이다.
훗날 결제가 실제로 생기면 티켓의 자리(부여 트리거)에 결제 webhook이 하나 더 들어오는 모양이 된다 — 확장이지 재설계가 아니다.

### 부수 — 만료 집행의 정밀도 (코드 관할, P2 설계 시 참고)

지금은 발급 시 필터(`FindValidUserAuthorities`)라 만료 집행이 토큰 수명만큼 지연된다. P2에서 클레임에 만료 시각을 함께 실으면
(`authorities: [{code, until}]`) 검증자가 스스로 비교한다 — **자연 만료는 정확히 집행**되고, 관리자 회수만 토큰 수명 지연(오늘과 동일 의미론)으로 남는다.

## 9. Zitadel의 동의 지형 — 조사 결과와, 권한과의 대칭성

사람의 물음: *"Zitadel은 동의 기능을 어떻게 구현하나. 권한을 auth-service가 주입했듯 동의도 가능한가."*

### Zitadel이 가진 것 / 없는 것

| | Zitadel | 비고 |
|---|---|---|
| **내장 동의** | 등록 시 ToS·개인정보처리방침 **링크 수락**(privacy policy settings, 언어별 링크) — 단일 수락 | Keycloak 내장 T&C와 같은 급. 4건 개별·시각 기록·재동의 불가 |
| **흐름 안 커스텀 폼** (Keycloak required action SPI에 해당) | **없다.** Actions는 스크립트(차단·클레임·외부 API 호출)이지 UI가 아니다 | 흐름 안 동의 화면을 가지려면 **로그인 UI 자체를 소유**해야 한다 — login v2가 MIT 라이선스 Next.js 앱으로 fork·self-host 가능(Session API 기반). SPI보다 무겁다(로그인 앱 운영) |
| **차단형 게이트** | post-authentication action이 속성 검사 후 **접근 거부** 가능 | 거부만 가능 — 동의 화면으로 보내 받아오는 상호작용은 못 한다 |
| **P2형 주입** | **가능** — complement token action이 auth-service를 호출해 클레임 주입(§7②에서 확인한 그 메커니즘) | 동의 상태도 권한과 같은 훅으로 나른다 |

### 답 — 가능하고, 권한과 완전히 같은 모양이 된다

앱 온보딩 게이트(§7)를 전제하면 동의의 배치는:

- **진실**: `agreement`·`user_agreement`·이력·재동의 판정 = **auth-service DB** — 권한과 동일.
- **UI**: careerhub-front의 온보딩 화면 — 제품 흐름 밖. Zitadel에 흐름 안 폼이 없다는 약점이 **무관해진다.**
- **집행**: P2 훅이 auth-service를 호출할 때 권한과 함께 **동의 충족 여부를 클레임으로** 받는다(`onboarded` 또는 필수동의 충족 플래그). 미충족이면 composer·auth-service가 거부하고 프론트가 동의 화면으로 유도.
- **재동의(약관 변경)**: auth-service가 현행 필수 약관 ↔ `user_agreement`를 대조해 판정 → 클레임이 자연히 미충족으로 떨어짐 → 같은 게이트가 작동. **Keycloak SPI가 하던 일이 앱 로직 한 조각이 된다** — 개별·버전·이력 전부 우리 DB이므로 오히려 required action보다 유연하다.

**→ 권한과 동의가 대칭이다.** auth-service의 정체가 이 지점에서 선명해진다:
**"정체성에 부속된 앱 도메인 상태(권한·티켓·동의)의 원장이자, 제품 발급 훅의 데이터 소스."**
발급 시 호출(§7③)은 권한·동의를 한 번에 나르므로 의존이 늘지 않는다.

### 수렴(사람) — 동의 클레임 + 403 게이트 + 프론트 리다이렉트

사람이 집행 형태를 확정했다: **동의 여부를 JWT 클레임에 넣고, api-composer·auth-service는 미충족 시 403으로 거부하며,
프론트는 클레임을 읽어 필수 동의 미완이면 동의 화면으로 리다이렉트.** 서버 집행과 프론트 UX 라우팅의 분리 — 올바른 배치다(집행은 항상 서버, 프론트의 클레임 읽기는 UX 힌트).

**모서리 셋** — 형태는 유효하되, 설계 시 함께 다뤄야 한다:

1. **동의 완료 직후의 역방향 신선도.** 클레임은 발급 시점의 스냅샷이다 — 온보딩 화면에서 동의를 마쳐도 **손에 든 액세스 토큰은 여전히 미충족**이라 403이 계속 나온다. **동의 완료 → 토큰 갱신 트리거가 흐름의 일부여야 한다**(refresh 강제 → P2 훅이 새 클레임을 실음). 티켓 사용(권한 획득) 직후도 같다. 오늘의 구조(발급 시 권한 박제)와 같은 의미론이라 새 비용은 아니지만, 프론트 흐름에 명시적으로 있어야 한다.
2. **재동의 발동의 발효 지연.** 약관 변경 시점에 이미 발급된 토큰은 수명(분 단위)까지 충족 클레임을 유지한다 — **재동의 강제의 발효 = 액세스 토큰 수명 지연.** 회수 지연(§7①)과 같은 의미론이고 수용이 정합이다. 정확 발효를 요구하면 체크타임 조회가 되어 §6①이 거부한 결합으로 미끄러진다 — 요구하지 않는다.
3. **"프론트가 JWT를 읽는다"는 토큰 저장 방식과 얽힌다.** `careerhub-front/discussion/260722_1617_token-storage-after-server-exists.md`(축 E)가 아직 열려 있다 — 토큰이 httpOnly 쿠키로 가면 프론트가 클레임을 직접 못 읽는다. **저장 방식과 무관한 대안: 403 응답에 기계 판독 사유 코드**(`consent_required` vs `authority_missing`)를 실어 프론트가 그것으로 라우팅. 클레임 직접 읽기는 저장 방식이 허용할 때의 최적화로 두는 편이 결합이 없다. — 이 모서리는 저쪽 논의로 넘긴다.

### 부수 둘

- **Keycloak의 남은 우위 하나가 사표가 된다** — "required action SPI로 흐름 안 동의 폼 가능"은 Keycloak이 확인된 능력이지만, 앱 온보딩 게이트로 수렴한 순간 **어느 제품에서도 그 능력을 쓰지 않는다.** 제품 비교에서 이 축이 소거된다.
- Zitadel 내장 ToS 링크 수락은 켜면 앱 온보딩과 **이중 동의 UX**가 된다 — 링크 미설정으로 끄는 쪽이 정합. 코드(설정) 관할.

## 10. Zitadel 선행 검토 둘 — AGPL과 성숙도·케이던스 (조사 결과)

### ① AGPL-3.0 — careerhub의 실질 의무는 0에 수렴한다

v3(2025-03-31)부터 Apache 2.0 → AGPL-3.0. **구성요소별로 갈린다:**

| AGPL-3.0 | **Apache 2.0 유지** |
|---|---|
| core(백엔드) · Console · Hosted-Login | **Proto 정의 · API · SDK · 예제 · 문서 · Helm chart · Terraform** |

의무 매트릭스 (Zitadel 공식 FAQ 기준):

- **미수정 운용(자체 호스팅 포함)** — *"identity platform으로 쓰기만 하면 라이선스 변경의 영향이 없다"* (공식 문안). 의무 없음.
- **수정 + 네트워크 서비스 제공** — 수정분을 AGPL로 공개해야 한다. **careerhub 앱 코드는 여기 해당하지 않는다** — HTTP API로 통신하는 별개 프로그램이고, 연동면(SDK·proto)이 Apache 2.0이라 감염 경로 자체가 없다.
- **Actions 스크립트(P2 훅)** — 콘솔/설정으로 주입하는 구성물이지 코어 수정이 아니다. 가장 보수적으로 읽어 공개 대상이라 쳐도, 클레임 매퍼 스크립트 공개는 개인 공개 프로젝트에서 비용 0이다.
- 유일한 실제 조심 지점: **login v2 UI를 fork·수정해 서비스하면** 그 fork는 공개 대상이다 — 앱 온보딩 게이트로 수렴했으므로(§9) fork가 필요 없고, 해당 없음.
- 막히면 상용 라이선스 출구가 있다.

**→ AGPL은 기업 정책형 리스크(사내 금지 규정류)이지, 개인 공개 프로젝트의 실질 의무가 아니다. 채택을 막지 않는다.**

### ② 성숙도·케이던스 — 발표와 실측이 다르고, 실측이 유리하다

**발표된 정책**은 "3개월마다 메이저"(v3.5.1 → v4.0.0)라 Keycloak과 같은 케이던스로 읽히지만, **릴리스 이력 실측(2026-07 기준)은 다르다:**

- v3 GA 2025-03 → v4 GA 2025년 하반기 → **2026-07 현재 v4.16.x** — 실제 메이저는 **~연 1회**, 나머지는 빈번한 마이너.
- ★ **v3.4.x가 v4 출시 후에도 병행 패치 중이다** — v3.4.14가 2026-07-29에 나왔다(v4.16.2와 같은 날).
  **직전 메이저에 보안 백포트가 실재한다.** V4는 최소 12개월 지원이 공언되어 있다.
- GA 기능은 *"이전 버전과 하위호환, 예외는 technical advisory 공표"* 가 명시 정책이다.

**Keycloak 커뮤니티판과의 대조** (1831 실측 + 이번 조사):

| | Zitadel | Keycloak (커뮤니티) |
|---|---|---|
| 메이저 실측 | ~연 1회 | 연 4회 |
| 직전 메이저 보안 패치 | **병행 유지 확인** (v3.4.x) | 없음 — 공식 문서가 *"정기 업그레이드가 어려우면 Red Hat build를 고려하라"* |
| 하위호환 정책 | GA는 하위호환 원칙 + 예외 advisory | 마이너당 마이그레이션 항목 30~46개 판독 |
| 커뮤니티 규모 | 14.5k stars · 250+ contributors · $12M 펀딩 · 160+ 기업 고객 · 6년 | **35.8k stars · 8.6k forks · CNCF incubating · 13년** · 대형 레퍼런스 다수 |

**판정:** 절대 규모·생태계는 Keycloak 우위가 명백하다. 그러나 careerhub가 실제로 낼 비용 — **업그레이드 노동의 곡선** — 은 Zitadel이 우위다: 메이저가 적고, 직전 메이저가 살아 있어 업그레이드 시점을 고를 수 있으며, 하위호환이 원칙이다.
**정직한 잔여 리스크 하나:** Zitadel은 단일 회사 의존이다. 회사가 꺾이면 AGPL이라 포크는 가능하지만, 포크를 받아줄 커뮤니티 질량이 Keycloak만 못하다. 이것이 이 비교에서 Zitadel 쪽에 남는 마지막 무게다.

### ③ Zitadel의 저장소 (확인)

- **PostgreSQL 단독** — v3부터 배타 지원(14~18). CockroachDB는 v2까지였고 v3에서 제거됐다(PostgreSQL 비호환 오버헤드가 사유).
- **이벤트소싱 + CQRS** — 진실은 append-only 이벤트 테이블(`eventstore.events2`)이고, 전체 상태를 이벤트에서 재계산할 수 있다. 읽기 모델은 projection 테이블. 스키마는 `zitadel setup` 단계가 관리한다.
- **careerhub 함의 셋:**
  1. **저장소 종류가 안 늘어난다** — auth-service가 이미 PostgreSQL이고 홈랩에 PG가 돌고 있다. 같은 인스턴스에 별도 database로 얹을지 전용 인스턴스로 갈지는 장애 반경 판단(코드·운영 관할).
  2. **백업 = PG 덤프 + masterkey.** 1831 ⑤에서 확인했듯 masterkey를 잃으면 암호화 데이터 전체를 잃는다 — 백업 대상에 masterkey가 반드시 포함되어야 한다.
  3. **이벤트소싱이 감사 이력을 구조적으로 남긴다** — 가입·로그인·탈퇴가 전부 이벤트 행이다. 주기 조정(§7④)과 D4 감지(마지막 로그인)의 재료가 공짜로 쌓인다. 반대급부: append-only라 이벤트 테이블은 단조 증가한다(N=1 규모에서는 무시 가능).

## 11. 후보 재조사 — 신생 오픈소스와, Keycloak 자신의 개선

사람의 물음: *"둘 외의 선택지는? Keycloak의 불편을 해소하려는 새 오픈소스가 나오지 않았나, Keycloak 자신이 다른 방식으로 풀지 않았나."*
필터는 수렴된 설계가 준다: **① 소셜 브로커(Google + Naver generic OIDC) ② OIDC 발급자(로컬 JWKS 검증) ③ 발급 시 클레임 주입 훅(P2) ④ arm64·경량 ⑤ 라이선스 ⑥ 성숙도.**

### ① ★ Keycloak 자신이 고쳤다 — 1831의 케이던스 판정은 낡았다 (교정)

1831이 인용한 "연 4회 메이저 + 마이너당 30~46개 마이그레이션 항목"은 **26.0 이전 체계**다. Keycloak 26.0(2024 말)부터:

- **마이너 분기별, 메이저는 2~3년마다** — 실측: 26.4(2025-09) · 26.5(2026-01) · 26.6(2026-04) · 26.7(2026-07). 26.x 라인이 2년째다.
- **마이너의 하위호환이 보장 정책이 됐다** — fully supported 기능·API 한정. 마이너의 breaking change는 **opt-in**, 제거는 다음 메이저에서만.
- 26.6부터 패치의 **zero-downtime rolling update** 지원.
- **변하지 않은 것**: LTS 없음은 공식 유지("만들 계획 없다") — 최신만 보안 패치를 받으므로 분기 마이너 추적은 여전히 의무다. 다만 그 한 걸음 한 걸음이 호환 보장 아래로 들어왔다.
- **P2 관점의 잔여 유의점**: 커스텀 protocol mapper(Java SPI)가 그 호환 보장의 "fully supported API"에 포함되는지는 SPI별로 다르다 — 채택 시 확인 항목.

**→ §10②의 비교표는 이 교정으로 좁혀진다.** Zitadel(메이저 ~연 1회 + 직전 메이저 백포트) vs Keycloak(분기 마이너 의무 + 호환 보장 + LTS 없음) — 운영 부담 격차는 1831 시점보다 **훨씬 작다.** 남는 실질 차이는 P2 비용(설정 vs Java SPI)과 메모리(512MB vs 1.7GiB), 반대편의 생태계 질량이다.

### ② 신생·누락 후보 스캔

| 후보 | 무엇 | 필터 판정 |
|---|---|---|
| **Ory Kratos** (1831 미검토 — 누락이었다) | Go · Apache 2.0 · **headless**(UI를 앱이 소유 — BYO UI) · 소셜 로그인 내장(id_token 검증·PKCE 정석) · Jsonnet 클레임 매핑 · 수명주기 웹훅 · **session→JWT tokenizer**(`tokenize_as` + claims_mapper = P2 경로) · ~50MB | **진지한 제3 후보.** 철학이 K2와 가장 정합(UI·온보딩을 앱이 소유) — 단 **표준 OIDC AS가 아니다**(그건 Hydra). 서비스가 검증할 JWT를 얻으려면 tokenizer 호출 배선(게이트웨이/BFF)이 필요해 **조립량이 Zitadel·Keycloak보다 많다.** 관리 콘솔도 없다(API뿐). SCIM·SAML·조직은 유료판 — 우리는 불요 |
| **Rauthy** | Rust 단일 바이너리 · 초경량 · passkey 우선 · **업스트림 소셜 브로커 지원**(Google + generic OIDC) | 필터 ①②④는 통과하나 **③(발급 훅)이 없고, 실질 1인 유지 프로젝트**다. 홈랩 SSO용이지 제품 인증 기반으로는 성숙도·훅 양쪽 미달 |
| **Pocket ID** | 경량 OIDC IdP · passkey 전용 | **탈락 — 업스트림 소셜 브로커가 없다.** 필터 ①에서 끝 |
| **Casdoor** | Go · Apache 2.0 · 소셜 프로바이더 다수(Naver 네이티브 포함 가능성) | 기능 커버리지는 넓으나 **보안 이력(누적 CVE)·코드 품질 평판 감점.** 신뢰 축에서 채택 부담 |
| Logto · Authentik · Authelia · SuperTokens | — | 1831 판정 유지(각각 리소스·무게·RP 불가·유료 링크). 재조사에서 뒤집을 재료 없음 |
| Better Auth · Stack Auth 등 TS 프레임워크 | 라이브러리형 | 스택 불일치(Go 백엔드) — 제품이 아니라 조립재 |

### ③ 순효과 — 경주는 여전히 둘, 다만 조건이 갱신됐다

- **새 오픈소스 중 판을 바꾸는 것은 없다.** Kratos만이 실질 제3 후보인데, 그것은 "더 나은 제품"이 아니라 **"더 많이 조립하는 대신 더 얇은 제품"** 이라는 다른 트레이드다 — R1(직접 구현)과 K2 사이의 중간형. 조립량을 늘릴 이유가 없으면 후보로만 기록한다.
- **Keycloak은 1831 시점보다 실제로 나아졌다** — 사람의 가설 ②가 참이었다. 케이던스 축에서 Zitadel 우위는 유지되되 폭이 줄었다.
- P2 비용 축(설정 vs Java SPI)과 메모리 축은 그대로 Zitadel 우위. 생태계 질량·단일 회사 리스크는 그대로 Keycloak 우위.

## 5. 열린 질문 — 사람의 것

**§6에서 닫히거나 좁혀진 것:**

- ~~왜 Zitadel이 아니라 Keycloak인가~~ → **둘 다 검토 대상으로 유지.** Keycloak이 기능이 더 많아 보인다는 관찰, 리소스는 수용 판정.
- ~~검증 사본을 어떻게 하나(게이트웨이? introspection?)~~ → **로컬 JWKS 검증**(§6①). 런타임 결합을 만들지 않는다.
- ~~auth-service 소멸인가~~ → **아니다, K2** — 인증을 들어내고 잔여 도메인 서비스로 존속.

**§7에서 추가로 닫히거나 좁혀진 것:**

- ~~동의를 어디에~~ → **앱 온보딩 게이트.** 제품 쪽 동의 기능·SPI를 쓰지 않는다. §1①②의 커스텀 비용이 통째로 소멸.
- ~~전파 수신 방식~~ → **주기 조정.** 조정 잡은 auth-service가 주인(§7④).
- 권한 클레임 → **P2로 좁힘**(P3는 §7①로 기각. 재고 조건: 시간 만료 권한·티켓의 폐기 가능 판정).

**남은 것:**

1. **제품 선택 — Zitadel vs Keycloak.** 재료는 다 모였다: P2 비용(§7② — 설정 vs Java SPI) · 동의 축 소거(§9) · AGPL 무해 판정(§10①) · 케이던스 실측(§10② — Zitadel 우위) vs 생태계 질량·단일 회사 리스크(Keycloak 우위). **판단만 남았다.**
2. **P2의 발급 시 의존(제품 → auth-service 권한·동의 조회) 수용**(§7③) — 실패 모드를 어느 쪽으로 다룰지는 코드 관할이지만 의존 자체는 결정의 일부다.
3. ~~시간 만료 권한·티켓의 실사용 여부~~ → **판정 불요로 격하**(§8). P3 재고 사유가 소멸했으므로 **P2로 확정 가능**하다.
4. ~~AGPL·커뮤니티 성숙도 검토~~ → **§10에서 조사 완료.** AGPL은 채택 비장애, 케이던스는 실측상 Zitadel 우위, 잔여 리스크는 단일 회사 의존 하나.
