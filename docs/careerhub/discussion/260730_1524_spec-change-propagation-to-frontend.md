> **결말(2026-08-01)** — ADR-0019(합의 선행 공표)·ADR-0020(provider 원천·공표물 결합)으로 파생·accept됐고, 이행은 Epic #28과 Task #30(REST 축)으로 넘어갔다. 여기서 벌린 옵션(O0~O3·축 A~C·합의 시점 P1)의 결론은 그 ADR과 티켓에 산다.
# 백엔드 스펙 변경을 프론트에 전파하는 방법 — 푸시인가 구독인가

## 아픔 — 무엇이 문제인가

ADR-0014의 컴파일 게이트("계약이 깨지면 프론트 컴파일이 깨진다")는 **프론트가 새 스펙으로 타입을 재생성했을 때만** 작동한다. 재생성이 일어나지 않으면 프론트는 낡은 계약의 타입으로 컴파일을 통과하고, 위반은 다시 런타임으로 숨는다 — ADR-0014가 없애려던 바로 그 상태로 퇴행한다.

즉 문제는 "감지"가 아니라 **"백엔드 계약 변경이 프론트의 재생성을 언제·어떻게 일으키는가"** 다. 이 경로가 서 있지 않으면 #12(프론트 타입 생성 파이프라인)는 절반만 완성이다.

처음 제안된 해법: 백엔드 PR에서 스펙 변경 감지 → 프론트에 같은 이름의 브랜치 자동 생성 → 코드 생성 → PR 자동 발행. 단, **생산자(백엔드)가 소비자(프론트)를 직접 지정하는 푸시가 아니라, 소비자가 스스로 감지하는 구독 방식이 가능한가**가 핵심 검토 사항이었다.

## 코드에서 확인한 현재

- **스펙의 위치·형태**: `careerhub-api-composer/careerhub/apicomposer/api/openapi.yaml` (1,125줄, `version: 0.1.0` 고정). Epic #13 완료로 스펙이 계약의 진실이고 서버는 생성 인터페이스(`oapi-codegen`)로 구속된다.
- **백엔드 CI**: `go-test.yaml`이 PR·push마다 재생성 diff로 스펙↔생성물 신선도를 게이트한다. **그러나 스펙을 저장소 밖으로 발행(publish)하는 단계는 없다** — 스펙은 파일로만 존재하고, 버전드 아티팩트가 아니다.
- **프론트(careerhub-web)**: Next.js + TS(strict). CI는 typecheck·lint뿐, 타입 생성 파이프라인은 아직 없다(#12 OPEN).
- **ADR-0014 Consequences**: *"프론트는 실행 중인 백엔드 서비스가 아니라 **버전된 계약 스펙**에 결합한다"* — 그런데 지금 "버전된 스펙"이라는 실체가 없다. 있는 것은 prod 브랜치의 HEAD 파일뿐이다.

## 재정의 — 전파는 "핀(pin) 범프"다

ADR-0014대로면 프론트는 스펙의 **특정 버전에 핀**되어야 한다(움직이는 HEAD에 결합하면 빌드 재현성이 사라진다). 그러면 모든 전파 방식은 하나의 구조로 환원된다:

> **핀이 어디를 가리키는가**(git SHA/태그 vs 패키지 버전) × **누가/무엇이 핀을 올리는가**(사람, 백엔드발 트리거, 프론트발 폴링, 의존성 봇)

프론트에 열리는 PR의 실체는 언제나 "핀 범프 + 재생성 결과"다. 이렇게 보면 옵션 간 차이가 선명해진다.

## 제약 — 조사에서 확인한 사실

1. **GitHub Actions에는 다른 repo의 push 이벤트를 구독하는 네이티브 기능이 없다** ("triggers are per-repository" — [community #26323](https://github.com/orgs/community/discussions/26323)). 순수 이벤트 구독을 하려면 ⓐ 생산자가 소비자를 직접 dispatch(=푸시, 결합), ⓑ 발행물(패키지 등)을 이벤트 버스 삼아 소비자 쪽 봇/폴링이 감지, ⓒ 자체 GitHub App/webhook 릴레이 운영 — 셋 중 하나다.
2. 따라서 **"구독"의 업계 실현체는 "발행 + 소비자측 감지"다.** 대표 사례가 GitHub 자신: [github/rest-api-description](https://github.com/github/rest-api-description)에 스펙 발행 → [octokit/openapi-types.ts](https://github.com/octokit/openapi-types.ts)가 타입 생성·npm 발행 → 소비자는 Renovate/Dependabot으로 수신. Stripe([stripe/openapi](https://github.com/stripe/openapi))도 같은 패턴.
3. 감지와 별개로 **breaking change 게이트**(oasdiff 등)는 생산자 PR 단계의 독립 계층이다 — 어느 전파 방식을 골라도 얹을 수 있다.

## 옵션

### O0. 안 한다 — 사람이 핀을 올린다

프론트가 스펙 SHA(또는 버전)를 핀하고, 백엔드 계약이 바뀌면 사람이 핀을 올리고 재생성한다.

- **이기는 조건**: 계약 변경 빈도가 낮고, 백엔드·프론트를 같은 사람이 만질 때. 지금이 정확히 그렇다 — 소비자 1개, 개발자 1인.
- **지는 조건**: 변경을 잊는다. 자동 알림이 없으므로 "핀이 낡았다"는 사실 자체가 보이지 않는다 — 아픔(조용한 퇴행)이 그대로 남는다. 리뉴얼 활성 개발기에는 계약 변경이 잦아 잊기 쉽다.
- 현상 유지의 비용: ADR-0014의 게이트가 사람의 기억력에 의존하게 된다.

### O1. 푸시 — 백엔드 CI가 프론트를 dispatch (처음 제안)

백엔드에서 스펙 변경 시 `repository_dispatch`/`workflow_dispatch`로 프론트 워크플로를 기동 → 재생성 → PR 자동 발행.

- **결합**: 생산자가 소비자 repo·워크플로명을 하드코딩한다. 의존 방향이 역전된다(생산자→소비자). 처음 제안이 스스로 지적한 그 결함이고, 조사에서도 핵심 한계로 확인됐다.
- **운영물**: cross-repo dispatch에는 PAT 또는 GitHub App 토큰이 필수. **PAT 만료 시 무음 단절** — 백엔드 CI는 성공으로 보이고 프론트만 조용히 뒤처진다. 무음 실패라는 점에서 O0의 실패 모드와 본질이 같다.
- **되돌리기**: 싸다. 백엔드 CI에서 스텝 하나 지우면 끝.

### O2. 폴링 구독 — 프론트 cron이 스펙을 감시

프론트에 `on: schedule` 워크플로: 백엔드 prod 브랜치의 `openapi.yaml` SHA를 조회 → 커밋된 핀과 다르면 fetch·재생성 → 핀 범프 PR.

- **결합**: 프론트가 백엔드 repo·경로를 안다 — 소비자가 생산자를 아는 **올바른 방향**의 의존. 백엔드는 아무것도 모른다(원하던 구독 성질).
- **운영물**: 같은 org public/내부 read라 토큰 부담이 작다. 레지스트리·발행 스텝 불요 — **백엔드 무변경**으로 성립한다.
- **비용**: 전파 지연 = cron 주기(일 단위면 충분해 보인다). "마지막으로 본 SHA" 상태는 프론트 repo에 커밋된 핀 자체가 담당하므로 별도 상태 저장이 없다.
- **실패 모드**: cron 워크플로가 죽어도 무음일 수 있다 — 단, 실패가 프론트 repo의 Actions 탭에 남으므로 O1의 PAT 무음 단절보다는 관찰 가능하다.

### O3. 발행 구독 — 스펙을 버전드 패키지로, Renovate가 수신 (업계 표준형)

백엔드 CI가 스펙 변경 머지 시 스펙을 npm 패키지(GitHub Packages)로 semver 발행 → 프론트는 devDependency → Renovate가 신버전 감지 → 자동 PR → PR CI에서 재생성+`tsc`로 호환성 즉시 판정.

- **결합**: 가장 낮다. 생산자는 "발행"에서 책임이 끝나고 소비자가 몇이든 무관 — **가장 순수한 pub-sub**. ADR-0014의 "버전된 계약 스펙"이라는 문구에 실체(semver 아티팩트)를 부여한다.
- **비용**: 백엔드에 발행 스텝 + 버전 규율(semver로 breaking 표현)이 생긴다. 프론트에 Renovate 도입. 현재 `version: 0.1.0` 고정인 스펙에 버전 올리기 규율이 새로 필요하다 — **기계가 아니라 사람의 규율이 하나 늘어나는 것**이 숨은 비용.
- **이기는 조건**: 소비자가 늘 때(모바일, 다른 서비스, SDK), 또는 "breaking 여부를 버전 숫자로 소통"하는 가치가 필요할 때.
- **지는 조건**: 소비자 1개인 동안은 레지스트리·발행·봇이라는 3개 부품이 O2의 cron 하나와 같은 일을 한다.

### 독립 축 A — 발행물이 스펙인가, 생성된 타입인가

O1~O3 공통의 하위 선택: 백엔드가 **스펙**을 내보내고 프론트가 생성하는가, 백엔드가 **TS 타입까지 생성해** 내보내는가(octokit 방식).

- 타입 발행은 프론트의 codegen 단계를 없애지만, **생성 도구 선택권이 백엔드로 넘어간다** — #12는 "도구 선택은 구현 판단(프론트의)"이라 했다. 소비자가 프론트 하나뿐인 지금은 스펙 발행 + 프론트 생성이 #12의 관할 구분과 맞는다.

### 독립 축 C — 핀의 표현: git SHA인가 `info.version`인가

논의 중 나온 지적: *"버전된 스펙"은 이미 있는 `openapi.yaml`의 `info.version` 아닌가?* — 이 지적이 O3를 두 독립 축으로 분해한다:

| | 무엇 | 필요한 것 |
|---|---|---|
| **버전 규율** | semver로 계약 변경의 의미(breaking 여부)를 소통 | `info.version` + CI 범프 게이트 (+태그) — **레지스트리 불요** |
| **전달 매체** | 소비자가 새 버전을 감지하는 통로 | 레지스트리+봇(O3) 또는 폴링(O2) |

즉 버전 규율은 레지스트리 없이 성립하고, O3의 고유 가치는 전달 매체(봇 생태계)뿐이다.

단, 지금의 `info.version`은 "버전 모양의 라벨"이지 아직 버전이 아니다. 핀이 되려면 두 결손을 채워야 한다:

- **① 주소성** — "0.2.0을 달라"로 그 내용을 가져올 수 있어야 한다. 가변 브랜치 위 파일 안의 문자열이므로 버전→내용 매핑(태그 `spec-v0.2.0` 또는 SHA 기록)이 필요하다. git SHA는 이것을 공짜로 준다.
- **② 불변 강제** — 내용이 바뀌면 라벨이 반드시 바뀌어야 한다. 현 백엔드 CI 게이트는 스펙↔생성물 신선도뿐이라 스펙이 바뀌어도 `info.version`이 0.1.0에 머무는 것을 막지 못한다(실제로 #13 전 기간 0.1.0 고정). 강제 없는 라벨은 거짓말할 수 있다. 채우는 법: "스펙 파일 diff 존재 → `info.version` 변경 필수" CI 스텝, 나아가 축 B(oasdiff)와 결합해 "breaking 검출 → major 범프 요구"까지 — 규율이 아니라 구조로 강제하는 §8의 모양이다.

핀 표현의 선택지:

- **SHA 핀**: 규율 0, 오늘 바로 동작. 대신 프론트 PR이 "abc123→def456" — breaking 여부는 diff를 읽어야 안다.
- **version 핀**: PR 제목이 "0.2.0→1.0.0 — breaking"이라 말한다. 대신 ② 게이트가 서 있어야만 신뢰 가능.
- **절충 — 기계적 핀은 SHA, 의미는 version**: 프론트가 `{sha, version}`을 함께 기록. 감지는 SHA 비교(강제 불요·거짓말 불가), 라벨링은 version. ② 게이트가 서기 전에도 동작하고, 선 뒤에는 version이 신뢰를 얻는다.

> 후속 발전(gRPC 일반화 discussion, `260730_1620`): **계약 공표 태그 `spec/vX.Y.Z`** (provider CI가 `info.version`에서 파생해 자동 생성, 앱 빌드 태그 `v*`와 네임스페이스 불교차)가 ①주소성과 ②불변 강제를 동시에 해결한다 — 태그 중복이 곧 범프 게이트다. 감지도 파일 SHA가 아니라 새 `spec/*` 태그 감시로 단순화되어 gRPC 경계와 완전 동형이 된다. 이쪽이 절충안보다 우월해 보인다.

### 독립 축 B — breaking change 게이트 (보완 계층, 어느 옵션에도 얹는다)

백엔드 스펙 PR에 [oasdiff](https://github.com/oasdiff/oasdiff) 게이트를 얹으면 "이 변경은 breaking"이 **소비자에 도달하기 전에** 생산자 PR 리뷰에서 드러난다. ADR-0018이 말한 "스펙 PR에서 계약 변경이 리뷰된다"를 기계가 보조하는 것. 전파 방식과 직교하므로 이 논의의 결론과 무관하게 별도 티켓 후보다.

## 비교

| 축 | O0 수동 | O1 푸시 dispatch | O2 폴링 구독 | O3 발행+Renovate |
|---|---|---|---|---|
| 생산자가 소비자를 아는가 | 아니오 | **예 (결합)** | 아니오 | 아니오 |
| 백엔드 변경 필요 | 없음 | CI 스텝+PAT | **없음** | 발행 스텝+버전 규율 |
| 전파 지연 | 무한대 가능 | 즉시 | cron 주기 | 봇 주기 |
| 감지→PR 자동화 | 없음 | 완전 | 완전 | 완전 |
| 주 실패 모드 | 잊음(무음) | PAT 만료(무음) | cron 실패(Actions에 가시) | 발행 누락 drift |
| 새 운영물 | 없음 | PAT 관리 | cron 워크플로 1개 | 레지스트리+semver+봇 |
| 되돌리기 | — | 싸다 | 싸다 | 싸다 (발행물 폐기 공지 필요) |

> 후속 검증(gRPC 일반화 discussion의 공표·전달 사례 조사, `260730_1620`): 업계 수렴점은 "공표 = 머지~CI 발행 시점의 버전드 아티팩트, 전달 = 빌드 타임 pull(봇 폴링 PR + 사람 머지)"로 확인됐다 — registry→소비자 push webhook 전달은 어느 생태에도 없다. **O2(폴링 pull)와 "자동 PR·수동 머지" 선이 독립 조사로 재확인된 것.** O1(푸시 dispatch)의 근거는 더 약해졌다.

**모든 옵션이 two-way door다** — 되돌리기가 다 한 시간 단위라서, 이 선택 자체는 ADR감이 아니라 #12(또는 그 형제 티켓)의 구현 판단으로 보인다. 단, O3를 고르면 "스펙 패키지"라는 대외 인터페이스와 semver 규율이 생기는데, 이것이 관례로 굳은 뒤에는 되돌리기가 점점 비싸진다 — 그 시점에는 ADR로 승격할 가치가 생긴다.

## 합의 시점 — 전파 이전의 축 (병렬 개발)

전파 방식(위 옵션들)과 독립인 더 앞선 질문이 논의에서 드러났다: **프론트는 언제부터 새 계약 위에서 개발을 시작할 수 있는가.** "머지 시점 전파"는 머지가 **구현 완료**를 뜻하는 동안에는 프론트를 백엔드 구현 뒤로 줄 세운다 — 개발이 직렬화된다. 이상형은 *계약을 먼저 합의하고, 합의된 스펙이 양쪽에 전달되어 동시 개발*이다.

### 코드에서 확인한 사실 — 현 구조는 이미 "합의 선행 머지"를 허용한다

- `controller/strict.go`의 `StrictServer`는 `var _ api.StrictServerInterface` 단언으로 명세 전 연산의 구현을 컴파일로 강제하지만, **501(ErrorResponse) 반환 stub도 그 강제를 만족한다.** "스펙 + 재생성 + stub"만 담은 PR이 머지 가능하다 — CI 신선도 게이트도 그대로 성립.
- 내장 명세 기반 요청 검증 미들웨어 덕에 stub 상태에서도 새 엔드포인트의 **요청 형식 검증은 이미 작동**한다.
- 즉 필요한 것은 구조 변경이 아니라 **머지의 의미 재정의**다: "스펙 수정 → 재생성 → 구현 한 PR" 관행을 "스펙 수정 → 재생성 → **stub** 한 PR(합의) + 구현 PR(후행)"로 쪼개는 것.

### 업계 사례 — design-first의 표준 흐름과 일치한다

- **Zalando API Guidelines Rule #100 "API First"**: 구현 전에 OpenAPI로 정의하고 **소비자(client developers)의 조기 리뷰**를 받는 것이 의무. 구현 후 스펙 공개는 명시적 bad practice. 스펙 리뷰가 합의 지점이고, 이후 개발은 "in parallel or in advance". lightweight를 반복 강조 — 리뷰가 무거워지면 병목이 되는 것이 알려진 실패 모드.
- **Adidas api-guidelines**: Design 단계에서 스테이크홀더 코멘트로 합의 → 합의 스펙에서 auto-mock을 세워 소비자 병렬 개발 → 구현이 스펙에 점진 수렴("초기 contract test는 전부 실패가 정상").
- **501 stub 선행은 도구의 기본 설계다**: OpenAPI Generator의 서버 stub 기본값이 501 반환이고, CAMARA(Linux Foundation)가 미구현 엔드포인트 501 응답을 표준화 논의로 다뤘다. 501은 "합의됨 ≠ 구현됨"을 **런타임에 구분해 주는 장치**이기도 하다.
- **미머지 브랜치 스펙에 핀하는 실무도 존재한다** ([openapi-typescript #1844](https://github.com/openapi-ts/openapi-typescript/discussions/1844)) — 단 리뷰 중 변경·PR 기각·force-push로 핀이 유령 계약이 되는 위험이 함께 문서화되어 있고, 같은 논의의 결론도 "합의 지점을 머지 가능한 최소 단위로 앞당기라"다.

### 병렬 개발의 소비 수단 — 스펙 기반 mock

합의된 스펙 위에서 프론트가 실제로 개발하려면 타입만이 아니라 **응답이 필요**하다. 표준 도구:

- **Prism**(Stoplight): 스펙에서 즉시 mock 서버. base URL env 스위칭으로 실서버 전환. validation proxy 모드로 전환기 검증까지.
- **MSW 계열**(msw-auto-mock, orval, openapi-msw): 네트워크 레이어 가로채기 — Next.js에 특히 맞고, 앱 코드가 mock 여부를 모른다.
- 알려진 실패 모드: example 기반 mock은 happy path만 재현(에러 example을 스펙에 넣지 않으면 에러 처리가 미검증으로 남는다), optional 필드를 mock이 항상 채우면 실서버의 "유효하지만 깨지는" 응답을 못 잡는다.

### 이 축의 옵션

- **P1. 스펙+stub 선행 머지 — 합의 = main 머지** (업계 수렴점): 백엔드에 "스펙+재생성+501 stub" PR을 먼저 머지. 프론트는 항상 main 스펙에 핀하므로 앞의 전파 옵션(O2 등)이 **합의 시점에** 발화한다 — 전파와 병렬성이 한 번에 풀린다. 비용: 머지 단위 관행 변경 + stub 작성(기계적).
- **P2. 미머지 스펙 SHA 핀**: 백엔드 무변경. 그러나 유령 계약 위험(기각·리뷰 변경)이 프론트에 전가되고, 전파 자동화(폴링)가 못 본다 — 수동 핀으로만 성립.
- **P3. 합의 장소의 구조화** (P1의 보강): 스펙 파일 경로에 CODEOWNERS + required review로 "스펙 변경 = 소비자 승인"을 구조로 강제. 단 1인 개발 조건에서는 자기 승인이라 조직적 의미가 약하다 — 지금은 관행으로 충분하고, 구조화는 개발자가 늘 때.

**P1이면 "즉시성" 질문(열린 질문 1)의 답도 바뀐다**: 합의 직후 개발을 시작하는 사람은 스펙 PR을 머지한 그 사람이므로, 프론트 폴링 워크플로에 `workflow_dispatch`(수동 버튼)를 함께 달면 cron 지연 없이 즉시 당길 수 있다 — 즉시성을 위해 O1(푸시)이 필요해지지는 않는다.

### 변경의 세 부류 — stub 패턴은 추가적 변경에만 성립한다

논의에서 드러난 한계: 위 P1의 stub 분해는 **기존 엔드포인트의 계약 변경에는 적용되지 않는다**(동작 중인 연산을 501로 되돌릴 수 없다). 변경을 부류로 나눠야 처리법이 갈린다:

| 부류 | 예 | 기계 감지 | 처리 |
|---|---|---|---|
| **추가적** | 새 엔드포인트·새 필드 | oasdiff: non-breaking | P1 그대로. 새 필드는 **optional로 선언해 머지** — stub의 필드 버전(프론트는 `T \| undefined`로 부재 처리 강제, 백엔드 구현 전 합의 머지 가능) |
| **구조적 파괴** | 타입 변경·필드 제거·rename | oasdiff: breaking | **expand-contract** (아래) |
| **의미적 파괴** | 타입 동일·의미 변경 | **불가** — oasdiff 침묵·컴파일 통과·mock 정상 | 규약으로 ②에 변환: **"의미가 바뀌면 이름을 바꾼다"** |

**구조적 파괴 — in-place 변경은 두 겹으로 막혀 있다.** ⓐ stub 분해 불가: 타입이 바뀌면 재생성 모델이 바뀌어 기존 핸들러의 수정이 같은 PR에 강제된다. ⓑ 배포 순서 결합: 백엔드가 신 계약으로 배포되는 순간 구 계약을 기대하는 실행 중 프론트가 깨진다 — SPA는 브라우저에 구 번들이 캐시되므로 "동시 배포"로도 이 창이 안 닫힌다. 일반해는 in-place를 포기하는 **expand-contract (parallel change)**:

1. **expand** — 신형을 곁에 추가(구형은 `deprecated: true`) → 추가적 변경으로 환원, P1 흐름과 호환
2. **migrate** — 프론트가 신형으로 이행 — 핀 범프 PR의 컴파일이 이행 완료를 증명
3. **contract** — 구형 제거 — 프론트 이행·배포 확인 후. **생성 타입 덕에 안전 증명이 기계화된다**: 제거된 스펙으로 프론트 타입을 재생성해 컴파일이 통과하면 "아무도 안 쓴다"의 증명이다

Zalando 호환성 규칙군("호환 확장 선호·하위 호환 파괴 금지")이 이 자세다. 축 B(oasdiff)는 우발적 in-place 파괴를 PR에서 거부하는 안전망으로, 축 C(semver)는 contract 단계 = major로 맞물린다.

**의미적 파괴 — 모든 게이트를 무사 통과하는 최악의 변경.** rename 규약("의미가 바뀌면 이름을 바꾼다")은 보이지 않는 변경을 구조적 파괴로 변환해 기계 가시권(oasdiff·컴파일)에 넣는다 — protobuf의 "필드 번호 재사용 금지"와 같은 계보. 규약을 어기는 잔여(이름 유지한 채 의미 변경)는 **스펙 PR 리뷰가 유일한 게이트**다 — 합의 지점(P1)이 중요한 또 하나의 이유. 순수 의미 변경 앞에서는 구조가 아니라 사람만 남는다.

## 처음 제안에 대한 반론 지점

1. **트리거 시점이 "PR 발생 시"인 것은 이르다 — 단, 이 반론의 전제는 절반만 옳았다.** 미머지 스펙은 리뷰 중 바뀔 수 있어 자동 추적 대상으로 부적합하다는 것은 유효하다. 그러나 "전파는 머지 시점"이 프론트 직렬화를 낳는 것은 **머지 = 구현 완료**인 관행 때문이지 구조의 필연이 아니다 — 머지의 의미를 "계약 합의"로 앞당기면(위 P1) 반론과 병렬 개발 요구가 충돌하지 않는다.
2. **"백엔드와 같은 이름의 브랜치"는 불필요한 결합이다.** 프론트 PR의 정체성은 "어느 백엔드 브랜치에서 왔나"가 아니라 "스펙 핀을 X→Y로 올린다"이다. 브랜치명 동기화는 유지할 이유가 없는 규약을 하나 늘린다.
3. **구독은 가능한가 — 가능하다. 단, 상상한 형태(순수 이벤트 구독)로는 아니다.** GitHub이 cross-repo 이벤트 구독을 제공하지 않으므로, 구독의 실체는 "발행물 또는 파일을 소비자가 감지"(O2·O3)다. 원하던 성질(생산자가 소비자를 모른다)은 두 옵션 모두 충족한다.

## 검토하고 버린 것

- **중앙 계약 repo** (스펙만 모으는 전용 저장소): 소비자 1·생산자 1에서 repo 하나를 늘리는 것은 비용만 있다. 스펙과 그것을 구속하는 코드(생성 인터페이스)가 한 repo에 있는 현 구조가 spec-first의 강점인데, 분리하면 그 구속이 끊어진다. 서비스 간 계약이 여럿이 될 때 재검토.
- **모노레포**: 전파 문제 자체가 소멸하는 근본 해법이지만, repo 통합은 이 아픔과 비교가 안 되는 별개 대형 결정이다. 이 논의의 관할 밖.
- **자체 GitHub App / webhook 릴레이** (홈랩 k8s에 올리는 것 포함): "생산자가 소비자를 모르는 진짜 이벤트 구동"의 유일한 형태지만, repo 2개 사이의 전파를 위해 상시 운영 인프라를 늘리는 것은 배보다 배꼽이다.
- **런타임 스펙 엔드포인트 폴링** (배포된 서버에서 스펙을 받는 것): 프론트가 결합할 대상은 "실행 중인 서비스"가 아니라 "버전된 스펙"이다(ADR-0014 Consequences). 배포 상태에 계약 원천을 다시 묶는 역행.

## 열린 질문 — 사람의 것

1. **전파 지연 허용치**: 일 단위 지연(O2·O3)이면 충분한가? — P1 채택 시 `workflow_dispatch` 수동 버튼으로 즉시성이 보완되므로, 이 질문의 무게는 크게 줄어든다.
1-2. **합의 단위(P1)를 채택할 것인가**: 백엔드 머지 관행을 "스펙+재생성+stub PR(합의) → 구현 PR(후행)"로 쪼갠다. ADR-0018의 Decision("스펙을 먼저 수정하고 … 구현이 따라온다")과 충돌하지 않고 오히려 그 순서를 PR 단위로 실체화하는 것 — 관행 변경이므로 ADR 불요로 보이나, 백엔드 repo의 규약 문서(CLAUDE.md)에 남길 가치는 있다.
1-3. **mock 계층(P3의 도구)**: Prism(별도 프로세스) vs MSW(코드 내장) — #12의 구현 판단으로 넘길 것인가, 별도 Task인가. 에러 응답 example을 스펙에 담는 규율(mock의 happy-path 한계 보완)도 함께.
2. **전달 매체**: 폴링(O2)으로 시작하고 소비자가 늘 때 발행형(O3)으로 이행하는 경로를 받아들일 것인가, 처음부터 O3인가. (축 C의 분해로 semver 소통은 이 선택과 무관하게 얻을 수 있다 — O3의 고유 가치는 봇 생태계뿐이다)
3. **버전 규율(축 C)**: `info.version` 범프 게이트를 지금 세울 것인가(oasdiff 축 B와 묶어 "breaking → major" 강제까지), 아니면 SHA 핀으로 시작하고 미룰 것인가.
4. **oasdiff breaking 게이트**(독립 축 B)를 백엔드에 얹는 것을 별도 티켓으로 낼 것인가 — 축 C를 세운다면 자연스럽게 묶인다.
5. 자동 생성된 프론트 PR의 **머지는 누가 하는가** — 자동 머지는 없다(컴파일 통과 ≠ 화면이 옳다). PR까지가 기계, 머지는 사람이라는 선을 확인해 두고 싶다.
