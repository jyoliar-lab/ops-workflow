# 결정 후보 — 무엇을 정하고, 무엇이 닫히고, 어느 티켓이 그때까지 못 나가나

`260805_1334_auth-requirements-to-code-mapping.md`가 요구·코드·강제력을 항목별로 짚었고, 그 발산에서 결정 후보 넷이 섰다.
**벌려 보니 셋이었다** — D4(접근수단 0 계정)는 결정이 아니라 준비였고, 대신 아직 안 연 축 하나(D5)가 드러났다.
이 문서는 **각각의 방향과 사정거리**를 적고, 그 아래에 **그것들과 부딪칠 여지가 있는 티켓 후보**를 등급별로 세운다.

항목 번호(1-2·2-7·7-3 …)는 전부 1334의 것이다.

---

## 1. 결정 넷

### D1 — auth-service가 세션 상태를 소유한다

> **auth-service가 세션 상태를 소유하고, 그 상태는 auth-service 안에서만 조회된다.**

**방향.** 지금은 토큰을 발급하고 잊는다. 세션 하나 = 행 하나를 두고, 두 토큰이 그 행의 식별자(`sid`)를 클레임으로 가리킨다. `/auth/*`는 요청마다 그 행을 조회하고, 없거나 폐기면 거절한다.

**닫히는 것**

| | |
|---|---|
| **3-1** 로그아웃 | 행 하나 삭제 → 그 기기의 두 토큰이 함께 즉시 죽고, 다른 기기는 산다 |
| **3-2** 정지·삭제 시 전 세션 종료 | 그 사용자의 행 전량 |
| **3-3** 동시 세션 상한 | 행을 세면 답할 수 있다 |
| (덤) 리프레시 회전 | 행에 현재 `jti`를 두면 재사용 감지가 거의 증분 없이 따라온다 |

**안 닫는 것** — api-composer 경로는 여전히 **최대 10분 지연**이다(액세스 토큰 수명이 상한). 이건 버그가 아니라 고른 것이다. 위험한 조작이 전부 `/auth/*`에 있어서 성립한다.

**경계.** 되돌리기 어려운 것은 두 성질뿐이다 — ⓐ *무상태를 포기한다* ⓑ **그 상태는 auth-service 안에서만 조회된다.**
ⓑ를 안 적어 두면 나중에 *"api-composer도 즉시 막아야 하지 않나"* 라는 합리적인 말이 나오고, 그 순간 없던 런타임 의존이 생긴다. **거절의 근거를 남기는 것이 이 결정의 절반이다.**
행의 컬럼 구성·식별자 형식·회전 여부는 코드의 관할이다.

### D2 — 로그인 왕복을 서버가 소유한다

> **로그인 왕복은 서버가 소유하는 트랜잭션 레코드 위에서 돌고, 로그인 수단 확장점은 검증된 정체성만 밖으로 낸다.**

**방향.** 왕복 시작 때 레코드를 만들어 `state`·`nonce`·PKCE 검증자를 담고, 콜백에서 **검증된 정체성**을 채우고, sign-in·sign-up·agree가 소비하면 지운다. 브라우저로 내려가는 것은 **불투명 참조 하나**다.
확장점은 *"토큰을 주면 사용자 정보를 준다"* 에서 **"왕복을 시작하고, 끝내면 검증된 정체성만 나온다"** 로 바뀐다 — 그 레코드를 소유하는 것이 곧 확장점이다.

**닫히는 것**

| | |
|---|---|
| **2-2** 왕복별 값 | 레코드가 왕복 단위라 덮어쓰기가 없다 |
| **2-4** 검증 가능한 신원 증명 | 확장점이 "검증된 정체성"을 요구하므로 검증이 계약이 된다 |
| **2-7** 대기 상태 | 만료·일회성·바인딩·위조·크기·검증이 한 번에 |
| **7-1** 확장점 모양 | 새 수단을 붙이는 사람이 안전한 경로만 채운다 |
| (덤) **AES 암호화기 소멸** | 봉투가 없어지면 비밀 겸용 문제 하나가 사라진다 |
| (덤) **2-6 위험 감소** | 새어도 짧고 1회용인 참조다. 단 origin 고정은 별개로 해야 한다 |
| (덤) **복제본 문제 해소** | 지금 왕복 상태가 서명 쿠키에 살아서 키를 두 복제본이 공유해야 한다. 레코드는 DB에 있어 그 제약이 없다 |

**안 닫는 것** — 다중 IdP의 mix-up 방어는 별개다(콜백 경로가 이미 프로바이더별로 갈라져 있어 유리하긴 하다).

**경계.** 되돌리기 어려운 것은 *"미검증 IdP 토큰이 확장점 밖으로 안 나온다"* 는 성질과 *"왕복 상태를 서버가 소유한다"* 는 성질이다. 레코드 스키마·참조 형식·라이브러리 선택은 코드의 관할이다.

> **시점이 비용을 정한다** — 수단이 하나인 지금 고치면 한 벌, 두 번째 수단이 현재 모양으로 먼저 들어가면 두 벌이다.

### D3 — 서명을 비대칭으로 가른다

> **토큰 서명을 비대칭으로 갈라 검증과 발급을 분리한다.**

**방향.** auth-service만 개인키를 갖고, api-composer는 공개키만 받는다. 지금처럼 자기 안에서 검증하므로 **런타임 결합이 0**이고, 검증할 수 있어도 발급은 못 한다.

**왜 이것 말고 없나.** MAC은 **검증자가 곧 발급자**다. 나눠 갖는 한 발급과 검증의 분리가 원리적으로 불가능하다. api-composer가 검증을 그만두게 하는 길은 런타임 결합이나 내부망 신뢰(NetworkPolicy가 지금 0건이다)를 사는 것이라 더 비싸다.

**닫히는 것**

| | |
|---|---|
| **1-3** 대상 미지정·키 공유 | api-composer가 관리자 토큰을 만들 수 없게 된다 |
| **2-7의 ④** | 봉투 위조 능력도 함께 사라진다 — 단 D2가 오면 봉투 자체가 없어진다 |

**딸려 오는 것 셋**
- **1-1(알고리즘 지정)이 선행 필수가 된다.** 공개키가 오가기 시작하면 그것을 대칭 비밀로 써서 위조하는 것이 전형적 공격이다. **반드시 같은 묶음이어야 한다.**
- **ES256이 RS256보다 맞다.** RSA 서명은 base64로 ~344자가 모든 요청 헤더에 붙고 ES256은 ~86자다.
- **키 배포·회전 경로가 새로 생긴다.** 현재 키는 자동 회전도 백업도 없다 — 그 상태를 물려받지 않는다.

**경계.** 되돌리기 어려운 것은 *"검증과 발급을 가른다"* 는 성질뿐이다. 곡선·알고리즘·배포 방식은 코드의 관할이다.

### D4 — 로그인 수단이 0이 된 계정: **결정이 아니라, 나중을 위한 준비다**

> **벌려 보고 결정 후보에서 내렸다.** 아래가 그 근거다. 재료는 `260805_1245` §3·§4와 1334의 4-4.

#### 무엇이 일어나는가

로그인 수단이 Google 하나뿐이라 그것이 끊기면 계정은 영구히 잠긴다. 경로는 넷 — Google의 2년 미사용 삭제 · 사용자의 앱 연결 해제 · 사용자의 IdP 계정 탈퇴 · (Naver 추가 후) 두 수단을 모두 끊음.

#### ① 실은 두 종류인데, 우리는 구별할 수 없다

| | `sub`가 | 같은 계정으로 돌아오면 |
|---|---|---|
| **(a) 연결 해제** | **살아 있다** | 다시 동의하면 같은 `sub` → **복원 가능** |
| **(b) IdP 계정 삭제** | **죽었다** | 새 계정을 만들어도 새 `sub` → **원리적으로 복원 불가** |

처분이 정반대여야 하는데 **우리 쪽에서는 둘 다 "로그인이 안 온다"로만 보인다.** 구별할 신호가 없다.
→ 보수적으로 (a)로 가정할 수밖에 없고, **그건 파기 기한이 길어진다는 뜻이다.** "몇 개월"을 정할 때 실제로 작동하는 제약이 이것이다.

#### ② 감지가 처분보다 먼저인데, 감지할 수단이 없다

- **수동 추정**(*"N개월 미로그인 = 접근 불가 의심"*) — 구별은 못 하지만 처분이 같다면 구별할 필요도 없다. 가장 싼 길이다.
  → **그런데 셀 수가 없다.** `user` 테이블에 `create_date`·`delete_date`뿐이고 **마지막 로그인 시각 컬럼이 없다.**
- **능동 확인**(IdP에 물어본다) — IdP 리프레시 토큰의 장기 보관이 필요한데, **D2가 봉투에서 IdP 토큰을 빼면서 이 길을 닫는다.** 되살리려면 260804_1831 §7의 *"IdP API를 대신 호출할 때만 정당화된다"* 를 이 용도로 넘어야 하는데 근거가 약하다.
- **콜백 수신** — **Naver는 연결끊기 콜백이 있고 Google은 없다.** 감지 능력이 IdP마다 달라서, 정책을 감지에 맞추면 IdP별로 갈린다.

#### ③ 파기를 택하면 삭제 전파를 만들어야 한다 — 그리고 그 구멍은 이미 있다

데이터가 두 저장소에 걸쳐 있다: auth-service PostgreSQL(`user`·`user_authority`·`user_agreement`·`ticket_used`)과 **userinfo-service MongoDB**(스크랩·매칭조건, `userId`로 인덱싱).

**그런데 auth-service에는 userinfo로 나가는 호출이 없다.** `Withdrawal` 전문을 확인했다 — 트랜잭션 안에서 동의·권한을 지우고 `user` 행을 익명화(`delete_date = NOW()`, `status = 'DELETED'`)할 뿐이고, gRPC 클라이언트 자체가 없다(auth-service는 mailer gRPC **서버**이지 클라이언트가 아니다).

> **즉 지금도 탈퇴하면 스크랩·매칭조건이 남는다. D4가 만드는 문제가 아니라 이미 있는 구멍을 D4가 드러내는 것이다.**

그리고 삭제 전파는 260804_1831 ②가 *"제품을 들이면 두 시스템에 걸친다"* 며 제품 도입을 거부한 **바로 그 종류의 일**이 자체 구조 안에서 필요해지는 것이다.

#### ④ 알릴 수단이 없다

통지 경로가 이메일뿐인데 **그 이메일이 곧 사라진 Google 계정의 주소다.** 계정이 지워지면 그 주소로 메일이 가지 않는다.
→ **다중 IdP가 이 문제를 완화한다** — Naver를 붙이면 두 번째 주소가 생긴다.

#### ⑤ 왜 결정 후보에서 내렸나

- **비활성화는 되돌릴 수 있다** → 임계선 미달. 티켓이다.
- **파기만 one-way door다.** 그러니 이 축의 실질은 *"파기할 것인가, 언제부터 세어서 언제"* 하나뿐이다.
- 그런데 **현재 가입자가 1명(운영자 본인)이라 사례가 0건**이고, 앞으로도 한동안 0이다.
- **무엇보다 셀 재료가 없어서(①의 컬럼 부재) 지금 어떤 기한을 정해도 공허하다.**

> **→ 지금 정할 것은 처분이 아니다. 나중에 정할 수 있도록 재료를 남기는 것이다.**

#### ⑥ 그래서 지금 하는 것 — 티켓 하나

**마지막 로그인 시각을 기록하기 시작한다.** 컬럼 하나 + 로그인 경로에서 UPDATE 한 줄이고, 넷 중 어느 것과도 안 부딪친다.
없으면 **미루는 동안 과거를 소급해 셀 수 없게 된다** — `260805_1308`의 *"지금은 가역, 나중은 불가역"* 과 같은 형태이고, D-4(동의 시각·버전)와도 같은 성질이다.

#### ⑦ ★ 그 대신 결정 자리가 하나 비어 있다

**앞선 판이 4-2·4-3·`auth_server` 삭제를 "D4 대기"로 걸어 두었는데, 잘못 걸었다.**
그것들이 기다리는 것은 접근수단 0 계정의 처분이 아니라 **정체성 저장 모델과 계정 연결 정책**이다 — 같은 사람의 두 IdP를 이을 것인가, 정체성을 `user` 행에서 분리할 것인가(`260804_1735` 축 F·F′, `260805_1245` 열린 질문 3).

**이 축은 아직 안 벌렸다.** 이 문서에서는 **D5(미발산)** 로 자리만 잡아 둔다 — 4-2·4-3·`auth_server`가 거기 걸리고, **Naver를 붙이는 순간 4-2가 기능 고장으로 드러난다**(같은 사람의 두 번째 가입이 이메일 유일 제약에서 실패한다).

## 2. 결정은 셋이다 — 그리고 서로 독립이다

| | D1 | D2 | D3 |
|---|---|---|---|
| **D1** 세션 상태 | — | 저장소는 같이 쓰되 수명·소유자가 다르다 | 무관 |
| **D2** 트랜잭션·확장점 | | — | D3가 오면 봉투 위조 논점이 사라지지만, D2는 봉투를 아예 없앤다 | 
| **D3** 비대칭 서명 | | | — |

**어느 하나가 뒤집혀도 나머지 둘은 유효하다.** 그러므로 셋은 별개 ADR 후보이고, 순서 제약도 없다.
다만 **D2는 두 번째 로그인 수단(Naver)보다 먼저**여야 비용이 한 벌로 끝난다.

**D4는 결정이 아니다**(§1의 판정). **D5(정체성 저장 모델·계정 연결)는 아직 안 벌렸다** — 벌리면 넷이 된다.

| **D-3** | 가입 시 기본 권한 부여 | auth-service | 독립 |
| **D-4** | 동의 이력에 시각·버전 추가 | auth-service | **시간이 비용을 밀어 올린다** — 과거 시각은 소급 복원되지 않는다. 셋과 무관하고 **미룰수록 손해다** |
| **D-7** | **마지막 로그인 시각 기록** | auth-service | D4를 안전하게 미루기 위한 전제(§1 D4 ⑥). 컬럼 하나 + UPDATE 한 줄. **없으면 과거를 소급해 셀 수 없다** |

### 🟡 대체될 수 있다 — 내되, 임시임을 알고 낸다

| 항목 | 무엇 | 부딪치는 결정 | 어떻게 부딪치나 |
|---|---|---|---|
| **2-1** | 쿠키 서명 키를 주입값으로 | **D2** | D2가 오면 쿠키가 나르는 것이 서명된 `state`에서 불투명 참조로 바뀌고, 쿠키 세션 라이브러리 자체가 빠질 수 있다. **지금 만드는 키 주입 배선이 버려진다** |
| **2-3** | 쿠키 속성·서버측 수명 | **D2** | 위와 같은 운명 |
| **2-5** | 콜백에 메서드 제한 | D2 | D2가 콜백 핸들러를 다시 쓰지만 `.Methods("GET")` 한 줄은 남는다. 사실상 손해 없음 |
| **6-1·6-2** | 관리자 조작 기록 1년 보관 | D1 | D1이 오면 로그에 세션 식별자가 들어가는 편이 자연스러워 필드가 는다. **다만 [법]이고 누적이 값이라 지금 시작하는 편이 낫다** |

> **2-1을 그래도 지금 내는 이유** — 지금 발급되는 모든 세션 쿠키가 소스에 박힌 문자열로 서명되고 있다. 미루는 동안 되돌릴 수 없는 것이 는다.
> **그리고 "프로세스 시작 시 임의 키 생성"으로 배선을 피하는 길은 없다** — auth-service가 복제본 2개라, 복제본마다 키가 다르면 로그인 왕복이 절반 확률로 깨진다. 공유 비밀 주입이 필요하고, 그 배선이 D2와 함께 버려진다.

## 4. 순서에 대한 제안

1. **6-6(개발 환경) 판단** — 🟢 아홉 건이 전부 운영에서 처음 도는 변경이다. 지금은 사설망 뒤라 위험이 낮아 **그게 지금 움직일 이유**이기도 하지만, 결정 셋의 이행은 규모가 달라 시험 없이 치기 부담스럽다.
2. **🟢 묶음 티켓** — 결정과 무관하다. 그중 **D-4(동의 시각·버전)** 와 **D-7(마지막 로그인 시각)** 은 성격이 다르다 — **미룰수록 손해다.** 과거 시각은 소급 복원되지 않으므로, 미루는 것 자체가 나중의 선택지를 지운다.
3. **D1·D2·D3 초안** — 셋이 독립이라 병렬로 써도 된다. **D2는 Naver보다 먼저.**
4. **D5 발산**(정체성 저장 모델·계정 연결) — 아직 안 벌렸다. 🔴 중 셋이 여기 걸려 있고, **Naver를 붙이면 4-2가 기능 고장으로 드러난다.**
5. **🔴 이행** — 결정이 accept·공표된 뒤.
