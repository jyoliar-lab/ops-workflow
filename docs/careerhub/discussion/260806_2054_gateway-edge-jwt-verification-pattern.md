# 게이트웨이 엣지 JWT 검증 패턴 — 해부와 careerhub 대입

## 질문

ADR-0029(데이터 경로 로컬 검증)의 Alternatives는 게이트웨이 집중 검증을 *"비대칭 서명 아래에서 사본은 문제가 아니다"* 한 축으로 기각했다. 그러나 이 패턴이 실무에서 파는 가치는 사본 문제 해소가 아니다 — 기각 논거가 패턴의 실체를 다 다루지 못했다는 지적이 accept 최종 검토에서 나왔다. 패턴을 해부하고 careerhub에 대입해, 0029의 기각이 여전히 서는지 검증한다.

## 패턴의 정체 — 신뢰 경계의 이동

엣지 인증(edge authentication): 검증의 책임을 각 서비스에서 **네트워크 경계(게이트웨이)** 로 옮긴다. 게이트웨이가 유일한 검증자(JWKS 서명·`iss`·`aud`·`exp` — 검증 자체는 게이트웨이의 로컬 검증이다)이고, 그 뒤는 신뢰된 내부로 간주한다.

신원 전달의 세 변형:

| 변형 | 방식 | 서비스가 받는 것 |
|---|---|---|
| **a. 토큰 통과** | 검증된 JWT를 그대로 전달 | JWT — 서명 확인 없이 클레임 파싱 |
| **b. 헤더 주입** (고전형) | 토큰을 벗기고 신뢰 헤더(`X-User-Id`·권한 목록) 주입 | 평문 헤더 |
| **c. 토큰 교환** | 외부 토큰 ↔ 내부 토큰 재발급 (RFC 8693 · phantom token) | 내부 전용 토큰 |

변형 c의 대표형이 **phantom token**(외부 opaque + 게이트웨이가 요청마다 introspection/교환 → 내부 클레임 전달)이다 — opaque와 엣지 검증의 조합도 성립한다는 뜻이다. 단 이 조합은 두 기각의 비용을 상속한다: introspection의 주체가 서비스에서 게이트웨이로 바뀔 뿐 발급자 왕복이 전 요청 경로에 있다는 사실은 같고(ADR-0029가 기각한 원격 확인의 핵심 비용), 아래 수렴의 기각 논거 셋(도입 수고·검증자 둘·제로트러스트 역행)도 그대로 적용된다. 새 결정면이 아니라 기존 기각 두 개의 교집합이다.

**사는 것**: 검증 코드 단일화(서비스별 드리프트 소멸) · 서비스 단순화(JWKS·암호 코드 제거) · 토큰의 내부 존 비노출(b·c) · 인증 정책의 단일 조작점.

**파는 것**:

- **신뢰 네트워크 전제.** "게이트웨이를 신뢰한다" = "서비스에 게이트웨이 외 경로로 도달할 수 없다"는 네트워크 사실의 신뢰다. 이 사실은 NetworkPolicy나 mTLS 메시로 만들어야 하며, 없으면 내부의 어떤 행위자든 헤더 위조로 인증을 통과한다. 패턴의 보안성은 게이트웨이가 아니라 **네트워크 격리의 함수**다.
- **내부 홉의 검증 소멸.** 서비스 간 호출(api-composer → auth-service gRPC)에서 검증 가능한 자격이 사라지고 헤더 릴레이만 남는다. 검증자가 줄어드는 것이 아니라 경계 안에서 검증이라는 행위가 소멸한다.
- **심층 방어 상실 + 게이트웨이의 인증 계통 편입.** 검증층이 하나가 되고, 게이트웨이 설정 오류가 곧 인증 붕괴가 된다.

**업계 위치.** 이 패턴이 이기는 조건: 다언어 서비스 다수(언어별 JWT 라이브러리 유지비 실재) · 플랫폼 조직이 게이트웨이를 소유하는 조직 경계 · 토큰 내부 비노출 컴플라이언스 · 이미 검증 기능이 있는 스마트 게이트웨이 보유. 흐름은 반대 방향이 우세하다 — 제로트러스트·서비스 메시는 홉마다 검증하며, Istio의 sidecar JWT 검증은 로컬 검증의 구현을 외주한 것이지 검증 위치의 중앙화가 아니다.

## careerhub 실측 대입

현행 토폴로지 (`jyoliar-k8s/gitops/base/services/careerhub/apps/gateway/`):

- **게이트웨이는 실재한다** — Gateway API + NGINX Gateway Fabric(`careerhub-nginx-gateway`), TLS 종단 + 경로 라우팅(`/`→frontend · `/api`→api-composer · `/auth`→auth-service). 현재 역할은 라우팅·TLS뿐, 인증 관여 없음.
- **NetworkPolicy가 없다** — `gitops/base/services/careerhub/`에 NetworkPolicy 리소스 0건. 서비스들은 클러스터 내부에서 게이트웨이를 우회해 도달 가능하다. 패턴의 성립 전제가 현재 부재하며, 도입하려면 격리 구축이 선행 비용이다.
- **검증자는 2개, 같은 언어(Go), 공용 모듈(goutils 계열)로 드리프트 통제 가능** — 단일화가 파는 가치의 크기가 ~0이다.
- **NGINX OSS의 JWT 검증(`auth_jwt`)은 Plus 전용** — NGF(OSS)에서 엣지 JWT 검증이 가능한지 자체가 **미확인**이다. 가능하지 않다면 게이트웨이 교체 또는 별도 인증 프록시가 추가 선행 비용이다.

**대입 판정(재료)**: 이기는 조건(다언어 다수·조직 경계·컴플라이언스·기성 검증 기능)이 전부 부재하고, 성립 전제(네트워크 격리)와 수단(게이트웨이의 검증 기능)이 둘 다 없어 선행 비용만 있다. 패턴의 정당한 서식지가 아니다.

## 수렴 (사람) — 기각, 논거 셋

- **검증 기능이 있는 게이트웨이의 조사·도입 수고** — 현행 NGF의 지원이 미확인이라 선행 비용이 된다.
- **검증자가 둘뿐이다** (auth-service·api-composer) — 단일화가 파는 가치가 ~0이다.
- **업계 흐름 자체가 제로트러스트** — 홉마다 검증. 검증을 엣지로 모으고 내부 홉의 검증을 소멸시키는 방향은 역행이다.

NetworkPolicy 부재는 기각 논거에서 **제외**한다 — 도입이 쿠버네티스 구성 수준이라 결정을 가를 비용이 아니다. 별도 보안 관찰로만 남는다.

→ ADR-0029 Alternatives의 게이트웨이 불릿을 이 논거로 보강 수정했다(proposed 상태의 수정).

## ADR-0029에 주는 함의

- **기각 결론은 서고, 기각 논거는 보강이 필요하다.** "사본은 문제가 아니다"는 이 패턴이 사본 해소용일 때만 유효한 반박이다. 실제 기각 근거는: ① 신뢰 네트워크 전제를 새로 구축해야 하는 비용 ② 내부 홉의 검증 소멸 ③ careerhub 규모에서 단일화 이득 ~0. accept 전 0029 Alternatives의 해당 불릿에 반영할 후보다.
- 이 검토는 0029 제거론(JWT 채택이 로컬 검증을 함의하므로 별도 결정 불요)에 대한 반례 재료이기도 하다 — JWT를 쓰면서 검증을 엣지로 모는 실무 패턴이 실재하므로, "각 서비스가 스스로 검증한다"는 JWT 채택만으로 닫히지 않는 별도 결정이다.

## 열린 것

- NGF의 엣지 인증 지원 실측 — 이 패턴을 기각했으므로 불필요, 재검토 시에만.
- NetworkPolicy 부재는 이 패턴과 무관하게 별도 보안 관찰이다 — 티켓화 여부는 별도 판단(이 논의의 범위 밖).
