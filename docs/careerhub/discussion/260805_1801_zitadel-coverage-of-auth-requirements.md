# Zitadel 도입은 auth-service의 요구사항을 얼마나 해소하는가 — 항목별 판정과 잔여 목록

## 0. 전제와 판정 어휘

`260805_1334`(요구·코드·강제력)와 `260805_1550`(결정 후보·티켓)은 **auth-service가 직접 구현하는 전제**로 쓰였다.
`260805_1635`가 그 전제를 뒤집는 방향으로 수렴 중이다 — **K2+P2 구조**:

> 인증(가입·로그인·세션·탈퇴)은 제품(Zitadel)이 소유한다. 권한·티켓·동의는 auth-service가 소유하고,
> 제품이 발급 시 auth-service(Actions v2 Target)를 호출해 클레임으로 싣는다.
> api-composer·auth-service는 제품 토큰을 로컬(JWKS)로만 검증한다. 동의는 앱 온보딩 게이트, 전파는 주기 조정.

이 문서는 그 구조를 가정하고 1334의 전 항목·1550의 결정과 티켓을 다시 판정한다. 어휘 넷:

| 판정 | 뜻 |
|---|---|
| **✂ 소거** | 요구 자체가 제품 관할이 되어 우리 코드에서 사라진다 |
| **↻ 변형** | 요구는 남되 형태가 바뀐다 — 다른 자리에서, 대개 더 싸게 |
| **● 잔존** | 우리 몫 그대로다. 제품이 안 가져간다 |
| **+ 신규** | 도입 자체가 만드는 새 일 |

## 1. 1334 항목별 판정

### §1 토큰

| 항목 | 판정 | 근거 |
|---|---|---|
| 1-1 알고리즘 지정 검증 | **✂** | 발급이 제품(RS256)·검증이 표준 라이브러리로 바뀌면 수제 keyfunc 자체가 소멸. 라이브러리 설정(iss·aud 고정)은 코드 관할 |
| 1-2 토큰 종류 표시·혼용 차단 | **✂** | 표준 OIDC 토큰 체계(access/refresh/id 구분)가 제품에서 온다. 수제 `ParseToken` 소멸 |
| 1-3 키 공유·audience | **✂** | **D3 그 자체가 소거된다.** 제품이 개인키를 갖고 서비스는 공개키(JWKS)만. `aud` 표준 포함 |
| 1-3-a 비대칭 전환 | **✂** | 위와 동일 — 전환 작업 자체가 불필요해진다 |
| 1-4 토큰 원문 로깅 | **↻** | 현행 로깅 코드는 리뉴얼로 소멸하나, **전환 전까지 지금도 Loki에 쌓인다**(§4 전환기). 새 검증 미들웨어에서 같은 실수를 반복하지 않는 것은 우리 규율 |

### §2 로그인 왕복

| 항목 | 판정 | 근거 |
|---|---|---|
| 2-1 state CSRF(하드코딩 키) | **✂** | 왕복 전체가 제품 소유. 쿠키 세션 스토어 자체가 소멸 |
| 2-2 왕복별 값 | **✂** | 제품 관할 |
| 2-3 쿠키 속성·수명 | **✂** | 제품 관할 (프론트 토큰 저장은 별개 축 — `260722_1617`) |
| 2-4 검증 가능한 신원 증명(ID Token) | **✂** | 제품이 Google·Naver에 대한 OIDC RP로서 id_token 검증을 수행한다. 우리는 제품 토큰만 검증 |
| 2-5 콜백 메서드 제한 | **✂** | 콜백 자체가 제품 것 |
| 2-6 `postMessage "*"` | **✂** | 팝업+postMessage 패턴 자체가 소멸(표준 리다이렉트로) — 단 프론트 로그인 재작성이 이행 작업으로 든다(§3 신규) |
| 2-7 `authToken` 봉투 | **✂** | 봉투·AES 암호화기 소멸. 봉투가 나르던 "인증됐지만 미가입" 상태는 **정식 토큰 + 클레임 게이트**(온보딩)로 대체된다 — 만료·바인딩 문제가 구조적으로 사라진다 |

### §3 세션 종료

| 항목 | 판정 | 근거 |
|---|---|---|
| 3-1 로그아웃 | **✂** | **D1이 소거된다.** 제품 end_session·세션 관리 |
| 3-2 정지·삭제 시 전 세션 종료 | **✂/↻** | 제품의 사용자 비활성화·삭제가 세션·refresh를 무효화한다. 단 로컬 JWKS 검증이므로 **이미 발급된 access token은 수명까지 유효** — 이 지연을 auth-service 자기 경로에서 좁히는 선택이 남는다. **→ §6 (C2의 원리는 살아남는다)** |
| 3-3 session fixation | **✂** | 제품 관할 |
| 동시 세션 수 문서화 | **↻** | 제품 세션 관리가 조회 수단을 준다. "정해 둔다"는 요구는 남되 답이 제품 설정값이 된다 |

### §4 정체성

| 항목 | 판정 | 근거 |
|---|---|---|
| 4-1 (provider, subject) 네임스페이스 | **✂** | 제품의 federated identity 모델이 표준형 그 자체다 |
| 4-2 `UNIQUE(email)` 처분 | **✂** | 정체성 열이 앱 `user` 테이블에서 사라진다. 계정 연결 정책도 제품 설정. **1550의 D5(정체성 저장 모델·계정 연결 — 미발산)가 발산할 필요 없이 통째로 소거된다** |
| 4-3 탈퇴의 정체성 파괴 | **✂/↻** | 익명화 UPDATE 로직 소멸(탈퇴는 제품의 사용자 삭제). 앱 잔여 데이터(동의·권한 행) 정리는 조정 잡의 몫으로 남는다 |
| 4-4 접근수단 0 계정 정책 | **●** | **정책 결정은 여전히 사람의 것.** 단 감지 재료(마지막 로그인)는 제품 이벤트가 공짜로 준다 — 1550의 D-7 티켓이 소거된다 |
| 4-5 저장소 독립 식별자 | **✂ + 이행** | 제품 user id(UUID)가 `260805_1308` 수렴을 그대로 충족한다. userinfo Mongo의 `userId` 치환 마이그레이션이 이행 티켓으로 남는다(N=1이라 ~0) |

### §5 응답과 경계

| 항목 | 판정 | 근거 |
|---|---|---|
| 5-1 보안 헤더(HSTS·CSP) | **●** | careerhub 앱 응답의 헤더는 우리 것. **담당 미정(앱 vs 게이트웨이) 문제 그대로** |
| 5-2 CORS | **●** | composer·auth-service의 CORS는 우리 코드 |
| 5-3 관리자 경로 분리 [법] | **↻** | 사용자 조회·강제 탈퇴가 **Zitadel 콘솔**로 옮겨간다 — 같은 질문이 "콘솔을 사설망 안으로 묶나"로 **형태를 바꿔 남는다.** 제품은 관리자 MFA를 주므로 취급자 조항 충족은 오히려 쉬워진다. 앱에 남는 admin(티켓 발급)의 노출 판단도 남는다 |

### §6 관측

| 항목 | 판정 | 근거 |
|---|---|---|
| 6-1 로그인 성공·실패 이벤트 | **✂/↻** | 이벤트소싱이 구조적으로 남긴다(`eventstore.events2`). [법]인 관리자 조작 기록 1년은 **이벤트 보존 기간을 우리가 보장**해야 충족 — PG 보존·백업 정책의 몫 |
| 6-2 권한 거부 로깅 | **●** | composer·auth-service의 403 로깅은 우리 코드 |
| 6-3 실패 응답 통일 | **↻** | 500의 근원(수제 파서)이 소멸. 새 검증 미들웨어의 401/403 규율은 우리 몫 — 1635 §9의 사유 코드 설계와 합류 |
| 6-4 rate limit | **●** | 앱/게이트웨이 배치 미정 그대로. 제품 로그인 엔드포인트 자체의 방어는 제품 몫 |
| 6-5 panic recover | **●** | 우리 코드 |
| 6-6 dev 환경 | **● 격상** | **더 중요해진다** — 제품 도입·연동이야말로 prod에서 처음 돌면 안 되는 종류의 변경이다. 모든 이행의 공통 선행 유지 |

### §7 구조 결정 — 여기가 가장 크게 바뀐다

| 항목 | 판정 | 근거 |
|---|---|---|
| 7-1 확장점 재설계 (D2) | **✂** | IdP 브로커가 제품이므로 `Ooauth` 확장점 자체가 소멸. `BeginAuth/CompleteAuth` 설계 불요 |
| 7-2 파서 분리 | **✂** | 수제 파서 소멸 |
| 7-3 세션 상태 소유 (D1, **S2+C2로 수렴했던 것**) | **✂ — 수렴 폐기** | ★ **1334의 7-3 수렴(S2+C2)은 "auth-service가 발급자"라는 전제 위의 답이었다. 이 방향에서는 그 전제가 사라지므로 수렴 자체를 폐기한다.** 세션 행·sid 클레임·회전 설계 전부 불요 — 제품이 갖는다 |
| 7-3-d 트랜잭션 레코드 | **✂** | 왕복을 제품이 소유하므로 레코드도 제품 것 |

## 2. 1550의 결정·티켓 재판정

### 결정 후보

| | 1550의 판정 | 이 방향에서 |
|---|---|---|
| **D1** 세션 상태 소유 | ADR 후보 (수렴) | **✂ 소거** — 제품 관할 |
| **D2** 왕복·확장점 소유 | ADR 후보 (수렴) | **✂ 소거** |
| **D3** 비대칭 서명 | ADR 후보 (수렴) | **✂ 소거** — 제품이 비대칭 발급 |
| **D4** 접근수단 0 계정 | 결정 아님·재료 수집(D-7) | **● 유지** — 단 D-7 없이 재료가 쌓인다 |
| **D5** 정체성 모델·계정 연결 | 미발산 | **✂ 소거** — 발산 불요 |

**→ 결정 셋이 소거되고, 대신 새 결정 하나가 선다** — `260805_1635` 말미의 문장:
*"인증은 외부 IdP 제품이 소유한다. 권한·티켓·동의는 앱이 소유하고, 제품은 발급 시 앱에서 클레임을 받아 싣는다. 서비스는 제품 토큰을 로컬(JWKS)로만 검증한다."*
D1·D2·D3을 각각 쓰는 대신 이 하나가 그 자리를 대체한다. **공동무효 판정(§4③)은 초안 시점에 돌린다** — 특히 제품명(Zitadel)을 결정에 포함하는지가 관건이다.

### 티켓 재판정

**여전히 유효 — 결정 없이 낼 수 있고, 이 방향과 안 부딪친다:**

| 1550 표기 | 무엇 | 비고 |
|---|---|---|
| **D-4** | 동의 이력에 시각·버전 | ★ **생존 티켓 중 가장 긴급.** 동의는 앱 소유로 남고, 과거 시각은 소급 복원되지 않는다 — 어느 방향이든 미룰수록 손해라는 성질이 유지된다 |
| D-1 | 죽은 MySQL DDL 삭제 | auth-service 저장소는 존속하므로 유효 |
| 5-2 | CORS 검증 | 유효 |
| 6-5 | 예외 수신 미들웨어 | 유효 |
| 1-4 | 토큰 로깅 제거 | **전환 전까지 값이 계속 쌓이므로** 전환 일정이 길어지면 지금 낸다(§4) |
| 1-3 절반 | composer `CreateToken` 삭제 | 죽은 코드 삭제 — 전환과 무관하게 지금도 싸다 |
| D-5 | 죽은 `auth_server` 테이블 삭제 | 1550은 "D5 대기(되살릴 수도)"로 묶었으나 **D5가 소거되므로 이제 지울 수 있다** |

**소거 — 낼 필요가 없어졌다:**

- **D-7**(마지막 로그인 기록) — 제품 이벤트가 공짜로 준다.
- **2-1·2-3**(쿠키 키 주입·속성) — 쿠키 스토어 자체가 소멸. **1550이 이 둘을 🟡("만드는 배선이 버려질 수 있다")로 표시했는데, 그 판정이 정확히 실현된 경우다.** 전환이 확정되면 내지 않는다.
- 2-5(콜백 메서드) · 2-6(postMessage) · 2-4(openid scope) · 1-2/7-2(종류·파서) · 4-2(email 유니크) · 4-3(탈퇴 파괴) — 전부 소거.

**변형 — 새 형태의 일감으로:**

- D-2(가입 시 필수 동의 강제) · D-3(기본 권한) → **JIT 프로비저닝 + 온보딩 게이트** 구현 안으로 흡수.
- D-6(ADMIN 부여 경로) → 콘솔 관리자(제품)와 앱 권한 부여가 분리된다. 앱 쪽은 여전히 판단 필요.
- D-8(탈퇴 시 삭제 전파) → **주기 조정 잡**으로 형태 확정(1635 §7④). 구현은 남는다.
- 6-1·6-2(관리자 기록 1년 [법]) → 제품 이벤트 + 보존 정책.

## 3. 해소되지 않는 것 — 최종 잔여 목록

**● 잔존 (제품이 안 가져가는 우리 몫):**

1. **접근수단 0 계정 정책**(4-4) — 유일하게 되돌릴 수 없는 축. 여전히 사람의 결정.
2. **보안 헤더·rate limit의 담당 판단**(5-1·6-4) — 앱이냐 게이트웨이냐. 도입 전에도 후에도 미정인 채로 남아 있다.
3. **관리자 노출 판단**(5-3 변형) — Zitadel 콘솔·앱 admin을 사설망 안으로 묶는가.
4. **앱 코드의 관측 규율**(6-2·6-3·6-5) — 403 로깅·응답 통일·panic recover.
5. **dev 환경**(6-6) — 격상. 이행 전체의 선행.
6. **동의 시각·버전**(D-4) — 앱 소유로 남는 도메인의, 미룰수록 손해인 티켓.

**+ 신규 (도입이 만드는 일):**

1. Zitadel 배포·운영 — 매니페스트, PG database, **masterkey 백업**, login v2 앱 배포(v4 기본 — 별도 컨테이너 여부 확인).
2. **P2 Target endpoint**(auth-service) — 권한·동의 클레임 응답. payload 서명 검증 포함.
3. **JIT 프로비저닝 + 온보딩 게이트** — 첫 로그인 시 앱 user 행 생성·동의 흐름·완료 후 토큰 갱신 트리거(1635 §9 모서리①).
4. **주기 조정 잡** — 제품 사용자 ↔ 앱 행 ↔ Mongo 문서 대조.
5. **Naver**: generic OIDC 브로커 설정 + **연결끊기 콜백 수신 → 제품 Admin API 호출**(auth-service가 제품의 관리 클라이언트가 된다).
6. **프론트 로그인 재작성** — 팝업/postMessage → 표준 리다이렉트. `260722_1617`(토큰 저장)과 합류.
7. **검증 미들웨어 교체** — goutils 공통 JWKS 검증 모듈(비대칭이므로 공통화가 안전 — 1735 A3 제약 해제).
8. **기존 사용자 마이그레이션** — N=1: 제품에 계정 생성 + Mongo `userId` 치환. 극단적으로는 버리고 재가입.

## 4. 전환기 주의 — 지금도 쌓이는 것 둘

전환이 확정되어도 **이행 완료 전까지** 현행 코드가 돈다. 1334가 [실질·지금]으로 판정한 것 중 둘은 전환 일정과 무관하게 값이 쌓인다:

- **1-4** — 토큰 원문이 지금도 Loki에 적재되고 있다.
- **2-1** — 지금 발급되는 모든 세션 쿠키가 하드코딩 키로 서명되고 있다.

**전환 일정이 짧으면(주 단위) 묵인 가능하고, 분기 단위면 1-4만이라도 먼저 닫는 것이 싸다**(몇 줄이다). 2-1의 키 주입 배선은 전환 시 버려지므로(1550 🟡 판정) 일정이 짧다는 전제에서 내지 않는다.

## 5. 요약 판정

**1334의 [실질] 항목 전부와 구조 결정(7-x) 전부가 해소된다** — 정확히는 §1·§2·§3·§4의 정체성/토큰/왕복/세션 축이 통째로 제품 관할로 넘어가고, D1·D2·D3·D5가 소거된다.
**해소되지 않는 것은 처음부터 인증이 아니었던 것들이다** — 정책(4-4), 배치 판단(5-1·6-4·5-3), 앱 관측 규율(6-x), dev 환경, 그리고 앱 도메인(동의 이력).
그 대가로 §3의 신규 8건 — 제품 운영과 이음새 구현 — 을 산다.

## 6. 보강(사람의 지적) — C2의 원리는 살아남는다

**지적:** 탈퇴·콘솔 강제 정지 후에도 **이미 발급된 access token은 수명까지 유효하다**(로컬 JWKS 검증의 대가).
그런데 티켓·권한 등의 API는 여전히 auth-service로 온다 — 그렇다면 1334의 **C2**(auth-service 자기 경로에서만 요청마다 상태 검사, 나머지 경로는 지연 수용)는 이 구조에서도 유효하지 않은가.

**맞다.** §1의 "7-3 수렴 폐기"는 **저장 형태(S2 세션 행)** 에 대한 것이지, **C2의 비대칭 원리** — *위험한 조작은 즉시, 조회성 경로는 토큰 수명 지연* — 는 발급자가 누구든 성립한다. 바뀌는 것은 검사의 상대뿐이다:

> 구형: auth-service 미들웨어 → **자기 세션 행** 조회
> 신형: auth-service 미들웨어 → **제품의 상태**를 본다

**위험 표면부터 정직하게** — 이 구조에서 auth-service에 남는 조작 중 즉시성이 값어치 있는 것은 **티켓 사용(권한 획득)과 admin 티켓 발급** 정도다. 탈퇴·전체 사용자 조회는 제품 콘솔로 갔고, P2 Target은 발급 시에만 불리는데 정지된 사용자는 애초에 발급(로그인·refresh)이 안 되므로 안전하다. 즉 **C2의 대상 경로가 구형보다 좁다.**

구현 형태 둘:

| | 모양 | 비용 | 발효 |
|---|---|---|---|
| **C2-a. introspection** | auth-service의 해당 경로 미들웨어가 요청마다 제품의 token introspection(RFC 7662)을 호출 | 해당 경로에 한해 auth-service → 제품 런타임 의존. 요청당 HTTP 1회 | **즉시** |
| **C2-b. 이벤트 push + 로컬 플래그** | Actions v2 **Event** Target(사용자 비활성화·삭제 등)이 auth-service를 호출 → 로컬 차단 플래그 기록. 미들웨어는 로컬만 조회 | 요청당 비용 0. 전달 실패 가능성 → **주기 조정이 백스톱**(이미 §3-4에 있다) | **준즉시** (이벤트 전달 지연) |

- composer 경로는 어느 쪽이든 **그대로 로컬 JWKS + 토큰 수명 지연** — 1334 C2와 동일한 배분이고, 그 배분이 성립하는 이유(위험 조작이 auth 쪽에 몰려 있다)도 유지된다.
- 1635 §6①이 거부한 것은 **composer 요청 경로의 introspection**(전 요청의 SPOF화)이지, auth-service 자기 경로의 상태 확인이 아니다 — C2-a는 그 거부와 충돌하지 않는다.
- 노출 창의 크기 자체는 **제품의 access token 수명 설정**(코드·설정 관할)이 정한다. C2-a/b는 그 창을 auth-service 경로에서 ~0으로 좁히는 추가 장치다.
- **C2-a vs C2-b는 코드 관할에 가깝다** — 결정에 담을 성질은 *"auth-service의 권한 변경 조작은 토큰 수명 지연을 수용하지 않는다"* 여부이고, 그 판단이 서면 구현은 바꿔도 결정이 안 흔들린다.

이에 따라 §3 잔존 목록에 하나를 더한다: **7. auth-service 위험 경로의 즉시 차단 장치**(C2-a 또는 C2-b) — 원하는 경우에 한해.

## 7. 보강(사람의 지적) — 공개키 전달과 Zitadel 의존의 정확한 모양

**지적:** JWKS 호출로 공개키를 받으면 auth-service·api-composer가 Zitadel에 의존하게 되는 것은 피할 수 없지 않은가.

**의존 자체는 맞다. 단, 종류가 다르다.** 이 논의가 거부해 온 것은 **데이터 경로 의존**(요청마다 원격 호출 — introspection·게이트웨이 검증)이고, JWKS는 **제어 경로 의존**이다:

- 표준 검증 라이브러리는 JWKS를 **캐시**하고, 미지의 `kid`를 만나거나 TTL이 지날 때만 재조회한다. **요청 경로에는 원격 호출이 없다.**
- Zitadel이 죽어도 캐시된 키로 **검증은 계속 동작한다.** 실패 창은 둘뿐이다 — ⓐ Zitadel 다운 중의 콜드 스타트(프로세스 재시작 직후 첫 fetch) ⓑ 다운 중의 키 회전(드묾).
- 그리고 이 구조에서 Zitadel 다운은 **어차피 신규 로그인·refresh 전면 불가**를 뜻한다. 캐시 JWKS의 한계 비용은 "로그인도 안 되는 상황에서 기존 세션마저 콜드 스타트 시 못 받는다" 수준 — 열화가 우아한(graceful) 쪽이다.
- 발급 위임을 택한 순간 **신뢰 의존은 원리적으로 제거 불가**하다. 조형할 수 있는 것은 가용성 결합의 모양뿐이다.

**키 전달 옵션:**

| | 모양 | 비용 | 회전 |
|---|---|---|---|
| **J1. JWKS + 캐시** (기본형) | 라이브러리가 lazy fetch + 캐시 + `kid` 미스 시 재조회 | 제어 경로 의존만. 코드 최소 | 자동 추종 |
| **J2. 키 고정(pinning)** | 배포 시 JWKS를 받아 Secret/설정으로 굽는다 | 런타임 의존 0 | **수동** — 회전이 배포 절차가 된다. Zitadel의 키 회전 관리(web keys API)와 절차를 맞춰야 하며, 어긋나면 전 서비스 검증 실패 |
| **J3. 배포 루프가 押전달** | 잡이 JWKS를 주기 fetch → Secret 갱신 → 서비스는 파일만 읽음 | 의존이 제어 루프로 이동. 기계장치 하나 추가 | 반자동 |

- 공개키는 비밀이 아니므로 전달에 필요한 것은 기밀성이 아니라 **무결성**(TLS/클러스터 내부 경로)뿐이다.
- 콜드 스타트 완화는 코드 관할이다 — lazy fetch + 재시도, 캐시의 디스크 지속화 등.
- **판정: J1이 기본형이고, J2·J3은 제어 경로 의존조차 수용 못 할 때의 대안이다.** 홈랩 전면 재기동(정전 등) 시 기동 순서 문제가 실측으로 아프면 그때 J3을 다시 본다.

**ADR 초안에의 함의** — 결정 문장의 *"로컬(JWKS)로만 검증한다"* 의 정확한 의미를 이렇게 새긴다:
**검증 연산은 로컬이다(요청 경로에 원격 호출 없음). 키 획득은 캐시되는 제어 경로다.** 데이터 경로/제어 경로의 구별 자체를 결정의 어휘로 남기면, 나중에 "JWKS도 의존이니 introspection과 같다"는 흐림을 막는다.

## 열린 질문 — 사람의 것

0. **auth-service의 권한 변경 조작(티켓 사용·admin 발급)에 즉시 차단을 요구하는가**(§6) — 요구하면 C2-a/b 중 하나가 신규 목록에 들어오고, 수용하면 토큰 수명이 상한이다. 구형 C2에서 이미 "즉시"를 골랐던 이력이 있어(1334 7-3 수렴) 같은 답이 나올 가능성이 높다.
1. **전환 일정의 단위** — §4의 판단(1-4를 먼저 닫을 것인가)이 여기 걸린다.
2. **새 ADR의 경계** — D1·D2·D3을 대체하는 한 문장에 제품명(Zitadel)을 포함하는가. 제품 교체가 결정을 무효화하는가(공동무효 판정)가 초안의 첫 관문이다.
3. **잔존 목록 3번(관리자 노출)** — Zitadel 콘솔을 사설망 안으로 묶을 수 있는가. 1334 열린 질문 5의 재판이다.
4. **이 문서의 신규 8건을 언제 티켓 트리로 벌리는가** — 근거 ADR(2번)이 accept·공표된 뒤라야 컨테이너를 낼 수 있다.

## 검토하고 버린 것

- **1334·1550을 이 문서로 대체(supersede)하는 것** — discussion은 결정이 아니라 얼지 않지만, 두 문서의 판정 다수가 이 방향에서 무효가 된다고 해서 문서가 무효가 되는 것은 아니다. 코드 실측(어디가 어떻게 어긋나는가)은 방향과 무관하게 유효한 재료로 남는다. 이 문서는 **덮어쓰기가 아니라 재판정**이다.
- **7-3 수렴(S2+C2)을 살려두는 것** — "제품이 실패하면 되돌아올 보험"으로 남겨둘 수 있으나, 그 수렴의 전제(자체 발급)가 사라진 상태에서 보험 취급하면 두 개의 설계가 병존하게 된다. 폐기를 명시하고, 되돌아올 일이 생기면 그때 다시 벌린다.
