# careerhub 는 무엇으로 돈을 버나 — 그리고 그게 성립하나

**프론트엔드 논의가 여기서 막혀서 열린 문서다.** 기술 결정이 아니라 그 결정들이 딛고 선 전제를 다룬다.

---

## 1. 이 문서가 열린 경위 — 전제가 무너졌다

프론트 리뉴얼 논의는 *"careerhub 를 사업으로 키운다"* 는 답 위에서 프레임워크를 정했고, 이어서 *"Google Ads 전환을 전제로 한 GA 데이터 수집"* 이라는 답 위에 **계측 설계를 세 라운드 쌓았다.**

**그 전제가 틀렸다.**

| | **Google Ads** | **AdSense** |
|---|---|---|
| 누가 쓰나 | 광고주 | **게시자 (careerhub)** |
| 돈이 | **나간다** | **들어온다** |

**Google Ads 로는 돈을 벌 수 없다 — 돈을 쓰는 도구다.** 둘은 같은 광고 네트워크의 양쪽 끝이다: Ads 가 광고를 넣고, AdSense 가 그것을 게시자의 사이트에 뿌리고 게시자에게 지불한다.

수익 모델은 **광고 게재(AdSense)** 다. 그러자 계측 논의(축 H)가 통째로 무너졌다 — **AdSense 는 전환 추적을 요구하지 않는다.** 페이지뷰와 광고 노출·클릭으로 지불하므로 최적화할 입찰이 없고, GA 가 오염돼도 수익은 안 변한다(Google 이 따로 센다).

> **★ 왜 이렇게 됐나 — 요구에 적힌 고유명사를 검증하지 않았다.**
> 코드는 파고들어 읽으면서, **전제로 주어진 단어는 한 번도 묻지 않았다.** *"desired 는 코드가 답한다"* 는 규율이 코드 **밖**의 전제에는 적용되지 않았고, 그 틈으로 잘못된 전제가 세 라운드를 끌고 갔다. 사람이 *"실은 Ads 로 어떻게 돈을 버는지조차 모른다"* 고 정직하게 말하기 전까지 아무도 그것을 건드리지 않았다.

---

## 2. ★★ 하나의 사실이 세 곳에서 문제를 낸다

**"공고 본문은 외부 채용 사이트에서 수집한 것이다"** — `careerhub-posting-provider` 가 Wanted·JumpIt 에서, `careerhub-review-crawler` 가 TeamBlind 에서 긁어온다.

이 **한 가지 사실**이 서로 다른 세 곳에서 문제를 낸다:

| 어디서 | 어떻게 |
|---|---|
| **유입 (SEO)** | 원본이 이미 색인돼 있다. 같은 본문으로는 **원본을 못 이긴다** — 중복 콘텐츠 |
| **수익화 (AdSense)** | 거절 사유 **"Valuable inventory: Scraped content"** 에 정면으로 걸린다. *다른 사이트에서 찾을 수 있는 콘텐츠*가 그 정의다. **채용 공고 사이트·뉴스 애그리게이터의 거절 사례가 흔하다** |
| **권리** | 크롤링해 재배포하는 것과 **그것으로 수익을 내는 것**은 다른 문제다(§5 미결 ③) |

**★ 세 문제가 하나이므로 해법도 하나다 — 원본에 없는 것을 만든다.**

코드가 이미 그 방향을 가리키고 있다. 원본에 **없는** 것:

- **리뷰 결합** — `careerhub-review-service`. 공고 옆에 그 회사의 TeamBlind 평점이 붙는다. **Wanted 에는 없다**
- **스킬 추출** — `careerhub-posting-skillscanner`. 공고 텍스트에서 요구 스킬을 뽑아 정규화한다. **원본은 자유 텍스트다**
- **교차 집계** — Wanted 와 JumpIt 을 한 자리에서. **어느 원본도 못 하는 것**

> **이것이 careerhub 의 유일한 자산이다.** 공고 본문은 자산이 아니다 — 원본의 것이고, 유입도 수익화도 막는다. **자산은 그 위에 얹은 세 가지다.**

## 3. 현재 상태 — 코드가 말하는 제약

| 사실 | 근거 |
|---|---|
| 공고를 Wanted·JumpIt 에서 수집 | `careerhub-posting-provider` |
| 리뷰를 TeamBlind 에서 수집 | `careerhub-review-crawler` |
| 수집은 **하루 한 번** CronJob | `jyoliar-k8s/.../apps/jobs/cronjob.yaml` |
| 스킬을 정규식으로 추출·정규화 | `careerhub-posting-skillscanner` |
| 셋을 병합해 REST 로 제공 | `careerhub-api-composer` |
| 사용자 기능: 스크랩(북마크) · 매칭 조건 | `careerhub-userinfo-service` |
| 원본으로 나갈 때 **서버를 안 거친다** | `careerhub-front/src/view/job_posting/postingId/Detail.svelte:87` — `window.open(url, "_blank")` |

**★ 사용자층은 개발자다.** Wanted·JumpIt 공고에 스킬 스캐너까지 붙은 이상 대상이 개발자임은 코드가 말한다.

## 4. ★ 사용자층과 수익 모델이 상극이다

**개발자는 광고 차단기 사용률이 가장 높은 집단이다.**

계측 논의에서는 이것이 *"GA 이벤트가 유실된다"* 는 문제였다. **AdSense 모델에서는 사업 모델 자체를 죽인다:**

> **광고가 차단되면 노출이 0 이고, 노출이 0 이면 수익이 0 이다.** 계측 손실이 아니라 매출 0 이다.

**개발자 대상 사이트 + AdSense 는 알려진 최악의 조합이다.** 그리고 이것은 §2 와 **독립적인** 문제다 — 원본에 없는 콘텐츠를 아무리 잘 만들어 AdSense 승인을 받아도, 그것을 보는 사람이 광고를 차단한다.

## 5. 옵션

### R0. 돈을 벌지 않는다 — 포트폴리오·학습으로 둔다

| | |
|---|---|
| 이길 때 | 수익화의 기대값이 운영 비용·법적 위험보다 작을 때 |
| 함의 | **프론트 리뉴얼의 근거가 바뀐다** — ADR-0012(Next.js)의 무효화 조건이 정확히 이것이다. 생태계 복리 논거가 사라지고 즐거움·학습 기준으로 다시 판단해야 한다 |
| 비용 | 0. **잃는 것도 0** — 지금도 돈을 안 벌고 있다 |

### R1. AdSense 게재

| | |
|---|---|
| 이길 때 | 트래픽이 크고, 사용자가 광고를 차단하지 않고, 콘텐츠가 원본과 구별될 때 |
| 막는 것 | **§2 승인 · §4 차단.** 둘 다 정면으로 걸린다 |
| 규모 | 수익 = PV × RPM. 의미 있는 금액에 도달할 PV 가 필요하다. **현재 PV 를 모른다**(미결 ①) |

### R2. 원본 사이트와의 제휴 — 지원 성사에 대한 수수료

| | |
|---|---|
| 이길 때 | 원본이 제휴 프로그램을 운영하고, careerhub 가 의미 있는 트래픽을 보낼 때 |
| 좋은 점 | **긁어온 것을 원본에 돌려주는 구조**라 §2·권리 문제와 이해가 정렬된다. 광고 차단과 무관하다 |
| 막는 것 | Wanted·JumpIt 에 제휴 프로그램이 있는지 **모른다**(미결 ②) |
| 기술 함의 | 전환 = **아웃바운드 클릭**. 지금은 `window.open` 이라 서버가 모른다 → `/go/` 리다이렉트가 필요해진다 |

### R3. 채용사 유료 노출 (B2B)

| | |
|---|---|
| 문제 | **순환이다** — 공고를 무료로 긁어오는데 채용사가 왜 돈을 내나. 이미 노출되고 있다 |
| 성립하려면 | careerhub 가 원본이 못 주는 것을 채용사에게 줘야 한다 (지원자 품질? 스킬 매칭?). 그건 규모가 있어야 성립한다 |

### R4. 개발자 대상 유료 구독

| | |
|---|---|
| 문제 | 공고 애그리게이터에 개발자가 돈을 낼 이유. §2 의 세 자산이 **구독료만큼 값진가** |
| 좋은 점 | 광고 차단과 무관. 스크랩 콘텐츠 정책과도 무관 |

### R5. 데이터 판매 — 스킬 트렌드 등

| | |
|---|---|
| 좋은 점 | `skillscanner` 의 산출물은 **원본에 없는 것**이라 §2 를 정면으로 피한다 |
| 막는 것 | 원본 데이터의 파생물을 파는 것의 권리(미결 ③). 그리고 살 사람이 있는지 |

## 6. 트레이드오프 축

- **사용자층과의 궁합** — 개발자에게 광고를 보이는 것(R1)과 개발자에게 값을 파는 것(R4)은 정반대 방향이다
- **원본 의존도** — R1·R3 는 원본 본문에 기댄다(§2 에 걸린다). R2 는 원본과 정렬된다. R4·R5 는 **우리가 만든 것**에 기댄다
- **트래픽 규모 요구** — R1 이 가장 크다. R4·R5 는 작아도 된다
- **광고 차단 노출** — R1 만 직격이다
- **권리 위험** — 수익화하는 순간 질이 달라진다(미결 ③)
- **되돌리기 비용** — 전부 낮다. **수익 모델은 코드가 아니라 시도다** — 해보고 아니면 접는다

---

## 7. 미결

① **현재 트래픽 규모** — PV·사용자 수. **코드가 아니라 로그·관측 스택이 답한다.** R1 의 성립 여부가 여기 달렸고, 지금은 아무도 숫자를 모른다

② **Wanted·JumpIt 에 제휴 프로그램이 있는가** — R2 전체가 여기 달렸다. **조사거리다**

③ **★ 크롤링한 데이터로 수익을 내는 것의 권리** — 학습용으로 긁는 것과 그것으로 돈을 버는 것은 **다른 문제**다. 원본 사이트의 이용약관을 읽지 않았다. **이것은 내가 답할 수 없고, 채우지 않는다** — 다만 R1·R3·R5 는 여기 걸릴 수 있고, **수익화를 시작하는 순간 위험이 질적으로 달라진다**는 것만 적어둔다

④ **§2 의 세 자산이 실제로 값진가** — 리뷰 결합·스킬 추출·교차 집계가 *"원본 대신 careerhub 를 쓸"* 이유가 되나. **이것이 R1 을 뺀 모든 옵션의 전제**이고, 첫 discussion 의 미결 ②(SEO 목표)와 **같은 질문**이다

---

## 8. 지금까지의 관찰

- **★ "SEO 목표"와 "AdSense 승인"과 "무엇으로 차별화하나"는 세 개가 아니라 하나의 질문이었다.** 첫 discussion 이 미결 ② 로 남긴 것이 여기서 사업의 근본 질문으로 되돌아왔다. **기술 논의가 세 라운드 돌아 원점의 질문을 다시 만났다.**
- **★ 공고 본문은 자산이 아니라 부채다.** 유입을 막고(중복 콘텐츠), 수익화를 막고(scraped content), 권리 위험을 만든다. **자산은 그 위에 얹은 것 — 리뷰 결합·스킬 추출·교차 집계뿐이다.** 코드는 이미 그것을 만들고 있는데, 사업은 아직 그것을 팔 생각을 안 했다.
- **★ 사용자층이 수익 모델을 죽인다.** 개발자에게 AdSense 는 최악이다. 이건 콘텐츠를 고쳐도 안 풀린다 — **§2 와 독립적인 두 번째 벽이다.**
- **수익 모델은 되돌리기가 싸다** — 코드가 아니라 시도다. **ADR 감이 아닐 가능성이 높다.** 다만 그 답이 **ADR-0012 의 무효화 조건을 건드린다.**
- **요구에 적힌 고유명사를 검증하지 않은 것**이 세 라운드를 낭비시켰다. 코드를 읽는 규율은 있었는데 **말을 읽는 규율이 없었다.**
