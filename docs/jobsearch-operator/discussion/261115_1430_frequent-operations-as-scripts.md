# jobsearch-operator에서 자주 쓸 기능 — 무엇을 스크립트로 둘 것인가

## 1. 문제

지원 현황을 sqlite에 담기로 했다.
그 DB에 기록하고 조회하는 일 가운데 반복되는 것은 스크립트로 따로 둔다.
어떤 기능이 그 "자주 쓸 것"에 해당하는지, 무엇부터 만들지가 정해지지 않았다.

열려 있던 것은 넷이다.
처음 만들 묶음, 지원한 공고를 다시 가져올 때의 처리, 전이 규칙을 어디서 얼마나 강제할지, 스크립트의 언어와 형태.

## 2. 실측

- 스키마는 `resume`, `posting`, `application`, `status`, `status_event`, `job_role`, `resume_role`, `posting_role`과 뷰 `application_current`다 — `docs/jobsearch-operator/discussion/261115_1407_application-tracking-sqlite-schema.md`의 DDL 초안.
- 무응답은 상태가 아니라 지원일과 오늘 날짜에서 계산하는 값이다(같은 문서 DDL 초안 아래). 계산해 보여주는 것이 없으면 보이지 않는다.
- 공고 본문은 사본을 두지 않고 한 행을 덮어쓴다(같은 문서 4-4 판정 B).
- 이력서는 DB에 버전과 경로만 두고 텍스트는 분석할 때 PDF에서 뽑는다(같은 문서 4-5 판정 B).
- 두 플랫폼의 공고 상세는 JSON을 돌려주는 주소로 원문 그대로 받을 수 있다 — `workspace/ref/careerhub-posting-provider/careerhub/posting_service/provider/source/wanted/client.go:37`, `.../jumpit/client.go:32`.
- `jobsearch-operator` 저장소에는 아직 스크립트도 DB도 없다(2026-11-15 확인).

## 3. 인터뷰에서 닫힌 축

### 3-1. 자주 쓰는 기능의 자리

**선택: 스크립트로 따로 작성한다.** 스크립트가 있는 기능은 agent가 그 스크립트를 거쳐 기록하고 조회한다. (인터뷰, 2026-11-15)

<details><summary>버린 안</summary>

- agent가 매번 SQL을 직접 쓴다 — 같은 일을 할 때마다 다르게 쓰게 되고, 전이 규칙을 지켜 줄 것이 없다

</details>

## 4. 열린 축 — 논의

### 4-1. 처음 만들 묶음

후보 기능은 다음과 같다.

| 묶음 | 기능 | 하는 일 |
|---|---|---|
| 기록 | 공고 등록 | 공고 URL로 플랫폼의 본문을 원문 그대로 가져와 넣고 "고려 중"으로 시작한다 |
| 기록 | 지원 기록 | 어느 공고에 어느 이력서로 언제 지원했는지 넣고 "대기"로 전이한다 |
| 기록 | 상태 전이 | 열람·서류 합격·불합격 등으로 바꾸고 날짜와 메모를 남긴다 |
| 기록 | 접기 | 고려하던 공고를 접고 이유를 남긴다 |
| 기록 | 이력서 등록 | PDF를 버전으로 등록하고 대상 직군을 붙인다 |
| 기록 | 직군 붙이기 | 공고에 표기 직군과 본문 요구 직군을 붙인다 |
| 조회 | 현황판 | 진행 중인 건을 상태별로 보여주고 그 상태로 며칠째인지 표시한다 |
| 조회 | 무응답 점검 | 지원 후 며칠이 지나도록 전이가 없는 건을 골라낸다 |
| 조회 | 한 건 상세 | 공고 본문, 사용한 이력서, 전이 이력 전체를 보여준다 |
| 조회 | 집계 | 이력서 버전별·직군별 통과 수, 단계별 소요일, 이력서와 공고의 직군이 엇갈린 건 |
| 분석 지원 | 분석용 내보내기 | 한 건의 공고 본문과 이력서에서 뽑은 텍스트를 나란히 내보낸다 |
| 분석 지원 | 공고 다시 가져오기 | 마감·수정 여부를 확인하고 본문을 갱신한다 |
| 유지 | 초기화 | 스키마 파일로 DB를 만든다 |
| 유지 | 정합성 검사 | 전이가 없는 건, 지원했는데 이력서가 빈 건 같은 어긋남을 찾는다 |

- A. **기록 경로 셋과 매일 보는 조회 둘** — 공고 등록, 지원 기록, 상태 전이, 현황판, 무응답 점검. 초기화는 전제로 포함한다.
  매 지원마다 쓰는 경로와 매일 여는 조회가 전부 들어간다. 지금까지의 지원 건을 옮기는 데도 이것이면 된다.
  접기와 직군 붙이기가 없어, 그 둘은 당분간 스크립트 밖에서 넣어야 한다.
- B. **기록 경로만** — 공고 등록, 지원 기록, 상태 전이.
  가장 빨리 쓰기 시작한다.
  무응답이 보이지 않는다. 조회는 agent가 그때그때 질의하게 된다.
- C. **기록 묶음 전체와 조회 둘** — A에 접기, 이력서 등록, 직군 붙이기를 더한다.
  DB에 쓰는 모든 길이 스크립트를 지난다. 4-3에서 강제를 고르면 빈틈이 없다.
  처음 만들 것이 여덟 개로 는다.
- D. **만들지 않는다** — 3-1을 미루고 agent가 직접 쓰며 시작한다.
  실제로 무엇이 반복되는지 보고 나서 만든다.
  그 사이의 기록에는 규칙이 걸리지 않는다.

**판정(사람, 2026-11-15): D의 변형. 미리 만들지 않는다 — 위 표의 기능을 구현 후보로 두고, 필요해질 때 즉석에서 구현한다.**

### 4-2. 지원한 공고를 다시 가져올 때

공고 본문은 한 행을 덮어쓴다.
지원 뒤에 공고가 수정되면, 다시 가져오는 순간 지원할 때 본 내용이 사라진다.

- A. **지원한 건은 본문을 다시 가져오지 않는다** — 지원 기록이 있는 공고의 본문 갱신을 스크립트가 거부한다. 마감 여부만 확인해 남긴다.
  지원 시점에 본 내용이 보존된다. 이력서와 공고의 연관성 분석이 실제로 보고 지원한 본문 위에서 이뤄진다.
  지원 뒤의 수정을 알 수 없다.
- B. **언제든 덮어쓴다** — 구분하지 않는다.
  규칙이 없어 단순하다.
  분석의 대상이 지원 시점의 공고가 아닐 수 있고, 그것을 알 방법이 없다.
- C. **바뀐 것이 있을 때만 알리고 덮어쓰지 않는다** — 다시 가져온 본문이 저장된 것과 다르면 다르다는 사실과 시각만 기록한다.
  지원 시점의 본문이 보존되고, 수정이 있었다는 것도 남는다.
  바뀐 내용 자체는 남지 않는다. 그것까지 남기려면 사본 테이블이 필요하고, 그것은 스키마 논의 4-4의 판정을 되돌리는 일이다.

**판정(사람, 2026-11-15): 지금 정하지 않는다. 공고 다시 가져오기를 구현할 때 정한다.**

### 4-3. 전이 규칙을 어디서 얼마나 강제하나

지켜야 할 규칙의 예는 이렇다.
정의되지 않은 상태로 가지 않는다.
전이 날짜가 앞선 전이보다 이르지 않다.
끝난 건(불합격·최종 합격 등)에는 전이를 더하지 않는다.
지원하지 않은 공고가 "열람"이 되지 않는다.

- A. **스크립트가 거부한다** — 규칙에 어긋나면 기록하지 않고 실패로 끝낸다.
  어긋난 기록이 들어가지 않는다. 막히면 그것이 규약이라는 방식과 같다.
  뒤늦게 온 연락처럼 규칙 밖의 실제 사건을 넣으려면 규칙을 고치거나 우회 인자가 필요하다.
- B. **스크립트가 경고만 한다** — 기록은 하고 어긋난 점을 알린다.
  현실의 예외를 막지 않는다.
  경고는 지나치기 쉽다. 정합성 검사가 따로 있어야 뒤에서 잡힌다.
- C. **DB 트리거로 강제한다** — 규칙을 스키마에 넣는다.
  스크립트를 거치지 않은 쓰기도 막힌다.
  규칙을 고칠 때마다 스키마를 고쳐야 하고, 규칙이 아직 잡히지 않은 단계에서는 자주 걸린다.

**판정(사람, 2026-11-15): 지금 정하지 않는다. 기록 기능을 처음 구현할 때 정한다.**

### 4-4. 스크립트의 언어와 형태

- A. **Python 표준 라이브러리, 기능마다 파일 하나** — `sqlite3`와 `urllib`만 쓴다.
  설치할 것이 없고, 기능 하나가 파일 하나라 읽고 고치기 쉽다. ops-workflow의 스크립트와 같은 방식이다.
  DB를 여는 부분과 규칙 검사가 파일마다 되풀이되거나, 공용 모듈이 하나 생긴다.
- B. **Python, 명령 하나에 하위 명령** — `jobsearch <기능>` 꼴이다.
  공용 부분이 한곳에 모인다.
  파일 하나가 커지고, 기능을 따로 작성한다는 3-1의 뜻과 조금 멀어진다.
- C. **셸과 `sqlite3` 명령** — 스크립트가 SQL 파일을 실행한다.
  가장 얇다.
  플랫폼 응답(JSON)을 풀어 넣는 일과 날짜 검사가 셸에서는 번거롭다.

**판정(사람, 2026-11-15): 지금 정하지 않는다. 첫 스크립트를 구현할 때 정한다.**

## 5. 반대편 — 이 설계가 틀리는 조건

- 지원이 주 3~5건이면 기록은 하루 한두 번이다. 스크립트를 만들고 고치는 품이 아끼는 품보다 클 수 있다.
- 무엇이 "자주"인지를 써 보기 전에 정했다. 만든 기능을 안 쓰고, 안 만든 기능을 매일 찾게 될 수 있다.
- 플랫폼의 상세 주소가 바뀌면 공고 등록이 깨진다. 기록 경로의 첫 단계가 외부에 달려 있다.
- 강제를 고르면, 규칙이 현실과 어긋나는 날 기록이 막힌다. 그때 규칙 밖으로 쓰기 시작하면 강제의 의미가 사라진다.

## 6. 버린 것

- **화면이 있는 도구** — 쓰는 주체가 agent다. 사람이 볼 것은 현황판의 출력이면 된다.
- **지원 자체를 자동으로 넣는 기능** — 플랫폼에 대신 지원하는 일은 다루지 않는다. 기록만 한다.

## 7. 임계선 — ADR감인가

ADR감이 아니다.
한 사람이 쓰는 저장소의 스크립트이고, 고치거나 버리는 데 한 시간이 걸리지 않는다.
